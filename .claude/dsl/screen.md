# DSL reference: Build / screen

The whole story of these verbs. The one-line index is `.claude/rules/dsl-reference.md`.

- `RubyGBA.game "NAME" do … end` — **the name is all the cartridge needs from you.** A cartridge also carries a four-character code, and that code is the only thing an emulator has to tell one cartridge from another: it reads the code to put a title in its window, and it reads the same code to decide what save hardware the cartridge has — plain memory, flash, a chip read a bit at a time — and whether there is a clock or a rumble motor in there. So a code made up by hand is a real footgun, and not a cosmetic one: thousands of cartridges shipped and the memorable codes are long gone, so landing on one means the emulator reports somebody else's game AND fits somebody else's save hardware — which it puts in place of the one your cartridge asked for, so a game that saves can stop saving with nothing on screen to say why. The framework works a code out from the name instead, starting with a letter no cartridge ever used, so nothing in the program mentions any of this. `code:` and `maker:` are still there for a game that wants its own — and a code a real cartridge already carries is a friendly error, naming the free letters (D, E, H, I, L, N, O, Q, T, W, Y). The maker is the two characters that name a publisher, and a game that says nothing says it has none, which is true: `01` is Nintendo's.
- `screen :bitmap` — pick the display. **A game that never says `screen` is on `screen :bitmap`**, exactly as if that were its first line, on every backend: the build switches the bitmap screen on at boot, so `pixel`, `fill_rect` and the rest show up with nothing else written. Not a warning and not an error — it is the default. Say `screen :bitmap` anyway when a reader would want to see it. `screen :bitmap, tear_free: true` = double-buffered (Mode 4). `screen :tiled` = tile backgrounds + hardware sprites (also decides which kind `sprite` makes). `screen :rotozoom` = a background that can turn and resize as one whole piece — a title screen that zooms in, a race track that spins and pulls away — instead of only scrolling straight the way `screen :tiled`'s layers do. See `background(...).rotate` / `.scale` under Tiled backgrounds. **A `screen :tiled` background can turn and resize too, and that is the arrangement nearly every game wants**, because a turning layer is almost never the whole picture: a title where an object flies at the player over a backdrop, a map screen that spins inside a fixed frame, a road that banks under a sky and a status bar. Nothing in the program says so — a background is one that turns because the program turns it, and the build picks the hardware that holds what was declared. **What it trades is scrolling layers**: `screen :tiled` gives four of them while nothing turns, and two of them beside a layer that does. **That trade is per SCREEN, not per game** — the console is told which arrangement it is in by one register and can be told again whenever the screen changes, so a title screen with something flying at the player over two scrolling layers can hand over to a game with four scrolling layers and nothing turning, in one cartridge. Declare each scene's backgrounds inside that scene and the build works the arrangement out per scene; nothing in the program names one. **That is four AT ONE TIME, not four in the whole game** — a background declared inside a `scene` is up only while that scene is, so scenes take turns with the layers and a game may declare four in each of as many scenes as it likes (see "A scene owns what it draws" under Scenes & funcs). Asking one screen for more than fits is a friendly error naming both counts and the scene that ran out, never a layer quietly left undrawn. So reach for `screen :rotozoom` only for a screen that is nothing BUT a turning layer — it is a third arrangement again (one background, no scrolling ones at all); a plain scroll on it is a friendly error pointing at `rotate`/`scale` instead.
- `screen :bitmap, tear_free: true, colors: [...]` — **say which colors the screen shows** instead of letting the framework work them out from the ones you name. The tear-free screen holds a number per pixel that picks a color out of a shared table, and normally the framework builds that table for you, silently, from the color names you write — which is right until your pictures come from somewhere that already decided. Art imported from another game or a paint program has pixels that are numbers picking out of *its* table, so give the colors in that table's order and the pictures line up. Everything else is unchanged: you still write color names everywhere, and you never write a slot number. **The order is the whole point** — nothing is moved, nothing is added (not even black, which the worked-out table always reserves at the front), and a color repeated in the list keeps both places, because dropping one would shift every color after it and move every pixel of every picture. Drawing with a color the screen was not given is a friendly error naming it; giving two screens different lists is a friendly error, because the display holds one table at a time; and `colors:` without `tear_free: true` is a friendly error, because a plain bitmap screen holds a whole color in every pixel and has no table to fill in.
- `floors = setting :floors, 60` — **what this build was told**, for a game that comes in several cuts: which floors are in it, where the player starts, which screen it boots on. The default is on the same line; a setting with no default has to be given. It is a value while the game is BUILT, a plain Ruby value like the numbers a game works its tables out from, not a variable the game keeps while it runs. It is handed to ONE build — `game.program(settings: { floors: 1 })`, `game.build_rom(settings: …)`, `RubyGBA.build(…, settings: …)`, `ruby-gba build game.rb --set floors=1`, or `write_if_main(settings: …)` on a game file's last line — so a test builds a one-floor cartridge beside a sixty-floor one, on another core at the same moment, and neither sees the other's. That is why it exists: reading the environment from inside the game's block reads something the whole process shares. The command line can only give text, and text is read as the kind of thing the default is (a number, a name, `true`/`false`); a setting with no default arrives as given. Three friendly errors: a setting the build gave that the game never asks for (a name spelled two ways would otherwise build the default and look right), a setting with no default that was not given (naming what was given instead), and text that cannot be read as its default's kind. Where a game still wants the environment, the line that builds it is the place to read it: `write_if_main(settings: { floors: ENV.fetch("FLOORS", "60") })`.
- `wait_vblank` — wait for the safe window to draw. A `game_loop` already does this each pass, so you only write it in a program that has no game loop, or under `frame_sync: :manual`.
- `halt` — stop (branch to self). `debug_halt` — truncate the ROM here (bisecting).
