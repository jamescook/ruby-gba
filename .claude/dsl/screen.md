# DSL reference: Build / screen

The whole story of these verbs. The one-line index is `.claude/rules/dsl-reference.md`.

- `VBlank.game "NAME", consoles: %i[gba] do … end` — **every game names the consoles it is for**: `%i[gba]` for the Game Boy Advance alone, `%i[gba gbc]` for the Game Boy Color too. A game that names none is a friendly error, since nothing is taken to be for the Advance, and `ruby-gba build` (and `ruby game.rb` with `write_if_main`) makes a cartridge for each console named; `play`, `profile` and `compare` run one cartridge, so for a game of two they need `--console`. Besides that, **the name is all the cartridge needs from you.** A cartridge also carries a four-character code, and that code is the only thing an emulator has to tell one cartridge from another: it reads the code to put a title in its window, and it reads the same code to decide what save hardware the cartridge has — plain memory, flash, a chip read a bit at a time — and whether there is a clock or a rumble motor in there. So a code made up by hand is a real footgun, and not a cosmetic one: thousands of cartridges shipped and the memorable codes are long gone, so landing on one means the emulator reports somebody else's game AND fits somebody else's save hardware — which it puts in place of the one your cartridge asked for, so a game that saves can stop saving with nothing on screen to say why. The framework works a code out from the name instead, starting with a letter no cartridge ever used, so nothing in the program mentions any of this. `code:` and `maker:` are still there for a game that wants its own — and a code a real cartridge already carries is a friendly error, naming the free letters (D, E, H, I, L, N, O, Q, T, W, Y). The maker is the two characters that name a publisher, and a game that says nothing says it has none, which is true: `01` is Nintendo's. **`stack_room:`** (also on `VBlank.build`) is how many bytes of the console's 32K quick memory the game's stack is given — the room where every routine keeps where to return to. Left out, the build gives it 1024 bytes, many times what any game here was measured to use (56 at most), and more for a game whose calls nest deeply, worked out from the program; a game can say more for safety or less for room. Every byte held for the stack is one its variables, lists and code cannot have, and a stack that outgrows its room writes over them with nothing to say so. It is a number of bytes, a multiple of 4, from 64 to 16384; anything else is a friendly error. **`code:`, `maker:`, `stack_room:`, `fast_cartridge:` and `fast_code:` are the Game Boy Advance's alone** (`Cartridge::AdvanceBuild::SETTINGS`): a game for both consoles says them once and its Color cartridge is built without them, and a game or a build for the Color alone that says one is a friendly error rather than a setting quietly dropped.
- `screen :bitmap` — pick the display. **A game that never says `screen` is on `screen :bitmap`**, exactly as if that were its first line, on every backend: the build switches the bitmap screen on at boot, so `pixel`, `fill_rect` and the rest show up with nothing else written. Not a warning and not an error — it is the default. Say `screen :bitmap` anyway when a reader would want to see it. `screen :bitmap, tear_free: true` = double-buffered (Mode 4). `screen :tiled` = tile backgrounds + hardware sprites (also decides which kind `sprite` makes). `screen :rotozoom` = a background that can turn and resize as one whole piece — a title screen that zooms in, a race track that spins and pulls away — instead of only scrolling straight the way `screen :tiled`'s layers do. See `background(...).rotate` / `.scale` under Tiled backgrounds. **A `screen :tiled` background can turn and resize too, and that is the arrangement nearly every game wants**, because a turning layer is almost never the whole picture: a title where an object flies at the player over a backdrop, a map screen that spins inside a fixed frame, a road that banks under a sky and a status bar. Nothing in the program says so — a background is one that turns because the program turns it, and the build picks the hardware that holds what was declared. **What it trades is scrolling layers**: `screen :tiled` gives four of them while nothing turns, and two of them beside a layer that does. **That trade is per SCREEN, not per game** — the console is told which arrangement it is in by one register and can be told again whenever the screen changes, so a title screen with something flying at the player over two scrolling layers can hand over to a game with four scrolling layers and nothing turning, in one cartridge. Declare each scene's backgrounds inside that scene and the build works the arrangement out per scene; nothing in the program names one. **That is four AT ONE TIME, not four in the whole game** — a background declared inside a `scene` is up only while that scene is, so scenes take turns with the layers and a game may declare four in each of as many scenes as it likes (see "A scene owns what it draws" under Scenes & funcs). Asking one screen for more than fits is a friendly error naming both counts and the scene that ran out, never a layer quietly left undrawn. So reach for `screen :rotozoom` only for a screen that is nothing BUT a turning layer — it is a third arrangement again (one background, no scrolling ones at all); a plain scroll on it is a friendly error pointing at `rotate`/`scale` instead.
- `screen :bitmap, tear_free: true, late: :show_now` (or `late: 40`, or `late: :wait`, the default) — **what the tear-free screen does with a page the game finished too late** for the break between pictures it was meant for. By default it waits for the next break, so the picture never tears, but a pass that runs a little over its frame then costs a whole frame: a game at sixty drops to thirty for it, and a player feels the hitch. `:show_now` shows such a page as soon as it is done, so a frame is only as late as it really is, and on those frames the picture can tear — it changes part way down. A row number from 0 to 159 shows it at once only while the screen is still sending the picture above that row, where a tear is least seen, and waits otherwise. A page finished during the break itself is shown at once by either, because nothing is being sent then and nothing can tear. **`pace:` says what late means**: the pictures a second the game aims for, 60 (the default), 30, 20 or 15, and a page is late when it misses the break that rate aims at. A game that runs at thirty and says `pace: 30` is on time on every pass that fits two frames, so it never shows those at once and never tears for them; only a heavy pass that runs into a third frame is shown at once, which keeps it at thirty where waiting drops it to twenty. Left at 60, a game at thirty is late on every pass, and `:show_now` then shows every page as soon as it is done — the most pictures a second, and a tear on most of them. **One tear does not set off another**: the pass after a page shown part way down starts part way down too, so it is late only for the break after the coming one, and a page it finishes in the coming break is shown there, where nothing tears. **It is said per `screen`, so per scene**: allow it while the game plays and keep a menu or a still picture from ever tearing; a scene with no `screen` line of its own does what the game's screen does, however the game reaches it. It changes when a page is shown, never what is on it, so the interpreter and the desktop and web builds draw the same game with or without it. `rom.profile` counts the pages it showed at once and how many of those were part way down the picture — which is what it cost, each a frame that may have torn — and counts them as new pictures in its frames a second. `late:` without `tear_free: true` is a friendly error, because only that screen keeps a finished page to show; so is a setting that is not one of the three, a pace other than 60, 30, 20 or 15, and `pace:` on a screen that waits.
- `screen :bitmap, tear_free: true, colors: [...]` — **say which colors the screen shows** instead of letting the framework work them out from the ones you name. The tear-free screen holds a number per pixel that picks a color out of a shared table, and normally the framework builds that table for you, silently, from the color names you write — which is right until your pictures come from somewhere that already decided. Art imported from another game or a paint program has pixels that are numbers picking out of *its* table, so give the colors in that table's order and the pictures line up. Everything else is unchanged: you still write color names everywhere, and you never write a slot number. **The order is the whole point** — nothing is moved, nothing is added (not even black, which the worked-out table always reserves at the front), and a color repeated in the list keeps both places, because dropping one would shift every color after it and move every pixel of every picture. Drawing with a color the screen was not given is a friendly error naming it; giving two screens different lists is a friendly error, because the display holds one table at a time; and `colors:` without `tear_free: true` is a friendly error, because a plain bitmap screen holds a whole color in every pixel and has no table to fill in.
- `floors = setting :floors, 60` — **what this build was told**, for a game that comes in several cuts: which floors are in it, where the player starts, which screen it boots on. The default is on the same line; a setting with no default has to be given. It is a value while the game is BUILT, a plain Ruby value like the numbers a game works its tables out from, not a variable the game keeps while it runs. It is handed to ONE build — `game.program(settings: { floors: 1 })`, `game.build_rom(settings: …)`, `VBlank.build(…, settings: …)`, `ruby-gba build game.rb --set floors=1`, or `write_if_main(settings: …)` on a game file's last line — so a test builds a one-floor cartridge beside a sixty-floor one, on another core at the same moment, and neither sees the other's. That is why it exists: reading the environment from inside the game's block reads something the whole process shares. The command line can only give text, and text is read as the kind of thing the default is (a number, a name, `true`/`false`); a setting with no default arrives as given. Three friendly errors: a setting the build gave that the game never asks for (a name spelled two ways would otherwise build the default and look right), a setting with no default that was not given (naming what was given instead), and text that cannot be read as its default's kind. Where a game still wants the environment, the line that builds it is the place to read it: `write_if_main(settings: { floors: ENV.fetch("FLOORS", "60") })`.
- `VBlank.game "NAME", consoles: %i[gba gbc] do … end` — **a game for the Game Boy Color as well as the Advance.** A game whose `consoles:` names `:gba` alone is for the Advance alone, and building it for a Game Boy Color (`game.program(console: :gbc)`, `game.build_rom(console: :gbc)`) is a friendly error naming both screens: a game laid out for 240×160 and shown on 160×144 loses a third of its picture, which no warning would make right. Saying `consoles:` is saying the game lays itself out from **`screen_width`** and **`screen_height`** — the size of the screen it is being built for, 240×160 or 160×144, read in the block like any Ruby number — rather than from numbers for one screen: `paddle_x = screen_width - 12`. Everything that already works from the screen does the same with no change: `:center` text, `clamp_to_screen`, `center_on_screen`, the edge tests, a grid checked against the screen. What each verb does on a Game Boy Color — works, or is refused naming the hardware it lacks and saying what to use instead — is `Console::ColorAnswers` (`lib/vblank/console/color_answers.rb`), and the reasons are in `doc/research/gbc-feature-policy.md`.
- `wait_vblank` — wait for the safe window to draw. A `game_loop` already does this each pass, so you only write it in a program that has no game loop, or under `frame_sync: :manual`.
- `halt` — stop (branch to self). `debug_halt` — truncate the ROM here (bisecting).
