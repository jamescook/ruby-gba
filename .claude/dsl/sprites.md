# DSL reference: Images & sprites

The whole story of these verbs. The one-line index is `.claude/rules/dsl-reference.md`.

- `image :name, "." => :transparent, "#" => :red do <<~ART … ART end` — ASCII art; or `image :name, width:, height:, data:` / `from: "file.png"` (file paths resolve next to your script).
- **A picture drawn from few colours costs half the video memory, and there is nothing to write for it.** The console holds a picture's pixels one of two ways — a whole number each, out of a table of 256 colours, or HALF a number each, out of sixteen — and half a number is half the memory for the same picture drawn at exactly the same speed. Sixteen sounds crippling and is not, because they are not the same sixteen for every picture: the table is read in groups of sixteen and a picture says which group it draws from, so two pictures can have sixteen colours each and share none of them. So the framework counts the colours in each piece of art and decides. **Fifteen or fewer and it halves** (the sixteenth is the see-through one); more and it is stored the way everything was before, out of the whole table, and the two kinds sit side by side in one game. It is worth knowing only because the two budgets it spends are fixed and small — 32K holds every sprite picture a screen can show, and one block holds every background tile — so **twice as much art fits**, and `rom.profile` says how much of each is left and how much of that the halving bought back. Pac-Man's sprites more than halved, from 5K to 2.5K. On the tile side it is the difference between 256 distinct 8×8 tiles for a whole game and 512.
- **A sprite's poses are stored at their own size, not the biggest one's, and there is nothing to write for that either.** Poses are drawn on one canvas, big enough for the widest frame — a sword swing, a jump — and most frames use a fraction of it. Every pose used to cost the canvas's size, because a sprite reads a run of tiles one after another and cannot share the blank ones the way a background shares a repeated tile. Each is now cut down to what it actually draws, and the offset comes with it so **the picture does not move**: the character's origin is the canvas's corner, which is where you put the sprite. Measured on a cycle drawn 64×64 whose character covers 24×32, four poses went from 8192 bytes to 4096, ten from 20480 to 10240, and a twenty-frame cycle that would not build at all came to 20480 and fits. Poses that come out the same size keep the plain draw; poses that genuinely differ carry a word each — which tiles, what shape, what size, how far along — read once a frame, which is what lets such a cycle be stored frame by frame instead of all at the largest. A sprite that **turns or resizes** is not cut down, and that is about being right rather than easy: the console spins an object about the middle of its own box, so trimming would move the pivot.
- **A part one pose shares with another is stored once, and nothing says so.** Most of a character does not change between two frames of a walk — the head, the torso, the arm that is not moving — and since a pose is stored as pieces, each naming its own tiles, the pieces that did not change are stored one time and every frame points at them. **This is the one saving a game written straight against the console cannot have**, which is worth knowing because everything else here merely spares you the bookkeeping: an object reads tiles one after another, so by hand every frame has to be its own run and a part that stood still is kept again in each. Two whole poses that are the same picture are the easy case of the same thing — a ping-pong cycle written `frames: [:a, :b, :c, :b]` costs three pictures rather than four, and a four-way character whose rest frame is the same in every direction keeps it once instead of four times (Pac-Man's chomp went from 1024 bytes to 640 on exactly that). **What it is really for is the big pictures**, where the same walk cycle can be the difference between building and not: eight frames of a 96×96 creature whose torso stands still came to 26K where the console holds 32K, and it needed 36K before — it did not build at all. Nothing in the program says which parts are shared, so `rom.profile` is the only place the number appears. **What it costs** is nothing to write and, for most sprites, nothing at all: a cycle whose frames are all the same picture, and a cycle where nothing repeats, are drawn exactly as before. A cycle where SOME pose repeats moves onto the per-pose word described above, which measured 12 instructions a frame — against at least one whole pose of picture memory, which is a wall a build hits rather than a frame anybody can see.
- **A character with more frames than sprite memory holds keeps one frame there at a time, and there is nothing to write for it.** Every picture a sprite can show normally sits in the console's 32K of sprite memory from the moment its scene starts, which is the fast arrangement — showing the next frame is pointing at different tiles — and every sprite gets it while the pictures fit. A character with a full set of animations can fill that on its own, though: Link in The Minish Cap is a resting pose and a ten-frame walk and run in three facings, the fourth facing the third one reversed — 63 stored pictures, 32,256 of the 32,768 bytes — and then not one enemy fits beside him. So when the pictures do not fit, the build picks the sprite with the most memory to give back and gives it room for ONE frame instead; whenever the frame it is showing changes, that frame is copied in out of the cartridge before the sprite is drawn. More are picked until everything fits. That is how the console's own retail games put a full cast on screen. Sprites showing the same pictures — every slot of a `pool` — are weighed together, since keeping one of them to a frame gives nothing back while the others still show the set, so a pool keeps its pictures whole unless keeping every slot to a frame is worth more. **What it costs** is that copy — one frame's worth of tiles, and only on a frame where the pose changed, so a sprite holding still copies nothing — against a wall a build otherwise hits. A sprite that always shows the same picture has no frames to give back, so a screen of still pictures that do not fit is still the friendly error, naming the biggest.
- **A sprite can be BIGGER than any picture the console draws, and it is still one sprite.** The console has twelve rectangles and the largest is 64×64, so a boss, a vehicle, a large creature, a title-screen character had to be built by hand out of several `sprite` handles the game then moved in step — real bookkeeping, easy to get subtly wrong, and exactly the machinery this framework exists to manage. Nothing about the hardware asks for it: several of those rectangles standing shoulder to shoulder look exactly like one big picture. So **write the picture at the size you drew it** — any whole number of tiles, up to 256 each way — and the framework works out how to cut it up, keeps the pieces together and draws them at one depth. It **moves, faces, animates and collides as one thing**, because it is one: `move`, `face`, `frames:`, `overlaps?` and the screen-edge tests all read the sprite's own position and its whole picture, and `mirror` reflects it about the picture as a whole so a character facing the other way does not turn inside out. The cut also **pays for itself in memory**, because a piece that draws nothing is not stored at all — a character is a ragged shape in a rectangular canvas, and one object has to keep every blank tile inside its own box: a 96×112 creature drawn on a 128×128 canvas came to 192 tiles against the 256 one box would have cost. **What it spends is sprites**, since the console draws 128 at once and each piece is one of them — that creature costs six, and it costs six sprites' worth of drawing too (a piece measured 37 instructions a frame against 32 for a whole small sprite). The framework weighs the two off against each other: a place in that table of 128 is worth about eight tiles, being about the same share of what there is, so a finer cut is only taken when the blank it drops pays for the places it spends. `rom.profile` says how many each sprite came to and how many are left. **A picture the console can already draw stays one sprite**, so nothing about an ordinary one changes; and a picture it has no size for but that fits inside one — 24×24, 48×48, sizes that used to be a build error — is one sprite too. Two things a big picture cannot do, both friendly errors naming it: it cannot **turn or resize** (the console spins each object about its own middle, so the pieces would pull apart), and it cannot be over 256 pixels either way. Worked example: `examples/shmup/boss.rb`, a 96×48 cruiser that slides along the top, banks the way it goes by mirroring, dives at the ship and takes fire anywhere in its picture — three of the console's objects, in a game already spending them on enemies, a ship, a shot and a HUD.
- `image :link, from: "link.png", colors: [:transparent, :white, …]` — **art that came from somewhere that already decided its colours**: a picture pulled out of another game, or one an artist drew against a fixed set. The list is that set, in its own order, **the see-through one first** — which is how a palette exported from anywhere else on this console is laid out, so it drops straight in. Say it and the framework keeps that order rather than working one out; say nothing, which is almost always right, and it works one out from the art. It changes nothing about what is drawn. Three friendly errors, all raised at the line that wrote the picture: a list longer than sixteen, a pixel drawn in a colour the list does not hold, and a pixel sitting on the first entry and nowhere else in the list (the first entry means see-through, so it would not be drawn). A cartridge's palette often keeps a real colour in that first slot and draws the same colour from a later place; such a list goes in as it is, and those pixels are drawn from the later place. The list can also be one declared with `colors`, by its name — `colors: :sea` — whose first entry then means see-through whatever it was written as; that is how a background drawn from several lists says which is which (see `bg.draw_with`). All the pictures one sprite shows must be given the same list, or none given one — the console draws a sprite from one table. The same goes for all the pictures of one `pool`, since each of its things is a sprite that can show any of them. Pictures that disagree are a friendly error naming the sprite or the pool, on the interpreter as on the console; to give one thing colours of its own, give the pictures one list and tell it `draw_with` another.
- `image :link, width: 16, height: 16, colors: [...], places: [0, 1, 2, …]` — **the pixels as NUMBERS into that list rather than as colours**, which is the shape art lifted off another cartridge arrives in: a block of index bytes, and the palette they count into. Place 0 means see-through and every other place is a colour in the list. It draws exactly what the same art given as colours draws, and **the one difference is the reason it exists**: a list may hold the same colour at two places, and nothing but a place can tell those two apart. A palette taken off a real cartridge nearly always repeats one (two blacks, two whites), and `draw_with` swaps colours BY PLACE — so a picture that kept only colours has pixels that could have come from either place, and a list that gives those two places different colours would recolour half of them wrong. Art given as places is never in doubt, and it saves the conversion besides. Where a picture is stored the big way — a `screen :rotozoom` background, whose tiles read the one shared table rather than a list of sixteen — there are no two places to keep apart in the first place, since a colour is a single entry there however often the list names it; the picture draws exactly the colours its places named. Five friendly errors, all at the line that wrote the picture: `places:` together with art drawn in characters, `data:` or `from:` (two ways of saying what a pixel is would have to agree, and nothing could check that they did), `places:` with no `colors:`, the wrong number of places for the size, a place the list does not hold, and a place the list is see-through at (only place 0 means see-through, so there would be no colour to draw).
- `tag = image :tag, from: name_list, width: 32, height: 8, colors: :ink` then `sprite :tag, at: [x, y]` and `tag.changed` — **a sprite's picture the game paints while it runs**: a name tag over a save slot, a portrait put together from parts, a number that floats up. It is the sprite side of `tiles ..., from: list` (see Tiled backgrounds) and works the same way: the pixels live in a `list ..., width: :byte` the game owns, packed the way the console keeps them, and `changed` shows them on the next frame. The picture's tiles are the list's 32-byte runs taken left to right and then top to bottom, which is the order one sprite keeps its tiles in, so a 32x8 tag is four tiles side by side and 128 bytes. It has to be a size the console draws a sprite at whole (8x8, 16x16, 32x32, 64x64, 16x8, 32x8, 32x16, 64x32, 8x16, 8x32, 16x32 or 32x64), since a painted picture is never cut into pieces; any other size is a friendly error listing them. It is kept whole and never shared with a picture that merely looks the same, and every sprite showing the same painted picture shows the same copy. It is the whole of its sprite: a sprite whose `facing:` or `frames:` puts it beside other pictures is a friendly error, and the way round is a sprite of its own for it. A scene that owns the sprite puts the picture up from the list as it is when the scene takes over again, and several scenes can each declare the sprite — `examples/hero.rb` keeps its map of the walk in the corner of the file screen too. It costs what painted tiles cost: one store for `changed`, one compare on a frame with nothing changed, one block copy of the picture's bytes on a frame with something. On `screen :bitmap` it is a friendly error, since a bitmap screen has `pixel` and `blit` for this.
- `colors :hurt, [:transparent, :yellow, :orange, :red]` then `hero.draw_with :hurt` — **a sprite drawn with a different list of colours while the game runs**: a character flashing warm while it cannot be hit, a poisoned enemy turning green, a team colour. `colors` declares a list no picture owns, laid out like a picture's own `colors:` list (see-through first, 2 to 16 colours), and the sprite is matched to it **by place**: a pixel drawn in the second colour of the sprite's list is drawn in the second colour of this one. So the shape and the shading stay exactly as drawn and only the colours move — nothing blinks and nothing is blended. It lasts until the sprite is told otherwise, and `hero.draw_with :own` is its own colours again. **One of several, by a number the game works out**: `hero.draw_with [:warm1, :warm2, :warm3, :warm4], showing: (frames >> 2) & 3` — the same `showing:` word `blit` and a menu row use — and a number outside the set is the sprite's own colours, so a value that ran off the end looks normal rather than wrong. Inside a pool's `each` it is per instance (`e.draw_with :hurt`), and an instance spawned into a slot starts in its own colours whatever the last one was doing. **The colours change on the frame the sprite's position and pose next do**, never a frame before or after, because on the console the choice is part of the sprite's table entry, written with them. **What it needs**: the sprite's pictures given a `colors:` list (art drawn in characters takes one too, beside the characters' colours; a sprite whose pictures come from `frames_from:`, `facing_from:` or `from_aseprite:` takes it once, `sprite ..., colors: [...]` or the name of a `colors` list, for every picture it imports), since a list swaps by place and a picture whose list the framework worked out has places nobody chose; a list at least as long as the sprite's own; and `screen :tiled`, since a bitmap screen keeps a whole colour in each pixel and has no list to swap. Each is a friendly error. So is one more, and it is the one worth knowing about before importing a palette: where the sprite's own list holds a colour at **two** places its art draws, and the list it is told to draw with gives those two places different colours, the build stops rather than recolouring half those pixels wrong — a picture stored as colours records no places, so nothing says which of the two a pixel came from. The error names both places, and the way round it is `places:` (above), which records them. **What it costs**: on the console, each different list takes one of the sixteen groups of colours sprites draw from (a sprite with its own colours takes one too, and two lists with the same colours share one). **A game with more lists than groups still fits, with nothing to declare**: the console then keeps a group for each sprite's own colours, for each list the same as one of those, and for each list told to `recolor` or given to `colors_in_use`, and lends the groups left over to the other lists — a list borrows one the frame something on screen first wears it, its colours copied in between frames with the sprite's row (through any tint in force), and the group is free to lend again once nothing has worn the list for a frame. That is how the console's own games hand their groups out, so what has to fit is what is on screen at once, never a room or a scene. More lists worn at once than groups left over draws the extra things in whatever colours a group already holds, and a profile of the game (`rom.profile`) says how many times; only the console has the limit, so the interpreter, desktop and web builds draw them right and a test that compares builds shows the difference. A group goes back once a whole frame passes with nothing drawn with it, not the moment its last wearer goes, so with every group lent out a thing arriving on the frame another leaves shows for that one frame in colours not its own. A sprite drawn with a borrowed list is written every frame, since being written is how it keeps its group, and each such write costs a call to the routine that lends. Sprites whose own colours take all sixteen groups leave none to lend: a friendly error naming the scene. **The sixteen are one scene's, not the whole game's**: a sprite and a list declared inside a scene take their groups only while that scene is up, and that scene's colours are sent as it takes over (through any tint or fade in force, so its sprites never arrive at full colour on a dark screen), while the sprites every scene shows keep their groups throughout. A sprite told `draw_with` spends a read of which list and a few instructions a frame, and a game that never says it emits nothing new. A colour a picture's own list holds twice is drawn from its first place. Worked example: `examples/shmup.rb`, where the ship pulses warm while it cannot be hit and the boss does for a moment after each shot lands.
- `recolor :slot, :goblin` (also `recolor :slot, [:goblin, :bat, :crow], showing: room`, and `recolor :slot, :own`) — **a list of sprite colours that holds other colours while the game runs**, so one list dresses many different things in turn. `draw_with` picks which list a sprite reads, and a list it could pick that does not fit beside the rest borrows a group of the console's sixteen while something wears it (see `draw_with` above). A slot is the other way, chosen by the game: the things in a room draw with a few lists that are **slots**, walking into the next room says what each slot holds, and a slot keeps its one group whatever is on screen. Declare the slot with `colors` like any list (that is what it holds at power-on), tell sprites and pool instances `draw_with` it, and `recolor` says which colours it holds now: one other list, one of several by a number the game works out (the same `showing:` word), or `:own` for the colours it was declared with — which is also what a number outside the set means, so a counter that has run off the end looks right. `draw_with` and `recolor` can come in either order. **A list that is recoloured takes one group however many sets pass through it**, and however many sprites draw with it; that group is the list's alone, so a picture or another list with the same colours does not change with it. Every sprite and pool instance drawn with it shows the new colours **on the frame its position and pose next change**, the rule `draw_with` keeps, because both are written in the same gap between frames. It **says which colours the list holds**, the way `show_map` says which map is showing: once or every frame, from a branch or a scene, and the copy is made on the frame the answer changed and no other. The colours go in **through any tint or fade in force**, and a tint that moves afterwards moves the colours the list holds, not the ones it was declared with. **A list only one scene's sprites draw with has its group while that scene is up**: told to recolour while another scene is up, it shows the new colours when its own scene is back, and it still holds them after another scene, or a `screen :bitmap` scene, has been and gone. A list that sprites of several scenes draw with, or a sprite every scene shows, keeps one group throughout. **What it costs**, measured on the console: a list told the colours it already holds, about 40 instructions a frame, most of them the game's own line picking the number; a list told new colours, about 340 on that frame — so ten slots filled on the frame a room is entered are about 3,400, around a fortieth of a frame, with or without a tint in force. A game that never says it emits nothing new. **What a set needs**: a colour for every place the list itself has, since the sprites drawn with the list were checked against that many — a friendly error. Five more: a name that is not a `colors` list, several sets with no `showing:`, a list no sprite or pool draws with (a name spelled two ways), a set that would recolour a picture given as colours wrongly (the rule `draw_with` keeps about a colour at two places), and a background drawn with a list that is recoloured — `recolor` reaches sprites only, and a background has `draw_with ..., showing:` of its own for this. Worked example: `test/ruby_gba/builder/test_recolor.rb`.
- `colors_in_use [:door, :zelda]` (also `colors_in_use [[:door, :zelda], [:octorok, :bush]], showing: room`) — **a hint, which a game does not need**: since the console lends its groups to the lists things on screen wear (see `draw_with` above), a scene with more lists than groups fits without it. What it still changes is which lists keep a group whatever is on screen. It says **which lists of sprite colours the room the game is in uses**. It is the same need `recolor` meets, said the other way round: there the game names the slots and fills them; here it names the lists each room uses, keeps telling each thing `draw_with` its own list as it always would, and the build works out the slots. A pool whose things are of many kinds, each kind drawn with a list of its own (`thing.draw_with KIND_LISTS, showing: thing.kind`), is the shape it is for. **Lists never in use together take turns in one group**, and lists of one set never share one, so the groups the sets take are as many as the biggest set has lists (more only for sets that overlap in a ring, each list in use with each of the others but never all at once). Which group a list takes turns in is settled once for the whole game, so a sprite is drawn through the same group whatever set is in use, and changing set copies colours and nothing more. **It says which set is in use**, the way `show_map` says which map is showing: once or every frame, from a branch or a scene, and the colours are copied in the gap between frames on the frame the answer changed and no other — the frame every sprite's position and pose are written too, so a frame shows the old room's things in their colours or the new room's in theirs, never a mix. **Until the game first says, the first set named is in use**, and so it is for a number naming no set. The sets are counted in the order they are written, across every `colors_in_use` in the game, and a set written twice is counted once. **A sprite drawn with a list that is not in use shows whatever its group holds now**: another list's colours, black past the end of a shorter list. That is what it does on the console, so every build does it; take a room's things away as it is left. Lists a game does not name in any set keep a group each for the whole scene, as before, and so does each sprite's own colours. **Scenes keep their own**: the lists only one scene's sprites draw with take turns among themselves, so the groups they take are that scene's while it is up and free for any other scene after; lists that sprites of several scenes draw with take turns among themselves too, in groups every scene keeps. **What it costs**: for each group the sets take, what `recolor` costs for one slot — a comparison a frame, and a copy of its colours on the frame the set changes. A game that never says it emits nothing new. **When a room does not fit**, the build stops with the friendly error about the sixteen groups, and it names the biggest set: its line, which of that line's sets it is (the number `showing:` picks it by), and its lists. Four more friendly errors: a name that is not a `colors` list, several sets with no `showing:` (or one set with it), a list no sprite or pool draws with (a name spelled two ways), and a list that is also told to `recolor`. Worked example: `test/ruby_gba/builder/test_colors_in_use.rb`.
- `mirror(:hero_right)` → **the same picture facing the other way**, as a picture name like any other — so it drops into `facing:`, `frames:`, a `pool` or a plain `blit` wherever a name goes. "Left is the right one, backwards" is how nearly every 2D game faces a character, and saying it used to mean drawing the art twice. Pass a list and get a list back (`facing: { right: WALK, left: mirror(WALK) }`), so a whole direction's frames turn round in one word. **On `screen :tiled` a mirrored pose costs no sprite memory at all**: the console draws an object reversed for nothing, so the build stores the picture once and says "that one, backwards". Measured on a character with an eight-frame walk drawn both ways, 256 tiles became 128 — and on a four-way character whose left mirrors its right, 320 became 240. **Nobody has to say so, either**: the sameness is judged on the pixels, so a game that drew its left-facing art by hand is noticed and stored once too, the same way two sprites showing the same picture already share it. What `mirror` saves you there is the art, not the memory. What it costs is on the drawing side and is small: a mirrored pose puts that sprite on the per-pose word described above, which measured 51 instructions a frame against 33 for the plain draw. Two things it does not do: a sprite that **turns or resizes** keeps both sets of pixels (the two attribute bits that reverse an object are the ones that name its rotation group once it is turning), and on `screen :bitmap` there is no such hardware, so a mirrored picture is drawn like any other. Naming a picture that is not defined is a friendly error. Worked example: `examples/hero.rb`, whose hero is drawn looking right and faces left by mirroring.
- `upside_down(:spike_up)` → **the same picture turned top to bottom**, which is `mirror`'s other way: `mirror` turns left to right, `upside_down` turns top to bottom. A reflection in water, a stalactite drawn from a stalagmite, an arrow that points up or down. It hands back a name, or a list for a list, exactly as `mirror` does, and the two compose: `mirror(upside_down(:arrow))` is the arrow turned both ways. Everything `mirror` says above holds for it: on `screen :tiled` the turned pose costs no sprite memory (the console draws an object upside down for nothing, and art drawn upside down by hand is noticed on its pixels too), it puts the sprite on the per-pose word, a sprite that turns or resizes keeps both sets of pixels, and `screen :bitmap` draws it like any other picture. Naming a picture that is not defined is a friendly error.
- `blit [:calm, :hurt, :dying], x, y, showing: damage` — **one of a set of pictures, picked by a number the game works out.** A face that watches you, a machine in four stages of wreckage, a dial drawn as a strip, a portrait picked by who is speaking. `showing:` is the same word a `menu` row and a two-colour `draw_text` already use for "this value decides which", and the number may be a variable or something worked out on the spot (`showing: hurt * 3 + look`). The pictures must all be the same size — one is drawn where the last was, so a smaller one would leave a bigger one's edges behind — and **a number outside the set draws nothing**, so a value still settling or one that ran off the end leaves the screen alone rather than drawing the wrong picture. It costs a test per picture, which is what writing it out by hand costs too — so for a set of a couple of dozen, consider laying them side by side in one picture and using `draw_column_at` instead, where which one to show becomes arithmetic rather than tests (that is what the Wolfenstein port's status-bar face does, and its comment says why).
- `blit :name, x, y` — draw an image at a runtime position (clips at edges). **On the tear-free screen** (`screen :bitmap, tear_free: true`) a solid picture draws too, with two rules that come from how that screen holds its pixels: it must start on an **even column** and be an **even number of pixels wide**. That screen takes two pixels at a time and will not take one, so a picture that starts or ends halfway through a pair cannot be copied in — the same rule `fill_rect` already lives by. Both are friendly build errors naming the number, and a column the game works out is fine as long as it can be *proved* even (`col * 2`), because a column nothing can prove is refused rather than drawn in the wrong place. A **see-through** picture there is a friendly error too (a solid one only, for now). It costs less than the same picture in direct colour — half as many units through the copying engine — and a tall picture costs more than a wide one of the same area, because every row is a copy of its own.
- **A sprite that never moves stops costing the frame anything, and nothing says so.** The console builds its picture from a table it re-reads every frame, and a row of that table stays exactly as it was last written — so a title screen's lettering, a border round the play area, a signpost in a room needs telling once and then never again. It used to be told on every frame like everything else, because nothing in a program says which of its sprites stand still. Now the build reads that off what the program DOES: a sprite is still when nothing that can run more than once changes where it is, which picture it shows, how it is turned or sized, or what colours it draws from. **What it buys is room in the console's quick memory**, which is the same 32K the framework keeps the frame's own code in, and which decides whether a whole frame runs about two and a third times faster or not — measured on `examples/shmup.rb`, the frame's code went from 10.8K to 7.7K and its work from 2951 instructions a frame to 2617; on `examples/dive` from 9.2K to 7.2K and 1469 to 1142. **It is judged pessimistically on purpose**: a sprite moved from anywhere at all — a scene, a routine, a timer's handler, a loop — keeps its per-frame write, and so does one whose position is worked out in a way the build cannot see through, one that keeps a single frame of its pictures in memory at a time, and one held out of a `fade … under:`. The one thing that may still change about a still sprite is whether it is SHOWN, since a sprite declared inside a `scene` is on screen exactly while that scene is; the frame asks that one question for every still sprite in the game together. A game that picks its scenes with two different variables gets none of this, and `rom.profile` shows the frame's size either way. **A sprite that DOES move, declared inside a scene, is written by a routine of that scene's own** rather than by the game loop's body — still in the gap after each frame, so nothing about which frame's numbers it shows changes. The game loop's body is the first thing kept in the quick memory, so a screen shown once used to take that memory from the scene the game is played in: a file-select screen's four sliding panels were 3K of code there. Now each scene's routine is placed like any other, by what a frame spends in it, and `rom.profile` lists it as "moving the sprites of scene :name". What it costs is one compare a frame per scene with moving sprites, and a call on that scene's frames.
- `sprite :name, at: [x, y]` → a sprite drawn each frame leaving no trail; the screen mode picks the kind. On `screen :bitmap` it's a software `Sprite` (save-under): `facing: {left: :img_l, …}` poses, `shown: false`, `hitbox:` (collision box — `:full` / an inset number / `[x,y,w,h]`; default is per-pixel collision, gated by the visible-pixel box), handle `x`/`y` (Values), `move(:left, by:)` / `move(dx, dy)`, `move_to`, `clamp_to_screen` (alias `stay_on_screen` — pin it fully on screen using its own size, no coordinate literals), `center_on_screen` (its sibling — put it in the middle, worked out the same way), `face`, `hide`, `show`, `overlaps?`, plus the screen-edge tests below. On `screen :tiled` it's a hardware (OAM) `HardwareSprite`, composited by the console: `x`/`y`/`move`/`move_to`/`clamp_to_screen`/`center_on_screen`/`hide`/`show`/`face(:left)`/`face_angle`/`turn`/`angle`/`overlaps?` handle plus `facing:` poses (the console swaps which uploaded picture it draws), and several stack in a stable order (later-declared in front, unless a `layer` says otherwise — see Layers; a `pool` with pictures stands among them where it was declared). Size must be an 8×8-tile multiple, up to 256 each way; one bigger than the console's largest picture is cut up for you (see above).
  - **Clearing the screen under a bitmap sprite is safe.** A bitmap sprite remembers the pixels it covers and puts them back as it moves, which is how it leaves no trail — and which would go wrong the moment the game repaints its field, for a new round or a change of scene, since what the sprite remembers is then a square of the picture that went. So `clear_screen` tells every sprite it is off the picture: nothing is put back, and the repaint before the next frame draws each shown sprite again over whatever the game painted after the clear — a wall drawn on the fresh field where the sprite stands is what it remembers from then on. A sprite declared before its field is cleared comes out right for the same reason. It is the WHOLE-screen clear that does this: a `clear_screen` inside an `inside` block clears that area and leaves the sprites alone, and painting over a sprite by hand (a `fill_rect` across it) is still yours to avoid, with `hide` before and `show` after. What it costs is a variable for each bitmap sprite, two stores a frame for each, and a store for each at every clear — 44 bytes of code a sprite, measured on `examples/sprite_mover.rb`. Clearing on EVERY frame is still the mistake it was, and still a friendly warning: the sprite is drawn in the gap before the frame and the clear wipes it straight after.
  - **Flipbook animation:** `sprite :name, at:, frames: [:f1, :f2, …], rate: N` (instead of `facing:`) cycles the same-size frames — one every N game-frames, timer hidden and managed — on either screen; composes with `move` (animate while moving). `facing:` and `frames:` are mutually exclusive (both drive the pose).
  - **A pose picked by a number the game works out:** `hero.face [:idle, :step1, :step2], showing: step` — the same `showing:` a `blit` and `draw_with` take, counting from 0, on either screen and on a pool's instance inside `each` (`g.face POSES, showing: g.state`). An animation step, a state, which variant of an effect: the pose a game wants is usually a number, and written as a test per pose (`(step == 0).then { hero.face :idle }` …) it is a few dozen bytes for every pose, which is how a character with a hundred frames ends up with kilobytes of code choosing one. This is the same few instructions whatever the number of poses: poses listed in the order they were declared are a sum, and any other order is read out of a small table built into the cartridge, one byte a pose. **A number outside the list leaves the pose as it was**, so a counter that has run past the last step holds the last one shown rather than jumping somewhere wrong. A list naming a pose the sprite was not given, one name with `showing:`, a number you wrote that is past the list, a name no variable has, a yes-or-no in place of a number, and a number holding a fraction are friendly errors.
  - **Directional animation:** give `facing:` a **list of frames per direction** — `facing: { left: [:walk_l1, :walk_l2], right: [:walk_r1, :walk_r2], … }, rate: N` — for a per-direction animation: the sprite runs that direction's cycle while it faces that way, so a character walks with its own cycle each way, or Pac chomps whichever way he moves (`examples/pacman.rb`). Every direction needs the same number of frames (two or more). The framework composes the facing and the frame into one pose for you (`face`/auto-facing `move` pick the direction, the hidden timer runs the frame). Works on both screen kinds.
  - **Import frames from a sprite sheet:** `sprite :name, at:, frames_from: "walk.png", tile: 16, rate: N, transparent: true` — slice one image file into equal-size frames (`tile:` is the frame size, a number or `[w,h]`) and cycle them; nothing to name or number. `transparent: true` honors a cut-out background. Path resolves next to your script. Mutually exclusive with `frames:`/`facing:`.
  - **Import directional poses from a sheet:** `sprite :name, at:, facing_from: "walk.png", tile: 16, dirs: [:down, :left, :right, :up], rate: N, transparent: true` — slice a four-way character's art from one file (the `facing:` counterpart to `frames_from:`). The sheet is a grid: each **row** is a direction (in `dirs:` order, top to bottom) and the **columns** of that row are its frames. One column = a still pose per direction (plain facing:, no `rate:` needed); several columns = a per-direction animation (feeds the directional-animation form above). `tile:` is the cell size, `transparent: true` honors a cut-out, path resolves next to your script. Mutually exclusive with `facing:`/`frames:`/`frames_from:`.
  - **A sprite put off the screen is off it, however far.** The console keeps a tiled sprite's row as one of 256 and its column as one of 512, and a place outside those is kept as a place inside them. Written straight against the console, a sprite parked at row 300 is drawn at row 44, and one that walks off the right edge and keeps going comes back in from the left. Here it does not: `enemy.move_to 0, 300` is a fine way to put a sprite away, a thing that flies off an edge never comes back, and each piece of a picture drawn as several is kept off by itself, so the far end of a big sprite cannot come round while the near end is on the screen. It works on a `pool`'s things too. **What it costs** is three instructions for the row and three for the column each time a sprite's place is written, none of them a branch (about nine for the row of the one tall box below) — measured on `examples/shmup.rb`, the frame went from 2999 instructions to 3025 — and nothing for text, whose places are written in the program. A sprite off the screen is still in the console's table, at its own place wherever the table can say it and at the first row below the screen or the first column right of it otherwise, so `v.sprites` in a test still finds it and still tells it from one the game hid. **One sprite can still show at the far edge, on both backends**: a sprite 64 pixels tall that *resizes* is drawn in a box of 128 rows about its middle, and the console counts only 96 rows past the bottom of the screen. So while its middle is 33 to 63 rows below the bottom edge and some of it is still on the screen, the bottom of that box shows at the top of the screen; and the same distance above the top edge, the top of the box shows at the bottom. Nothing can keep that part off short of hiding the sprite while some of it still shows, so both backends draw it. A game with such a sprite hides it before its middle is 33 rows past either edge, or keeps it to a size where none of it reaches the screen from there (up to about its drawn size). A 64-pixel sprite that only *turns* never does this, because its picture never reaches the rows that come round, and neither does any smaller sprite.
  - **Change size (tiled sprites):** `sprite.scale(1.5)` draws a `screen :tiled` sprite bigger or smaller about its own center — `1.0` is the size it was drawn at, `2.0` twice as big, `0.5` half. A boss that swells, an item that pops when you collect it, an enemy that shrinks into the distance. With no argument, `sprite.scale` hands back the size as a `Value` you can read and ease (`coin.scale.approach! 1.0, 0.05`), so growing over time is the expression DSL and nothing new; the size may be a whole number, a fraction, or something the game works out. It rides in the same hardware as `face_angle`, so a sprite can turn **and** resize at once for the price of either, and twice the drawn size is the ceiling (past that the picture runs out of the box the console gives it). It is the dearest thing a sprite does — drawing at a size means dividing by it, once a frame, which the framework does for you. On `screen :bitmap` resizing is a friendly error (draw the sizes you need as separate `image`s), and a size of 0 or less is a friendly error wherever you write it.
  - **Turn to any angle (tiled sprites):** `sprite.face_angle(degrees)` points a `screen :tiled` sprite at an exact heading — degrees clockwise from upright, pivoting on its own center — and `sprite.turn(degrees)` turns it by that much from where it points now (positive clockwise, negative counter-clockwise). Both wrap; `sprite.angle` reads the heading (0..359) as a `Value`. This is real rotation to any angle (the console's sprite rotate/scale), not the fixed-pose swap `face`/`facing:` do — a ship that points where it aims, a bird that tilts to climb (`examples/bird.rb`). `degrees` may be an Integer or a `Value`. Up to 32 sprites can turn at once (a friendly error past that); on `screen :bitmap` turning is a friendly error (a blitted sprite can't rotate — use `facing:` poses for a few fixed directions).
  - **Import from Aseprite (named animations):** `sprite :name, at:, from_aseprite: "bird.aseprite"` — import a sprite the way an artist authored it in Aseprite. Point it **straight at the native `.aseprite` file** (no export step) — the framework reads the binary directly: it composites the layers, decompresses the frames, resolves the palette, and reads each frame's duration and each **named animation** (frameTag). Or pass a `.json` export instead (both the array and hash layouts), where it slices the frames from the PNG named in the JSON's `meta.image` beside it. Either way it exposes each tag as an animation you play on demand: `hero.play(:walk)` / `hero.play(:attack)` (a `Sprite`/`HardwareSprite` method). The current animation loops until you play another; the first tag plays at boot (a file with no tags is one looping animation). The frame speed comes from the frames' durations. Path resolves next to your script. Mutually exclusive with the other pose sources.
- `rgb r, g, b` (0–31) / `rgb8 r, g, b` (0–255) / `color value` — make a 15-bit color.
