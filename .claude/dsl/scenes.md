# DSL reference: Scenes & funcs

The whole story of these verbs. The one-line index is `.claude/rules/dsl-reference.md`.

- `func(:name) { … }` + `call :name` — a subroutine. A `func` or a `scene` that nothing calls is a friendly warning naming it, since it is still in the cartridge and never runs; a call from anywhere that runs counts — the game loop, the lines before it, a timer's handler, another routine that is itself called, a `case_var`, a call picked by number or by a variable's name. `func(:name, fast: true) { … }` keeps it in the console's quick memory, where code runs about **two and a third times faster** — you rarely need to say so, because the framework works out which routines a frame spends its time in (the game loop's own body first of all) and puts them there for you. Say `fast: true` to insist on one it didn't pick, or `fast: false` to keep one out. A `scene` takes the same word, and the routine the build makes to write that scene's moving sprites goes with it either way. `rom.profile` lists what it chose, **how big each one is**, how much of the 32K is left, and — the part worth reading — **what did NOT fit**, with what it wanted and what was left. A routine the frame spends real time in that just missed is where a game lost that whole factor, and nothing else can tell you afterwards. To stop it choosing at all, build with `RubyGBA.build(..., fast_code: false)` — a routine you marked `fast: true` still goes. It can never overrun the memory on its own: the choice is made afresh each build from what the game actually uses, so a game that grows gets a smaller share, never a broken build. **When what a game wants there does not all fit, each scene gets a share of its own**, and nothing in the program says so. Only one scene runs on any pass, so a title screen's routines and the game's are never wanted at the same moment — yet kept for the whole game, the title's held its room while the game was played. So then the room is split: what every scene runs (the game loop's own body, the routine that answers the display, anything those reach outside a scene) keeps a place for the whole game, and each scene's own routines — those only that scene reaches — are copied in as it takes over, into a room the scenes share, so it costs only as much room as the biggest of them. Sets small enough to sit side by side in that room get places of their own and stay in together, and a scene with nothing of its own leaves whatever is in. A set holding something the game loop runs outside its scene — a save's routines, written a piece a pass whichever screen is up — is kept clear of where the others go where there is a choice, and goes in first at power-on, so a game's logos and title leave the file screen's routines in through the opening, where the saves are checked; then every other set that fits beside those goes in. A game whose dispatch names more than 31 scenes keeps one share for the whole game. `fast: true` then means "while the scenes that run it are up": a `func` only play reaches goes with play, and a `save_data` record's word goes with the one scene that asks for its saves — so two words that did not fit together, on two screens that are never up together, now both fit where they used to stop the build. **A routine reached while another scene is up still runs**, from the cartridge, slower: a save the file screen started and play finishes, say. **What it costs** is a copy of the arriving scene's routines on the pass it takes over, a few instructions before each scene is called, and a word of the quick memory for each routine a scene keeps; a game where everything fits is built as it always was and pays none of it. The swap happens at the game's scene dispatch written in the game loop's own body: a `case_var`, or a `call mode` whose names are scenes, which is the same dispatch. A dispatch anywhere else keeps one share for the whole game. The swap never moves a routine an interrupt or a timer can reach. A measured build fills the shares twice — once by what the whole game spends in each routine, once by what a frame of one scene spends — and keeps whichever leaves more of the scenes' measured work in the quick memory, so a routine every scene runs a little of does not take the room each scene's own busy routine needs, and a routine every scene runs a lot of keeps its room. `rom.profile` lists what each scene keeps, and says of a routine that did not fit whose share it missed — a scene's, or the one kept for the whole game. **`func` is about SIZE as much as speed**, and this is the one thing about the framework you cannot work out by reading your own program: a plain Ruby method called from inside a build block runs at every call and records its work THERE, so a helper written once and called from eight places is emitted eight times. A `func` is emitted once and called eight times. Measured in a real game, two such helpers made one routine 27.9K — too big to keep in the quick memory, which cost the whole factor; as `func`s they were emitted once, both were kept, and the code they held ran at the quick memory's speed instead of the cartridge's. When a routine misses its place, `rom.profile` names its most repeated line and says whether several lines repeat together, which is what a helper looks like from the outside. **A body is built after the whole program block has run**, not at the line that writes `func` — which is why a `call` may come before the routine it names. And a `func` written inside another routine's body is built too, however deep that goes, so a routine can be declared **the first time something needs it**: a restart routine declared only by the code that asks for a restart is in the cartridge when a game restarts and costs nothing in one that never does.
- `call HANDLERS, number: opcode` — **one of several routines, picked by a number the game works out.** A plain `call` names one routine; give it a list instead, and `number:` says which of them, counting from 0. What it is for is a number that came out of DATA rather than out of your program: the instruction byte of a script read off a cartridge, the state kept on each of thirty guards, the move an enemy chose. **It goes straight to the routine that number names**, so a list of a hundred and thirty-nine costs exactly what a list of two does — where asking "is it this one?" of each name in turn costs a test per routine, and every one of them is asked on every call. Measured on a game dispatching sixteen times a frame: about 640 instructions a frame either way, against about 22,800 for the tests written out. **A number naming no routine calls nothing** — below 0, or past the end of the list — so a number read out of data needs no test around it, the same answer `show_map` and a song list give. The number may be a variable, something worked out on the spot, or **a field of an instance inside a pool's `each`**, which is the case this exists for: one line there runs a different routine for every one of them. A number you write in the program picks while the cartridge is built, so `call HANDLERS, number: 2` is the plain `call` it would have been. **Or write no number at all**: `call mode`, where `mode` is a variable declared with a name (see `var :mode, :title` under Variables & math), runs the routine that variable names — the same dispatch with the numbering taken off your hands. That is the one to reach for when the game invents its own states; this one is for a number that came out of data. Five friendly errors: `number:` on a single routine, a list with no `number:`, an empty list, something in the list that is not a routine's name, and a written number past the end of the list. A number that holds a fraction is a sixth (use `.to_i`), since the fraction is kept in the low bits and would pick by those.
- `scene(:name) { … }` — a named game state (a routine run once per frame while active). **It takes `func`'s `fast:` word, and the word carries the scene's sprites with it**: `scene :file_screen, fast: false` keeps both the scene's code and the routine that writes its moving sprites in the cartridge, and `fast: true` insists on both. Worth saying about a menu, a title or a game-over screen: what goes in the quick memory is picked by measuring every scene for the same number of frames, so a menu the player sees for seconds counts as much as the scene they play in, and a busy one can take the room ahead of the game — or push the game out. Nothing the scene does changes; `rom.profile` shows where it went. Hold the current state in a variable (`var :state, 0`); `case_var(:state) do when_val 0, :title; when_val 1, :playing; … end` runs exactly one scene per frame; `set! :state, N` transitions (e.g. `pressed(:start).then { set! :state, PLAYING }`).
- **A scene owns what it draws — and that is a budget, not only a look.** The console keeps every sprite picture a game might show in 32K, and a sprite declared inside a scene is on screen only while that scene is the active state — so no two scenes' pictures are ever wanted at once, and **the budget a game has to fit is one scene's, not the whole game's**. A game with more art than 32K still builds so long as no single scene has too much, which is what lets a game with hundreds of rooms declare each room's cast where it belongs. A scene's pictures are sent when it takes over rather than at boot, so staying in a scene costs one comparison a frame and changing scene costs a copy. **A pool's pictures are the exception, and are sent a pose at a time, the first time one of its things shows each**: a pool holds every pose its things could ever show — a pot's shards, an explosion — and most are not on screen when the scene arrives, so copying them then made the arrival wait for pictures nobody was looking at, which in a scene that arrives close to the end of its frame costs a whole frame. That is how the console's own games load an effect's pictures, when one is spawned. What it costs is a load and a compare for each live thing a frame, and the copy of one pose on the frame a thing first shows it in that visit to the scene; the time goes to the routine that draws the scene's sprites. A pool showing the same pictures as some other sprite of its scene, and one kept to one frame at a time, are sent as before. Running out inside one scene is a friendly error naming that scene and its biggest pictures. **The same is true of BACKGROUND LAYERS**, and for the same reason: the console holds four scrolling layers at one time, a `background` declared inside a scene is up only while that scene is, and scenes take turns with them — so a game with many rooms declares each room's scenery in the scene the room belongs to and gets four layers in each, where four for the whole game would not go far. Scenery declared OUTSIDE any scene is up throughout, so it is in every scene's four (a backdrop plus three per scene). Running out is a friendly error naming the scene. **The scenery's MEMORY takes turns as well**: the console keeps every tile picture and map on screen in 64K, and a scene's own tiles and maps go in as it takes over, into room the other scenes use too — so a game whose scenes together hold far more than 64K of scenery builds, as long as no one scene (with what every scene shows) holds more. What it costs is a copy on the frame a scene takes over, with the layers switched off while it runs so the backdrop shows rather than half-sent art, and cartridge space: a scene's own art is stored unpacked, because the console unpacks slowly enough that a big scene took frames of game logic away on arrival. Unpacked, even the largest maps arrive inside the frame, and a scene's logic runs from the frame it takes over on both backends. A scene that runs out is a friendly error naming it. **So do the sixteen groups of colours sprites draw from** (see `draw_with`): a scene's sprites and lists take their groups while it is up, and running out inside one scene is a friendly error naming it. **And so do the groups BACKGROUNDS draw from** — fifteen of that table's sixteen, since the first holds the colour behind everything: the colours of the scenery every scene shows keep their places throughout, and each scene's own scenery takes the rest while it is up, its table sent with its tiles as it takes over and through any tint or fade in force. So a title whose light rays keep a group to themselves for `draw_with` and a room whose tiles fill every other group both fit, where one table for the whole game would not; a scene whose own backgrounds need more than there are is a friendly error naming it. What it costs is a copy of the table on the frame a scene with backgrounds of its own takes over. Nobody writes a layer number, and nothing about the picture changes: a game that declares no scenes is one screenful and comes out exactly as it did. And **two sprites showing the same picture store it once**, whatever they are — which is what makes a `pool` of thirty-two affordable, since each of its slots is a sprite of its own and used to keep its own copy of the art. Nobody writes any of this; `rom.profile` says how much of the 32K is used, how much of that sharing saved, and how many pictures turned out to be repeats.
- **A scene owns what it draws.** A `sprite`, `draw_text`, or `draw_number` declared **inside** a scene belongs to that scene — it's on screen only while that scene is the active state. Belonging to a scene *is* the visibility, so switching state switches the whole screen (a game-over screen hides the field and shows its own banner) with **no per-draw visibility flag**. Sprites/HUD declared at the top level (outside any scene) are always shown — a persistent HUD. Worked example: `examples/shmup.rb` (a PLAYING scene and a GAME OVER screen). **A sprite on `screen :bitmap` keeps that promise too, and there it is more than hiding**: a bitmap sprite is painted into the one picture and remembers what it covered, so a scene's sprite is put on the picture while its scene runs and taken off again, with what it covered put back, when another scene takes over. It is repainted in the gap before each frame like a sprite declared above the loop, in the same two passes, so the two kinds can cross each other and neither leaves a trail. **It first appears the frame after its scene's first pass**, one frame later than a tiled sprite does, and that is on purpose: the pass a scene takes over is its turn to paint its own field, and a sprite put down before that would remember the last scene's picture and put a square of it back a frame later. So paint a scene's field on its first pass, or where the game changes scene (`clear_screen :black` and then the state, with the leaving scene's sprite still up, is fine — see the `sprite` entry), and the sprite arrives on top of it. What it costs is one store a pass in each scene, saying which scene ran last; a game with no bitmap sprite inside a scene emits none of it. A sprite declared inside a `func` is repainted the same way, and belongs to no scene.
- **A scene can be a class in its own file.** Like the multi-file parts pattern, a screen can be a plain object: construct it *inside* its `scene` block (so its sprites/HUD are tagged to that scene) and call its per-frame `update` — `scene(:playing) { s = PlayingScreen.new(self); s.update }`.
- **Per-scene display mode.** A scene may declare its own `screen` at the top of its block (a direct-color bitmap title, a double-buffered play scene, a tiled game) and the framework switches modes on the transition — a scene's `sprite`/`draw_text`/`draw_number` pick software vs hardware from *its own* mode, and crossing bitmap↔tiled flips which display system presents so the old screen doesn't bleed through. This works on both backends: the reference interpreter models it (including a bitmap title handing off to a tiled game), and the GBA backend reconfigures the whole display live on the crossing (the mode register plus the VRAM/OAM layout — tiled assets are re-uploaded on entry since a bitmap scene reuses the same video memory). Coming back from a bitmap screen, a tiled scene shows its own backgrounds and sprites on a clean backdrop, and everything every tiled screen shows is put back too — the backgrounds declared outside any scene, as declared (cells changed with `set_tile` shut again and the first map showing, the same as a scene's own), still scrolled and turned as the game left them, and pictures the game paints from a list, each as its list holds it then. **A bitmap sprite every scene shows — declared above the loop, or inside a `func` — is on screen in the bitmap scenes only.** It is painted into a picture, and a tiled scene has none: the memory a bitmap screen keeps its pixels in is where a tiled one keeps its tile pictures, so painting the sprite there would write a sprite's worth of pixels over the tiles. So it is left off while a tiled or rotozoom scene is up, a `show` said then waits, and it is drawn again the frame after a bitmap scene's first pass, the same wait a scene's own sprite makes. A character meant to be on every screen of such a game is declared in each scene, where it gets the kind of sprite that screen draws. What it costs is one store a pass in each scene, saying which kind of screen it draws on, and a compare a frame for each such sprite; a game whose scenes are all bitmap emits none of it. A single-display-system ROM (all bitmap, or all tiled) is unaffected. `examples/` — see the per-scene-mode and scene-display-mode tests.
- `dump_func :name` — disassemble a func from the built ROM (debug).
