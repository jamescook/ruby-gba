# DSL reference: Control flow

The whole story of these verbs. The one-line index is `.claude/rules/dsl-reference.md`.

- `game_loop do … end` — the per-frame loop. It runs its body once per frame: the framework waits for the screen and repaints your sprites and HUD at the top of every pass, so you never write a frame sync. **The screen stays switched off until the first of those frames is set up**, so whatever the game says before its loop — a flash or a fade it opens on, sprites placed, a picture painted — is all in force on the first frame anybody sees, however long setting up takes. A console with its picture switched off shows plain white, so a game that takes a while to set up opens on a frame or two of white, where it used to open on its picture without any of that. Build with `frame_sync: :manual` (on `VBlank.game` / `VBlank.build`) to place `wait_vblank` yourself.
- `repeat(n) { |i| … }` — runtime-counted loop (n may be a `Value`/list length). **A loop given `stop_when:` leaves as soon as that holds**, which makes `n` a ceiling rather than a number of passes. (`estimate:` is taken and set aside with a warning; see the hint note in `.claude/dsl/variables.md`.) Counting, testing and jumping back costs something before the body does anything, so a long loop over a cheap body is mostly loop — and **what it costs depends on where the count is kept**, which the build decides and you do not write. Kept in the console's own registers it is less than a plain step a pass; kept in memory it is about one and a half. And **a loop whose body never uses `i` is cheaper still**, because nothing needs 0, 1, 2 and it can count down to nought instead, which spends no compare. The build uses registers whenever the body leaves them free, and a body that **calls a routine, holds another loop, runs a scene, or drops to raw instructions** needs them for that instead. One such statement is worth saving the registers around, so they are kept; two or more cost more to save around than memory does, so the count goes there — so moving a call out of a hot loop is worth doing, and `rom.profile` shows the routine getting cheaper when you do.
- `every(n) { … }` / `every(0.5, :seconds) { … }` — run on a beat. `after(n) { … }` — once, n frames in.
- `once_a_frame { … }` — run a body **once a frame**, wherever the game's own code goes that frame, and **once for each frame that really passed**. It differs from the same code written in `game_loop` in two ways. It always runs — a branch or a scene switch can step over a loop body, and this runs anyway, in the gap between frames — which makes it the home for an effect you set off once and something has to carry along afterwards (`shake_screen` is built on it, and it's the seam an effect pack uses). **And it keeps real time.** A pass of the game loop is one frame on a game that fits and two on a game that doesn't, so a body run once per *pass* silently slows down when the game does: a half-second fade would take a second and a half. This one is run again for each frame that really passed, so it takes as long as it says whatever the game is doing (a very slow pass is capped, so a game is never asked to catch up half a second inside one already-late frame). That makes it where anything that must keep time goes. **Movement written straight in a `game_loop` moves a step per pass**, so a game too heavy for a frame runs in slow motion — smoothly and uniformly, which is safe and is the default; move it in here and the world keeps real time instead (`once_a_frame { hero.walk }` with the drawing left in the loop). **What goes in here is what MOVES, not what a press does**: a button read on its edge (`pressed`) has to be read once per press, so leave the trigger in the loop — read here, one pull of it would fire a bullet for every frame a late pass answered for. Optional name (`once_a_frame(:name) { … }`) if something has to find the routine later.
- `frames_since_power_on` → a `Value`: **how many frames the screen has shown since the power came on**, read-only. It keeps real time like `once_a_frame` (a pass that took two frames adds two), and **it counts the frames spent setting up before the first pass**, which nothing counted in passes can. That is what a screen held for an exact number of frames needs: setting up takes longer on some power-ons (save memory never written is laid out from scratch the first time) and in some builds than others, so a hold counted in passes ends on a different frame each time, while `(frames_since_power_on >= 49).then { … }` ends on the same one. On the console the first pass reads the frames setting up took (1 when it fits inside one); the interpreter, native and JavaScript builds have no setting up, so their first pass reads 1. A game with no game loop shows no frames and reads 0. Costs nothing per frame: the count is the screen interrupt's own, and a game that reads it adds a few instructions at power-on to start it at nought. Worked example: `test/vblank/builder/test_frames_since_power_on.rb`.
- `each_pass(:name) { |job| … }` → a `PassJob`: **a step taken once a pass of the game loop, from when the game starts it until it stops** — the other half of `once_a_frame`, for an effect that steps with the game's own passes rather than with real time, the way a game being copied counts (a pass that takes three frames takes one step). It does nothing until `job.start`, which **takes the first step there and then**, on the pass that calls it, and one more straight after each gap between frames after that; `job.stop` ends it (a step that stops its own job finishes the step it is on), `job.running?` is a test to branch on, and `start` on a job already running does nothing. A step that stops its own job and starts it again keeps it running, and takes its next step on the next pass, not again at once. The block is handed the job, so a walk can stop itself when it arrives: `each_pass(:closing) { |job| light.radius.sub! 4; (light.radius <= 0).then { light.radius.set! 0; job.stop } }`. `each_pass :name` with no block gives back the job made under that name, so the verbs of one effect share it (`each_pass(:closing).start`). Friendly errors: no block and no name, a name given two blocks, and a name asked for before its job is made. Worked example: `test/vblank/builder/test_game_defined_iris.rb`.
- `timer :name, per_second: N` → a `Timer`: a free-running hardware counter that ticks N times a second, independent of the frame loop. `t.ticks` → a `Value` (how many ticks so far, wraps at 65536); `t.on_tick { … }` runs a body on every tick, precisely, off the timer's interrupt (a low-level building block higher-level verbs sit on — a game rarely writes it directly), and like `once_a_frame` it is the timer's from power-on wherever it is written — one inside a routine nothing calls still runs, and a second for the same timer replaces the first; `t.stop` freezes it. For frame-paced gameplay timing prefer `every`/`after`; reach for `timer` for precise/free-running timing (and it's the clock sampled audio will ride on). **A fast `on_tick` is not free:** the rate decides the cost, and it's written on the `timer` rather than near the handler — at `per_second: 4000` the body runs 67 times a frame, which is ~5 of a frame's 228 scanlines with a one-line body, and there is a cost per tick before the body does anything. **And a rate can be more than the console will deliver:** a tick that arrives while the last one is still being answered is lost — there is no queue — so a handler too long to finish between two ticks answers every second tick, or every third, and the game silently runs at a fraction of the rate you asked for. **`rom.profile` counts the ticks that really arrive** and says the rate you are getting against the rate you asked for, so this stops being silent. What it will NOT do is tell you whose fault it is, and that is measured rather than modest: **drawing costs ticks too**, because a transfer stalls the console and holds interrupts off while it runs — with a handler that does one addition, one full-screen `clear_screen` a frame costs about a fifth of a 4kHz timer's ticks and four of them cost three quarters. A handler too slow to keep up answers every second tick, which is half. The two ranges overlap completely, so no rule could tell them apart, and a warning that blamed your handler would send you to rewrite the wrong code. You get the number and both causes.
- Low-level (asm-tier): `if_eq` / `if_ne` / `if_gt` / `if_lt` / `if_ge` / `if_le` (`:var, operand`) with aliases `if_gte` / `if_lte`. Prefer the `(a > b).then { }` expression form.
