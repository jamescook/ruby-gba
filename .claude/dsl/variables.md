# DSL reference: Variables & math

The whole story of these verbs. The one-line index is `.claude/rules/dsl-reference.md`.

- `var :name, init` → a `Value` handle; the initial value is applied **once at boot**, so declaring a variable inside a scene or loop still initializes it a single time. **One name is one variable however many places declare it**, so a helper that declares its state and is called twice is fine — but two declarations that start it differently (a fraction in one place and a whole number in another, or two different numbers, or a `save_var` and a `var`) are a friendly error naming both lines, because that is two parts of a game that each wanted their own scratch variable and would silently write the same one. `set! :name, value` re-assigns at that point (every time that code runs).
- `var :mode, :title` — **a variable that holds one of a set of NAMES** rather than a count, which is what a game state is: `:title`, `:playing`, `:over`; `:idle`, `:chase`, `:attack`. Write the names and the framework gives each one a number, in the order it first appears — the same bargain it already makes for colours, which you name while the console is handed a number out of a table it never shows you. `mode.set! :playing` moves it on, `(mode == :playing)` tests it, and **`call mode` runs the routine of that name** (see `call` under Scenes & funcs) — a `func`, or a `scene` of that name, and a variable whose names are scenes picks between screens exactly as `case_var` does: each scene owns its text, sprites and scenery and shows them only while it runs (a name that is both a scene and a func is a friendly error) — so a game's states, the tests on them and the routines behind them are one set of names, where otherwise they are a number per state that three separate places have to keep in step by hand. **A pool field says it the same way** (`pool :guard, state: :idle`) and then every instance keeps its own, which is thirty guards each doing their own thing from one line inside `each`. A name joins the set the first place it is used, wherever that is, so a state reached only from inside another routine counts too. It costs exactly what the number costs, since the number is all the variable holds and nothing about the names survives the build. Three friendly errors: `call` on a variable that holds plain numbers (it says to write the list form instead), a name that has no routine of that name to run, and a variable whose names are scenes and also anything else — a func, or a name no scene has — since a variable that picks a screen holds only screens (the error names which are which, wherever in the game each name was first set).
- `save_var :name, default` → a `Value` handle for a variable that **survives power-off** (a high score, an unlock, a setting). Used exactly like `var`, but its value is kept in the cartridge's save memory: it comes back at power-on with the value it had last time (or `default` the first time the game is ever run), and every change is saved for you automatically — no separate save step. `default` is a whole number. The framework picks and drives the save backend and emits the save-type signature emulators/flashcarts need; no SRAM addresses at the surface. A game can have 1023 of them, which is what the first 4K of save memory holds; one more is a friendly error saying to keep the rest in a `save_data` record. **On 64K or 128K a change is saved a pass later, not on the spot**: that save memory is flash, which takes a byte only once between two wipes of a 4K block, so writing each change in place would wipe a block every time a number moved. There the `save_var`s are kept together as a hidden record with one copy, saved in the background like a `save_data` one on the pass after any of them changes — and at most once in 300 passes of the game loop (five seconds, for a game running at full speed), so a number that changes every frame (a play clock) does not wear the chip out: a chip lasts about a hundred thousand wipes of a block, which that takes hundreds of hours of play to reach. Its last change is saved within 300 passes, and turning the power off before then keeps the save before it. An update to the game that adds a `save_var` keeps the ones saved, and the new one starts at its default. The 8K EEPROM (`save_memory: 8`) keeps them the same way, since it wears with each write too. A game with a `save_var` on flash or the EEPROM needs a `game_loop`, since that is what saves it, and one without is a friendly error. Nothing in the game changes, and on 32K a change is still written as it happens.
- `files = save_data :file, copies: 3 do keep hearts, name, flags end` → a record of the game's own state — variables and lists — **kept in save memory when the game says so**, which is the difference from `save_var`: a player who turns the console off without saving finds the game as it was when they last saved. `files[n]` is one copy (`n` may be worked out as the game runs; a written number the record does not have is a friendly error, and a worked-out one that names no copy does nothing and reads as empty). A copy **saves** (`files[n].save`) the kept things into save memory, **loads** (`files[n].load`) them back — and loading a copy that is not good changes nothing, so `settings[0].load` at power-on needs no test around it — and **erases** (`files[n].erase`). `files.copy 0, to: 2` copies one copy over another (only a good one; the one written over keeps its last save until the whole copy is in), and `files.reset` puts every kept thing back as it was declared — a new game, touching nothing in save memory. `files[n].state` is one of the names `:empty` (never saved), `:erased`, `:good` or `:damaged` (a save that was cut off after its first bytes went in and before it finished, with no earlier one to fall back on — cut before anything went in, the copy reads as it did before the save), with `good?`, `empty?`, `erased?` and `damaged?` as tests; and `files[n].peek(hearts)` reads a kept variable as that copy holds it, without loading it, which is how a file-select screen shows each file's hearts (0 for a copy that is not good); a kept list reads the same way, `files[n].peek(name)[i]` and `files[n].peek(name).length`, which is how it shows each file's name. **The record can come before what it keeps**: `files = save_data :file, copies: 3` with no block is a record the game can save, load, erase, copy and peek at straight away, and `files.keep hearts` adds to it later, from wherever the thing is owned — as many times, from as many places, as the game likes. That is what a file-select screen wants, since it comes first in a game and what it saves belongs to the gameplay declared after it; without it every kept variable had to be hoisted above the screen. A peek can name a thing before it is kept (`files[n].peek(:hearts)`), and is checked once the whole program is declared. The block form is the same `keep`, said at once. **A pool can be kept too**, which is what a save made in the middle of a level needs — every guard where it stood: `files.keep guards` keeps every field of every slot and everything that makes the pool whole again, which slots are live, which are free, how many there are, and each one's facing, place in its animation and colours where the pool has them — so a load puts the same guards back in the same slots and the next one spawned lands where it would have. `files.keep guards.field(:hp)` keeps one field on its own, and a load puts back that field in every slot and leaves the rest of the pool as the game has it. A pool is the dearest thing to keep, since every slot is kept whether it is live or not: thirty guards of a dozen word fields is over 1.4K a copy before the bookkeeping, and the fit check counts all of it. A `reset` (a new game) empties a kept pool, every slot free and every field nought. The record is laid out when the whole program is declared — where each thing sits, how big a copy is, and whether the records fit — so the order things are kept in is the record's shape, and moving a `keep` so that it comes before another changes the shape, which (as below) reads earlier saves as empty. Friendly errors: a record that ends the build keeping nothing, and a peek read the wrong way for what is kept (a list as one number, or a variable item by item). **A save is written in the background, and the game goes on while it is**: a save, an erase or a copy is written a piece each pass of the game loop — a full-size file (1204 bytes) in about five passes — so nothing the player is watching stops for it, even with the save code in the cartridge. What it saves is **the moment it was asked for**: the kept things are copied aside there and then, so a game that changes the hearts on the next pass does not save half of the change. `files.saving?` holds from the moment one is asked for until it is written, which is the game's cue to show saving however it likes — an icon, a line, a locked menu, or nothing — and `files.finished?` holds for the one pass after one is written, the place for "Saved!". `files.failed?` holds when the last one did not read back — the chip did not keep it. **Reading a copy finishes its save first**: `state`, `peek` and `load` of a record with a save still in hand write the rest of it on the spot, so a file screen shown straight after saving shows the save (that pass costs what the rest of the save costs). **Two saves at once**: `when_busy:` says what a save, erase or copy asked for while one of the record's is still in hand does — `:wait` (the default, and the one that loses nothing) goes in line and is written after it, `:replace` takes the place of a job on the same copy that is not written yet, and `:refuse` does nothing and makes `failed?` hold, for a game that locks its menu while it saves. A third job asked for while one is written and one waits finishes the first on the spot. Turning the power off before a save is written keeps the save before it, as a cut half way always did. **What it costs**: each record keeps two snapshots' worth of buffer in the roomy memory, filled at power-on, and a pass that asks for a save pays for copying the kept things aside; `rom.profile` names each save routine after its record ("saving save_data :file"). **Where its save routines run from**: `save_data :file, copies: 3, fast: true` keeps them in the console's quick memory, `fast: false` keeps them in the cartridge, and left out the build decides — the word `func` takes, meaning what it means there. It is worth saying `true` in one case, and it is a case no build can see for itself: a build that measures its game runs it with nobody at the controls, so the game never saves, and the routines that save are measured at nothing and left in the cartridge. The passes of a save then run at the cartridge's speed, and in a game that uses most of each frame one of them does not fit and the game is a frame behind from there — nothing a player would name, and exactly what a game counting its frames against another cannot have. Said, what is kept is what every pass of a save runs: the routine that writes a piece of it, the one that looks the copy over when the last piece is in, and the small routines that keep saves in line — for a game that saves, erases or copies, since a game that only loads writes nothing. The jobs themselves (save, load, erase, copy, reset) run once, on the pass that asks for them, and are a small part of it, so they are left to the build like any routine; kept as well, they came to more than twice the room. It is one record's word: another record that says nothing is left to the build. **What it takes is the reason it is a word and not what every game gets**: kilobytes of the 32K — the two came to about 4.6K for a record keeping one number, and they do not grow with what a record keeps. **They go in ahead of everything the build picks for itself**, the game loop and the routine that plays the music among them, as everything the author insists on does (see `func`): where they do not fit for the whole game, they go with the one scene that asks for the record's saves, in that scene's own share, and the build fills what is left. So whether the word fits never depends on the build's own choices, and a build that measured the game and one that did not agree on it. Where the routines take the room the game loop wanted, the game loop runs from the cartridge and the build says so in a warning; where they do not fit even in their scene's share, it is a friendly error naming the record. **On flash or the EEPROM it reaches less far**: the chip is written through a routine of its own for each byte, which always stays in the cartridge, so the word speeds up the save's own work and not the chip's. `fast: false` is for the other way round: a build that does not measure keeps the routines by what the frame can reach, and a game that wants that room for code it runs every frame says so; with every record kept out, the routines that keep saves in line are kept out too. A record whose routines do not fit is a friendly error naming the record, and a `fast:` that is not true or false is one too. **A save cut off half way loses nothing**: every copy is kept twice and a save goes into the older half, which only counts once the whole of it is written, so the power going off mid-save leaves the last good save in place and the other copies untouched. A record whose shape changes in a later build reads old saves as empty rather than as nonsense. **An update to the game keeps every save it did not change**: where each record lives is written in a small table in save memory and read back at power-on, rather than worked out from the records declared before it — so adding a setting to one record, declaring the records in another order, or dropping one leaves the others' saves where they were, and a record given more copies keeps the ones it had (moved into a bigger place when the room after it is taken). A record the game no longer declares keeps its room until a new one needs it. That table is written at power-on when the records changed, which on a first run is the first thing the cartridge writes, and it is kept the same safe way a save is; the one step that is not is the last resort for a nearly full save memory whose free room is in pieces, where records are slid together (and, for a record given more copies, the ones above it lifted to let it grow) and a cut during that can damage one; it is also the one slow step, a few frames at power-on, once. Room a record is given is wiped first, so a copy an earlier build dropped, or another record's old save, never reads as one of its saves. On 32K it all lives after the first 4K of save memory, which stays `save_var`'s, so the two never touch; flash keeps the `save_var`s in a record of their own (see `save_var`), which counts as one of the 16 records a game can have. **How much save memory there is, the build works out**: a cartridge has 32K, or 64K or 128K of flash, and the build picks the smallest that holds every record. `RubyGBA.game "NAME", save_memory: 128` (also on `RubyGBA.build`) names one instead, for a game that wants room to grow — and **`save_memory: 8` is the one size the build never picks**: an 8K EEPROM, the chip retail games with a small save used because it needed no battery and cost least. It is the slowest to write by far, since the console sends it eight bytes at a time a bit at a time and the chip then settles for most of half a frame: so on it a save writes eight bytes a pass, measured at 97 of a frame's 228 lines a pass, and a 1K save takes a little over two seconds while the game goes on. Its save_vars are kept in a record as on flash, for the same reason (it wears with each write). The half-kilobyte EEPROM some cartridges had is not offered: the table of places alone needs more than it holds. The chip is written a block of eight bytes at a time, so what a pass writes is held in a copy of one block and written back as the pass ends. Records that do not fit the size named are a friendly error saying the size they need, and a size no cartridge has is one too. `rom.profile` says which size the cartridge got and whether the game asked for it, what takes the room (each record's copies, the table of places, the block kept for `save_var` on 32K) and how much is free, and on flash or the EEPROM about how many passes a save of each record takes. Flash is wiped 4K at a time, so on it every half of a copy takes whole 4K blocks: a 5K save is 8K a half and 16K a copy, and 128K holds seven of them. **A save on flash takes longer and costs no more frames**: the chip takes a byte at a time and slowly, so a pass writes 32 bytes of a save rather than 256 — a full-size file in about forty passes — and the chip wipes a half before it is written, a block at a time, while the game goes on. The first power-on of a fresh flash cartridge takes a few frames, which is the table of places being written. Friendly errors: a record declared twice, or given `copies:` below 1; a record name that is not letters and digits with one underscore between words (`:file`, `:high_scores`), since a record's save routines are named after it and an odd name could run into another's; `keep` given anything but a `var`, a `list`, a `pool`, a pool's `field`, or `random_numbers`; a field a pool does not have; a thing kept in two records; a `save_var` kept in a record (it saves itself); `peek` of something the record does not keep; and records too big for save memory, naming each record's bytes. On the interpreter the save memory is a `RubyGBA::IR::SaveImage` handed to `Reference.new(save:)`, laid out byte for byte as the console lays out its chip, so the same one given to a second run is the same cartridge powered on again, and the Verifier takes it too (`save:`) to start the console from those bytes. **A test can write a save straight in rather than play until the game makes one**: `Reference.save_into(SaveImage.new, program, :file, 0, hearts: 12, name: [76, 73, 78, 75])` writes copy 0 of `:file` holding those values and hands the image back — a whole number for a variable, a Float for one holding a fraction, an Array for a list, `random_numbers:` for the random numbers — and what it does not name keeps the value it was declared with. The copy is written by the game's own save routine on the interpreter, so it is the copy the game would write, on 32K or flash alike, and the game treats it as its own: good, peeked, loaded, saved over (that save counting as newer), erased and copied. Other copies and records already in the image are left alone, so one built cartridge can start from as many saves as a test wants. A record that is not declared, a copy it does not have, a name it does not keep (the error lists what it keeps), a value of the wrong kind (a list for a variable, a Float for a whole number or the other way round), a list past its capacity and an item too big for its slot are friendly errors; so is a pool, or one field of one, which cannot be written yet. **A `save_var` is written the same way**: `Reference.save_vars_into(SaveImage.new, program, best: 9999)` hands back an image the game starts with that high score, written by the game's own code on 32K or flash alike, and the save_vars it does not name keep what power-on gave them. A name that is not one of the program's save_vars (the error lists them) and a value that is not a whole number are friendly errors. Worked example: `examples/hero.rb`, whose file screen shows three walks, greys CONTINUE on an empty file, and saves with START.
- `saves_keep_everything except: [:mode]` — **the build refuses a game whose records leave some of its state out**, for a game that saves in the middle of play. Such a save is right only while it keeps everything the play depends on, and the way it goes wrong is quiet: a variable added to the game later and never added to a record, and the load puts back everything else while that one thing stays as it was. Say this once, anywhere in the game, and at the end of the build every variable, list and pool the game declared — and the random numbers, if it rolls any — must be kept by some `save_data` record or named in `except:`, which is for what a load must leave alone (which screen the game is on, a setting the player chose). The friendly error names every thing no record keeps. A name that starts with `_` is scratch and never needed, a `save_var` saves itself, and nothing the framework keeps for itself counts. **A pool counts only when it is kept whole**: one field kept on its own leaves which slots are live as they were, so a game that means that names the pool in `except:`. The random numbers are `:random_numbers` there. A keep or a declaration written inside a `func` counts, since the check runs once every routine is built. It costs nothing in the cartridge. Friendly errors: a name in `except:` that the game does not declare, a name in `except:` that a record keeps after all, saying it with no record in the game, and saying it twice.
- `add! :name, operand` (alias `add_var!`) / `sub! :name, operand` (alias `sub_var!`).
- `copy! :dest, :src`, `negate! :name` (alias `flip!`), `abs! :name`, `negate_abs! :name`.
- `clamp! :name, min, max`, `approach! :name, target, step` (move toward, capped). Both `clamp!`'s bounds and `approach!`'s step can be fixed numbers **or** things the game works out as it runs (`x.clamp! 0, limit`, `level.approach! 100, speed`) — a limit that depends on the level, an easing whose speed changes. A floor worked out to above its ceiling gives the ceiling, since the value is held at the floor first and the ceiling second. A computed `approach!` step is read as a distance, so a negative one still moves toward the target and `0` holds still. Fixed values cost exactly what they always did; only a computed one costs more.
- **A word without `!` never changes a variable.** `abs`, `clamp`, `approach`, `flip` and `negate_abs` on a variable or a pool field are NEW numbers — the number the `!` word would store, with the variable left as it was — which is what Ruby's own `Integer#abs` and `Comparable#clamp` promise, and what `(apart.abs <= reach)` reads as. So `d.abs <= 5` asks how far d is from nought and leaves d's sign alone, `d.clamp(0, 9)` is a number to compare or store, and `d.approach(target, step)` is where d would be one step on. To change the variable, end the word in `!`: `d.abs!`, `d.clamp! 0, 9`. The old spelling on a line of its own now works out a number nobody keeps, which is a friendly error naming the `!` word, and a flat verb without its `!` (`abs :d`) is a friendly error too. A new number costs about what its `!` word does, with nothing stored: `abs` a compare and one instruction, `clamp` two compare-and-replace steps.
- Introspection: `variables`, `var_address :name`.
- **Expression DSL** (on a `Value`): `+ - * / %` and unary `-x` (the value the other way round, leaving `x` alone — `.flip` is the same number, and `.flip!` the same idea as a *mutation*), `.abs`, `.clamp(lo, hi)`, `.approach(target, step)` and `.negate_abs` (new numbers, see above), comparisons `> < >= <= == !=` → a `Condition`; change the variable with `.set!/.add!/.sub!/.clamp!/.flip!/.approach!/.abs!/.negate_abs!`. Compose conditions with `&` (both) / `|` (either); branch with `.then { } .else { }`. **An expression you build and never keep is a friendly error**, because it did nothing at all: `flags | 4` hands back a NEW number and leaves `flags` as it was, so changing the variable is `flags.set! flags | 4`. Take care with Ruby's own shorthand too — `flags |= 4` reads as `flags = flags | 4`, which moves the *Ruby* name onto the new number and leaves the game's variable untouched, with the name still looking right afterwards. `hp + 1` where you meant `hp.add! 1` is the same slip. Naming a handle on its own (`hero.x`) is not an error — it is pointless but harmless, since there was no work to throw away. A **comparison costs about twice what `+` or `-` does**, and there is nothing to write differently — adding two numbers is the answer, where comparing them leaves the console to turn its flags into a yes or a no. Worth knowing only where a condition sits in the hottest loop of a frame; anywhere else it is not the thing to look at.
- **The hint note: `estimate:` does nothing, and says so.** A `list`, a `pool`, a `repeat`, a `.then` and a stretched `draw_rect_at` or `draw_column_at` once took `estimate: { usually: N }` (and `most:`, `in:`) — how big or how often the thing normally was — for a cost estimate that worked a frame's time out from the program. That estimate is gone: the build measures a game by running it, scene by scene and with every list and pool held full. A game that still writes one is not refused. Whatever it says, it is set aside before it reaches the program, and the build gives **one warning naming every line that gives one**, saying to remove it. The game plays the same with or without it (`test/ruby_gba/ir/guardrails/test_ir_guardrail_estimate_does_nothing.rb`).
- **The bits themselves** — `&` `|` `^` `~` `>>` `<<` on a value, against a number you wrote or another value. **What they are for is packed data**, and packed data is what a real console's own files are made of: a background map cell holds a tile number, two flip flags and a colour group in one half-word; a collision shape is one bit per pixel; a save file is flags all the way down. `&` keeps the bits both sides have, which is how a field is pulled out and how a flag is tested; `|` keeps the bits either side has, which is how one is put back and how a flag is set; `^` keeps the bits exactly one side has, which turns a flag over; `~` turns every bit round, so `flags & ~DOOR_OPEN` clears one; and `>>` and `<<` slide the bits along. **Dividing is not a substitute, and that is why these exist rather than being sugar**: a mask over two fields that are NOT next to each other — asking about bits 2 and 7 in one go — has no arithmetic form at all, in any number of steps. They are also the cheap way to say what you already meant. `x & 15` and `x % 16` are the same single instruction, so the mask was always what got emitted and the surface simply could not name it; but `x >> 4` is one instruction where `x / 16` is three, because dividing has to correct the sign of a negative number and sliding the bits does not. **`>>` keeps the sign** — a negative number stays negative — which is what both the console and Ruby do. **A number you wrote can stand on the left of `&`, `|` and `^`** (`0x0F & flags`) but not on the left of a shift: Ruby will not have a worked-out number to the right of `<<` or `>>`, so `0x8000 >> col` is a friendly error saying to write `(row >> col) & 1` instead, which reads the one bit and is the same answer. **A count of 32 or more empties the number** — nothing left going up, and going down the sign filling in, so 0 or -1 — and **a negative count does the same rather than turning round and shifting the other way**. That is the one place the framework declines to follow Ruby, which does turn round: a negative shift count in a game is a mistake, and reversing direction quietly hides it. A count you wrote costs one instruction; a count the game works out costs a few more, since it has to be held inside that range first. **A count that empties the number and is written down is a friendly error**, since a person who wanted nothing would have written nothing; the same count worked out as the game runs is left alone, because that one comes out of data and can land anywhere. Two more friendly errors, both for slips this borrows straight from C. A bit operation on a number that **holds a fraction**: the fraction is kept in the low bits, so a mask would change the fraction and not the number you can see — use `.to_i` first. And **`.then` on a number**, which is how a flag test is written in C (`if (flags & MASK)`) and is the first thing most people write here: Ruby gives every object a `then` of its own, so that would run the block while the program was being BUILT and record its body with no test around it — the body running every frame with nothing said. Compare the number first: `((flags & MASK) != 0).then { … }`.
- **`%` wraps a value onto a range** — Ruby's meaning, so `-1 % 64` is 63. That's what you want for an angle that stepped below zero (it comes back near a full turn) or a map coordinate off the left edge (it comes back against the right one). `/` truncates toward zero (`-7 / 4` is `-1`), so `/` and `%` don't decompose on negatives — `%` follows Ruby because you know Ruby.
- **Dividing by zero has no answer, so the framework gives one**, and it is the same on the interpreter and on the console: `/` gives 1, or -1 for a number below zero, and `%` gives the number back as it was. The game does not stop on either, which is the point — a console has nobody to stop for, so a test on the interpreter shows what the cartridge will do. A number that holds a fraction gets the same bare 1 or -1, which it reads as the smallest fraction there is and not as 1.0. So a divisor that can reach zero wants a floor (`x / d.clamp(1, 99)`), the same advice the fraction divide gives below. A zero **written** as the divisor (`x / 0`, `x % 0`, or a fraction too small to keep, which is stored as 0) is a friendly error, since that one the build can read.
- **Dividing costs what its divisor makes it cost**, and there is nothing to write differently — the build works out which case you are in. A number **you wrote in the program** never calls the console's divide routine: a power of two (2, 64, 256) is a shift and costs about three quarters of a plain step, and any other fixed number (10, 60, 100) is turned into a multiply at build time and costs about twice a plain step. A divisor **the game works out** (`x / d`, where `d` is a variable) is the dear one, at about five times a plain step, and it is the only one whose cost depends on the numbers — it works the answer out a bit at a time, so a big answer costs about two and a third times a small one. `%` follows its `/`. (Throughout, **a plain step** is one ordinary statement — `x.add! 1`.) The build works out which of the three you wrote; a power of two is a shift and costs nothing worth naming.
- **Numbers with a fraction** — a variable holds whole numbers, so a game that needs halves and quarters (speeds, angles, anything smooth) has to keep them another way. **Write a Float and it is handled for you**: `var :px, 3.5` declares a variable that holds a fraction, `table :sin, (0...512).map { |a| Math.sin(...) }` a table of them. The scale is declared once, there and nowhere else — every handle for that variable carries it, and arithmetic carries it along.
  - `+ - < >` and friends: a number **written in your program** is converted for you (`speed + 1` means one faster). Mixing a fraction with a whole number **the game works out** is a friendly build error naming your line — say which you meant with `.to_f` or `.to_i`.
  - `*`: times a plain **count** is ordinary multiplication (`speed * 2` is twice as fast). Times another **fraction** is the one that would overflow — two multiplied-up numbers come out multiplied up twice, far too big for a variable (1.5 × 1.5 needs 9,663,676,416 on the way) — so the framework works that product out at full width automatically. You never have to spot which of your multiplies is the dangerous one, which was the whole problem.
  - `/`: by a plain count is ordinary division. By another **fraction** it is the mirror of the multiply above — two numbers multiplied up by the same amount would divide that amount straight back out, so the framework widens the numerator first and the answer keeps its fraction (`3.0 / 2.0` is `1.5`, not `1`). A plain number can stand on the left too: `WALL_HEIGHT / distance` is the perspective divide, and `examples/raycaster.rb` uses exactly that for its wall heights. **It is the dearest arithmetic there is**, because it works the answer out a bit at a time, three instructions a bit, and an answer holding a fraction has the fraction's sixteen bits to work out as well as its whole part. Bits the answer cannot have are skipped, sixteen or eight at a time: an answer below one works out sixteen bits, one whose whole part is under 256 twenty-four, and a bigger one all thirty-two. A hot one is worth precomputing into a `table` instead. An answer too big to hold is held at the end of the range rather than wrapped, so dividing by something very near zero gives the biggest number there is and not a negative one. **That protection does not survive the next step, and this is worth knowing before you need it:** the answer is now AT the end of the range, so adding anything to it wraps — `(WALL_HEIGHT / distance + 0.5).to_i`, the ordinary way to round a perspective divide to the nearest pixel, comes back very NEGATIVE once the divide has saturated. It bit exactly where you would expect: a first-person view, a player standing a hair from a wall, and the wall vanishing because a negative height draws nothing. **Give the divisor a floor** (`WALL_HEIGHT / distance.clamp(NEAREST, FAR)`, which holds the number divided by and leaves `distance` itself alone) rather than the answer a ceiling — a floor on the distance costs one clamp and changes nothing you can see, where a ceiling on the height holds a near wall short across the whole last half-cell, which a player can see plainly.
  - `.to_i` — drop the fraction (rounds down), for a pixel coordinate or a table index. **One instruction**, not the divide it replaces. `.to_f` — give a whole number a fraction so it can meet one.
  - Worked example: `examples/raycaster.rb`, where positions, ray steps and distances all hold fractions and the word "fixed point" never appears.
