# DSL reference: Composition (pools of a component)

The whole story of these verbs. The one-line index is `.claude/rules/dsl-reference.md`.

- `pool :name, field: default, …, capacity: N` → a `Pool`: many of a thing that has named fields and behaves (bullets, enemies, particles), without hand-managing parallel lists that desync. `spawn(field: value, …)` fills a free slot (safe no-op when full); `each { |b| … }` runs the body once per live instance with a row handle whose fields are mutable Values (`b.x.add! b.vy`, `b.y.set! 0`, read/compare `b.x`), which can retire itself (`b.remove`), and whose own slot `b.index` hands back as a Value — save it in a variable to remember which instance won a comparison (the nearest enemy, the one just hit) and act on it once the loop has ended; `count` (a Value) / `full?` (a Condition) introspect it. Behind the scenes it's parallel lists + an active column + a `repeat`, so the fields can never desync and the cost model prices it per-pool.
  - **`each` goes in the order things were spawned**, oldest first, whatever slot each one landed in: a thing removed leaves the order, and a new one always goes last, even in a slot an older one gave back. That is the order a player can see. Things that each roll `rand` in the walk roll one after another, so the same seed gives each thing the same numbers however the slots were shuffled by what came and went before; and things that act on each other or on something shared act first come, first served. It is how a console game keeps the things in a room. **During a walk**: a thing removed before its turn is passed over and every other thing is visited once, and a thing spawned during the walk is first visited by the next walk, so a thing that splits in two does not split again in the same pass. A thing removed during a walk keeps its slot until the walk ends, so a spawn in the same walk takes a different slot, and a pool that had no room still has none — `full?` says so, since it tells whether a spawn will find a free slot rather than counting what is live. The walk goes through the live things only, so it costs what is live rather than the capacity. Each `each` written in the game keeps three variables of its own, so a walk inside another walk of the same pool keeps its place. **`each(newest_first: true)` walks the other way**, newest first, for a game where the last thing added has to act first (which of two things in reach is struck, when the newest should win). It is the exact reverse of the plain walk, and every rule above about a walk holds the same way round, a pool's own routines included. It costs the same as the plain walk, and anything but true or false is a friendly error. It changes only the order that one walk visits things in: which thing is drawn in front stays as below. **Drawing order is the plain walk's order too**: where two things of one pool overlap, the one spawned first is in front, whatever slots they landed in. A thing spawned into a slot an older one gave back is still behind everything older than it, and a thing a full `:recycle_oldest` pool reuses goes behind the rest, as the newest. So a game that needs one of a pair in front spawns that one first — a bed's cover, then its pillow end — and the answer does not change as other things of the pool come and go. **What it costs** is one walk of the live things a frame. Each of the console's sprite rows has a fixed place in front of or behind the others, so before each frame is drawn the framework copies where each live thing is, which picture it shows and which colours it draws with into the order they are drawn in. That is one small routine per pool however many slots it has (`rom.profile` lists it as "putting the sprites of pool :name oldest in front"), a few bytes of memory a slot, and time for each LIVE thing rather than each slot: measured on `examples/dive`, with its six fish and up to twelve bubbles, the frame went from 3473 instructions to 4189, which is under half a hundredth of a frame. A pool keeps a sprite place for every slot, and a game can keep 512 places though the console draws 128 at once: what has to fit in 128 is what shows on one frame (see "the console's 128 places for sprites" in `scenes.md`). **Against a plain sprite, a pool takes the place it was declared in**, by the rule two sprites follow: a sprite declared after the pool is in front of all its instances, and one declared before is behind them. A game that needs one in front puts it in a sprite or a pool of its own, in a `layer`.
  - **Spawn-when-full policy:** `on_full:` decides what `spawn` does with no free slot — `:drop` (default, ignore it) or `:recycle_oldest` (reuse the longest-lived instance so a new one always appears — the usual choice for particles/effects). The longest-lived is the first in the walk order, so finding it costs one read whatever the capacity. The one exception is a spawn into a full pool from inside that pool's own walk: the walk is following the order, and moving its first thing to the end would cut the walk short (or, newest first, carry it past where it ends), so that spawn is dropped. `pool :spark, x:, y:, life:, capacity: 32, on_full: :recycle_oldest`. Worked example: `examples/sparks.rb`, a shower of particles walked every frame on a bitmap screen, each drawn by the body and removing itself off the bottom.
  - **A routine that works on ONE instance:** `guards.func(:chase) { |g| g.x.approach! hero.x, 1 }`, called from inside the walk — `guards.each { |g| call g.state }`. A pool's behaviour starts as a block inside `each` and wants to move out of it as a game grows, for two reasons: a block is emitted again at every place it is written (a `func` is emitted once, see `func` under Scenes & funcs), and a cast with states wants a routine per state rather than one block of tests. **What stops a plain `func` doing it** is that a routine is built once, wherever it is called from, so its own code has no way to say WHICH guard is chasing — `g` belongs to the block, and the routine is somewhere else entirely. This hands it the instance the walk is on, and everything the block form has comes with it: the fields by name, `g.remove`, `g.face`, the collision box. It pairs with `call g.state` (see `var :mode, :title`), which is a game's whole cast behaving in one line — every instance running the routine its own state names. **What it costs** is a write per live instance per pass, and **only a pool that declares such a routine pays it**: the write is taken out again at the end of the build when no routine reads it, so a pool of sixty bullets drawn inline is exactly what it was. Two walks over one pool (a pairwise test, or a routine that walks the pool it was called from) keep their places, because a walk puts the place back as it leaves — a save and a restore per walk, not per instance. **Calling one from outside a walk is a friendly error**, since there would be no instance for it to run on; the rule is to call it inside `each`, or from another routine of that pool, which is how a state hands over to the next one.
  - **Spriteful pool:** add `image: :art` (needs `x:`/`y:` fields and `screen :tiled`) and each live instance auto-draws as a hardware sprite at its x/y — `spawn` shows one, `remove` hides it, and the console composites them. The row handle then also has a collision box (its x/y plus the image's size), so `b.overlaps?(other)`, the screen-edge tests (`b.off_screen?` / `b.below_bottom?` / …) and `b.clamp_to_screen` work per instance. A pool declared inside a `scene` is scene-owned (its sprites show only while that scene is active). **The code that draws a pool's sprites is written once, however many the pool holds**: every one of them is drawn the same way from the same lists, so the build writes the drawing one time and goes round it. That code is what the build tries to keep in the console's 32K of quick memory, so a pool of forty-five asks that memory for what a pool of four does — a few hundred bytes, where a copy for each was most of 20K — and costs a frame a handful of instructions more for each thing. **A slot with nothing in it costs a frame next to nothing**: the places past the last live thing are marked hidden, a store for each of a place's rows, before the live ones are written, so a pool sized for a game's busiest room costs a quiet room what its live things cost, and a few instructions for each empty slot. A pool whose things are kept out of a `fade … under:`, or that keeps one frame of its pictures in memory at a time, still gets a copy for each, and so does every sprite declared by hand; `rom.profile` shows the size either way. On a bitmap screen, drop `image:` and draw the pool yourself in `each`.
  - **Pooled things face and animate, each on its own.** Give the pool `facing:` or `frames:` (with `rate:`) *instead of* `image:` — the same words a `sprite` takes, meaning the same thing: `pool :guard, x:, y:, capacity: 32, rate: 6, facing: { left: [:walk_l1, :walk_l2], right: [:walk_r1, :walk_r2] }`. Inside `each`, `g.face :left` is the same verb a sprite has. **What is per-instance is the point:** the direction and the place in the cycle belong to each slot, so one test written once leaves ten guards leaning ten ways in the same frame, and one spawned just now starts its walk where it starts rather than in step with the rest. That is the pool's own bookkeeping — a hidden slot beside the fields, never a field you declare — and a slot reused by a later spawn starts fresh. Without this a game with a cast had two bad choices: ten sprites declared by hand with their state in parallel lists that desync, which is the exact thing `pool` exists to prevent, or ten identical statues. **What it costs** is one counter for the whole pool deciding *when* a step happens, so a frame that is not a step is one compare and a step walks the slots — a `rate: 6` makes that one walk in six. Naming two picture sources (`image:` and `facing:`), or a direction the pool was not given, is a friendly error. Worked example: `examples/shmup/enemies.rb`, where the enemies flap and turn to face the ship they are diving at.
  - **A field can be called almost anything.** A pool keeps lists of its own beside the fields — which slots are live, where each instance is in its animation, the order they came in — and none of them can meet a field, so a guard can have a field called `frame`, `active`, `count`, `colors` or `next`. Two kinds of name are refused, each a friendly error. One is a name an instance already answers to (`remove`, `index`, `move`, `face`, `draw_with`, `left`, `right`, `top`, `bottom`), since `g.remove` would mean the verb and never the field. The other is one of `pool`'s own words (`capacity`, `image`, `facing`, `frames`, `rate`, `on_full`, `estimate`, `widths`, `fast`), since a field is written the same way those are. A pool's own name cannot end in an underscore or hold two in a row (`:guard_walk` is fine).
  - **Say how big each field is:** `pool :guard, dir: 0, hp: 0, capacity: 145, widths: { dir: :byte, hp: :byte }` — a pool is one list per field, so a field left at its full width costs four bytes a slot to keep a direction or a flag, and a pool is sized for the worst moment of a game rather than a normal one. Naming the narrow ones is the single biggest thing you can do for a big pool: measured on Wolfenstein's guards, ten of thirteen fields narrowed freed about 3.7K of the console's 32K, which the framework then gave to three more routines of hot code. Same three widths a `list` takes, same rule about going below nothing (so a countdown is safe), and the same friendly error for a width the framework does not know. A field declared with a fraction (`x: 0.0`) cannot be narrowed and says so — a fraction is mostly its own fractional part and needs the whole word. **The pool's own bookkeeping is narrowed without being asked**, because unlike a field the framework knows exactly what it holds: the live-or-not column is a byte whatever the pool is, and the free-slot stack is as wide as the largest slot number needs.
  - **`estimate:`** is taken and set aside with a warning; see the hint note in `.claude/dsl/variables.md`. A pool is sized for the worst moment of a game, and the build measures each scene with every pool held full (see the list note in `.claude/dsl/lists.md`).
