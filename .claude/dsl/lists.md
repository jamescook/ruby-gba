# DSL reference: Lists (runtime-sized collection)

The whole story of these verbs. The one-line index is `.claude/rules/dsl-reference.md`.

- `list :name, capacity: N` → a `List`: `push`/`<<`, `pop`, `shift`, `[]`, `[]=`, `first`, `last`, `length`, `each { |v| }`.
  - **Start it full:** `list :lettering, capacity: 3328, width: :byte, full_of: 0` — a list starts empty unless it says this, and then it starts holding `capacity` items, every one the value given, so every item is there to read and write by its place from the first frame: a box the game letters text into, a row of flags, a board. Each time the declaration runs it is made full again, the way an empty list is emptied again. What it is for is speed: the loop it replaces, `repeat(3328) { lettering.push 0 }`, finds the place for each item and stores the length again for each, about twenty instructions an item on the console, where this sets the length once and fills the whole words of the list with the console's copying engine. In setup that loop is work the first pass pays before the game shows anything — the 3,328 bytes above were most of a large game's first frame. A Float (`full_of: 1.5`) also says the list holds fractions, as `holds: 0.0` does. A number that is too big for a narrow slot keeps the low bits, as a push of it would. A fraction for a list `holds:` says is whole, and anything but a number, are friendly errors. **A build names the loops this replaces**: a `repeat` whose count is a list's capacity and whose body is one push of a number gets a warning naming the list and the line. The framework's own collections start full this way too — a pool's slots, a canvas's bytes, a save record's buffer — so a pool one slot bigger costs one push at power-on, not one for every field.
  - **Set it to one value at once:** `box.fill 0x77` sets every item the list holds now, and `box.fill 0xFF, from: f, count: n` a run of them — clearing the area a dialogue box letters into, a row of a board. The value, `from:` and `count:` may each be worked out as the game runs. What it is for is speed: the loop it replaces, `repeat(n) { |i| box[i] = v }`, works out an address and stores one item at a time, where this hands the whole words of the run to the console's copying engine and sets only the bytes at its ends one at a time — measured on a 3,328-byte clear a frame, about a fiftieth of the frame against more than two thirds. A run must stay inside the items the list holds now: the interpreter stops with an error past them, where the console only holds the run to the capacity. A list the game also `shift`s cannot be filled, since its items wrap round its memory. A run written past the list's capacity or from before its first item, a fill on a `table` (stored in the cartridge, so read-only), and a value of the wrong kind for the list (a fraction into whole numbers, or the other way round) are friendly errors.
  - **Copy a run of a table into it at once:** `name.copy_from letters, at: which * 64, count: 64` — the list then holds exactly `count` entries of the `table`, from entry `at` on: the picture of a letter a name is painted with, a frame of an animation, a row of a level. `at` may be worked out as the game runs and is held inside the table, so the run never reads past either end; `count` is a number you write. What it is for is speed: the loop it replaces, `repeat(64) { |i| name[i] = letters[start + i] }`, reads and writes one entry at a time, where this hands the whole run to the console's copying engine — measured on eighteen 64-byte runs a frame, a fiftieth of the frame against about a fifth, and the gap is far wider for a game whose code runs from the cartridge. It is widest when the start and the length are whole words (`which * 64` always is), and a run that is neither words nor halves is still copied, a byte at a time. The table and the list must keep entries the same width, and hold the same kind of number (both whole, or both with a fraction), since a copy moves them as they are; a count over the list's capacity or the table's length is a friendly error too.
  - **Where it lives, which you almost never have to say.** The console has two work memories — a small quick one and a large one that makes it wait about six times as long for a whole number — and everything a program declares used to come out of the small one, so a game with a lot of state **did not build**. Now what a frame touches goes in the quick one and the rest falls into the roomy one, so it does. Which is which is read off the program rather than guessed: a collection named anywhere in the per-frame path (the game loop, the scenes it runs, the routines those call, a timer's handler) is one a frame touches. **Say `fast: false`** about one you know is cold — a world state read when a menu opens — and it moves whatever the room, which hands the quick memory back to the things walked every frame; **`fast: true`** insists on one the framework did not pick. It is the same word `func` already takes for the same question about code, and it changes nothing the program does, only how long a read takes. Why it is worth a thought at all: the quick memory is **also** where the hot code is kept, and a routine left out of it runs from the cartridge at about two and a third times slower. **The build weighs collections and code by one rule**: what the author insisted on goes first (a `func`, `scene` or `save_data` that says `fast: true`, and a collection that does), then the collections a frame touches, then the routines the build picks, then the collections no frame touches. So a routine the author insisted on moves a collection nobody said anything about to the roomy memory rather than stop the build, and a collection no frame touches gives its room to the game loop. A pool moves whole, all its columns together. **A build that measures the game** (`build_rom`, which does by default) counts how many times a frame reads or writes each collection, and weighs that against the routines by what each saves a frame: one read of a whole number kept in the quick memory saves about what four instructions of a routine do, and one of a half or a byte about one and a half. So a list a frame touches once gives its room to a routine a frame runs thousands of instructions of, and the build report says how often a frame touched each collection it moved. A build that does not measure keeps a collection a frame touches ahead of its own routines, since nothing then says how much a frame reads it. `rom.profile` says what went where. A `pool` takes `fast:` too, and moves all its columns together. **A pool over 16K is too big to share the quick memory**, which is 32K and holds the hot code as well, so it is kept in the roomy one without being told — a thousand things of four fields is 25K, and builds. Saying `fast: true` about such a pool is a friendly error, since the game has asked for a place the pool cannot have. A pool bigger than the roomy memory itself, 256K, fits nowhere and is a friendly error at its own line; and a game whose collections do not fit the two memories together is refused by the check that adds up everything it declares, which names the biggest of them. **A collection's own numbers go with it**: a list keeps how many items it holds (and, one that is shifted, where its oldest is), and a pool keeps a dozen or more of its own — how many are live, the first and last of its order, where each walk of it has got to — and wherever the collection went, by `fast: false` or because the build moved it, those go too, so a cold pool leaves nothing of itself in the quick memory. Reaching one there costs what reaching the collection's items already costs. A **variable** the game declares cannot move and never will: it is reached by its distance from the start of the quick memory, which is what makes reading one two instructions instead of four — so a program with more variables than fit is a friendly error saying exactly that, and suggesting a list.
  - **Say it holds fractions:** `list :speeds, capacity: 8, holds: 0.0` — a list keeps whole numbers unless you show it otherwise, exactly as a variable does. Write a Float as the example and every value read out carries the fraction and every value put in is checked against it, so a game with many of something that moves in halves and quarters never picks a scale of its own. The number is only an example — a list still starts empty — and `length` stays a plain count whatever the items are. A pool field says the same thing with its default (`pool :spark, vy: 0.0`). Putting a fraction into a list of whole numbers, or a worked-out whole number into a list of fractions, is a friendly error naming the list.
  - **It holds exactly what you asked for, and what it COSTS depends on whether you `shift` it.** A list you only push onto and index into is a plain row of slots: `capacity: 145` takes 145 of them, and a read skips straight to the one you named. A list you `shift` — dropping from the front, which moves where the oldest item lives — is a ring instead, and a ring's slots are rounded up to the next power of two so the wrap can be a single step: `capacity: 145` then takes 256, and the 111 slots in between are room you pay for and can never fill. So a queue you shift is the one to give a power-of-two capacity. Nothing about this changes what the list holds or what it does; the framework works out which of the two you wrote. A plain row is also the FASTER of the two to read, having no head to look up first.
  - **Say how big one slot is:** `list :hurt, capacity: 64, width: :byte` — a slot holds a whole 32-bit number unless you say otherwise, and hardly anything a game keeps in one needs that much. A direction, a state number, a countdown, how many hit points are left, a plain yes-or-no: every one of those is a **byte**, at a quarter of the memory, and `:half` is a half. That memory is the console's 32K of quick memory, which is the same 32K the framework keeps your hot code in — so on a big collection this is the difference between the game's frame running fast and running from the cartridge. Reading and writing a narrow slot costs exactly what a wide one costs; only the room differs. **A narrow slot always goes below nothing** (`:byte` holds -128..127), and there is deliberately no way to ask for 0..255 instead: the case that decides it is a countdown, where `wait.sub! 7` followed by `(wait <= 0)` really does hold -4 while that test runs, and a slot that could not go below nothing would read -4 back as 252 and the test would never fire. Nothing at build time can see that coming, because the value is worked out as the game runs — which is also why a `table` CAN be asked and a list cannot: a table's values are all known while the cartridge is built. A number that has to reach past 127 asks for `:half`. A number too big for its slot keeps the low bits, exactly as the console does, and both backends drop the same bits (200 in a `:byte` reads back as -56 on each). A byte is the smallest there is — the console can load 8, 16 or 32 bits and nothing narrower, so a flag costs a byte and packing eight of them into one would cost several instructions on every read.
  - **A list sized for the worst moment.** (`estimate:` is taken and set aside with a warning; see the hint note in `.claude/dsl/variables.md`.) A collection sized for the worst moment of a game and walked item by item every frame is fine for the whole of development and falls over in the one session that fills it. A snake's body list is sized for the whole board and holds four cells for most of a game. **The build watches for that now, and measures it rather than working it out**: a build that measures its game (`build_rom`, `ruby game.rb`, the `ruby-gba` command) runs each scene a second time with every `list` and `pool` the game declared held at its capacity, and a scene that keeps up as it stands and falls behind full is a friendly warning naming the collections that do it and the frame rate it measured — each one held full on its own decides which to name, and where no one of them does it alone, the warning says it is all of them at once. Only the length is held: the items past the ones the game put there are whatever is in memory, usually nothing, so a walk whose work depends on an item's value (skipping an item that is nought, using an item as a loop count) is measured at what those values cost, which can be more or less than a real full list. It costs build time and nothing in the cartridge: a run per scene, and a run per collection for a scene that falls behind.
