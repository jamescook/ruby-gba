# DSL reference: The date and time

The whole story of these verbs. The one-line index is `.claude/rules/dsl-reference.md`.

- `clock` → a `Clock`: **the date and time, as the clock a cartridge carries keeps them.** The console has no clock of its own: switched off it forgets, and switched on it only knows how long it has run. Some cartridges carry a clock chip with a watch battery of its own, which keeps counting while the console is off, and that is what a game asks — for berries that grow while nobody plays, or something that happens once a day. Its readings are numbers like any variable's, to draw, compare or keep: `now.hour` (0–23), `now.minute`, `now.second`, `now.year` (as written: 2026), `now.month` (1–12), `now.day` (1–31) and `now.weekday` (0 for Sunday to 6 for Saturday, as the chip counts). **Every reading in one pass of the game loop is of the same moment**, so a minute cannot turn over between reading the minute and the second. **Summer time does not move it**: a clock holds the local time it was set to and counts one second a second. There are no time zones: the chip holds whatever local time it was set to.

  **Ask before you show it.** `now.present?` is false when the cartridge has no clock — most emulators give a cartridge none unless they are told to, and so do some flash cartridges — and `now.set?` is false when the clock is there and was never set: its battery went in or ran out, and it has been counting up from 2000-01-01. **Every reading is 0 when either is false**, so a game that forgets to ask shows zeros, which look wrong, rather than a date that looks right and is not:

  ```ruby
  now = clock
  (now.present? & now.set?).then { draw_number now.hour, 40, 60, :white, digits: 2 }
  ```

  **A game that reads the time and never asks either one is warned when it builds**, naming the first line that reads it. A game that reads it where nobody sees it — to seed its random numbers — can leave the warning be.

  **A game sets the clock with `now.set_to(year:, month:, day:, hour:, minute:, second: 0)`**, each a number or a `Value` — what the player chose on a screen that asks, the way the console's own games with a clock ask once when it was never set. The readings are that moment straight away, in the same pass, and move on from it; `set?` is true from then on. **On a cartridge with no clock it does nothing**, and every reading stays 0, so a game still asks `present?` first. Each part is held to what a clock can keep: the year to 2000–2099, the month to 1–12, the day to the days that month has (30 February is the 28th, or the 29th in a leap year), the hour to 0–23, the minute and second to 0–59. The day of the week is worked out from the date; a game never gives it.

  **The clock itself is never changed.** An emulator keeps the time its own clock says whatever a cartridge tells its chip (mGBA does), and the computer's or the browser's clock is not the game's to change, so what is kept is **how far the time set is from the clock's own**, to the whole second, and every reading adds it on. It is kept in two numbers saved like any `save_var` (`__clock_offset_days`, `__clock_offset_seconds`), the moment they change — so **a game that sets the clock has save memory**, added for it if it had none, and the time set comes back at the next power-on on every build: the cartridge's save chip, the desktop build's save file, the browser storage the web build keeps its save in. On a cartridge, a chip whose battery ran out is put back to its first moment as it is set, which is what clears what it says about the battery, so it reads as set at the next power-on too. (mGBA clears that as soon as the cartridge tells the chip how to count the hours, at every power-on, so no emulator test can show the difference.) Whether a clock reads as set at power-on is otherwise the clock's own answer: a test's `clock_at(time, set: false)` is a battery that ran out again. **A reading made in a variable's starting value comes before the saved offset is read back**, so it is the clock's own time; anywhere after that, the top of the game included, it is the time set. The time can move on past 2099, into a 2100 with no 29 February, on every build alike; only what is set is held to 2099. On the cartridge the offset is added to the chip's reading by plain arithmetic (a calendar of whole-number steps, `IR::ClockCalendar`), the first time the game reads the clock after each wait for the screen, or after the offset changes.

  **Where each build reads it.** The cartridge reads its clock chip — the one the console's own games with a clock carried, a Seiko S-3511A on the cartridge's own pins — after each wait for the screen, which in a game loop is once a pass: a conversation of about a thousand instructions run from the cartridge, and only in a game that reads the clock. At power-on it asks whether the chip is there and was ever set, and tells the chip to count the hours 0 to 23; a chip that is not there, or whose battery ran out, is not asked again. The desktop build reads the computer's clock, in its local time, before the game starts and at every frame boundary; it is there and set whenever the computer's clock can be read, and it keeps counting while the window is paused, as a cartridge's chip counts while the console is off. The web build reads the browser's the same way, in its local time, and keeps counting while the page is paused or in the background. The Game Boy Color's cartridge carries a chip that counts days and keeps no date, so a game there reads no time, and `set?` is false, until it sets one with `set_to`; `.claude/dsl/game-boy-color.md` says so, and `test/vblank/ir/backends/gbc/test_gbc_clock.rb` tests that cartridge alone.

  **An emulator gives a cartridge no clock unless told.** mGBA switches its clock on for the real games it knows to have one, and for nothing else, whatever the cartridge holds; nothing a VBlank cartridge carries can switch it on (mGBA goes by a list of real games' four-character codes, and a real game's code is refused by the build). Its Game Overrides window cannot do it for a homebrew game either: the window is greyed while a game runs, and with no game loaded it has none to save the setting for. Its settings file can: with mGBA closed, add `[override.CODE]` and `hardware=1` on the next line to its `config.ini` (`~/.config/mgba/` on a Mac or Linux), CODE being the four characters `vblank inspect` prints for the cartridge and 1 the number mGBA gives a clock. The clock also works in SkyEmu. Until then the game is told `present?` is false, which is why it asks.

  **In a test**, the interpreter has no clock unless the test gives it one, the way it is given the buttons held: `game_player.clock_at(Time.new(2026, 10, 22, 21, 7, 5))`, and `clock_at(time, set: false)` for a clock that was never set. On the native and JavaScript runs `game_player.clock_at` starts the desktop build's or the web build's windowless program at the same moment, and the checked run holds its readings to the interpreter's on every frame. The time moves on one of the console's frames for every frame the screen shows — a little more than a sixtieth of a second, since the console shows about 59.73 frames a second, so a test of the cartridge in the emulator reads each second turn over on the same frame — however many passes of the game loop those took, and nothing a test checks depends on when the test runs. A run that ends after 60 frames reads a second later than it started. The emulator is given a clock the same way: `Verifier.new(rom, clock: time)` (and `Profiler.run(rom, clock: time)`, and the emulator gem's `probe.clock_at(time)`) gives the cartridge a chip that reads that moment at power-on and moves on a console frame each frame, never the computer's clock; it works the seconds out into a date in the computer's own time zone, so a test of the cartridge stays clear of the night the clocks change.

  **The worked example is `examples/clock.rb`**: the time and the date in big letters, painted once a second through `keep_showing`, and a line of its own when there is no clock or it was never set. Its test, `test/examples/test_clock_example.rb`, starts the clock at a moment and reads the words off the screen. The verb's own tests are `test/vblank/builder/test_clock.rb`, with what a chip that keeps the date reads unset in `test/advance/vblank/builder/test_clock_on_the_advance.rb`, setting it `test/vblank/dsl/test_clock_set_to.rb` (and its Advance twin), and `test/vblank/ir/backends/gba/test_clock_chip.rb` for the cartridge read and set against the interpreter, frame by frame, into a new year and across a power-off; `test/vblank/ir/test_clock_calendar.rb` holds the cartridges' calendar to Ruby's.
