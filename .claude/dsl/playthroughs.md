# DSL reference: Playing a finished game with nobody at the controls

The whole story of these verbs. The one-line index is `.claude/rules/dsl-reference.md`.

Not verbs either — these drive a built cartridge.

- `walk = VBlank.playthrough "walk to the signpost" do … end` → a **playthrough**: a game driven with nobody at the controls, from a **script** that says what to press. A game can otherwise only be played by a person, or poked by a test that writes out which button is down on which frame; a script says it the way a person would, and gives the same minutes of play every time. The block is read where the playthrough is declared, so a slip in it (a button the console does not have, a count of frames that is not a whole number above nought, two moments of one name) is a friendly error there and not part way through playing. Nothing is played until `play`. The block is run with the script as itself, so the steps need nothing written in front of them; a local variable from around the block is still in reach inside it, and a method or instance variable of the place it was written is not. (And a local called `hold` or `press` would hide the step of that name.) Inside the block:
  - `press :a` — **a tap**: the button goes down for one frame and comes up for one. The frame up is part of the tap, which is what makes two taps in a row two presses — a menu reads the press and not the hold, so a button simply left down would be one press however long it stayed there. `press :l, :r` taps several together. **A tap is never missed by a slow game**: the console notes a press on every frame and hands it to the game the next time the game looks. What a slow game can do is fold two taps of one button into one, when both land inside a single trip round its loop.
  - `hold :right, frames: 40` — keep one or more buttons down for that many frames, then let go. **Frames, not trips round the game's loop**: a game that fits its work into a frame sees the button forty times, so a character that walks two pixels a time has walked eighty; a game too slow for that goes round less often and sees it fewer.
  - `wait frames: 30` — let that many frames go by with nothing pressed, for an animation to finish or a screen to settle.
  - `wait_until("the file menu is up") { |game| game.var(:screen) == 1 }` — **let frames go by until something is true of the game.** Counting frames is exact and brittle: the day a screen takes a frame longer to come up, every step after it is a frame out. This asks the game instead. The block is handed the running cartridge — the same reader `play` hands out at a moment — and is asked after every frame, so the script carries on from the **first** frame the answer is yes. It always plays one frame at least, since the game is asked after a frame and never before one. The words say what is being waited for, written to sit in the middle of a sentence, and they are not decoration: they are what a wait that never ends has to say for itself. **The block has to answer true or false.** A number is a friendly error, because Ruby takes every number for yes, nought included — so `game.var(:flags) & 4`, the way the test is written in C, would end the wait on its first frame whatever the flags were. Compare it: `(game.var(:flags) & 4) != 0`.
  - `hold_until("the hero is at the door", :right) { |game| game.var(:px) >= 200 }` — the same, with buttons down while it waits. They come up when the wait ends. The words come first, as in `wait_until`, and the buttons after.
  - **A wait that never ends stops the playthrough** instead of hanging it. Both steps take `within:`, how many frames to go on asking (600, ten seconds of play, unless said). After that many the playthrough raises `VBlank::Playthroughs::GaveUp`, whose message says whose script it was, which wait in its own words, the frame it gave up on, and — on a line of its own, to copy — where it wrote a picture of the screen at that frame. The picture is usually the whole answer, because the game is on a screen the script did not expect. The error also answers `words`, `frame` and `picture`. The picture is left in a folder of its own in the machine's temporary files, and nothing takes it away.
  - **A script with a watching step is declared where it is used, not kept in a constant of a test class.** This suite runs each test on a core of its own, and a constant has to be something every core can read; a block that watches a game is not. A script that only counts frames can be a constant.
  - `moment :at_the_signpost` — **name the frame that has just been played**, so it can be asked for afterwards. A moment has to come after a step, since before the first one no frame has been played. The name is a symbol of letters, digits and underscores: a tape writes it down as a word, so it has to be one.
- **Open a script with a wait.** A cartridge spends its first frame or more setting itself up, and a press made then is deliberately forgotten — on a real console too — so that a button held through power-on is not taken as a press. A tap on the very first frame is not seen. How long setting up takes depends on the game, so a `wait_until` that watches for the first screen is the opening that survives the game changing; `wait frames: 10` is the one that needs no thought.
- `played = walk.play(cartridge) { |moment, game| … }` — play it, from power-on (or from a save, or after a lead-in: see the entries below), on a cartridge the build made (`VBlank.build`, `game.build_rom`), or on a cartridge file by its path (see below). At each named moment the block is handed the moment's name and the running cartridge, which answers everything a test of a running cartridge asks: `game.var(:px)`, `game.sprites(:hero)`, `game.pixel_gba(x, y)`, `game.frame_gba`. **What it is asked of the whole screen is cheap enough to ask on every frame**, because the emulator answers it in one pass over the picture: `game.only_color` (the one colour every pixel is, or nil), `game.brightness` (every pixel's red, green and blue added up, each 0 to 31), `game.frame_colors` (the screen as one string, two bytes a pixel, to keep a still as or to hash), `game.same_picture_as?(other)` and `game.difference_from(other)` (how many pixels differ, the box they lie in and the first of them with both colours), where `other` is another running cartridge or a `game.picture` kept from earlier. Each is answered at the precision a console shows, five bits each of red, green and blue (see `compare` below for why that is not the emulator's own bytes); `game.all_black?` is the one that asks the emulator's eight, as it always did, so a screen the display has darkened to almost nothing is black to `only_color` a frame before it is to `all_black?`. `game.frame_gba` is the same colours as a list of numbers, for looking pixels up in; it costs several frames' worth of time, so a script that only keeps or compares screens wants the others. `played.frames` is how many frames went by, `played.moments` the frame each moment fell on (`{ at_the_signpost: 42 }`), `played.game` the cartridge as the last frame left it, and `played.tape` the presses that were made (see the next entry). **`played.pictures` is the screen at each named moment** (`played.pictures[:at_the_signpost]`): every pixel's colour as the console's own 15-bit number, a row at a time from the top, so the pixel at (x, y) is at `y * 240 + x` — the same list `game.frame_gba` gives, and the one `VBlank::Graphics::PNG.write` takes. **To look at them, ask for files:** `walk.play(cartridge, pictures_in: "pictures")` writes each as a PNG named for its moment (`pictures/at_the_signpost.png`), making the folder if it is not there, and `played.picture_files` says where each went. With no `pictures_in:` no file is written and `picture_files` is empty. Each is written as its moment is reached and not at the end, so a playthrough that gives up further on leaves the pictures of how far it got. **A file already there under a moment's name is written over, and files an earlier playing left are not taken away**, so a folder used twice can hold pictures of both: give a playing an empty folder to tell them apart. Everything that can be wrong with the folder is a friendly error before a frame is played, since the first picture may be minutes of play in: a `pictures_in:` that is a file or is not a path, a folder that cannot be made or written to, and two moments whose names differ only in their capitals (`:Door` and `:door`), which are one file on a disk that does not tell a capital from a small letter. What the pictures cost is memory: each is kept for as long as what the playing handed back is, about a third of a megabyte a moment, whether or not it was written to a file. Worked example: `test/vblank/playthroughs/test_playthrough_pictures.rb`. **A long playing does not pile its sound up in memory**: the running cartridge holds a minute of play at most, and the sound before that is written to a scratch file in the machine's temporary files, which is removed when the playing is no longer held or when the program ends. `game.audio_energy`, `game.sound?` and `game.audio_energy_by_frame` still answer for the whole playing, and they can be asked on every frame of it: how loud each frame was is worked out once and kept, so the only sound an asking reads is the frames played since the last one, and `game.audio_energy_by_frame.last` after a frame is how loud that frame was. The first asking of a long playing reads the file, once. (`game.audio_samples` is every sample of the playing at once, read from the file each time it is asked, so that one is slow to ask often and does hold a long playing's sound in memory.) **Frames are counted from 1**: frame 1 is the first one played. It plays in the emulator, as fast as the machine goes, and with no emulator installed it stops with what to install. Worked example: `test/vblank/playthroughs/test_playthrough.rb`, which takes `examples/hero.rb` from its file screen out into the world.
- `walk.play("game.gba")` — **play a cartridge file**, wherever a cartridge goes: `play`, `tape.play` and both sides of `compare` take the path of one in place of a cartridge the build made. That is how a cartridge this framework did not build is driven — the original of a game being rebuilt, to lay the rebuilt one beside — and one of this framework's own, once it has been written to a file, is the same case. **Nothing in such a cartridge has a name.** Which variable is where and which sprite is which is what the build worked out, and that is kept beside a cartridge and never in it, so a file has none of it. **What can be read is what is really there**: the screen (`game.pixel_gba(x, y)`, `game.white?(x, y)` and the other colour tests, `game.frame_gba`), memory by its address (`game.mem8`, `game.mem16`, `game.mem32`), the sound, the save memory. **What cannot is anything by name**: `game.var(:px)` and `game.sprites(:hero)` are a friendly error saying the cartridge was not built here and what to read instead. So a script watches such a cartridge by a pixel or by an address — `wait_until("the title is up") { |game| game.pixel_gba(120, 40) == LOGO_RED }`, `hold_until("the door", :right) { |game| game.mem8(0x0300_1234) == 3 }` — where the address is one somebody found, since nothing here can say what it holds. Pictures at moments, tapes, saves and comparisons all work as on any cartridge. The framework never learns what the cartridge is: it runs the bytes it is given and keeps none of them, and all a tape says of it is the title in its heading and a checksum, for a person. **Nothing is written beside the file**: the console plays a copy of its own, and a save goes where every playthrough's does (see the next entry), so playing a cartridge twice plays the same cartridge twice. **Its save can be of any size.** Save memory comes in more kinds than this framework builds with; a save of a size its own cartridges have comes back as the same `IR::SaveImage` theirs does, and one of any other size is kept as its bytes (a `VBlank::Diagnostics::SaveBytes`), which is all that is known of it. Both answer `to_sav` and `write_sav`, and both start another playthrough. Nothing checks that a save handed to such a cartridge is one of its own, since nothing says how much save memory it has. Friendly errors before anything is played, on either side of a comparison: a path with no file at it, a file that is not a cartridge (every cartridge carries the same byte at one place in its heading, and a file without it is something else), the bytes of a cartridge given where its path was meant, and something that is neither a cartridge nor a path. Worked example: `test/vblank/playthroughs/test_playthrough_cartridge_file.rb`.
- `walk.play(game.build_rom(console: :gbc))` — **play a Game Boy Color cartridge**, built here or from a `.gbc` file: the same script, the same frames and buttons, the same moments, tapes, saves and pictures (the Color's whole 160×144 screen). The running cartridge handed to each moment answers what holds on both consoles the same way: the screen and every question about it, `game.var`, memory by address, the save memory, the sound, `game.step`, and `game.showing` / `game.hearing` with the Color's own layers and voices (`game.layers` is `[:bg, :bgwin, :sprites]`). Three are answered the Color's way: **`game.sprites(:hero)`** is each sprite the game placed in its last pass, by its name, where the game put it and the picture it shows (the rows the interpreter gives, `name`, `x`, `y`, `picture` — the Color's own table of 8×8 pieces cannot say whose a piece is); **`game.palette`** is the Color's 64 colours, eight lists of four for the backgrounds and then eight for the sprites (`game.palette(:sprites, 2)` is one list of four); and **`game.passes`** is how many times round the game loop it got, counted by the Color's runtime itself, so it needs no `count_passes:` — for a `game_loop` that waits for the screen itself, once at its top, which is every game loop not told `frame_sync: :manual`; a game that also waits in places of its own is a friendly error, since the Color counts waits and not passes. What only an Advance cartridge's reader can say — `registers`, `run_until`, `wave_rate`, `pad_reads` (the Color reads its buttons a row at a time, so the emulator's count of reads is not the times the game asked), and the mixer of recordings a Color game cannot have (`voices`, `sounding`, `sample_clock`, `sound_drops`) — a Color cartridge's reader does not have at all (`game.respond_to?(:registers)` is false), and asking it anyway is a friendly error naming the Color and what to read instead. The Color's speaker settles over its first few frames after power-on, so a silent game has some sound energy there; ask about the game's own sound once it has started. `compare` refuses a Color cartridge, since it lines screens up at the Advance's size. Worked example: `test/vblank/playthroughs/test_playthrough_color.rb`.
- `walk.play(cartridge, save: saved)` and `played.save` — **start a playthrough holding a save, and get the save memory back when it ends.** A game that keeps its progress in the cartridge can only be played from its first screen otherwise, and the third room is then every playthrough's first three rooms over again. `played.save` is the cartridge's save memory as the last frame left it (a `VBlank::IR::SaveImage`, the same one the interpreter takes, or nil for a cartridge with no save memory), and `save:` takes one — so one playthrough plays to the save point and every other one starts there: `at_the_door = to_the_door.play(cartridge).save`, then `fight.play(cartridge, save: at_the_door)`. **Or a save file**: `played.save.write_sav("door.sav")` writes it as the file an emulator keeps a cartridge's save in, and `save:` takes the path of one (`save: "door.sav"`), from this framework or from an emulator a person played in. A save file is as big as its cartridge's save memory, which for a cartridge this framework built is 8K, 32K, 64K or 128K. **The save handed over is left as it was.** The game goes on to save over its own copy, and that is in the `played.save` that comes back, so one save can start as many playthroughs as wanted and each begins in the same place. **A game that saves needs time to**: this framework writes a save in the background, a piece each trip round the game's loop, so a script waits after the press that saves before it ends (see `save_data` for how long a save takes: a handful of trips for a kilobyte on the 32K memory, several times that on flash) — a playthrough that ends sooner hands back the save from before. **No save file is left beside the cartridge**, which is where an emulator left to itself writes one — and the next playing would then start in the last one's save. Each console keeps its save memory in a file of its own, in a folder the framework takes away when the program ends, so two playthroughs at the same moment never see each other's, and the save to keep is the one handed back. Friendly errors, before the console is switched on: a `save:` that is neither, a path with no file at it, the bytes of a save given where its path was meant, a file that is not the size of any save memory (a tape given in its place), and a save from a cartridge with another size of save memory than this one's. **A tape says which it was recorded from** — its third line is `starts from: power-on`, or `starts from: a save 0x1A2B3C4D` with a checksum of the save's bytes, for a person to tell which save the tape goes with (nothing holds the tape to that checksum, as nothing holds it to the cartridge's). One recorded from a save is refused without a `save:`, since the same presses from power-on are a different game; a tape recorded from power-on can be played from a save, and that is the caller's to mean. The save itself is not in the tape: a tape is the presses, and played on another cartridge it wants that cartridge's own save. A comparison starts both cartridges from power-on unless it is given a save for both (`save:` on `compare`, below), so a tape recorded from a save is compared with one. Worked example: `test/vblank/playthroughs/test_playthrough_saves.rb`, which saves a walk in `examples/hero.rb` and starts again from it.
- `walk.play(cartridge, lead_in: past_the_logos)` — **a lead-in: another playthrough, played on the cartridge first and not counted.** A cartridge somebody else made shows its logos and an introduction before its first screen and another does not, so the same script from power-on finds the two in different places before a button is pressed. A lead-in gets a cartridge to where the playthrough should begin by its own road, which is usually a wait that watches for the first screen: `past_the_logos = VBlank.playthrough("past the logos") { wait_until("the title is up") { |game| game.pixel_gba(120, 40) == LOGO_RED } }`. **Nothing in it is counted**: frame 1 is the first frame after it, `played.frames` and `played.moments` count from there, and its presses are not on the tape. A moment it names is nobody's to ask for. It is played after the console is switched on holding its `save:`, so the two go together. **A tape says it was recorded after one** — its third line ends ` after a lead-in` (`starts from: power-on after a lead-in`) — and is refused without a `lead_in:`, since with none the same presses start in a different place. The lead-in itself is not on the tape, for the reason a save is not: it is how THIS cartridge gets to the start, and another cartridge has its own. A wait in a lead-in that never ends gives up as any wait does, saying it was the lead-in's. Something that is not a playthrough is a friendly error. Worked example: `test/vblank/playthroughs/test_playthrough_lead_in.rb`.
- `tape = played.tape` → a **tape**: the presses of that playing, written down — which buttons were down on each frame, and the frame each named moment fell on. **A script says what to do; a tape says what was done.** The difference shows the moment a script watches the game: `hold_until("the door", :right)` is as many frames as *this* game took to reach the door, and the tape holds that number, so it needs nothing to watch. That makes a tape the same presses on the same frames whatever it is played on, which is what lets two cartridges be handed exactly the same game. `tape.play(cartridge) { |moment, game| … }` plays it, and gives back what playing a script gives back, pictures included (and `pictures_in:` writes them the same way). `tape.frames` and `tape.moments` read it without playing it. `tape.up_to(46)` is the same tape ending on that frame: a hold the frame falls inside is cut short, a moment is kept when the frame it names is still on the tape, and a frame past the end is the whole tape — play it and the cartridge is on that frame. `tape.presses_within(1..60)` says what was down on those frames, as a list of stretches each with its `frames` (a range) and its `buttons`. `tape.write("walk.tape")` writes it to a file and `VBlank::Playthroughs::Tape.read("walk.tape")` reads one back, the same tape. **The file is plain text**, a line for each stretch of frames with the same buttons down, so a person can read one, write one by hand, and see a change to one as a change to a few lines:

  ```
  ruby-gba tape 1
  recorded on: HERO 0x5C0FFEE5
  starts from: power-on

  10 -
  1 down
  1 -
  20 right up
  moment walked
  ```

  Three lines of heading, always those three in that order. Below them: a count, then the buttons down for that many frames, `-` for none; a moment on a line of its own, naming the frame the line before it ended on; and, for the reader, blank lines and lines that start with `#`. A hold of twenty frames is one line, and two lines that say the same buttons are read as one. **What it was recorded on is for a person**: the cartridge's title and a checksum of its bytes say which game and which build the tape came from, and nothing holds the tape to them — playing it on another cartridge is the point. (A title holding bytes that cannot be printed, as a cartridge somebody else made can, is written with `?` in their place.) A line that cannot be read is a friendly error naming the line, what is on it, and what a line there has to look like; a file that is not there, or is not a tape, is one too. **A tape can be kept in a constant** and read from any core, which a script with a watching step cannot: it holds nothing but names and numbers. Worked example: `test/vblank/playthroughs/test_playthrough_tape.rb`.
- `result = walk.compare(ours, theirs)` (also `tape.compare(ours, theirs)`) → a **comparison**: two cartridges played side by side on the same presses, and the first frame on which their pictures differ. Somebody rebuilding an existing game wants to know where their cartridge has drifted from the original, and a change to a game that moves something a frame early wants catching without two people looking at two screens; both are the same question. `result.drift?` says whether the two ever differed, `result.drift.frame` the first frame they did, counted from 1, and `result.drift.moment` the last moment the script named before that frame, for a person to place it by — nil when it had named none, and a moment naming the very frame they drifted on is not before it. `result.drift.differed` is what differed on that frame: `[:picture]`, unless readings are compared too (see `readings:` below). `result.drift` is nil when they never did. `result.frames` is how many frames were played. **There are two ways to compare, and this is the one a comparison uses with nothing said** (the other, `same: :script` below, plays the script on each cartridge by itself and compares the two at each named moment, which forgives timing). **Both get the same presses on the same frames.** What is compared is a tape, so a script is first played on the FIRST cartridge alone, to make one — and where that script watches the game (`hold_until("the door", :right)`), it is the first cartridge it watched, and the second is handed exactly the walk the first one took. A second cartridge whose door is a frame further off is still walking when the first has stopped, and the two differ from there. A tape holds its presses already, so it is compared as it stands. **Every pixel of every frame, and it stops at the first drift**: one frame out is nearly always every frame after it out too, so the first is the one worth having, and `result.frames` is then how far it had played when it stopped. (`carrying_on: true`, below, plays to the end and lists every drift.) **The same colours are the same picture**, whatever the console built them from: a rebuilt game that draws with a sprite what the original drew with a background has not drifted, so long as every pixel comes out the colour the original's does. **A colour is compared at the precision a console shows**, five bits each of red, green and blue. The emulator keeps eight, and what it holds below the five is its own working: it fills a colour read out of the colour table in one way, and works a colour the display brightened, darkened or mixed out at all eight. So it can hold the same five-bit colour as two different numbers, and two screens that differ only down there are one picture here: a game that fades where the original swapped colours has not drifted, so long as its colours come out the same at five bits. What it costs is the two cartridges running at once and a compare of the two pictures a frame, which comes to about half the speed of playing one; a script costs one more playing of the first cartridge before that, which a tape does not. Worked example: `test/vblank/playthroughs/test_comparison.rb`, which builds `examples/hero.rb` a second time with a quicker hero and finds the frame the two part on. **How alike is alike enough is said where the comparison is made**, on `compare`, with the settings below. With none of them said, one pixel out on one frame is drift — right for checking that a change to a game moved nothing, and wrong for a game being rebuilt to match another, where one stray pixel several minutes in would hide everything after it. Each is read before a frame is played, so one that makes no sense — or a setting `compare` does not have, which is a name spelled wrong — is a friendly error straight away:
  - `share_may_differ: 0.01` — **the share of the pixels that may be a different colour** before a frame counts as differing, from 0 to 1: a share and never a count, so `1` is every pixel there is. The screen has 38,400 pixels, so 0.01 is 384 of them and `1.0 / 38_400` is one. A frame differs when MORE than that share is out; exactly that many is still alike, however the share was written. **It is a share of the pixels that are looked at**: with half the screen ignored (below), 0.01 is 192 pixels, so ignoring more of the screen never makes the share looser than it says.
  - `frames_in_a_row: 3` — **how many frames running have to differ** before it is drift, 1 unless said, so that one frame of flicker is not. (Where readings are compared too, each thing counts its own: see `readings:` below.) The frame reported is the FIRST of the stretch and the moment the one before that frame, while `result.frames`, for a comparison that stops at its first drift, is the last frame it had to see to be sure. A stretch that ends sooner is forgotten, and so is one the tape runs out on.
  - `ignoring_rectangles: [[0, 128, 240, 32]]` — **rectangles of the screen that are not looked at**, each `[x, y, width, height]` in pixels from the top left: a status bar not drawn yet, a clock, a part known to differ. A difference wholly inside them is no difference; one that reaches outside still counts by the pixels outside. Rectangles can overlap. A rectangle has to lie on the screen, and one written with no list around it (`ignoring_rectangles: [0, 128, 240, 32]`) is a friendly error showing how one is written.
  - `ignoring_frames: [1..120, :title..:in_the_world]` — **stretches of the playthrough that are not looked at**: an opening the rebuilt game does not have yet, a screen that shows the time of day. Both cartridges are still played through a stretch, since the game has to get to the other side; what differs inside it is not counted, and the comparison carries on to the next drift outside it. A difference that begins inside a stretch and is still there when it ends is drift on the first frame after. **A stretch is a Ruby range, of frame numbers or of the names of two moments.** The named form is the one to reach for, because frame numbers all move the day a script gains a step and the moments move with the game. A moment stands for the frame it names, so `:title..:in_the_world` is those two frames and every frame between, the same on a script and on its tape. Both frames, because of how a moment usually comes to be: a script waits until the title is up and names that frame, which is the first frame OF the title, and leaving it in would report the title as drift on the one frame of it that was not left out. Being a range it means what one means: three dots leave its last frame out, `(900..)` runs to the end of the playthrough and `(..:title)` from its start. A range with neither end is every frame, and is refused: a comparison that looks at no frame finds nothing. A frame that is not looked at also breaks a run of differing frames, so with `frames_in_a_row:` the frames either side of a stretch are never frames in a row. Friendly errors, all before a frame is played: a moment the playthrough does not declare (naming the ones it does — a script says its moments where it is declared, so this costs no playing), two moments or two frames the wrong way round (shown the right way round), a range that goes below frame 1, a range that holds no frame, and one range written with no list around it. One is found later, because it is not known sooner: two moments a script declares one straight after the other name the same frame, and three dots between those leave out the only frame there is — refused once the script has been played and the frames are known, and on a tape before anything is played.
  - `readings: { paces: :paces, hero_x: [:px, ->(game) { game.mem16(0x0300_1234) }] }` — **named readings: numbers read off both running cartridges on every frame that is looked at and compared, as well as the picture.** Two games can show the same screen and be a long way apart underneath — a position a pixel out behind a wall, a counter that will run out a second early — and where the pictures do differ, "the hero is at 61 on one and 60 on the other" says what went wrong where two screenshots only say that something did. A reading is a name you choose and a way to read it, and there are three ways to say the way. **A variable's name** (`paces: :paces`) reads that variable from both, which is all it takes on two cartridges this framework built. **A block** (`where: ->(game) { [game.var(:x), game.var(:y)] }`) is handed each running cartridge in turn — the same reader a script's `wait_until` is handed — and what it gives back can be anything two of which can be the same: a number, a pair of them, a colour's name. **A list of two** (`hero_x: [:px, ->(game) { game.mem16(0x0300_1234) }]`) is one way for each cartridge, the first's and then the second's, each a variable's name or a block. That last one is what somebody rebuilding a game needs, because the two cartridges are not the same program: the rebuilt one keeps the hero's position in a variable with a name and the original keeps it at an address somebody found, and it is "the hero's position" all the same. **A reading that differs is drift on the first frame it differs**, like the picture: `ignoring_frames:` leaves it out of the same frames, and `share_may_differ:` and `ignoring_rectangles:` are about the picture only — a reading is the same on both or it is not. (Two values that are both not a number count as the same.) **With `frames_in_a_row:` each thing counts its own frames**: the picture has to differ that many frames running, or one reading has to. A picture that flickers for a frame and a count that is out on the next are two flickers and no drift, where counted together they would be two frames in a row. `result.drift.differed` then lists what differed from that frame for as long as it took, the picture first: `[:picture, :paces]`, or `[:paces]` for two cartridges whose screens agree. **`result.drift.readings` is every reading on both cartridges on that frame**, the ones that agree too, each name with the first cartridge's value and the second's (`{ paces: [1, 2], where: [22, 22] }`); the ones that agree say what the difference is not. With `frames_in_a_row:` they are of the frame the drift began. What it costs is each reading read once from each cartridge on every frame that is looked at, whether or not readings are compared, which for a variable or an address is one read of memory. **A block that stops with an error** raises `VBlank::Playthroughs::Comparison::ReadingFailed`, which says which reading and which cartridge (the block's own error is its `cause`); since every reading is read on the first frame that is looked at, that is where a block that cannot work is found. Friendly errors, before a frame is played: a variable's name on a cartridge that was not built here (a cartridge file has no names — give that side a block that reads memory by its address), a variable the cartridge does not have (naming the ones it does), a way that is none of the three, a name that is not a symbol, and a reading named `:picture` or `:frames_apart`, which are what the picture and the frames between the two are called where what differed is listed. Worked example: `test/vblank/playthroughs/test_comparison_readings.rb`.
  - `comparing: [:readings]` — **what is compared, as a list**: `:picture`, `:readings`, or both. With nothing said it is the picture, and the readings where any were given. **The readings alone** is for a game whose numbers are right long before its pictures are: the hero walks at the right speed weeks before the scenery is drawn, and comparing the readings only says whether the game underneath has drifted while every frame of the picture still differs. **The picture alone, with readings given**, compares the picture and still reads the readings, so a drift in the picture says what each reading was on both cartridges without a reading that is known to differ being called the drift. Friendly errors: an empty list, something that is not a list, a thing a comparison cannot compare, and `:readings` with no `readings:` given.
  - `carrying_on: true` — **play on past the first drift, to the end, and list every stretch of drift.** It answers what the first drift cannot: do the two come back into step, or is everything after it different for one reason? A hero who takes a corner a frame late and is in step again a second later is a different finding from one who is a pixel out for the rest of the game, and the first drift is the same frame in both. `result.drifts` is every drift in the order they happened, and each says the frame it began on (`drift.frame`), the last frame of it (`drift.last_frame`), both as a range (`drift.stretch`, `46..48`), how it ended (`drift.ended`), and what any drift says: its moment, what differed, the readings on the frame it began. `result.drift` is still the first, and `result.frames` is then the whole tape. **How a drift ended is the answer to the question**: `:back_in_step` when the next frame was one on which the two were within the settings again (`drift.back_in_step?`), `:tape_ran_out` when the two were still apart on the last frame of the tape, and `:not_looked_at` when the next frame was one `ignoring_frames:` leaves out, where nothing is known and a difference still there afterwards is another drift. **A drift is under way while something goes on differing that has differed for as long as `frames_in_a_row:` asks**, and its last frame is the one before the frame on which nothing has. With one frame asked for, that is every differing frame until the first frame the two are alike again. With three, a reading that is out for a single frame straight after a picture's drift does not carry the drift a frame further — and a single frame alike in the middle of a long difference does end it, the rest being a drift of its own once it has lasted three frames again. **No frame is in two drifts**: where one thing stops differing while another that had already begun goes on long enough to count, that is one drift from the first frame of the one to the last of the other. **`drift.differed` is everything that differed for long enough while the drift lasted**, in the order each began, so a drift the picture began and a reading carried on says `[:picture, :late]`. **With nothing said it stops at the first drift**, `result.drifts` holds that one, and its `last_frame`, `ended` and `stretch` are nil: a comparison that stops never finds out how long the drift lasted. What it costs is the rest of the tape played, and with `reports_in:` a report written for every drift — so two cartridges that flicker differently on every other frame for a minute write nearly two thousand folders, and want `frames_in_a_row:` said first. Not `true` or `false` is a friendly error. Worked example: `test/vblank/playthroughs/test_comparison_carrying_on.rb`.
  - `same: :script` — **play the same script on each cartridge by itself, in place of the same tape on both**, and compare the two at each named moment. There are two ways to compare and they find different things. **On the same tape**, which is what a comparison does with nothing said, the second cartridge is handed the first one's presses on the first one's frames: a door that opens a frame late is out of step from that frame on, and every frame after it differs. That is the strict comparison and the right one for a change that should move nothing, or for a rebuilt game that is nearly there. **On the same script** each cartridge presses A when its own text box is up and stops walking at its own door, so each arrives at "the door" however long it took, and the two are compared there. That forgives timing and finds a game that LOOKS different, which is the one to use while a rebuilt game is still frames out everywhere and the question is whether its screens are right. **The two are compared at the moments the script names and nowhere else**, since there is no frame they share: the picture and any readings, exactly as they were as each cartridge reached the moment. A drift then names the moment it is at (`drift.moment`), its `frame` is the frame the first cartridge reached it on, and it has no last frame, being one point. **`result.moments` is the frame each cartridge reached each moment on**, the first's and then the second's (`{ title: [12, 12], door: [200, 203] }`), so how long each took is always said, drift or not. (On the same tape it is there too, the same frame twice, for the moments reached before the comparison stopped.) `result.frames` is the frames the first cartridge played. It stops at the first moment that differs unless `carrying_on: true`, which lists every one. `share_may_differ:`, `ignoring_rectangles:`, `readings:` and `comparing:` mean what they mean on a tape; `ignoring_frames:` takes ranges of MOMENTS only and leaves out the moments a range covers. What it costs is each cartridge played once from start to end, whatever is found, and no comparing between moments. Friendly errors, before anything is played: a script that names no moment, or whose every moment `ignoring_frames:` leaves out (there is nowhere to compare), `frames_in_a_row:` or a range of frame numbers (each cartridge counts its own frames, so neither means anything), `same:` given anything but `:tape` or `:script`, and `same: :script` or `frames_apart:` given to a tape, which holds presses and no script. A script that gives up on one of the two — the second never reaches what the first reached — raises the playthrough's `GaveUp`, saying which cartridge, which wait and where its picture is; what the two had been through before that is not kept. Worked example: `test/vblank/playthroughs/test_comparison_same_script.rb`.
  - `frames_apart: 5` — **how many frames apart the two may reach a moment**, on the same script. It is not checked unless said: a rebuilt game is compared for its look first, and for its timing when somebody is ready to. With it, two cartridges further apart than that at a moment drift there, `drift.differed` holding `:frames_apart`, though their screens are the same. It is a friendly error on the same tape, where the two are always on the same frame, and when it is not a whole number, 0 or more.
  - `lead_ins: [nil, past_the_logos]` and `save: "door.sav"` — **start the two cartridges in step.** Two cartridges from power-on are only in step when they are the same game built two ways. An original and a game rebuilt to match it differ before anything is pressed — logos, an introduction, a different number of frames to the first screen — and every frame after that is drift for a reason nobody is asking about. There are two answers and they can be used together. **A lead-in for each** is a playthrough of its own played on that cartridge first, the first cartridge's and then the second's, either of them `nil` for none (see `lead_in:` on `play`, above): each gets its cartridge to the same place by its own road, and the comparison starts there. Its frames are not on the tape and are not compared, and **frame 1 of the comparison is the first frame after both lead-ins**, so every frame number in the result and in a report counts from there. **One save for both** (`save:`, a save a playthrough handed back or the path of a save file, exactly as on `play`) switches both consoles on holding it, which skips whatever a game does before its save is loaded. A report says where the two started, and its tape says it too, whatever the tape that was compared said, so the tape is played back with the lead-in or the save it needs. **Where the two were started differently** — a lead-in for one and none for the other — a report holds a tape for each, `first-to-the-drift.tape` and `second-to-the-drift.tape`: the same presses under two headings, each playing its own cartridge. A tape recorded after a lead-in is compared with `lead_ins:` holding at least one, and one recorded from a save with `save:`; without, it is a friendly error. The save is read once and made to fit each cartridge before anything is played, so a save of the wrong size for either is a friendly error then, saying which cartridge. `lead_ins:` that is not a list of two, each a playthrough or `nil`, is a friendly error, and so is a save that is not one. A lead-in that gives up says which cartridge it gave up on.
  - `reports_in: "drift"` — **a folder to write a report of the drift into**, for a person to look at. A frame number says the two parted and nothing about how, so a comparison given a place writes one folder for the drift it finds, named for the frame (`drift/frame-000046`), and `result.drift.report` is that folder's path. A comparison that carries on writes one folder for each drift, as each ends, and each drift says its own. It holds these files. `first.png` and `second.png` are the two screens on the drifting frame. `difference.png` is the first screen in grey with every pixel that differed in magenta — only the pixels that were looked at, so a part left out with `ignoring_rectangles:` is never marked. `side-by-side.png` is the two screens and the difference in one picture, left to right, at twice the console's size: the one to open first, and the one to send somebody (on the same tape it is the picture `write_side_by_side_picture` writes for that frame: see below). `report.txt` says it in short sentences: the frame, how long the drift lasted and how it ended where the comparison carried on, the moment named before it, what differed and how many pixels did, every named reading on both cartridges whether it differed or not, which two cartridges were played (title and checksum), what was compared and every setting that was in force (a stretch left out is said as its frames, and one written in moments as the moments and the frames they came to), and which buttons were down on the drifting frame and for the second before it. `to-the-drift.tape` is every press up to that frame, and it is the file that matters most: a picture says what the two screens were, where the tape plays EITHER cartridge to that exact frame again, with a script asking it things, which is where finding out why starts. (Two cartridges that were started differently get a tape each: see `lead_ins:` above.) **On the same script the folder is named for the moment** (`drift/moment-door`) and holds two tapes in place of the one, `first-to-the-moment.tape` and `second-to-the-moment.tape`: each cartridge made its own presses, and its own tape is the one that plays it back to that moment. Its text says the frame each reached the moment on and the last second of presses on each. Since the folder is the moment's name, two moments that differ only in their capitals are a friendly error there, as they are for pictures. **With `frames_in_a_row:` it is all of the frame the drift BEGAN**, the same frame `result.drift.frame` names: by the time a stretch is long enough to be called drift both consoles have played past its first frame, so the two screens are kept from the start of every stretch. **Nothing is written when there is nothing to report**: with no drift not even the folder named is made, and with no `reports_in:` a drift's `result.drift.report` is nil. A folder that is not there is made, one that is already there is added to, and a report already in it for the same frame is written over. What it costs is two screens copied out at the start of each stretch of differing frames, and the writing once for each drift; a comparison given no place copies nothing. Friendly errors, before a frame is played: a place that is not a path, a place that is a file, and a place that could never be made — one inside a file, or inside a folder that cannot be written to. A report that still cannot be written when the drift is found (a disk that filled) raises `VBlank::Playthroughs::Comparison::ReportNotWritten`, which says the frame and holds the finding as `drift` — and, for a comparison that carried on, the drifts found before it as `earlier` — so the playing is not lost with it. Worked example: `test/vblank/playthroughs/test_comparison_drift_report.rb`.
  - **What the settings cost**: next to nothing beside the playing. Two frames the emulator holds as the same bytes are known to be the same picture in one comparison of them, whatever is set, and a frame that is not looked at costs nothing but the playing. With a share or a rectangle said, a frame that differs at all is gone through to count what is out, and the emulator does the counting, in a small fraction of the time the frame took to play — so two cartridges that differ a little on every frame are compared about as fast as two that agree. `frames_in_a_row:` costs nothing more.
- `walk.write_side_by_side_picture(ours, theirs, "door.png", at: :at_the_door)` (also `tape.write_side_by_side_picture(ours, theirs, "frame-46.png", at: 46)`) → **one picture of one frame on two cartridges**, for a person to look at: the first cartridge's screen, the second's, and the difference between them, left to right in one PNG. A frame number says two cartridges parted and nothing about how; two screenshots side by side say it, and the third panel says where to look. A drift report holds this picture for the frame it reports (`side-by-side.png`, above), and this is the same picture for any frame somebody wants — one a comparison called alike, the frame before a drift, a moment that looks wrong. **Each panel is the console's screen at twice its size**, 480 by 320, with a thin grey strip between two panels. Nothing is written on it: the left panel is the first cartridge handed over and the middle one the second. **`at:` says which frame**, by its number, counted from 1, or by the name of a moment, which is the frame that moment names. **The third panel is the first screen in grey with every pixel that differs in magenta**, the marking a drift report's `difference.png` has, so the two never disagree about what differed; two screens that are the same give a grey panel with no mark in it. `difference: false` leaves the panel out, and the picture is the two screens. **Both cartridges get the same presses on the same frames**, as in a comparison on the same tape: a tape is played as it stands, and a script is first played on the first cartridge alone to learn its presses. So the picture a report of a drift at a moment holds (`same: :script`, where each cartridge made its own presses) is not one this writes. Some of a comparison's settings mean here what they mean there, and the rest are refused: `ignoring_rectangles:` (a part of the screen left out is never marked, though both screens still show it), and `save:` and `lead_ins:` to start the two in step — a tape recorded from a save or after a lead-in asks for them. They are said again here and not remembered from a comparison, so the picture of a frame a comparison reported matches the report's when it is given the same ones. The folder the file goes in is made when it is not there, a file already there is written over, and the path is handed back. What it costs is both cartridges played to that frame, with nothing compared on the way, and for a script one playing of the first cartridge before that. Friendly errors, before anything is played: a frame past the end of a tape, a moment the playthrough does not name (naming the ones it does), an `at:` that is neither or is left out, a place that is not a path, is a folder, is a file that cannot be written over, or is inside a file or a folder that cannot be written to, a `difference:` that is not true or false, and a setting a picture does not have. One is found later, because it is not known sooner: how long a script plays, so a frame past a script's end is refused once the script has been played on the first cartridge. The command line has no command of its own for it; `ruby-gba compare --reports-in` writes it in every report. Worked example: `test/vblank/playthroughs/test_comparison_side_by_side_picture.rb`.
- `ruby-gba play walker.rb --script walk.rb` — **play a game from the command line**, and print how many frames went by and the frame each named moment fell on. The cartridge is a game file (a `.rb` that declares a game, built first the way `build` builds it, taking `--set`) or a cartridge file (a `.gba`, yours or somebody else's). **What to press is a script file or a tape.** A script file is a plain Ruby file that declares one or more playthroughs with `VBlank.playthrough "NAME" do … end` and nothing else, the way a game file declares a game; `--playthrough NAME` says which when it declares several, and several with none picked is a friendly error listing them. `--tape walk.tape` plays a tape in place of a script. A playthrough declared with a symbol for a name (`VBlank.playthrough :walk`) is picked by the same letters. `--save door.sav` starts from a save file, and `--lead-in NAME` plays another playthrough from the script file first and does not count it. **A lead-in is declared in a script file, so `--script` is needed for one even when a tape says what to press**; a tape recorded after a lead-in, or from a save, asks for what it needs by its flag. **What it writes is what it is asked for**: `--pictures-in DIR` the screen at each moment as a PNG named for the moment, `--write-tape PATH` the presses that were made, `--write-save PATH` the save memory as the last frame left it (a cartridge with none says so and writes nothing). A place a tape or a save cannot be written to is refused before a frame is played, since both are written after the last one. A script that gives up, a file that is not there and a setting that makes no sense are each said in a sentence, before the game file is built wherever that can be known, and the command ends as a failure. `ruby-gba play --help` lists its options.
- `ruby-gba compare ours.gba theirs.gba --script walk.rb --reports-in drift` — **compare two cartridges from the command line**, and say the frame they drift on, the moment before it, what differed and where the report is. **How it ends is for another program to act on, and it is the way `diff` ends: with 0 when the two agree, with 1 when they drift, and with 2 when they could not be compared** — a file that is not there, a setting that makes no sense, a script that gave up — so a build, or a program working through a list of scripts, never takes a file name spelled wrong for a drift. Each cartridge is a game file or a cartridge file, and what to press is `--script` (with `--playthrough`) or `--tape`, as for `play`. `--set` goes to every game file, so one game built two ways is two game files, or a cartridge file built ahead of time with `ruby-gba build --set`. **Every setting `compare` takes from Ruby is the flag of the same name**, with a dash for each underscore, and means what it means there: `--share-may-differ 0.01`, `--frames-in-a-row 3`, `--ignoring-rectangles 0,128,240,32` (each rectangle `X,Y,WIDTH,HEIGHT`, several separated by spaces), `--ignoring-frames 1..120 title..in_the_world 900..` (ranges of frame numbers or of moments, a moment by its name with no colon in front, two dots or three to leave the last frame out, and an end left off for an open one), `--comparing picture readings`, `--carrying-on`, `--same script`, `--frames-apart 5`, `--save door.sav`, `--lead-ins past_logos -` (a playthrough from the script file for each cartridge, `-` for none, and `--script` needed for them even with `--tape`) and `--reports-in drift`. A message that comes from the library names a setting the way Ruby writes it, and a line under it says which flag that is. **A reading on the command line is a variable**: `--readings steps` reads the variable `steps` from both, `--readings where=x` reads `x` from both under the name `where`, and `--readings hero=px,hx` reads `px` from the first cartridge and `hx` from the second. A variable's name means something only on a cartridge built here, so a reading needs game files, and one that needs Ruby to read it — an address in somebody else's cartridge — is given from Ruby. With `--same script` it also prints the frame each cartridge reached each moment on. Worked examples: `test/vblank/playthroughs/test_command_line_play.rb` and `test/vblank/playthroughs/test_command_line_compare.rb`.
