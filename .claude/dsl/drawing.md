# DSL reference: Drawing (Mode 3, direct color)

The whole story of these verbs. The one-line index is `.claude/rules/dsl-reference.md`.

- `pixel x, y, color` — one pixel (fixed coords).
- `fill_rect x, y, w, h, color` / `dma_fill_rect x, y, w, h, color` — a filled rect (fixed, even w).
- `draw_rect_at xpos, ypos, w, h, color` — a rect whose **position and size** the game can all work out as it runs (each of `xpos`/`ypos`/`w`/`h` may be `:var`/`Value`). That's the bar-or-column shape: a health meter that empties sideways (`draw_rect_at 8, 8, health, 6, :red`), a wall column in a first-person view, a tower that grows. A width or height of 0 or less draws nothing, so a bar can empty without a test around it, and **any width works — odd included** (unlike `fill_rect`/`dma_fill_rect`, which still want an even one). A size fixed when you write it costs exactly what it always did. `estimate:` is taken and set aside with a warning; see the hint note in `.claude/dsl/variables.md`.
- `draw_column_at :picture, slice:, x:, top:, height:, width: 1` — **one column of a picture, stretched to a height the game works out**. `width:` is how many pixels ACROSS the strip is (a number you write, 1 by default), and a view whose strips are wider than a pixel wants it rather than a loop of its own: every pixel of a strip shows the same picture column at the same height, so **one walk down the screen fills all of them** — calling it once per pixel works the same answer out that many times over, and measures about three times dearer for a three-pixel strip. This is what a first-person view is made of: for each strip across the screen, work out how far away the wall is, turn that into a height, and draw a column of wall that tall — near walls tall, far walls short. `slice` picks which column of the picture (which part of the wall you are looking at), `x` is where it lands on screen, `top` and `height` are where it starts and how tall it is; all four can be worked out as the game runs. A height of 0 or less draws nothing and anything past the top or bottom is clipped, so a wall you are nose-to-nose with needs no test around it. **Many textures fit in one picture**: `slice` is a runtime value, so lay the wall pictures side by side and `slice` becomes `which_wall * width + column` — no runtime picture choosing needed. Also what a scaled sprite is (a thing that grows as it nears you), and a door sliding open. **A see-through picture costs the rows that hold pixels, not its height.** A scaled sprite is mostly nothing — a lamp in a square of ceiling, a clip of ammunition in a square of floor — and the framework works out, for each column of such a picture, where that column holds pixels, then walks those and skips the rest. So a picture nine tenths empty costs about a tenth, and there is nothing to write for it: leaving the empty rows in is free, and cropping them away saves no time at all. Any picture up to 256 rows tall gets this. One taller walks every row instead, and `rom.profile` names it, says why, and says what to change. Horizontal is not this verb; a row stretched across the screen would be its sibling. `estimate:` is taken and set aside with a warning; see the hint note in `.claude/dsl/variables.md`.
- `clear_screen color` — whole screen, one DMA.
- `inside x, y, w, h do … end` — **everything the block draws stays inside that part of the screen**, and what falls outside is CUT OFF rather than covered up: those pixels are never worked out. That is the difference worth having, because a game with a panel — a strip of world with numbers under it, a map beside it, a letterboxed cut scene — would otherwise draw the world over the whole screen and paint the panel on top, having paid for every pixel underneath it. In a first-person view, where a wall you stand close to is drawn taller than the screen, that is most of a near wall: measured over a floor of Wolfenstein with a 32-row bar, one row in twelve was drawn and then covered. It **clips, it does not move**: a pixel drawn at (10, 10) is at (10, 10) whatever area is in force, so an area goes round drawing that already works and only what was falling outside changes. `clear_screen` inside one clears the area rather than the screen, which is what you meant. Drawing after the block is untouched by it — that is where the panel goes. The edges are settled while you write the program (where a panel goes is part of how a screen is laid out, not something a game works out as it runs — a computed edge is a friendly error), and areas do not nest (a friendly error too). Calling a `func` that draws from inside an area is a friendly error too: the routine is built once, for wherever it's called from, so it can't carry one call site's clip along with it — put the `inside` block inside the routine itself instead. Bitmap screens; on `screen :tiled` the console composes the picture and a `layer` is how depth is said.
- `camera x, y` — move the visible window over the whole picture (`camera 0, 0` = as drawn). Nothing is redrawn — the picture stays put and the window moves — so it costs the same whatever is on screen. Where the window falls off the picture, the backdrop shows along that edge. Bitmap screens only (on `screen :tiled`, scroll a `background` instead).
- `camera_follows hero, across: world` (also `at: [120, 80]`, where the character stands in the world) — the follow-you camera almost every adventure game uses: the character stays where it is on screen and the world slides underneath. Call it once where the sprite is declared; wherever the sprite is standing then is where it stays (pair it with `sprite.center_on_screen` for the middle, or put it low for a platformer). **What it changes is more than a line saved:** without it a game whose world is bigger than the screen has to keep the character's world position in variables of its own, so the character is a pair of numbers rather than a sprite and none of the sprite verbs reach it. With it you write `hero.move :right` like any other sprite and the world moves instead — so facing, walk cycles and poses all work. What does *not* line up is anything that reads the character's position as a place in the WORLD (`blocked_by`, `overlaps?` against something placed in the map), because its position is where it sits on the screen. Needs `screen :tiled` (a bitmap picture *is* the screen — use `camera`) and a `game_loop`. Worked example: `examples/hero.rb`.
- `fade :black` / `fade :white, 50` / `fade :black, 0` — fade the whole screen toward black or white. The second argument is how far, 0 (as drawn) to 100 (nothing but that color); it defaults to 100. Nothing is redrawn — the picture is still there and comes back untouched — so it costs the same however much is on screen, and it works on **either** kind of screen (unlike `camera`). It sets the level where you call it; to fade over time, move a variable and pass it (`fade :black, level`). A full fade left un-lifted is a friendly warning. In a game with a **see-through layer** it leaves that layer alone: the water goes on showing the floor underneath it and the whole picture — water, floor and the mix of the two — darkens together, which is what a fade out should look like. What it costs to get that is the one thing worth knowing, and it is the only case where a fade is not free: such a game's fade moves the *colors themselves* rather than asking the display to darken what it draws, which is a blend per color the game declared — never per pixel on screen — and **only on a frame where the fade actually moves**, so holding one still, or holding it at 0, costs a single check. That is the same price `tint` pays on a tiled screen, for the same reason, and `rom.profile` says so beside the layer it bought. A plain `screen :bitmap` in such a game has no colors to walk, so while one is up the display fades it, free and in its own 17 levels; a fade still in force when the game changes screen carries on in the next screen's way, as a tint does. A game that sees through no layer keeps the free one and draws exactly the same picture, so nothing about the choice reaches the author and the report has nothing to say about it. The one fade that cannot take the colors route is a **placed** one — see `under:` below. **How many levels a fade has**: the display's own fade counts in sixteenths, so it has **17** from the picture to the color, and a fade walked over more frames than that shows some of them twice — the picture changes every other frame. **An amount that holds a fraction** (`fade :black, 37.5`, or a variable declared with one) is still a percentage, and it asks for finer steps: on a screen drawn through a color table (tiled, rotozoom, tear-free) such a fade moves the colors themselves in thirty-seconds, **33** levels, one a frame over a fade twice as long — which is how the console's own games fade. That costs what the see-through route above costs, a blend per declared color on each frame the fade moves. A whole-number amount keeps the 17 on every screen, the plain bitmap screen has no table to walk and keeps them whatever it is given, and so does a placed fade. `tint` takes a fraction the same way.
- `fade :black, 100, under: :ui` — **put the fade at a place in the stack** instead of over everything: it names a layer, and that layer and everything in front of it are left as they are while everything behind it fades. "Fade the game out to the game-over screen and keep the score showing" is one word, and it is why a stack is worth naming (see Layers). Needs `screen :tiled` and the layer has to be one you declared — a bitmap screen paints the whole picture into one place before the display sees it, so there is nothing left there to tell apart (friendly error). Something that named no layer is never on the kept side. **This is the one member of the fade family that is not always free:** where the line falls between the *sprites* — a HUD kept out of a fade that reaches the player — the framework holds the fade off each kept sprite one at a time, which costs a sprite slot and a table write per frame for each. A line that falls between two *backgrounds*, or that keeps every sprite (`under: :actors` — fade the scenery, keep everything that moves), still costs nothing at all. **It is also the one fade that still takes a see-through layer's blend**, and that is not a gap waiting to be filled: putting the fade at a depth is something only the display's blend unit can do — it can hide a brightness change from what sits in front of a line — where moving the colors themselves reaches everything that draws from them and has no notion of who is reading. So a game that places a fade AND sees through a layer gets the layer solid until the fade lifts, and a friendly warning at build time saying so, because neither verb mentions the other. The way round is the plain whole-screen `fade`, which keeps the layer. For the same reason **a placed fade keeps the display's 17 levels** and never gets the 33 a fraction asks for, so a long one changes the picture every other frame; `rom.profile` says so for a game that asks.
- `fade :black, 100, inside: [0, 0, 240, 128]` / `fade :black, 50, outside: [60, 40, 120, 80]` — **hold the fade to a rectangle of the screen**, `[x, y, width, height]` in pixels: `inside:` fades the rectangle and leaves the rest as drawn, `outside:` fades everything but it. The view of a first-person game faded with its status bar left alone, a pause box kept bright over a dimmed game. It is the one way to keep part of a **bitmap** screen out of a fade, since `under:` needs layers and a bitmap screen has none; it works on every screen. **It costs what a whole-screen fade costs**: the display has windows — rectangles it is told about — and switches its darkening on in one part and off in the other as it draws, so a few register writes where the fade is said and nothing per pixel. The rectangle is numbers you write (a rectangle the game works out is a friendly error), held to the screen, and one with no width or height holds nothing. Each `fade` says where it reaches, a plain one included, so the last fade said is the one in force, and a `tint` after a held fade reaches the whole screen. `fade_out` and `flash_screen` take the same words the way they take `under:`, said once for the game's one screen fade, and a plain `fade_in` comes back in the same place (`fade_out inside: [0, 0, 240, 128]`, then `fade_in`). What it gives up, because it is the display's own fade: **every fade in a game that holds one is the display's**, so a fade with a fraction keeps the display's 17 levels rather than walking the colours in 33, the same trade a placed fade makes. Friendly errors: `inside:` and `outside:` together, either beside `under:`, a rectangle that is not four whole numbers, a screen fade to a colour other than black or white held to a rectangle, two different rectangles for the screen fade, and a game that holds a fade and also has a light, a see-through layer, or a fade placed with `under:` (each of those needs the same window or the same blend). Worked example: `test/ruby_gba/builder/test_fade_held_to_area.rb`.
- `tint :red` / `tint :orange, 30` / `tint :red, 0` — tint the whole screen toward **any** color, which is the part `fade` cannot do: red for damage, blue for cold water, orange for a sunset. Same second argument as `fade` — how far, 0 (as drawn) to 100 (nothing but that color), defaulting to 100 — and the same bargain: nothing is redrawn, the picture is all still there, and it comes back untouched when the tint lifts. It sets the level where you call it, so tinting over time is a variable moved a little each frame (`tint :red, hurt`). A full tint left un-lifted is a friendly warning. Works on **every** screen, and a tiled one tints the scenery and the sprites together. **What it costs depends on the screen**, and that is the one thing to know: the plain `screen :bitmap` is free, like `fade`, because it holds a whole color in every pixel and the display mixes the tint in as it draws. `screen :bitmap, tear_free: true` is NOT, although it is one word away: it holds a number per pixel that picks a color out of a shared table, the same as `screen :tiled` and `screen :rotozoom`. Those three draw every pixel through that table, so the framework moves the table instead — a blend per color the game declared (never per pixel on screen), and **only on a frame where the tint actually changes**, so holding one still, or holding it at 0, costs a single check. It also stores that table in the cartridge unpacked, a few bytes more, because the blend reads the original colors from it one at a time. A tint and a fade are one effect on the display, so the last one you set is the one in force.
- `fade_out` / `fade_in` / `flash_screen` — the same fade walked over time, which is what a scene change and a hit flash both are. `fade_out` (`:black` by default, or `:white`; `frames:` / `duration:` in seconds, half a second by default) darkens the screen to nothing over that many frames; `fade_in` brings it back, and with **no arguments at all** it returns in the same color at the same speed, so a scene change is two words and no bookkeeping. `fade_in` is the only one that takes the speed of what came before: a `fade_out` with no length is always half a second, so a quick flash before it cannot turn the next scene change into a blink. `flash_screen` (`:white` by default) is the same thing in a hurry — full on the first frame, then falling back over six frames unless it says otherwise, whatever fade ran before it — for a hit, a score, a life lost; pair it with `shake_screen`. Call each once at the moment it happens; the framework walks the level every frame from there, and stops working entirely once the screen settles. **Any color works** — `flash_screen :red` for damage is the one a game reaches for most, and `fade_out :red` is a redout for a death. Black and white are a brightness change (`fade` underneath); every other color is mixed in (`tint` underneath), so on a screen drawn through a color table a colored one costs what that many colors cost while it is moving. A black or white one costs that too in a game with a **see-through layer**, and for the same reason, except on a plain `screen :bitmap`, which the display fades for nothing — see `fade` above, where the whole bargain is written out. Nothing is redrawn in any of those cases, so it costs the same however much is on screen and works on **either** kind of screen. **A long fade steps every frame**: when any fade in the game takes more than 17 frames — the default half second does — the level is handed to `fade` with its fraction, so on a screen drawn through a color table it walks the colors in 33 levels rather than repeating the display's 17 (see `fade`). The screen is fully faded, and fully back, on the same frames either way. A game whose fades are all 17 frames or shorter keeps the display's free fade, and `rom.profile` says which a game got. `fade_out` and `flash_screen` also take **`under:`** and place the whole game's fade in the stack the way `fade` does (`fade_out under: :ui` — dim the game, keep the HUD; `fade_in` then brings it back with nothing to repeat). A game has one screen fade and it sits in one place: two different layers is a friendly error, because the console has one set of blend registers and two fades at two depths cannot both be in force. A **colored** fade cannot be placed at all (the console can hide only a brightness change from what sits in front of it), so a game that says both is a friendly error whichever order it says them in. Two friendly warnings: a `fade_out` with no `fade_in` anywhere leaves the game running behind a flat screen, and a fade with no `game_loop` has no frames to run on. Worked examples: `examples/pong.rb` (`flash_screen :red` when the cpu scores), `examples/breakout.rb` (a red flash on losing a life, a fade between scenes) and `examples/shmup.rb` (`fade_out under: :ui` — the field and the ships in it go dark on the way to the game-over screen and the score stays readable).
- `fade_level` → a `Value`: how far the screen is faded right now, 0 (as drawn) to 100 (nothing but the color). This is what makes a **scene change** writable, because fading out leaves the screen dark on purpose — so whatever you draw next is invisible until something lifts it, and the switch has to wait for the fade to arrive: `(fade_level == 100).then { state.set! GAME_OVER; fade_in }`. Swap screens while nobody can see it and the player sees one smooth dip to black and back. A value rather than a yes-or-no, so half way through is a place you can act too.
- `pixelate 8` / `pixelate 1` / `pixelate 6, under: :ui` — show the screen in flat blocks, which is the pixelate effect of a scene change, a hit, a dream, a teleport. The number is **how many pixels a block is each way**: 1 is the picture as drawn, 8 is blocks of eight by eight, and 16 is the biggest the console draws. A size you write outside 1 to 16 is a friendly error, one the game works out is held to 1 and 16, and a number that holds a fraction is a friendly error too (use `.to_i`). Nothing is redrawn — the console does it as it draws, so the picture is all still there and comes back untouched at `pixelate 1` — and it costs the same however much is on screen: one register write where you call it, and nothing on a frame you do not. It sets the size where you call it, so pixelating over time is a variable moved a little each frame (`pixelate blocks`); in a game too slow for its frame, a size said after the console has begun drawing shows from the row it had reached, for that one frame. It works on **every** screen, and it is the one effect of this family that reaches a `screen :bitmap` picture the game paints for itself, sprites and text included, since to the console that whole picture is one layer. **The blocks are fixed to the screen, not to the picture**: a block starts at every column and row that is a multiple of the size and shows the colour its top left pixel would have had, so a background that scrolls slides under a grid that stays still, and the picture shimmers as it moves. **Each layer and each sprite is put into blocks by itself**, before they go over one another, so a block of a front layer whose corner is see-through shows the layer behind all the way across. **A sprite's blocks have edges worth knowing**: a block that starts off its left or top shows the sprite's own first column or row, its last block across runs on past its right edge to the end of that block, and nothing is drawn below its bottom edge — so a sprite in big blocks sits a little to the right of where it stood. Text on `screen :tiled` is a small sprite for each character, so it goes into blocks too, a letter at a time, and at a big size a line of it is mostly gone. **`under:` leaves part of the picture sharp**: it names a layer, and that layer and everything in front of it stay as drawn — pixelate the game and keep the score readable. That is free here where a placed `fade` is not, because the console keeps "drawn in blocks" as a switch on each background and each sprite; the price is that those switches are set as the cartridge is built, so **a game pixelates from one place**, and two different `under:`s (or one with and one without) is a friendly error. `under:` needs `screen :tiled` and a layer you declared, like a placed fade. A fade or a tint is done to the finished picture, so either can be in force with blocks at once — with one mix refused: a fade placed so that it keeps some sprites and fades others, while one of the kept sprites is in blocks. The console keeps a sprite out of a fade by the shape it was drawn in, and a sprite in blocks has another shape, so that is a friendly build error saying to give `pixelate` the same `under:` as the fade. **One size is not what its number says**: a background that turns (`rotate` / `scale`) is left a single pixel wide at `pixelate 2`, so its rows double and its columns do not. That is the emulator the picture is checked against; from 3 up it is in blocks both ways like everything else. Worked example: `test/ruby_gba/builder/test_pixelate.rb`.
- `pixelate_out` / `pixelate_in` (both take `frames:` or `duration:` in seconds, half a second by default; `pixelate_out` also takes `under:`) — the same effect walked over time: the picture breaks up into bigger and bigger blocks until they are the biggest there are, and comes back together. The pair to `fade_out` / `fade_in`, and said the same way: call each once, at the moment it begins, and the framework walks the size every frame from there, then stops working once it arrives. `pixelate_in` with no length comes back as fast as the picture last went out, so a scene change is two words. Calling either while a walk runs turns it round from where it is. There are sixteen sizes, so a walk longer than sixteen frames shows some of them for more than one. `under:` places the whole game's pixelate, as on `pixelate`, and holds for both verbs. Two friendly warnings: a `pixelate_out` with no `pixelate_in` anywhere leaves the game running in blocks too big to read, and a walk with no `game_loop` has no frames to run on. Worked example: `examples/meadow.rb`, whose cabin door pixelates the room and the hero out and back in and keeps the room's name sharp with `under:`.
- `pixelate_size` → a `Value`: how big a block the walk has on screen on this frame, 1 (as drawn) to 16 (a size a game sets itself with `pixelate` is not read back here). This is what makes a scene change by pixelating writable, the way `fade_level` does for a fade: the picture is hardest to read at the biggest block, so that is the moment to swap what is drawn — `((leaving == 1) & (pixelate_size == 16)).then { state.set! NEXT_ROOM; pixelate_in; leaving.set! 0 }`. **Keep a flag of your own in that test**: the size reads 16 on the old scene's last frame and again on the new scene's first, which is what puts both in the biggest blocks, so a test on the size alone is true twice. Worked example: `examples/meadow.rb`, where walking through the cabin door swaps the room at that moment.
- `light = spotlight at: [120, 80], radius: 40, dark: 75` → a `Spotlight`: **a light** — the picture as drawn inside a circle and darkened everywhere outside it. A lantern in a cave, a torch in a dungeon, a searchlight. `at:` is where its middle starts, in screen pixels, `radius:` how far it reaches, and `dark:` how dark the rest is, 0 (as drawn) to 100 (black), 75 if not said. All three are where it STARTS, applied once at power-on like a `var`'s value; the handle's `x`, `y`, `radius` and `dark` are `Value`s the game changes, and `light.move_to x, y` moves it (`light.move_to hero.x + 4, hero.y + 4` every frame is a lantern). The picture shows what they hold at the end of the frame. **It is the console's own hardware, and nothing is redrawn**: the display has windows, and darkens the picture outside one as it draws. A window is a rectangle, so the light is that rectangle given a new left and right edge on every row of the screen, worked out in the gap before each frame and handed to the display a row at a time by a copying engine — the same one `scroll_each_row` rides, so a light and up to two bends fit the three engines there are, and past that the line interrupt carries them all. What it costs is that per-row working out, the same however much is on screen. **Up to a radius of 150 the circle is the midpoint circle the console's own games draw**, row for row: a light of radius r lights rows y - r + 1 to y + r - 1, each from x - w up to (not including) x + w, w that circle's half width on the row, held to the screen — so a game copying one lands on every pixel. Past 150 it is a square root read from a table. Each row works its half width out once, one way or the other, and on the console the rows are worked out only on a frame the light darkens something and has moved or changed size since they last were — so there a light switched off in a scene, one darkening nothing until an iris starts, and one standing still cost next to nothing. (The desktop and web builds work them out every frame; it costs them nothing a player sees.) A radius set in a frame is drawn on the next picture, as a sprite's place is. **`spotlight` with nothing after it hands back the game's light**, and a game with none gets one that reaches past every edge and darkens nothing, which is how `iris_out` finds it. A game has one light: a second `spotlight` is a friendly error, and so is one declared after an `iris_out` gave the game a light. **It shares the screen with a plain fade**: a game with a light fades by walking its colours, so the whole picture fades and the light's darkness stays on outside it. Friendly errors: a light on any screen but `screen :tiled`, or in a game that shows one (a bitmap screen has no layers to darken around a light, and the turning-background screen's window is not switched on, so the whole screen would go dark), `spotlight at:` with no `radius:`, in a scene that also sees through a layer or fades with `under:` (each needs the display's one blend), or beside either in a game with no scenes, with no `game_loop` (no frame to work it out in), and a start that is not numbers in range. The darkening is the emulator's to the bit: it works a channel out at eight bits, so white three quarters dark is red 8, green 7, blue 7. **The light is off in a scene that sees through a layer or fades with `under:`**, and on in every other: the display is told what to mix afresh each frame and a game is in one scene at a time, so a title with see-through rays and a scene with a lantern share it by taking turns. Each scene says which as it starts its pass: the light goes OFF on the picture of the pass that changed to such a scene, since that scene takes the mixing for its own there and then, and comes back ON a picture after a lit scene takes over, the way a moved light is drawn a picture later. A scene that moves the light there (`iris_out`, `light.radius.set!`) is the friendly error, and so is a fade placed with `under:` outside every scene, which is in force in all of them. Worked example: `examples/cave.rb`.
- `iris_out` / `iris_in` / `iris_shut?` — **the iris: a circle closing on a point until the screen is black, and opening again.** The pair to `fade_out`/`fade_in` and `pixelate_out`/`pixelate_in`, said the same way: call each once, at the moment it begins, and the framework walks it every frame (`frames:` or `duration:` in seconds, half a second by default). `iris_out at: [hero.x + 4, hero.y + 4]` closes on that point; left out, on wherever the light is. It closes **the game's own light** — the display has one — and `iris_in` gives that light back as big and as dark as it was, so a lantern comes back a lantern; `iris_in dark: 0` (and `radius:`) opens onto another light instead, out of a cave into daylight, and onto a light that darkens nothing the circle opens on past the corners rather than stopping at the lantern's size. `iris_in` with nothing closed before it starts the screen black and opens, which is how a game opens on an iris. A game with no `spotlight` is given one that darkens nothing, so the iris is all a game needs to write. The walk runs between nothing and about the screen's farthest corner from the point (never short of it, at most an eighth past), so the circle is seen moving from its first frame. **While it runs it owns the light's radius and darkness**: a game that sets those itself every frame undoes it, so move only the light's place, or set the rest when `iris_shut?` is false and no walk is under way. `iris_shut?` holds from the frame a walk out arrives until the next `iris_in`, which is the moment to swap the scene: `((leaving == 1) & iris_shut?).then { room.show_map :meadow; iris_in; leaving.set! 0 }` — keep a flag of your own in that test, as with `pixelate_size`. An `iris_out` with no `iris_in` anywhere is a friendly warning. **A walk can be said in pixels, the way a game being copied says it**: `iris_out from: 150, by: 4` starts the circle at 150 and takes 4 off it every frame, the first step taken on the frame it is called, so the light holds 146 at the end of that frame, then 142 … 2 and then 0, and `iris_shut?` holds from the frame the size is 0; `iris_in by: 4, to: 150` opens from 0 by 4 a frame (4 on the frame it is called, 8 … 148) and lets the light go — back as it was, or as `radius:` and `dark:` say — on the frame it would pass 150. `by:` beside `frames:` or `duration:` is a friendly error. A size set in a frame is drawn on the next picture. Worked example: `test/ruby_gba/effects/packs/test_iris.rb`.
- `pulse sprite, to: 1.3` (also `from:`, and `over:` in seconds — one full round trip, 2.0 by default) — a sprite that breathes: it grows to that size, shrinks back, and keeps doing it. A collectable that begs to be picked up, a boss winding up, the selected item on a menu. Call it once where the sprite is declared; the framework runs the rhythm every frame from there, and calling it again on the same sprite replaces the rhythm rather than adding a second one. Tiled sprites only (it is built on `sprite.scale`), and it needs a `game_loop` — a friendly warning otherwise. Worked example: `examples/bird.rb`, where the bird drifts nearer and further.
- `keep_showing :status_bar do … end` → a handle for **a picture that is drawn when it changes and then left alone** — a score, a health bar, a GAME OVER banner. Most of a game is repainted every frame and wants none of this; a picture that changes now and then is far cheaper left there, and **on `screen :bitmap, tear_free: true` leaving it there is the thing that goes wrong**. That screen keeps TWO pictures and shows them in turn (which is what stops a player ever seeing a half-drawn one), so a change painted a single time reaches one of the two and the figure then flickers between the new value and the old, half the frames each. Say when it changed and the framework paints it once per picture the screen keeps. Three words on the handle: `.changed` at the moment the thing it shows moves (the score goes up, the game ends), `.draw` every frame at the point in the drawing order where the picture belongs, and `.cancel` where the thing it showed is put back (a new game starting over a finished one), which drops any paints still owed so a banner cannot follow the old game into the new one. **The same game code is right on a plain screen**, where one picture means one paint — nothing in the program says which screen it is on, so a game moved to `tear_free: true` keeps working and the flicker never appears. A frame with no change outstanding costs one comparison and draws nothing. The block is built into a routine of its own, so a picture painted from three places costs its code once; declare it where the picture belongs (top level, or inside the `scene` that owns it). Declaring the same name twice, or leaving out the name or the block, is a friendly error; declaring one and never calling `.draw` is a friendly warning, because then the picture never appears at all. **What it cannot do is repeat a moving sequence** — it paints the *same* picture again, so a dissolve or a trail (different pixels every frame) needs its own answer, and the Wolfenstein port's `lib/wolf3d/dying.rb` shows one: two walkers a frame apart.
- `shake_screen intensity: 3, frames: 8` (or `duration: 0.2` for seconds) — shake the screen on impact. Call it once at the moment of the hit; the framework jitters the camera every frame from there and puts the picture back exactly where it was. Calling it again mid-shake restarts it. Needs a `game_loop` (that is what gives it a frame to run on).
- `grid :name, cols:, rows:, cell:, over:` → a `Grid`: `set_cell cx, cy, color` / `clear_cell cx, cy` (cell coords; `over:` is the background).
