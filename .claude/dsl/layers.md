# DSL reference: Layers (a named place in the stack)

The whole story of these verbs. The one-line index is `.claude/rules/dsl-reference.md`.

A game is drawn in layers — the scenery, the characters, the score on top — and without a name for them the only way to say what sits in front of what is the order the declarations happen to run in. That order is invisible, it lives in prose comments, and in a game split across files it depends on which file was required first.

- `layers :sky, :world, :actors, :ui` — declare the stack, **back to front**, one time. The order is global on purpose: "in front of" is a relation across the whole screen, so one line answers the question a reader of somebody else's game actually has. Naming a layer twice, or declaring the stack twice, is a friendly error.
- `layer :name do … end` — everything the block declares belongs to that layer. The block runs on the build, exactly like a `func` body, so **every verb works inside** and the parts-in-files pattern does too (`Enemies.new(self)`). What can take a layer is a `background`, a `sprite` (either screen kind — but see the bitmap note below), a `pool` with `image:`, and `draw_text`/`draw_number` on a tiled screen — the things the framework draws again for you every frame. Nesting one `layer` inside another, or naming a layer that isn't in `layers`, is a friendly error.
- `layer :water, transparency: 40 do … end` (also `transparency: 100 - mist` — **an amount the game works out**, for fog that thickens, water that gets murkier as you descend, a backdrop that dims in; write a variable or an expression where you would write a number) — **see through this layer to what is behind it**: water, glass, fog, a dimmed backdrop behind a menu. 0 is solid (the picture as drawn), 100 is invisible. What it means is what it looks like — whatever sits directly under the layer at a pixel shows through it, anything in **front** of it draws solid, and where the layer itself has a see-through tile what is behind shows plain — and that is also exactly what the console does, so there is one rule to learn, and it is about a see-through sprite over another sprite (below). **It costs nothing**: the display blends as it draws, so a see-through layer costs the same as the same layer drawn solid, however much is on screen. (An amount the game works out keeps that bargain for the blending and adds one thing: the display has to be told the new amount before each frame, which is a single register write the framework puts at the frame boundary for you. `rom.profile` says which of the two a picture got.) The property belongs to the layer, so it rides on the layer and there is no new verb; say it on the block, one time. Works for a layer of `background`s and a layer of `sprite`s alike (two different mechanisms in the console, and you never learn which one you got). **One see-through sprite — a ghost, a shield bubble — is a layer holding just it**, `layers :ghosts` and `layer(:ghosts, transparency: 50) { sprite :boo, at: [x, y] }`, and nothing else in the game has to name a layer, since what names none keeps the place it had; there is no per-sprite word, because it would reach the same bit of the sprite's table entry and share the console's one amount. The one thing the layer form cannot do is make a single member of a `pool` see-through, since a pool's instances cannot change layer. **A see-through sprite shows the scenery under it, never another sprite**: where a ghost passes over the hero, the hero is not seen there at all and the floor shows through the ghost instead. The console keeps only the front sprite at each pixel before it blends anything, so the sprite behind is gone by the time the mixing happens. To see a character through something, make that something scenery: a see-through layer holding a `background` does show the sprites behind it. **A SCREEN has one see-through layer, and a game can have one on each of its screens** — a title whose light rays shimmer and a menu whose window glows, in two scenes that are never up together. Two on one screen is a friendly build error naming both layers and the scene, because the console blends one layer with what is behind it, and a see-through layer sitting directly over another one is the one arrangement the two backends would draw differently. What a game with several pays is one compare a frame per layer, to tell the display the amounts of the one on screen. Needs `screen :tiled` — a bitmap screen paints its whole picture into one place before the display sees it, so there is nothing left behind a layer to see through (a friendly error). `transparency: 100` is a friendly warning: none of the layer shows, and the game still draws it (said only about a number you wrote — an amount the game works out passes through 100 whenever the fog clears, so nothing is said about one). **A fade does not disturb the layer** — it goes on showing what is behind it while the screen fades, and the whole picture (the layer, what is behind it, and the mix of the two) darkens together, which is what a fade out should look like. That is not free the way the blending is, and it is the only thing about a see-through layer that costs: seeing through a layer and darkening a finished picture are the display's *one* blend unit, so a game that does both moves the **colors themselves** toward black instead — a blend per color the game declared, never per pixel on screen, and only on a frame where the fade actually moves. It is measured on both backends rather than assumed, and `rom.profile` says so. A `tint` never took the layer's blend in the first place, so `flash_screen :red` costs the same and always did. **The one fade that still takes it is a PLACED one** (`fade … under:`), because placing a fade is the thing only the blend unit can do — that one leaves the layer solid until it lifts, and says so as a friendly warning at build time. Worked examples: `examples/lake.rb`, where half-see-through jellyfish drift across the lake and the ripple keeps travelling through their bells, and `examples/hero.rb`, where mist declared in front of the hero thickens as you walk north (`transparency: 100 - mist`) and clears on the way back.
- `layer :window, shows: 94, shows_behind: 63 do … end` — **the same see-through layer with its two amounts said apart**: `shows:` is how much of the layer itself shows and `shows_behind:` how much of what is behind it, each 0 to 100. `transparency: t` is the pair adding to 100, which is glass; these need not, and that is what light is — a shaft of sunlight shows ALL of the water behind it and some of itself on top, so where it crosses the water the picture is brighter than either, and a channel that runs past its brightest stops there, as the console's does. The display mixes in sixteenths, so each amount is taken to the nearest one: 94 and 63 are the 15 and 10 a cartridge that was drawn in sixteenths says (a file-select window over its backdrop), and `transparency:` keeps the rounding it always had. Either amount can be something the game works out (`shows: 57 - glow, shows_behind: 57 + glow`, light rays stepping through), at the same one register write a frame. The two go together — one without the other, or either beside `transparency:`, is a friendly error — and a `shows:` small enough to round to nothing is the same friendly warning `transparency: 100` gets. It costs exactly what `transparency:` costs. Worked example: `examples/dive`, whose title's near light shafts show three quarters of themselves over all of the water behind them, beside the dive's own see-through water on the next screen.
- **A layer holds things, not brushstrokes.** The instinct people arrive with is that a layer is a surface you draw on — clear this layer, put a pixel on this layer. Nothing on this console works that way, and it is not close: a bitmap screen has one framebuffer, a tiled screen's layers are grids of references to shared tiles rather than canvases of their own, and giving each layer its own pixels means blending two full screens in software every frame — over twice the time a frame has, and the memory besides. So `pixel`, `fill_rect`, `dma_fill_rect`, `draw_rect_at`, `blit`, `clear_screen` and bitmap `draw_text`/`draw_number` are a friendly error inside a `layer` block: they paint where you call them, and no ordering applied later can reach back and change where they landed. What you write instead is the retained-mode answer, which is what `sprite` already is: make a thing, and put the thing in the layer. `fade` and `camera` are a friendly error there too — they change the whole screen, so they cannot belong to one depth. An effect is **placed, not contained**: `fade :black, 100, under: :ui` says where in the stack it sits (see Drawing), which is a different thing from being one of the layer's things.
- **`draw_text` is the one verb whose nature changes with the screen** — layerable on `screen :tiled` (where the console draws each character for you every frame), a friendly error on `screen :bitmap` (where it paints into the framebuffer at the call). Same seam tiled text already has, where it must be declared once above the game loop or inside a scene; the error says which of the two you are in.
- **A scene is WHEN, a layer is WHERE IN THE STACK**, and they never need to know about each other. A HUD can be in `:ui` and in `:playing` — on top, and only while playing. Containment goes one way: `layer` blocks inside a `scene`. A `scene` inside a `layer` is a friendly error (a state holds things at many depths; a layer is one depth). A **routine** — a `func` or a `once_a_frame` — may sit inside a layer, but **declaring a `sprite` or a `background` inside one is a friendly error**: a routine's body is built later, when the layer is not in force, so it would quietly sit at no depth at all. The error names what you wrote and the way round that works (put the `layer` block inside the func; move a declaration out of a per-frame body, where it runs once anyway). What is refused is the *declaration*, not the routine — so a `func` that only moves the sprite it sits beside is fine, and so is every effect verb that declares a per-frame routine of its own (`pulse`, `camera_follows`, `fade_out`, `shake_screen`): a game says `pulse coin` on the line after it declares the coin.
- **A `background` can sit in FRONT of a sprite** — the fence a hero walks behind, grass that passes over their feet — by declaring its layer in front of theirs. That is the one arrangement a picture cannot fall into by accident, and it needs the console's own stacking, so it comes with two rules. **The console keeps four levels of depth**, and a level is spent only by a `background` (the sprites in front of one share its level), so you can name as many layers as you like and a game with one background and five sprite layers uses one level. Asking for more depth than that is a friendly build error that names the layer which cost the level and shows your stack — `rom.profile` lists the same thing for a build that fits. And once a background is in front of a sprite, **every** background and sprite must name a layer: the usual arrangement (scenery behind, everything that moves in front) is gone, so there is no longer a place to leave something that named none. That too is a friendly error.
- `hero.put_in_layer :walking` (also `hero.put_in_layer [:upper, :walking, :stairs], showing: floor`) — **a sprite that changes which layer it is in while the game runs.** A room drawn as two backgrounds has three places a character can stand: upstairs, in front of both; on the ground floor, behind the top one and in front of the bottom one; and on a flight of stairs, behind both, showing only where both are see-through. One cartridge holds rooms of every kind and a staircase moves the character between them mid-walk, so no one place in the stack is right for the whole game. Declare a layer for each place (`layers :stairs, :ground, :walking, :scenery, :upper`), declare the sprite in one of them, and name another as the game runs. A layer the sprite is only ever put in still gets a depth of its own, so the stairs are a layer behind every background with nothing else in it, and it is not a layer that holds nothing. `showing:` picks one of a list by a number the game works out, counting from 0, the same word `draw_with` and `face` take, and **a number outside the list puts the sprite back in the layer it was declared in**. The change shows on the frame the sprite's position and pose next do, never a frame before or after, since on the console the depth is part of the sprite's table entry and is written with them. Every layer it can be in spends depth the way the sprite in it would, so the stairs above take a level of the console's four. **Declare the character once and every room gets it right**: the console counts depth from the front, so the ground floor of a room with a top layer is one further back than in a room without one, and a sprite shown in both is told the number of the room that is up — read off the variable the game picks its scenes with, as the sprite is drawn. **What it costs**: a read of which layer and a table read a frame, a read of which room as well for a sprite whose rooms disagree, and a sprite never moved emits nothing new. Friendly errors: a layer the stack does not have, a game with no `layers`, several layers with no `showing:`, a sprite whose rooms disagree and are not picked by one `case_var` (declare it inside each scene instead), and the verb on `screen :bitmap` (whose backgrounds are painted in once and have nothing to go behind) are friendly errors. Hardware sprites only, not a `pool`'s instances.
- `draw_in_order hero, guard, guards` — **sprites drawn in an order the game works out, so whoever stands lower is in front.** Everywhere else, which sprite is in front is settled when the cartridge is built — the one declared later, unless a layer says otherwise — and a top-down game cannot live with that: walk round below something and you are drawn over it, walk round above it and it is drawn over you, and the answer changes every time two things pass each other. Name the sprites and pools that pass each other, and each frame they are drawn in the order of a number: the bottom of each one's box unless a block says otherwise (`draw_in_order(hero, puffs) { |thing| thing.bottom + thing.lift }`, handed the sprite, or one of a pool's things the way `each` hands it), with the highest number in front unless `front: :lowest` turns it round. A pool's things take part one by one. Things whose numbers are level keep the order they were already in, so two characters standing side by side never flicker in front of each other — with one exception: two level things of a pool can swap once when a thing older than both is removed, since a pool's things keep their places by age. They can be named in any order. **The order is among the things named**: they are drawn together where the backmost of them was declared, and anything else keeps its own place in front of or behind the whole run — so the things of one order are in one layer, and in one scene or none, and a layer orders the runs the way it orders sprites. The order is worked out in the gap before each frame from where everything stands then, the same moment the sprites themselves are drawn from. **What it costs**, measured on the console: three sprites, about 300 instructions a frame; a pool of 32 beside a hero, about 4,200 with four of them live and 4,900 with all 32, which is about a thirtieth of a frame. The number is worked out for every place a pool has, live or not, and the sort starts from last frame's order, so what costs is the size of the run rather than how often things pass. Each place in the run also keeps a copy of its row of the sprite table in work memory, 8 bytes a place. A game that orders nothing builds exactly as before. Friendly errors: a bitmap screen (a sprite there is painted into the picture, so there is no order left to change), anything but a sprite or a pool that draws, one sprite on its own, a thing in two orders, things in different layers or scenes, a `front:` other than `:highest` or `:lowest`, and a sprite in an order that is also told `put_in_layer`.
- **Only what named a layer is moved.** While the usual arrangement holds, a thing that named no layer keeps the exact place it had — so wrapping one part of a game in a layer can never pick up and move a part that says nothing about layers, which is what makes it safe to adopt a bit at a time. Two things in the same layer keep the order they were declared in.
- Layers are **opt-in**: a game that declares none keeps its ordering exactly (declaration order, and a HUD drawn last). What a layer becomes — a background layer, a sprite priority, the order things are painted — is the framework's business; you never write a BG index or a priority.
- **A stack decides the picture on both screens — with one exception, and it is about `background`.** Sprites follow their layer on either screen: on `screen :bitmap` the framework repaints them every frame, so it repaints them back to front and a sprite in a front layer covers one behind it, exactly as on `screen :tiled`. Worked example: `examples/sprite_mover.rb`, where the heart passes in front of one post and behind another. A **`background` on `screen :bitmap`** is the exception, and permanently: it stamps its tiles into the one picture where you declare it, and nothing draws it again, so no layer can move it afterwards. Where a stack asks a bitmap screen for a background order it cannot give — two backgrounds the stack reverses, or a background put in front of a sprite — that is a friendly build **warning** naming both orders, what you asked for and what the screen will show. On `screen :tiled` there is no exception at all.
- **`rom.profile` shows the stack** — each layer with what it holds, which of the console's four levels it landed on, and how many are left. That is the tiled screen's whole bargain, made visible: a background is drawn by the display for free once it is up, however big it is, so several layers sharing one level is the normal answer rather than a compromise. A see-through layer gets a line of its own, saying that the display blends it for nothing — and, in a game that also fades, a line saying which of the two ways of fading that bought: a whole-screen fade walks the colors and keeps the layer (and costs a blend per declared color on each frame it moves), where a fade PLACED in the stack takes the blend and leaves the layer solid until it lifts. What a layer COSTS is a question about time, and the measured half of the same report answers it by routine.
- **A layer that holds nothing** — a name in `layers` no `layer` block ever puts anything in — is a friendly warning too. It is harmless to the picture, and it is almost always a name spelled two ways or a leftover from an edit, which quietly stops the stack meaning what it says. A layer named only by an effect (`fade … under: :cut`) counts as used: it is deciding where the line falls.
