# DSL reference: Tiled backgrounds

The whole story of these verbs. The one-line index is `.claude/rules/dsl-reference.md`.

- `tiles :name, "#" => :brick, "." => :floor` — a tileset: map each character to a tile `image` (all same size). Add `solid: ["#"]` to mark wall tiles a sprite can't move through (see `blocked_by` under sprites). **A key need not be a character** — `tiles :room, 0 => :tile_0, 1 => :tile_1` — which is what a game whose level is worked out rather than typed already calls its tiles; `solid:` takes whichever keys the tileset has, with no change in spelling. **Import from a tile sheet** instead of naming images: `tiles :name, from: "tiles.png", tile: 8, "#" => 0, "." => 1` — each key points at a cell (a number counting left-to-right, or `[col,row]`); `tile:` is the tile size, `transparent: true` honors cut-outs, path resolves next to your script. **Import the WHOLE sheet as numbered tiles** (no characters): `tiles :name, from: "world.png", tile: 8` — every cell becomes a tile numbered 1, 2, 3… left-to-right (the numbering a map editor exports), and a map over it is written in those numbers, from a CSV or straight into `map:`; `solid:` then takes tile numbers (`solid: [1, 2]`).
- `box = tiles :box, from: canvas, count: 104, colors: :ink` then `box.changed` — **tiles whose pixels the game paints while it runs.** Every other tile is a picture fixed when the cartridge is built. These hold whatever the game works out: a name, a count, a message typed a letter at a time, a meter, a map drawn from where the player has been. `from:` is a `list ..., width: :byte` the game owns, and `count:` is how many tiles it holds. The tiles are keyed 1 to `count`, in the order their bytes sit in the list, so a background names them with Array rows (`map: [[1, 2, 3], [4, 5, 6]]`), and other keys in the same `tiles` call are ordinary tiles beside them (a box's frame). **The list holds the pixels the way the console's memory does**: a tile is 32 bytes, 8 rows of 4; each byte is two pixels, the left one in the low four bits; and each four bits is a place in `colors:` (a `colors` list by name, or the colours themselves, 2 to 16, place 0 see-through). That is what lets the copy be a plain copy, and what lets a game match another cartridge's buffer byte for byte. Writing into the list changes nothing on screen by itself. **`box.changed` shows it on the next frame**: the list is copied in the gap between frames, so a picture is never seen half copied. Saying it several times in one frame is one copy, and saying it every frame copies every frame. A scene that owns the tiles puts them up from the list as it is when the scene takes over again. **What it costs**: `changed` is one store, a frame with nothing changed pays one compare, and a frame with a copy pays one block copy of `count × 32` bytes — a 104-tile run measured at about a hundredth of a frame, and about two and a half hundredths when the list is in the roomy memory (`fast: false`). The tiles are never merged with any other tile, since two that look the same now may not on the next frame. Friendly errors: on a `screen :bitmap` (use `pixel` or `blit`, which already paint the screen); a list that is not `width: :byte`, or holds fewer than `count × 32` bytes; a `count:` that is not a whole number above 0; a `colors:` list missing or over 16; a key 1 to `count` also given a picture; a background that turns, or whose other tiles need more than 15 colours; and a list the game also `shift`s, anywhere in the game, since that moves its bytes out of order. **One run can be shown in several scenes** — a dialogue box in the overworld, a house and a shop — each scene by a background of its own, and each puts the box up from the list as it is when it takes over. A background every screen shows and a scene's own background can show the same run too, and so can two backgrounds on one screen: there is one copy, and each points at it. A scene that does not show the run can still say `changed`, and nothing is drawn there. What it costs is one store a frame in each scene, saying where the run sits on that scene's screen, and a load and a compare on each copy. A list starts empty, so a game fills it first (`repeat(3328) { canvas.push 0 }`) and then writes into it by index.
- `board = canvas :board, width: 208, height: 32, colors: :ink` then `background :box, tiles: :board, map: board.cells` — **a picture the game draws into with words while it runs**, and the friendly side of the entry above: the canvas keeps the list, packs every pixel for you and says `changed` after each word, so what you draw shows on the next frame. The words, all in colour names and all clipped at the canvas edge when a position is worked out as the game runs: `board.pixel x, y, :white`; `board.clear` (see-through) or `board.clear :blue`; `board.fill_rect x, y, w, h, :red` (any width, and 0 or less draws nothing — a meter); `board.blit :icon, x, y` (an `image`, whose see-through pixels leave the canvas alone and whose colours must be the canvas's); `board.draw_letter code, x, y, :white, font: :default`, where `code` is a character or a number the game works out — a name kept in a list, drawn a letter at a time — and which hands back how far across the letter reached, gap included, as a variable, so `pen.add! board.draw_letter(name[i], pen, 0, :white)` types; `board.draw_text "HELLO", x, y, :white`; and `board.draw_number score, x, y, :white, digits: 5`, right-aligned with no leading zeros like `draw_number`. `board.cells` is the canvas's tiles as rows of map keys, ready for a `map:`, and keys given to `canvas` itself are ordinary tiles in the same tileset beside it (a box's frame). `as: :sprite` makes the canvas a sprite's picture instead (`sprite :board, at: [x, y]`), and then it is a size the console draws a sprite at. `board.list` is the packed bytes, for a game that wants to write some itself (say `board.changed` after). Each side is a whole number of tiles, so a multiple of 8, and a colour the canvas does not have, a position written as a number outside it, and a canvas on a bitmap screen are friendly errors. **What it costs**, measured on the console: a pixel is about 140 instructions; a letter of the 5x7 default font about 5,600; clearing a 208x32 canvas about 3,400, since it is filled four bytes at a time; a 20x8 rectangle about 4,000, and about 6,100 when its left and right edges fall on odd columns, since a byte holds two pixels and an odd edge pixel is drawn on its own — on top of the copy the tiles above cost on a frame something was drawn. Worked example: `examples/hero.rb`, whose signpost types which file you are in and how far you have walked, and whose corner map gains a dot wherever you go.
- `bg.set_tile col, row, "."` — **one cell of the scenery becomes a different tile, while the game runs.** A door that opens, a pot that breaks, a wall a bomb takes out, a block the player pushes: every one of those is one tile changing, and without this every one of them has to be a sprite instead, out of a budget a game would rather spend on things that move. `col` and `row` are **cell** coordinates, not pixels, and either may be something the game works out; the tile is named the way the map was — one of the tileset's own keys, whether those are characters or the numbers a computed level counts in, or a number from an imported sheet — so nothing here is a place in video memory. **A cell outside the map is left alone**, so a coordinate that ran off the edge needs no test around it. A changed cell lasts until the map is put up again: `show_map`, or, for a background declared inside a scene, that scene taking over again (see `show_map`, below), or, for any background, a scene on a `screen :bitmap` coming between — that screen uses the same video memory, so the background comes back as declared, showing its first map. Every tile the tileset names is shipped whether the map used it or not, so a door can be drawn in the tileset and only ever appear once something opens it. A tile the tileset does not name, and `set_tile` on a `screen :bitmap` background (which is painted into the picture once, so it has no cells left), are friendly errors. `bg.cols` / `bg.rows` read the map's size back. **What it costs** is one write — the change lands where you call it rather than being held for the frame boundary. A cell is a single half-word, so it can never be read half-written; the whole effect of writing while the display draws is that one 8-pixel cell can be split across a single frame, and only when the write lands inside that cell's own six-thousandths of a frame. What that does not cover is a **bulk** change — a whole room swapped in one frame — where half the old room and half the new really would show at once; that is `show_map`, below. Worked example: `examples/tiles.rb`.
- `background :rooms, tiles: :set, map: { hall: HALL, cave: CAVE }` then `rooms.show_map :cave` — **the whole background becomes a different map, while the game runs.** That is what walking through a door is in a game with a lot of rooms: a room is a map, and going into one is naming it. Give `map:` (or `from:`, for CSV files) a **Hash** of them instead of one map and the background has several, one showing at a time; the first is the one showing when the game starts. **They can be different sizes** — a hut and a field on one background — and then each is kept at its own size, so a small room does not cost a big one's room (see "bigger than the grid" below for what that changes). `show_map` takes one of those names, or **a number counting from 0 in that order — and that number may be something the game works out**, which is what a game with hundreds of rooms wants: the room number IS the map number, so walking is arithmetic rather than a test per room. `rooms.showing` reads back which one is showing as a `Value`, `rooms.map_number(:cave)` turns a name into its number for comparing, and `rooms.map_count` is how many there are. **A number naming no map leaves the picture alone**, so a room number that ran off the end needs no test around it. **The map comes back exactly as declared**: a cell you had changed with `set_tile` — a door you opened — is shut again when you return to that map, because the whole map is copied in over whatever was there. A game that remembers such things opens them again on the way in, which is where it wants that decision anyway. **Coming back to a scene is the same thing**: a background declared inside a scene is put up as declared each time that scene takes over, so a cell changed with `set_tile` is back as drawn and the background is showing its first map again (`showing` reads 0), whatever the last visit did. **What it costs**: one copy, in the gap between frames, and only on a frame where the answer changed — so saying the map already showing costs a single comparison, and `show_map` can be written every frame, from a branch, from a scene. Nothing in the program names video memory or a moment it is safe to write. **A mover is blocked by the walls of the room it is in**: `blocked_by` reads the grid of the map that is really showing, so a cell that is a wall in the hall can be open floor in the cave, and the room you are standing in is the room that stops you. The map to read is worked out once for the whole check rather than once per cell, so sixty-four rooms ask exactly what two do (measured: the same emitted check, and one room's worth of bytes more than a background with a single map). It reads the map really IN the cells rather than the one the game last asked for — those differ for the one frame `show_map`'s copy is pending, and a player can feel being stopped by a wall that is not on screen where they cannot feel a frame of lag. What it cannot do is `show_map` on a `screen :bitmap` background, for the same reason `set_tile` is. The maps are stored uncompressed, because finding the map you asked for is arithmetic on where the first one starts. Worked example: `examples/tiles.rb`, where LEFT and RIGHT walk between three rooms while A and B open and shut a door in one of them.
- `background :ground, tiles: { shrine: :shrine_tiles, clearing: :clearing_tiles }, map: { shrine: { hall: HALL, stairs: STAIRS }, clearing: { glade: GLADE } }` — **a background whose rooms are in different AREAS, each area drawn from its own set of tiles.** That is how a game with a lot of world fits: the console's tile memory holds one area's tiles at a time, so a game holds the area the player is in, and walking into the next area brings that area's tiles in, and the colours they are drawn in with them. `tiles:` names each area's tileset and `map:` gives each area's maps under the same name, in the same order; the maps are counted area after area, which is the number `show_map` takes, so `ground.show_map room` with a room number the game works out walks between areas as it walks between rooms. **What has to fit is one area, not all of them**: each area's tiles on their own must fit beside everything else on the screen, and each area's colours beside the colours every area shares. Several backgrounds can walk together — a ground and the scenery over it — and the ones that name the same area share its colours, so they must change area on the same frame, which they do when each is told `show_map` with the same room. **When it shows**: on the same frame a `show_map` within one area would, on both backends. The area's tiles, its colours and the map all go in in the gap before that frame, with the background layers switched off while they do, so no frame shows a map over the wrong area's tiles; a whole area is thousands of bytes, so the frame that brings one in can run late, and a copy longer than the gap shows the backdrop at the top of that frame instead of half an area. **The colours arrive through whatever tint or fade is in force**, so an area walked into on a dark screen arrives dark and a fade back in shows its own colours. Walls follow the area like they follow the room (`blocked_by` reads the map really showing), a scene that comes back shows its first area again, and `rom.profile` counts each area brought in under the background's name. **What it costs every other frame is a question and a call**: bringing an area in is a routine of each background's own, kept in the cartridge and listed by the profile as "bringing background :name another set of tiles", so the game loop holds only the test for whether the area is changing — about sixty bytes a background, where the work written out in the loop was most of the loop and took the quick memory from routines every frame of play runs. Friendly errors: maps not under the area names, two maps of one name, `set_tile` (a tile name can be in several areas, so give each look of a room a map of its own), walking backgrounds that start in different areas, `draw_with`, a tile of more than 15 colours, a painted tile, a turning background, an area whose colours do not fit, and areas whose tiles are different sizes.
- `bg.draw_with :dusk` (also `bg.draw_with [:s0, :s1, :s2, :s3], showing: step`, and `bg.draw_with :own`) — **the whole layer drawn from a different list of colours, while the game runs.** Shafts of light that shimmer, water that turns murky as you go down, a sky that walks from day to dusk, a room that changes with the weather. It is the same word a sprite already takes and it means the same thing: the lists are declared with `colors`, see-through first, and matched to the list the tiles were drawn from **by place** — so every pixel keeps the place it was drawn at and only the colour that place shows changes. The scenery is not redrawn, not one cell of the map moves, and the art is drawn once however many times of day it has. **A number outside the set is the colours it was drawn in**, so a counter that has run off the end looks right rather than wrong, and `showing:` is the same word a `blit`, a `menu` row and a sprite's own `draw_with` use. **A layer drawn from SEVERAL lists** — a backdrop with more colours than sixteen, each tile drawn from one of its lists — steps them all together: name each list its tiles were drawn from (`colors :sea, [...]` then `image :wave, ..., colors: :sea`), and give `draw_with` a hash of those names to what each walks through, `backdrop.draw_with({ sea: %i[sea0 sea1 sea2], sky: %i[sky0 sky1 sky2] }, showing: step)` — one number picks the same step of every list, which is how a retail title animates a full-screen backdrop across four groups of colours at once. `backdrop.draw_with({ sea: :sea_dusk })` gives one list each, with no number; a list the hash leaves out stays as drawn; and a number outside the steps draws every list as drawn. Giving such a layer a single list is a friendly error naming its lists, and so are a name none of its tiles is drawn from and lists with different numbers of steps. It costs one copy of sixteen colours for each list the layer is drawn from, on the frame the step changes and no other. **What it needs**: the tiles given a `colors:` list of their own (a swap goes by place, and a picture whose list the framework worked out has places nobody chose), a list at least as long as theirs, and `screen :tiled` — a bitmap background is stamped into the one picture where it is declared, so it has no colours left to swap (a friendly error). A **turning** background is a friendly error too, whichever order the two are written in: its cells hold a tile number and nothing else, so its tiles read every colour in the game rather than a list of their own, and there would be nothing to swap. **What it costs**: one copy of sixteen colours, in the gap between frames, and only on a frame where the answer changed — so saying the list already showing costs a single comparison, and it can be written every frame, from a branch, from a scene, exactly like `show_map`. It costs the same however much of the layer is on screen, because the console draws every pixel by looking its colour up in a table and this moves the table. The one thing it spends is a group of sixteen colours: a layer that can be recoloured is given colours **nobody else reads**, since the write lands in the table and anything else drawing from those sixteen would change colour with it — so two layers drawn from the same art can shimmer one at a time. A **fade or a tint** over such a layer darkens or moves the list it is really drawing from, not the one it was drawn in, so the two compose and neither has to know about the other. Worked example: `examples/dive`, whose title screen has two sheets of light shafts drifting at different speeds and shimmers the near one.
- **Two tiles that come out the same are stored once, and nothing says so.** Nothing about a tileset says which of its tiles are really the same picture — a wall's interior repeats in every variation of that wall, half a metatile of grass is the same grass in dozens of cells — and on a real tileset that is a large fraction of it. The build notices; you write the tileset you drew, and it costs nothing at run time because a tile number is a tile number. **A tile that is another tile MIRRORED is stored once too** — reversed left to right, upside down, or both — because a map cell can say "draw it turned round" and the console does that as it draws, for nothing. A room's left wall is its right wall reversed and a corner is the same corner four ways, so on a real area this is often half the tiles: counted on one game's twenty-room area by cutting its rooms into tiles, a layer of 1,553 different tiles is 708 once mirrors are one, which is the difference between past the about a thousand one layer can name and comfortably inside it. `set_tile` and `show_map` name the tile the same way the map did, so a changed cell shows it the right way round. `rom.profile` says how many tiles turned out to be repeats and how many were mirrors, and a layer still too big after this says how many mirrors it found. A **turning** background cannot do this: its cells hold a tile number and nothing else, so it keeps each mirror as a picture of its own.
- **How many different tiles a game can have, which used to be one number for the whole game and is now the memory.** A cell of a map names its tile by counting from a starting point, and it has ten bits to count with — so **one layer reaches about a thousand tiles** (twice that where the art needs more colours, since those tiles are stored at twice the size). That used to be the ceiling for a whole game, because every layer counted from the same place. Now **each layer counts from its own**, worked out at build time from where its tiles landed, so a second layer picks up where the first left off and what a game holds is simply what fits: **roughly nineteen hundred small tiles across two layers**, against the 256 a whole game got before any of this. Nothing in the program says a word about it, and it costs nothing at run time. It is not always exactly free of MEMORY: the console allows a starting point only at four fixed marks, so lining a layer up with one can leave a gap behind it, and `rom.profile` says how big — along with how much of the memory the tiles and the maps have each taken, which is the number to watch, since they share it and grow toward each other. A tileset too big for one map to count across is a friendly error naming the background and saying to declare it before the bigger ones.
- `background :name, tiles: :set, map: <<~MAP … MAP` → a `Background`; stamps a grid of tiles (`map` is rows of tileset keys — a string or array of row strings, one character per cell, a space = empty cell). **Or write the grid the build worked out:** a row may be an **Array** instead of a String, one element per cell, and then a cell is whatever the tileset is keyed by rather than a single character (`nil` = empty cell) — `background :room, tiles: :room, map: [[0, 1, 1, 2], [3, nil, 1, 2]]`. That is the third way a game gets a level, beside a person typing it and an editor exporting it, and the one that had no spelling: a level decoded from somewhere has a tile *number* per cell and never had characters, and a screenful of a real game holds far more distinct tiles than the 94 printable characters anybody would read. Same verb, same argument, same tileset; nothing about the level is a file on disk. **Or import the map from a file:** `background :name, tiles: :set, from: "level.csv"` reads a CSV tilemap exported from a map editor like Tiled — a grid of tile numbers, one row per line, `0` = empty cell (path resolves next to your script). Give `map:` or `from:`, not both. **Or a Hash of several maps** the game can walk between — see `show_map` above. Drawn by the tile hardware in `screen :tiled`, and like tiled text it is **declared once — above `game_loop`, or inside a `scene`** — and drawn for you every frame from then on; declaring it inside `game_loop` on a tiled screen is a friendly build error (show another map from the loop with `show_map`). A `screen :bitmap` background is painted where it is written, so the loop is no error there. **Say what STOPS a mover apart from what it SHOWS:** `walls:` is a grid of its own, the same shape as the map, saying which cells cannot be entered — `background :rooms, tiles: :set, map: { hall: HALL, cave: CAVE, sky: SKY }, walls: { hall: HALL_WALLS, cave: CAVE_WALLS }`. Leave it out and the walls are the tileset's `solid:` tiles, read off the picture, which is what a small game wants and what every game wrote before this existed. Write it and the two are separate data, which is what a real game's collision already is: a room's walls are authored, imported or decoded beside its picture rather than worked out from which tile happened to be drawn — so the same brick can be a wall in one room and scenery in the next with nothing about the art changing. **A map `walls:` does not name has no walls**, which is the explicit way to say a room is somewhere you walk anywhere: a fly-over map, a cut-scene tableau, scenery rather than a place. That is one missing line, not a second background, and it is visible at a glance beside the maps themselves. A cell is a wall unless it is BLANK — a space, a `.`, a `0`, or nothing at all — so a grid drawn by hand and a collision layer decoded out of somewhere else both drop in with no table of which value means what. A `walls:` key naming no map is a friendly error, because it would quietly leave that one room walkable, which reads as broken collision rather than as the typo it is. **Scroll it:** `bg.scroll_by dx, dy` / `bg.scroll_to x, y` move the visible window over the map (in pixels; a map that fits the console's grid wraps at its edge) — call them anywhere in the frame, from a branch or deep in a scene; the framework applies the camera once a frame so scrolling can never tear. **Up to 64×64 tiles** — 512×512 pixels, more than four screenfuls — and the map wraps at that edge, not at the last row you wrote (past the rows you filled in you see the backdrop, and the picture comes round again at the grid's edge; that is what a background does, and both backends agree on where). You write the rows you want and the framework picks the smallest of the console's grid sizes that holds them; a map bigger than one piece of video memory is cut up and laid out for you, and nothing in the program says so. **A map BIGGER than the grid works too, and nothing says so either** — a room of 126×126 cells, a field a dozen screens across. The console's grid is at most 64×64 cells, so such a background keeps its whole map in the cartridge and, in the gap before each frame, copies in the column or row of cells coming into view; a 32×32 grid that comes round under the view is all it needs, since the screen shows 31 columns and 21 rows at most. The same happens to a background whose maps are of different sizes. **What it changes is the edge**: past the edge of such a map there are no cells, so the view shows the backdrop and the layers behind there, rather than the map coming round again — a room has edges, and a small repeating backdrop that fits its grid still comes round as before. A `show_map` to another room, a scene taking over, and a view that moved more than eight cells in a frame fill the whole view again in that same gap, so **the frame the view lands on already shows the right picture**, and a room of another area comes in with its tiles exactly as a small one does (see the area entry above). `blocked_by` reads each room's walls at that room's own size. **What it costs**: a few dozen instructions and no copy on a frame the view stayed inside one cell; a column of 21 cells or a row of 31 on a frame it crossed one, a handful of instructions a cell; the whole view, 21 rows of 31, on a jump. `rom.profile` counts it as "bringing the view of background :x along its map", and lists a routine of that name: the work is one routine for each such background, called from the scroll and from wherever the whole view is filled, and placed like a routine somebody wrote, by what a frame spends in it, so a game that scrolls a big map can keep it in the quick memory while there is room. Friendly errors: `set_tile` on such a background (its cells are copied in again as the view moves, so give each look of a room a map of its own), turning it (a layer that turns has to hold its whole map), and `scroll_each_row` on it (a bent row reaches past the cells around the view). Worked example: `examples/meadow.rb`, where a hero walks out of a one-screen cabin into a meadow of 120x100 cells on the same background. Sprites compose over a scrolling background (the console draws them on top for free) — a hero centered while the world scrolls under it is a follow-cam (`examples/hero.rb`). **Stack layers:** declare more than one `background` (up to 4 showing at one time — declare them inside a `scene` and each scene gets its own four) and they compose — the first declared is the backmost (unless a `layer` says otherwise — see Layers), each later one in front, and a front layer's see-through tiles (empty cells, or `:transparent`/backdrop pixels) let the layer behind show; scroll a near and a far layer at different speeds for parallax (`examples/parallax.rb`).
- `bg.scroll_each_row { |row| offset }` — give every **row** of a background its own sideways offset, so the picture *bends* instead of moving as one flat rectangle. The block is handed the row (0 at the top of the screen, 159 at the bottom) and gives back how far across that row sits, on top of the background's own scroll — so a background can scroll and bend at once. Move a variable the block reads and the bend travels: rippling water, a heat haze, a reflection wobbling, a screen melting into a transition. Worked example: `examples/lake.rb`, where a sine table shifted a little each frame rolls a wave down a lake and the sun's reflection snakes. Declare it once where the background is declared — it keeps running from there, and calling it again replaces the bend. Rows bend sideways only. Tiled screens only (a bitmap screen has pixels you drew, not a layer to bend — a friendly error). **Your block runs once per row, in the gap between frames** — all 160 rows worked out before the picture is drawn, never while it is being drawn. That is what keeps a bend in step with everything else the frame moved (a sprite riding on the water shows the same frame the water does), and it is most of what the effect costs: about as much as running your block 160 times, whatever is in it. Write what you like there — a `table` read, arithmetic, a variable set, a `func` call. **It is not free.** **How many layers bend decides the rest.** Up to three at once are fed to the display by its own copying engines, with the CPU untouched, so a parallax pair of rippling layers costs nothing beyond the two blocks; a **fourth** is one more than there are engines and then the game is interrupted on every one of the display's 228 lines to hand the rows over, which is several times the price of the blocks themselves. A game playing `sample`/`instrument` audio is fed from an engine too, and then there is one left, so one layer.

- `bg.rotate degrees` / `bg.scale size` — turn or resize the WHOLE background as one piece, pivoting on the middle of the screen — the same trick a hardware sprite's `face_angle` / `scale` does, done to a background layer instead of one picture. `degrees` is clockwise from upright and wraps (370 is the same as 10); `size` is 1.0 at the size it was drawn, 2.0 twice as big, 0.5 half. `bg.angle` reads the heading back as a `Value`; `bg.scale` with no argument does the same for size, so easing it is the expression DSL (`bg.scale.approach! 1.0, 0.05`) same as a sprite's. **Works on `screen :tiled` as well as `screen :rotozoom`, and saying it is how the hardware gets picked**: a background that turns is the one thing the console cannot arrange alongside four scrolling layers, so writing `rotate` or `scale` is what asks for the arrangement that holds it — two scrolling layers plus this one. **It asks for it on THAT SCREEN only**: a scene that turns nothing keeps all four scrolling layers, in the same cartridge, because the console is told which arrangement it is in as each scene takes over. Nothing else in the program mentions it, the other layers keep their scroll, their `show_map`, their `set_tile` and a see-through layer, and a third scrolling layer beside it is a friendly error naming both counts. A `screen :bitmap` background cannot turn at all (a friendly error), because that screen has no layer — it has pixels you drew. **What a turning background gives up, wherever it lives**, and this is the part to read before moving one onto `screen :tiled`, because these used to read as facts about `screen :rotozoom` and are really facts about turning: its map must be **square** (16, 32, 64 or 128 tiles a side — it turns about its own middle), it can name at most **256 distinct tiles** (its cells hold one byte each, where a scrolling layer's hold two), its tiles are always stored at full size, and **`set_tile` cannot change one of its cells** (there is nothing in a cell but a tile number). Each is a friendly error naming the background. `show_map` still works. In exchange this background's own `scroll_by`/`scroll_to`, and `scroll_each_row`, become a friendly error, since panning this kind of layer is done by turning/resizing it, not by the plain scroll registers `screen :tiled` uses. **Its tiles are always stored at full size**, which is the one place the halving described under Images does not apply: this pair of layers reads a whole number per pixel whatever the art is drawn from, and its cells have no room to say otherwise — so a turning background drawn from four colours takes what one drawn from two hundred takes. Nothing to write; `rom.profile` shows it as tiles that got the big storage. **A size or angle written on the line that DECLARES the background — `background(:sword, tiles: :sword, map: grid).scale(16.0)` — is what the picture starts at, and it is applied once at power-on**, the same promise `var` makes about the value it is declared with. That matters inside a scene and nowhere else: a scene's body is reached on every frame that scene is up, so a size read as a per-frame write there would be put back at the top of every frame and whatever was easing it would get one step and no more — a title screen whose picture flies at the player would arrive stuck. Write the same number further down and it is what it says: set the size, here, every time this runs. **The display is told how the layer is turned only on a frame where the answer CHANGED**, the same bargain `show_map` and a scroll already make, and here it buys more than the time: a picture that has arrived costs two comparisons and no write at all, where writing every frame means writing on the frames a game starts late as well — and a write that lands after the picture has begun to be drawn moves the layer for the rest of that frame, so a picture that has stopped moving visibly jumps and snaps back every few seconds. Nothing in the program says any of this; a turn that moves is written on every frame it moves. Worked example: `examples/rotozoom_bg.rb`.
- `bg.turns_around x, y` — **which point on the screen the picture turns around**: the one place that stays still while the rest of it swings or grows about it, and the place the same point of the picture keeps landing on. The middle of the screen unless you say so, which is right for a picture that IS the whole screen — a spinning map, a race track that pulls away — and wrong for a picture that arrives somewhere in particular. A title screen where something flies at the player pivots wherever that thing comes to rest, and the difference is not cosmetic: at sixteen times magnified only a sixteen-by-ten patch of the picture is on screen, so a pivot eight pixels off puts the whole thing outside the screen for the first half of its arrival — it flies in from nowhere, and the art has to be moved inside its own grid to compensate, which then throws off where it comes to rest. **Say it once, where the background is declared** (`background(:sword, tiles: :sword, map: grid).turns_around(120, 72).scale(16.0)`): a picture turns around one point however many times the game turns it, so there is nowhere for a second answer to live. It takes two numbers you write — a point the game works out is a friendly error, because a pivot that MOVES is its own effect and a different one. **Nothing moves when only the pivot does**: at its drawn size, upright, a background lands in exactly the same place whatever it turns around, so this can be said before the animation that reads it exists. It costs nothing at all — the same one multiply-and-subtract per axis the middle of the screen already cost.
