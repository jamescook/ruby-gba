# DSL verb reference — the flat `RubyGBA.build` API

The verbs you call inside a `RubyGBA.build "NAME"` block (they mix
into `Builder` from `lib/ruby_gba/builder/*.rb`). A **drift test**
(`test/ruby_gba/test_dsl_reference.rb`) fails if a builder verb isn't mentioned here — so
when you add a verb, add a line below.

Conventions: coordinates are pixels, top-left origin, screen is 240×160. A
`:symbol` names a variable; an `Integer` is a literal; a `Value` (from `var`) is an
expression. `fill_rect`/`dma_fill_rect` need an **even width**; `draw_rect_at` takes any.

## Build / screen

- `RubyGBA.game "NAME" do … end` — **the name is all the cartridge needs from you.** A cartridge also carries a four-character code, and that code is the only thing an emulator has to tell one cartridge from another: it reads the code to put a title in its window, and it reads the same code to decide what save hardware the cartridge has — plain memory, flash, a chip read a bit at a time — and whether there is a clock or a rumble motor in there. So a code made up by hand is a real footgun, and not a cosmetic one: thousands of cartridges shipped and the memorable codes are long gone, so landing on one means the emulator reports somebody else's game AND fits somebody else's save hardware — which it puts in place of the one your cartridge asked for, so a game that saves can stop saving with nothing on screen to say why. The framework works a code out from the name instead, starting with a letter no cartridge ever used, so nothing in the program mentions any of this. `code:` and `maker:` are still there for a game that wants its own — and a code a real cartridge already carries is a friendly error, naming the free letters (D, E, H, I, L, N, O, Q, T, W, Y). The maker is the two characters that name a publisher, and a game that says nothing says it has none, which is true: `01` is Nintendo's.
- `screen :bitmap` — pick the display. `screen :bitmap, tear_free: true` = double-buffered (Mode 4). `screen :tiled` = tile backgrounds + hardware sprites (also decides which kind `sprite` makes). `screen :rotozoom` = a background that can turn and resize as one whole piece — a title screen that zooms in, a race track that spins and pulls away — instead of only scrolling straight the way `screen :tiled`'s layers do. See `background(...).rotate` / `.scale` under Tiled backgrounds. **A `screen :tiled` background can turn and resize too, and that is the arrangement nearly every game wants**, because a turning layer is almost never the whole picture: a title where an object flies at the player over a backdrop, a map screen that spins inside a fixed frame, a road that banks under a sky and a status bar. Nothing in the program says so — a background is one that turns because the program turns it, and the build picks the hardware that holds what was declared. **What it trades is scrolling layers**: `screen :tiled` gives four of them while nothing turns, and two of them beside a layer that does. **That trade is per SCREEN, not per game** — the console is told which arrangement it is in by one register and can be told again whenever the screen changes, so a title screen with something flying at the player over two scrolling layers can hand over to a game with four scrolling layers and nothing turning, in one cartridge. Declare each scene's backgrounds inside that scene and the build works the arrangement out per scene; nothing in the program names one. **That is four AT ONE TIME, not four in the whole game** — a background declared inside a `scene` is up only while that scene is, so scenes take turns with the layers and a game may declare four in each of as many scenes as it likes (see "A scene owns what it draws" under Scenes & funcs). Asking one screen for more than fits is a friendly error naming both counts and the scene that ran out, never a layer quietly left undrawn. So reach for `screen :rotozoom` only for a screen that is nothing BUT a turning layer — it is a third arrangement again (one background, no scrolling ones at all); a plain scroll on it is a friendly error pointing at `rotate`/`scale` instead.
- `screen :bitmap, tear_free: true, colors: [...]` — **say which colors the screen shows** instead of letting the framework work them out from the ones you name. The tear-free screen holds a number per pixel that picks a color out of a shared table, and normally the framework builds that table for you, silently, from the color names you write — which is right until your pictures come from somewhere that already decided. Art imported from another game or a paint program has pixels that are numbers picking out of *its* table, so give the colors in that table's order and the pictures line up. Everything else is unchanged: you still write color names everywhere, and you never write a slot number. **The order is the whole point** — nothing is moved, nothing is added (not even black, which the worked-out table always reserves at the front), and a color repeated in the list keeps both places, because dropping one would shift every color after it and move every pixel of every picture. Drawing with a color the screen was not given is a friendly error naming it; giving two screens different lists is a friendly error, because the display holds one table at a time; and `colors:` without `tear_free: true` is a friendly error, because a plain bitmap screen holds a whole color in every pixel and has no table to fill in.
- `floors = setting :floors, 60` — **what this build was told**, for a game that comes in several cuts: which floors are in it, where the player starts, which screen it boots on. The default is on the same line; a setting with no default has to be given. It is a value while the game is BUILT, a plain Ruby value like the numbers a game works its tables out from, not a variable the game keeps while it runs. It is handed to ONE build — `game.program(settings: { floors: 1 })`, `game.build_rom(settings: …)`, `RubyGBA.build(…, settings: …)`, `ruby-gba build game.rb --set floors=1`, or `write_if_main(settings: …)` on a game file's last line — so a test builds a one-floor cartridge beside a sixty-floor one, on another core at the same moment, and neither sees the other's. That is why it exists: reading the environment from inside the game's block reads something the whole process shares. The command line can only give text, and text is read as the kind of thing the default is (a number, a name, `true`/`false`); a setting with no default arrives as given. Three friendly errors: a setting the build gave that the game never asks for (a name spelled two ways would otherwise build the default and look right), a setting with no default that was not given (naming what was given instead), and text that cannot be read as its default's kind. Where a game still wants the environment, the line that builds it is the place to read it: `write_if_main(settings: { floors: ENV.fetch("FLOORS", "60") })`.
- `wait_vblank` — wait for the safe window to draw. A `game_loop` already does this each pass, so you only write it in a program that has no game loop, or under `frame_sync: :manual`.
- `halt` — stop (branch to self). `debug_halt` — truncate the ROM here (bisecting).

## Drawing (Mode 3, direct color)

- `pixel x, y, color` — one pixel (fixed coords).
- `fill_rect x, y, w, h, color` / `dma_fill_rect x, y, w, h, color` — a filled rect (fixed, even w).
- `draw_rect_at xpos, ypos, w, h, color` — a rect whose **position and size** the game can all work out as it runs (each of `xpos`/`ypos`/`w`/`h` may be `:var`/`Value`). That's the bar-or-column shape: a health meter that empties sideways (`draw_rect_at 8, 8, health, 6, :red`), a wall column in a first-person view, a tower that grows. A width or height of 0 or less draws nothing, so a bar can empty without a test around it, and **any width works — odd included** (unlike `fill_rect`/`dma_fill_rect`, which still want an even one). A size fixed when you write it costs exactly what it always did. **Say how tall it usually is:** `estimate: { usually: 44 }` (or a range) — the same hint `draw_column_at` takes, for the same reason and with the same rules, because the two are the two ways to draw a wall as tall as the distance says. It changes **nothing** about how the game runs, and nothing reads it today — it was written for a build-time estimate that has since been deleted in favour of measuring the game. It stays as documentation of intent: a height that comes out of perspective is most of what such a game costs, and `examples/raycaster.rb` says 44, which is what its walls measure. Saying it on a height you wrote as a number is a friendly error, because that one is already known.
- `draw_column_at :picture, slice:, x:, top:, height:, width: 1` — **one column of a picture, stretched to a height the game works out**. `width:` is how many pixels ACROSS the strip is (a number you write, 1 by default), and a view whose strips are wider than a pixel wants it rather than a loop of its own: every pixel of a strip shows the same picture column at the same height, so **one walk down the screen fills all of them** — calling it once per pixel works the same answer out that many times over, and measures about three times dearer for a three-pixel strip. This is what a first-person view is made of: for each strip across the screen, work out how far away the wall is, turn that into a height, and draw a column of wall that tall — near walls tall, far walls short. `slice` picks which column of the picture (which part of the wall you are looking at), `x` is where it lands on screen, `top` and `height` are where it starts and how tall it is; all four can be worked out as the game runs. A height of 0 or less draws nothing and anything past the top or bottom is clipped, so a wall you are nose-to-nose with needs no test around it. **Many textures fit in one picture**: `slice` is a runtime value, so lay the wall pictures side by side and `slice` becomes `which_wall * width + column` — no runtime picture choosing needed. Also what a scaled sprite is (a thing that grows as it nears you), and a door sliding open. **A see-through picture costs the rows that hold pixels, not its height.** A scaled sprite is mostly nothing — a lamp in a square of ceiling, a clip of ammunition in a square of floor — and the framework works out, for each column of such a picture, where that column holds pixels, then walks those and skips the rest. So a picture nine tenths empty costs about a tenth, and there is nothing to write for it: leaving the empty rows in is free, and cropping them away saves no time at all. Any picture up to 256 rows tall gets this. One taller walks every row instead, and `rom.profile` names it, says why, and says what to change. Horizontal is not this verb; a row stretched across the screen would be its sibling. **Say how tall it usually is:** `estimate: { usually: 40 }` (or a range) — the same hint a `list`, a `pool` and a loop that stops early take, and like those it changes **nothing** about how the game runs. Nothing reads it today — it was written for a build-time estimate that has since been deleted in favour of measuring the game — and it stays as documentation of intent: a height the game works out is exactly what perspective produces, so this is every column of a first-person view and therefore most of what such a game costs. Saying it on a column whose height you wrote as a number is a friendly error, because that one is already known.
- `clear_screen color` — whole screen, one DMA.
- `inside x, y, w, h do … end` — **everything the block draws stays inside that part of the screen**, and what falls outside is CUT OFF rather than covered up: those pixels are never worked out. That is the difference worth having, because a game with a panel — a strip of world with numbers under it, a map beside it, a letterboxed cut scene — would otherwise draw the world over the whole screen and paint the panel on top, having paid for every pixel underneath it. In a first-person view, where a wall you stand close to is drawn taller than the screen, that is most of a near wall: measured over a floor of Wolfenstein with a 32-row bar, one row in twelve was drawn and then covered. It **clips, it does not move**: a pixel drawn at (10, 10) is at (10, 10) whatever area is in force, so an area goes round drawing that already works and only what was falling outside changes. `clear_screen` inside one clears the area rather than the screen, which is what you meant. Drawing after the block is untouched by it — that is where the panel goes. The edges are settled while you write the program (where a panel goes is part of how a screen is laid out, not something a game works out as it runs — a computed edge is a friendly error), and areas do not nest (a friendly error too). Calling a `func` that draws from inside an area is a friendly error too: the routine is built once, for wherever it's called from, so it can't carry one call site's clip along with it — put the `inside` block inside the routine itself instead. Bitmap screens; on `screen :tiled` the console composes the picture and a `layer` is how depth is said.
- `camera x, y` — move the visible window over the whole picture (`camera 0, 0` = as drawn). Nothing is redrawn — the picture stays put and the window moves — so it costs the same whatever is on screen. Where the window falls off the picture, the backdrop shows along that edge. Bitmap screens only (on `screen :tiled`, scroll a `background` instead).
- `camera_follows hero, across: world` (also `at: [120, 80]`, where the character stands in the world) — the follow-you camera almost every adventure game uses: the character stays where it is on screen and the world slides underneath. Call it once where the sprite is declared; wherever the sprite is standing then is where it stays (pair it with `sprite.center_on_screen` for the middle, or put it low for a platformer). **What it changes is more than a line saved:** without it a game whose world is bigger than the screen has to keep the character's world position in variables of its own, so the character is a pair of numbers rather than a sprite and none of the sprite verbs reach it. With it you write `hero.move :right` like any other sprite and the world moves instead — so facing, walk cycles and poses all work. What does *not* line up is anything that reads the character's position as a place in the WORLD (`blocked_by`, `overlaps?` against something placed in the map), because its position is where it sits on the screen. Needs `screen :tiled` (a bitmap picture *is* the screen — use `camera`) and a `game_loop`. Worked example: `examples/hero.rb`.
- `fade :black` / `fade :white, 50` / `fade :black, 0` — fade the whole screen toward black or white. The second argument is how far, 0 (as drawn) to 100 (nothing but that color); it defaults to 100. Nothing is redrawn — the picture is still there and comes back untouched — so it costs the same however much is on screen, and it works on **either** kind of screen (unlike `camera`). It sets the level where you call it; to fade over time, move a variable and pass it (`fade :black, level`). A full fade left un-lifted is a friendly warning. In a game with a **see-through layer** it leaves that layer alone: the water goes on showing the floor underneath it and the whole picture — water, floor and the mix of the two — darkens together, which is what a fade out should look like. What it costs to get that is the one thing worth knowing, and it is the only case where a fade is not free: such a game's fade moves the *colors themselves* rather than asking the display to darken what it draws, which is a blend per color the game declared — never per pixel on screen — and **only on a frame where the fade actually moves**, so holding one still, or holding it at 0, costs a single check. That is the same price `tint` pays on a tiled screen, for the same reason, and `rom.profile` says so beside the layer it bought. A plain `screen :bitmap` in such a game has no colors to walk, so while one is up the display fades it, free and in its own 17 levels; a fade still in force when the game changes screen carries on in the next screen's way, as a tint does. A game that sees through no layer keeps the free one and draws exactly the same picture, so nothing about the choice reaches the author and the report has nothing to say about it. The one fade that cannot take the colors route is a **placed** one — see `under:` below. **How many levels a fade has**: the display's own fade counts in sixteenths, so it has **17** from the picture to the color, and a fade walked over more frames than that shows some of them twice — the picture changes every other frame. **An amount that holds a fraction** (`fade :black, 37.5`, or a variable declared with one) is still a percentage, and it asks for finer steps: on a screen drawn through a color table (tiled, rotozoom, tear-free) such a fade moves the colors themselves in thirty-seconds, **33** levels, one a frame over a fade twice as long — which is how the console's own games fade. That costs what the see-through route above costs, a blend per declared color on each frame the fade moves. A whole-number amount keeps the 17 on every screen, the plain bitmap screen has no table to walk and keeps them whatever it is given, and so does a placed fade. `tint` takes a fraction the same way.
- `fade :black, 100, under: :ui` — **put the fade at a place in the stack** instead of over everything: it names a layer, and that layer and everything in front of it are left as they are while everything behind it fades. "Fade the game out to the game-over screen and keep the score showing" is one word, and it is why a stack is worth naming (see Layers). Needs `screen :tiled` and the layer has to be one you declared — a bitmap screen paints the whole picture into one place before the display sees it, so there is nothing left there to tell apart (friendly error). Something that named no layer is never on the kept side. **This is the one member of the fade family that is not always free:** where the line falls between the *sprites* — a HUD kept out of a fade that reaches the player — the framework holds the fade off each kept sprite one at a time, which costs a sprite slot and a table write per frame for each. A line that falls between two *backgrounds*, or that keeps every sprite (`under: :actors` — fade the scenery, keep everything that moves), still costs nothing at all. **It is also the one fade that still takes a see-through layer's blend**, and that is not a gap waiting to be filled: putting the fade at a depth is something only the display's blend unit can do — it can hide a brightness change from what sits in front of a line — where moving the colors themselves reaches everything that draws from them and has no notion of who is reading. So a game that places a fade AND sees through a layer gets the layer solid until the fade lifts, and a friendly warning at build time saying so, because neither verb mentions the other. The way round is the plain whole-screen `fade`, which keeps the layer. For the same reason **a placed fade keeps the display's 17 levels** and never gets the 33 a fraction asks for, so a long one changes the picture every other frame; `rom.profile` says so for a game that asks.
- `fade :black, 100, inside: [0, 0, 240, 128]` / `fade :black, 50, outside: [60, 40, 120, 80]` — **hold the fade to a rectangle of the screen**, `[x, y, width, height]` in pixels: `inside:` fades the rectangle and leaves the rest as drawn, `outside:` fades everything but it. The view of a first-person game faded with its status bar left alone, a pause box kept bright over a dimmed game. It is the one way to keep part of a **bitmap** screen out of a fade, since `under:` needs layers and a bitmap screen has none; it works on every screen. **It costs what a whole-screen fade costs**: the display has windows — rectangles it is told about — and switches its darkening on in one part and off in the other as it draws, so a few register writes where the fade is said and nothing per pixel. The rectangle is numbers you write (a rectangle the game works out is a friendly error), held to the screen, and one with no width or height holds nothing. Each `fade` says where it reaches, a plain one included, so the last fade said is the one in force, and a `tint` after a held fade reaches the whole screen. `fade_out` and `flash_screen` take the same words the way they take `under:`, said once for the game's one screen fade, and a plain `fade_in` comes back in the same place (`fade_out inside: [0, 0, 240, 128]`, then `fade_in`). What it gives up, because it is the display's own fade: **every fade in a game that holds one is the display's**, so a fade with a fraction keeps the display's 17 levels rather than walking the colours in 33, the same trade a placed fade makes. Friendly errors: `inside:` and `outside:` together, either beside `under:`, a rectangle that is not four whole numbers, a screen fade to a colour other than black or white held to a rectangle, two different rectangles for the screen fade, and a game that holds a fade and also has a light, a see-through layer, or a fade placed with `under:` (each of those needs the same window or the same blend). Worked example: `test/ruby_gba/builder/test_fade_held_to_area.rb`.
- `tint :red` / `tint :orange, 30` / `tint :red, 0` — tint the whole screen toward **any** color, which is the part `fade` cannot do: red for damage, blue for cold water, orange for a sunset. Same second argument as `fade` — how far, 0 (as drawn) to 100 (nothing but that color), defaulting to 100 — and the same bargain: nothing is redrawn, the picture is all still there, and it comes back untouched when the tint lifts. It sets the level where you call it, so tinting over time is a variable moved a little each frame (`tint :red, hurt`). A full tint left un-lifted is a friendly warning. Works on **every** screen, and a tiled one tints the scenery and the sprites together. **What it costs depends on the screen**, and that is the one thing to know: the plain `screen :bitmap` is free, like `fade`, because it holds a whole color in every pixel and the display mixes the tint in as it draws. `screen :bitmap, tear_free: true` is NOT, although it is one word away: it holds a number per pixel that picks a color out of a shared table, the same as `screen :tiled` and `screen :rotozoom`. Those three draw every pixel through that table, so the framework moves the table instead — a blend per color the game declared (never per pixel on screen), and **only on a frame where the tint actually changes**, so holding one still, or holding it at 0, costs a single check. It also stores that table in the cartridge unpacked, a few bytes more, because the blend reads the original colors from it one at a time. A tint and a fade are one effect on the display, so the last one you set is the one in force.
- `fade_out` / `fade_in` / `flash_screen` — the same fade walked over time, which is what a scene change and a hit flash both are. `fade_out` (`:black` by default, or `:white`; `frames:` / `duration:` in seconds, half a second by default) darkens the screen to nothing over that many frames; `fade_in` brings it back, and with **no arguments at all** it returns in the same color at the same speed, so a scene change is two words and no bookkeeping. `fade_in` is the only one that takes the speed of what came before: a `fade_out` with no length is always half a second, so a quick flash before it cannot turn the next scene change into a blink. `flash_screen` (`:white` by default) is the same thing in a hurry — full on the first frame, then falling back over six frames unless it says otherwise, whatever fade ran before it — for a hit, a score, a life lost; pair it with `shake_screen`. Call each once at the moment it happens; the framework walks the level every frame from there, and stops working entirely once the screen settles. **Any color works** — `flash_screen :red` for damage is the one a game reaches for most, and `fade_out :red` is a redout for a death. Black and white are a brightness change (`fade` underneath); every other color is mixed in (`tint` underneath), so on a screen drawn through a color table a colored one costs what that many colors cost while it is moving. A black or white one costs that too in a game with a **see-through layer**, and for the same reason, except on a plain `screen :bitmap`, which the display fades for nothing — see `fade` above, where the whole bargain is written out. Nothing is redrawn in any of those cases, so it costs the same however much is on screen and works on **either** kind of screen. **A long fade steps every frame**: when any fade in the game takes more than 17 frames — the default half second does — the level is handed to `fade` with its fraction, so on a screen drawn through a color table it walks the colors in 33 levels rather than repeating the display's 17 (see `fade`). The screen is fully faded, and fully back, on the same frames either way. A game whose fades are all 17 frames or shorter keeps the display's free fade, and `rom.profile` says which a game got. `fade_out` and `flash_screen` also take **`under:`** and place the whole game's fade in the stack the way `fade` does (`fade_out under: :ui` — dim the game, keep the HUD; `fade_in` then brings it back with nothing to repeat). A game has one screen fade and it sits in one place: two different layers is a friendly error, because the console has one set of blend registers and two fades at two depths cannot both be in force. A **colored** fade cannot be placed at all (the console can hide only a brightness change from what sits in front of it), so a game that says both is a friendly error whichever order it says them in. Two friendly warnings: a `fade_out` with no `fade_in` anywhere leaves the game running behind a flat screen, and a fade with no `game_loop` has no frames to run on. Worked examples: `examples/pong.rb` (`flash_screen :red` when the cpu scores), `examples/breakout.rb` (a red flash on losing a life, a fade between scenes) and `examples/shmup.rb` (`fade_out under: :ui` — the field and the ships in it go dark on the way to the game-over screen and the score stays readable).
- `fade_level` → a `Value`: how far the screen is faded right now, 0 (as drawn) to 100 (nothing but the color). This is what makes a **scene change** writable, because fading out leaves the screen dark on purpose — so whatever you draw next is invisible until something lifts it, and the switch has to wait for the fade to arrive: `(fade_level == 100).then { state.set! GAME_OVER; fade_in }`. Swap screens while nobody can see it and the player sees one smooth dip to black and back. A value rather than a yes-or-no, so half way through is a place you can act too.
- `pixelate 8` / `pixelate 1` / `pixelate 6, under: :ui` — show the screen in flat blocks, which is the pixelate effect of a scene change, a hit, a dream, a teleport. The number is **how many pixels a block is each way**: 1 is the picture as drawn, 8 is blocks of eight by eight, and 16 is the biggest the console draws. A size you write outside 1 to 16 is a friendly error, one the game works out is held to 1 and 16, and a number that holds a fraction is a friendly error too (use `.to_i`). Nothing is redrawn — the console does it as it draws, so the picture is all still there and comes back untouched at `pixelate 1` — and it costs the same however much is on screen: one register write where you call it, and nothing on a frame you do not. It sets the size where you call it, so pixelating over time is a variable moved a little each frame (`pixelate blocks`); in a game too slow for its frame, a size said after the console has begun drawing shows from the row it had reached, for that one frame. It works on **every** screen, and it is the one effect of this family that reaches a `screen :bitmap` picture the game paints for itself, sprites and text included, since to the console that whole picture is one layer. **The blocks are fixed to the screen, not to the picture**: a block starts at every column and row that is a multiple of the size and shows the colour its top left pixel would have had, so a background that scrolls slides under a grid that stays still, and the picture shimmers as it moves. **Each layer and each sprite is put into blocks by itself**, before they go over one another, so a block of a front layer whose corner is see-through shows the layer behind all the way across. **A sprite's blocks have edges worth knowing**: a block that starts off its left or top shows the sprite's own first column or row, its last block across runs on past its right edge to the end of that block, and nothing is drawn below its bottom edge — so a sprite in big blocks sits a little to the right of where it stood. Text on `screen :tiled` is a small sprite for each character, so it goes into blocks too, a letter at a time, and at a big size a line of it is mostly gone. **`under:` leaves part of the picture sharp**: it names a layer, and that layer and everything in front of it stay as drawn — pixelate the game and keep the score readable. That is free here where a placed `fade` is not, because the console keeps "drawn in blocks" as a switch on each background and each sprite; the price is that those switches are set as the cartridge is built, so **a game pixelates from one place**, and two different `under:`s (or one with and one without) is a friendly error. `under:` needs `screen :tiled` and a layer you declared, like a placed fade. A fade or a tint is done to the finished picture, so either can be in force with blocks at once — with one mix refused: a fade placed so that it keeps some sprites and fades others, while one of the kept sprites is in blocks. The console keeps a sprite out of a fade by the shape it was drawn in, and a sprite in blocks has another shape, so that is a friendly build error saying to give `pixelate` the same `under:` as the fade. **One size is not what its number says**: a background that turns (`rotate` / `scale`) is left a single pixel wide at `pixelate 2`, so its rows double and its columns do not. That is the emulator the picture is checked against; from 3 up it is in blocks both ways like everything else. Worked example: `test/ruby_gba/builder/test_pixelate.rb`.
- `pixelate_out` / `pixelate_in` (both take `frames:` or `duration:` in seconds, half a second by default; `pixelate_out` also takes `under:`) — the same effect walked over time: the picture breaks up into bigger and bigger blocks until they are the biggest there are, and comes back together. The pair to `fade_out` / `fade_in`, and said the same way: call each once, at the moment it begins, and the framework walks the size every frame from there, then stops working once it arrives. `pixelate_in` with no length comes back as fast as the picture last went out, so a scene change is two words. Calling either while a walk runs turns it round from where it is. There are sixteen sizes, so a walk longer than sixteen frames shows some of them for more than one. `under:` places the whole game's pixelate, as on `pixelate`, and holds for both verbs. Two friendly warnings: a `pixelate_out` with no `pixelate_in` anywhere leaves the game running in blocks too big to read, and a walk with no `game_loop` has no frames to run on. Worked example: `examples/meadow.rb`, whose cabin door pixelates the room and the hero out and back in and keeps the room's name sharp with `under:`.
- `pixelate_size` → a `Value`: how big a block the walk has on screen on this frame, 1 (as drawn) to 16 (a size a game sets itself with `pixelate` is not read back here). This is what makes a scene change by pixelating writable, the way `fade_level` does for a fade: the picture is hardest to read at the biggest block, so that is the moment to swap what is drawn — `((leaving == 1) & (pixelate_size == 16)).then { state.set! NEXT_ROOM; pixelate_in; leaving.set! 0 }`. **Keep a flag of your own in that test**: the size reads 16 on the old scene's last frame and again on the new scene's first, which is what puts both in the biggest blocks, so a test on the size alone is true twice. Worked example: `examples/meadow.rb`, where walking through the cabin door swaps the room at that moment.
- `light = spotlight at: [120, 80], radius: 40, dark: 75` → a `Spotlight`: **a light** — the picture as drawn inside a circle and darkened everywhere outside it. A lantern in a cave, a torch in a dungeon, a searchlight. `at:` is where its middle starts, in screen pixels, `radius:` how far it reaches, and `dark:` how dark the rest is, 0 (as drawn) to 100 (black), 75 if not said. All three are where it STARTS, applied once at power-on like a `var`'s value; the handle's `x`, `y`, `radius` and `dark` are `Value`s the game changes, and `light.move_to x, y` moves it (`light.move_to hero.x + 4, hero.y + 4` every frame is a lantern). The picture shows what they hold at the end of the frame. **It is the console's own hardware, and nothing is redrawn**: the display has windows, and darkens the picture outside one as it draws. A window is a rectangle, so the light is that rectangle given a new left and right edge on every row of the screen, worked out in the gap before each frame from a table of half widths and handed to the display a row at a time by a copying engine — the same one `scroll_each_row` rides, so a light and up to two bends fit the three engines there are, and past that the line interrupt carries them all. What it costs is that per-row working out, the same however much is on screen. **`spotlight` with nothing after it hands back the game's light**, and a game with none gets one that reaches past every edge and darkens nothing, which is how `iris_out` finds it. A game has one light: a second `spotlight` is a friendly error, and so is one declared after an `iris_out` gave the game a light. **It shares the screen with a plain fade**: a game with a light fades by walking its colours, so the whole picture fades and the light's darkness stays on outside it. Friendly errors: a light on any screen but `screen :tiled`, or in a game that shows one (a bitmap screen has no layers to darken around a light, and the turning-background screen's window is not switched on, so the whole screen would go dark), `spotlight at:` with no `radius:`, beside a see-through layer or a fade placed with `under:` (each needs the display's one blend), with no `game_loop` (no frame to work it out in), and a start that is not numbers in range. The darkening is the emulator's to the bit: it works a channel out at eight bits, so white three quarters dark is red 8, green 7, blue 7. Worked example: `examples/cave.rb`.
- `iris_out` / `iris_in` / `iris_shut?` — **the iris: a circle closing on a point until the screen is black, and opening again.** The pair to `fade_out`/`fade_in` and `pixelate_out`/`pixelate_in`, said the same way: call each once, at the moment it begins, and the framework walks it every frame (`frames:` or `duration:` in seconds, half a second by default). `iris_out at: [hero.x + 4, hero.y + 4]` closes on that point; left out, on wherever the light is. It closes **the game's own light** — the display has one — and `iris_in` gives that light back as big and as dark as it was, so a lantern comes back a lantern; `iris_in dark: 0` (and `radius:`) opens onto another light instead, out of a cave into daylight, and onto a light that darkens nothing the circle opens on past the corners rather than stopping at the lantern's size. `iris_in` with nothing closed before it starts the screen black and opens, which is how a game opens on an iris. A game with no `spotlight` is given one that darkens nothing, so the iris is all a game needs to write. The walk runs between nothing and about the screen's farthest corner from the point (never short of it, at most an eighth past), so the circle is seen moving from its first frame. **While it runs it owns the light's radius and darkness**: a game that sets those itself every frame undoes it, so move only the light's place, or set the rest when `iris_shut?` is false and no walk is under way. `iris_shut?` holds from the frame a walk out arrives until the next `iris_in`, which is the moment to swap the scene: `((leaving == 1) & iris_shut?).then { room.show_map :meadow; iris_in; leaving.set! 0 }` — keep a flag of your own in that test, as with `pixelate_size`. An `iris_out` with no `iris_in` anywhere is a friendly warning. Worked example: `examples/cave.rb`.
- `pulse sprite, to: 1.3` (also `from:`, and `over:` in seconds — one full round trip, 2.0 by default) — a sprite that breathes: it grows to that size, shrinks back, and keeps doing it. A collectable that begs to be picked up, a boss winding up, the selected item on a menu. Call it once where the sprite is declared; the framework runs the rhythm every frame from there, and calling it again on the same sprite replaces the rhythm rather than adding a second one. Tiled sprites only (it is built on `sprite.scale`), and it needs a `game_loop` — a friendly warning otherwise. Worked example: `examples/bird.rb`, where the bird drifts nearer and further.
- `keep_showing :status_bar do … end` → a handle for **a picture that is drawn when it changes and then left alone** — a score, a health bar, a GAME OVER banner. Most of a game is repainted every frame and wants none of this; a picture that changes now and then is far cheaper left there, and **on `screen :bitmap, tear_free: true` leaving it there is the thing that goes wrong**. That screen keeps TWO pictures and shows them in turn (which is what stops a player ever seeing a half-drawn one), so a change painted a single time reaches one of the two and the figure then flickers between the new value and the old, half the frames each. Say when it changed and the framework paints it once per picture the screen keeps. Three words on the handle: `.changed` at the moment the thing it shows moves (the score goes up, the game ends), `.draw` every frame at the point in the drawing order where the picture belongs, and `.cancel` where the thing it showed is put back (a new game starting over a finished one), which drops any paints still owed so a banner cannot follow the old game into the new one. **The same game code is right on a plain screen**, where one picture means one paint — nothing in the program says which screen it is on, so a game moved to `tear_free: true` keeps working and the flicker never appears. A frame with no change outstanding costs one comparison and draws nothing. The block is built into a routine of its own, so a picture painted from three places costs its code once; declare it where the picture belongs (top level, or inside the `scene` that owns it). Declaring the same name twice, or leaving out the name or the block, is a friendly error; declaring one and never calling `.draw` is a friendly warning, because then the picture never appears at all. **What it cannot do is repeat a moving sequence** — it paints the *same* picture again, so a dissolve or a trail (different pixels every frame) needs its own answer, and the Wolfenstein port's `lib/wolf3d/dying.rb` shows one: two walkers a frame apart.
- `shake_screen intensity: 3, frames: 8` (or `duration: 0.2` for seconds) — shake the screen on impact. Call it once at the moment of the hit; the framework jitters the camera every frame from there and puts the picture back exactly where it was. Calling it again mid-shake restarts it. Needs a `game_loop` (that is what gives it a frame to run on).
- `grid :name, cols:, rows:, cell:, over:` → a `Grid`: `set_cell cx, cy, color` / `clear_cell cx, cy` (cell coords; `over:` is the background).

## Images & sprites

- `image :name, "." => :transparent, "#" => :red do <<~ART … ART end` — ASCII art; or `image :name, width:, height:, data:` / `from: "file.png"` (file paths resolve next to your script).
- **A picture drawn from few colours costs half the video memory, and there is nothing to write for it.** The console holds a picture's pixels one of two ways — a whole number each, out of a table of 256 colours, or HALF a number each, out of sixteen — and half a number is half the memory for the same picture drawn at exactly the same speed. Sixteen sounds crippling and is not, because they are not the same sixteen for every picture: the table is read in groups of sixteen and a picture says which group it draws from, so two pictures can have sixteen colours each and share none of them. So the framework counts the colours in each piece of art and decides. **Fifteen or fewer and it halves** (the sixteenth is the see-through one); more and it is stored the way everything was before, out of the whole table, and the two kinds sit side by side in one game. It is worth knowing only because the two budgets it spends are fixed and small — 32K holds every sprite picture a screen can show, and one block holds every background tile — so **twice as much art fits**, and `rom.profile` says how much of each is left and how much of that the halving bought back. Pac-Man's sprites more than halved, from 5K to 2.5K. On the tile side it is the difference between 256 distinct 8×8 tiles for a whole game and 512.
- **A sprite's poses are stored at their own size, not the biggest one's, and there is nothing to write for that either.** Poses are drawn on one canvas, big enough for the widest frame — a sword swing, a jump — and most frames use a fraction of it. Every pose used to cost the canvas's size, because a sprite reads a run of tiles one after another and cannot share the blank ones the way a background shares a repeated tile. Each is now cut down to what it actually draws, and the offset comes with it so **the picture does not move**: the character's origin is the canvas's corner, which is where you put the sprite. Measured on a cycle drawn 64×64 whose character covers 24×32, four poses went from 8192 bytes to 4096, ten from 20480 to 10240, and a twenty-frame cycle that would not build at all came to 20480 and fits. Poses that come out the same size keep the plain draw; poses that genuinely differ carry a word each — which tiles, what shape, what size, how far along — read once a frame, which is what lets such a cycle be stored frame by frame instead of all at the largest. A sprite that **turns or resizes** is not cut down, and that is about being right rather than easy: the console spins an object about the middle of its own box, so trimming would move the pivot.
- **A part one pose shares with another is stored once, and nothing says so.** Most of a character does not change between two frames of a walk — the head, the torso, the arm that is not moving — and since a pose is stored as pieces, each naming its own tiles, the pieces that did not change are stored one time and every frame points at them. **This is the one saving a game written straight against the console cannot have**, which is worth knowing because everything else here merely spares you the bookkeeping: an object reads tiles one after another, so by hand every frame has to be its own run and a part that stood still is kept again in each. Two whole poses that are the same picture are the easy case of the same thing — a ping-pong cycle written `frames: [:a, :b, :c, :b]` costs three pictures rather than four, and a four-way character whose rest frame is the same in every direction keeps it once instead of four times (Pac-Man's chomp went from 1024 bytes to 640 on exactly that). **What it is really for is the big pictures**, where the same walk cycle can be the difference between building and not: eight frames of a 96×96 creature whose torso stands still came to 26K where the console holds 32K, and it needed 36K before — it did not build at all. Nothing in the program says which parts are shared, so `rom.profile` is the only place the number appears. **What it costs** is nothing to write and, for most sprites, nothing at all: a cycle whose frames are all the same picture, and a cycle where nothing repeats, are drawn exactly as before. A cycle where SOME pose repeats moves onto the per-pose word described above, which measured 12 instructions a frame — against at least one whole pose of picture memory, which is a wall a build hits rather than a frame anybody can see.
- **A character with more frames than sprite memory holds keeps one frame there at a time, and there is nothing to write for it.** Every picture a sprite can show normally sits in the console's 32K of sprite memory from the moment its scene starts, which is the fast arrangement — showing the next frame is pointing at different tiles — and every sprite gets it while the pictures fit. A character with a full set of animations can fill that on its own, though: Link in The Minish Cap is a resting pose and a ten-frame walk and run in three facings, the fourth facing the third one reversed — 63 stored pictures, 32,256 of the 32,768 bytes — and then not one enemy fits beside him. So when the pictures do not fit, the build picks the sprite with the most memory to give back and gives it room for ONE frame instead; whenever the frame it is showing changes, that frame is copied in out of the cartridge before the sprite is drawn. More are picked until everything fits. That is how the console's own retail games put a full cast on screen. Sprites showing the same pictures — every slot of a `pool` — are weighed together, since keeping one of them to a frame gives nothing back while the others still show the set, so a pool keeps its pictures whole unless keeping every slot to a frame is worth more. **What it costs** is that copy — one frame's worth of tiles, and only on a frame where the pose changed, so a sprite holding still copies nothing — against a wall a build otherwise hits. A sprite that always shows the same picture has no frames to give back, so a screen of still pictures that do not fit is still the friendly error, naming the biggest.
- **A sprite can be BIGGER than any picture the console draws, and it is still one sprite.** The console has twelve rectangles and the largest is 64×64, so a boss, a vehicle, a large creature, a title-screen character had to be built by hand out of several `sprite` handles the game then moved in step — real bookkeeping, easy to get subtly wrong, and exactly the machinery this framework exists to manage. Nothing about the hardware asks for it: several of those rectangles standing shoulder to shoulder look exactly like one big picture. So **write the picture at the size you drew it** — any whole number of tiles, up to 256 each way — and the framework works out how to cut it up, keeps the pieces together and draws them at one depth. It **moves, faces, animates and collides as one thing**, because it is one: `move`, `face`, `frames:`, `overlaps?` and the screen-edge tests all read the sprite's own position and its whole picture, and `mirror` reflects it about the picture as a whole so a character facing the other way does not turn inside out. The cut also **pays for itself in memory**, because a piece that draws nothing is not stored at all — a character is a ragged shape in a rectangular canvas, and one object has to keep every blank tile inside its own box: a 96×112 creature drawn on a 128×128 canvas came to 192 tiles against the 256 one box would have cost. **What it spends is sprites**, since the console draws 128 at once and each piece is one of them — that creature costs six, and it costs six sprites' worth of drawing too (a piece measured 37 instructions a frame against 32 for a whole small sprite). The framework weighs the two off against each other: a place in that table of 128 is worth about eight tiles, being about the same share of what there is, so a finer cut is only taken when the blank it drops pays for the places it spends. `rom.profile` says how many each sprite came to and how many are left. **A picture the console can already draw stays one sprite**, so nothing about an ordinary one changes; and a picture it has no size for but that fits inside one — 24×24, 48×48, sizes that used to be a build error — is one sprite too. Two things a big picture cannot do, both friendly errors naming it: it cannot **turn or resize** (the console spins each object about its own middle, so the pieces would pull apart), and it cannot be over 256 pixels either way. Worked example: `examples/shmup/boss.rb`, a 96×48 cruiser that slides along the top, banks the way it goes by mirroring, dives at the ship and takes fire anywhere in its picture — three of the console's objects, in a game already spending them on enemies, a ship, a shot and a HUD.
- `image :link, from: "link.png", colors: [:transparent, :white, …]` — **art that came from somewhere that already decided its colours**: a picture pulled out of another game, or one an artist drew against a fixed set. The list is that set, in its own order, **the see-through one first** — which is how a palette exported from anywhere else on this console is laid out, so it drops straight in. Say it and the framework keeps that order rather than working one out; say nothing, which is almost always right, and it works one out from the art. It changes nothing about what is drawn. Three friendly errors, all raised at the line that wrote the picture: a list longer than sixteen, a pixel drawn in a colour the list does not hold, and a pixel sitting on the first entry and nowhere else in the list (the first entry means see-through, so it would not be drawn). A cartridge's palette often keeps a real colour in that first slot and draws the same colour from a later place; such a list goes in as it is, and those pixels are drawn from the later place. The list can also be one declared with `colors`, by its name — `colors: :sea` — whose first entry then means see-through whatever it was written as; that is how a background drawn from several lists says which is which (see `bg.draw_with`). All the pictures one sprite shows must be given the same list, or none given one — the console draws a sprite from one table. The same goes for all the pictures of one `pool`, since each of its things is a sprite that can show any of them. Pictures that disagree are a friendly error naming the sprite or the pool, on the interpreter as on the console; to give one thing colours of its own, give the pictures one list and tell it `draw_with` another.
- `image :link, width: 16, height: 16, colors: [...], places: [0, 1, 2, …]` — **the pixels as NUMBERS into that list rather than as colours**, which is the shape art lifted off another cartridge arrives in: a block of index bytes, and the palette they count into. Place 0 means see-through and every other place is a colour in the list. It draws exactly what the same art given as colours draws, and **the one difference is the reason it exists**: a list may hold the same colour at two places, and nothing but a place can tell those two apart. A palette taken off a real cartridge nearly always repeats one (two blacks, two whites), and `draw_with` swaps colours BY PLACE — so a picture that kept only colours has pixels that could have come from either place, and a list that gives those two places different colours would recolour half of them wrong. Art given as places is never in doubt, and it saves the conversion besides. Where a picture is stored the big way — a `screen :rotozoom` background, whose tiles read the one shared table rather than a list of sixteen — there are no two places to keep apart in the first place, since a colour is a single entry there however often the list names it; the picture draws exactly the colours its places named. Five friendly errors, all at the line that wrote the picture: `places:` together with art drawn in characters, `data:` or `from:` (two ways of saying what a pixel is would have to agree, and nothing could check that they did), `places:` with no `colors:`, the wrong number of places for the size, a place the list does not hold, and a place the list is see-through at (only place 0 means see-through, so there would be no colour to draw).
- `tag = image :tag, from: name_list, width: 32, height: 8, colors: :ink` then `sprite :tag, at: [x, y]` and `tag.changed` — **a sprite's picture the game paints while it runs**: a name tag over a save slot, a portrait put together from parts, a number that floats up. It is the sprite side of `tiles ..., from: list` (see Tiled backgrounds) and works the same way: the pixels live in a `list ..., width: :byte` the game owns, packed the way the console keeps them, and `changed` shows them on the next frame. The picture's tiles are the list's 32-byte runs taken left to right and then top to bottom, which is the order one sprite keeps its tiles in, so a 32x8 tag is four tiles side by side and 128 bytes. It has to be a size the console draws a sprite at whole (8x8, 16x16, 32x32, 64x64, 16x8, 32x8, 32x16, 64x32, 8x16, 8x32, 16x32 or 32x64), since a painted picture is never cut into pieces; any other size is a friendly error listing them. It is kept whole and never shared with a picture that merely looks the same, and every sprite showing the same painted picture shows the same copy. It is the whole of its sprite: a sprite whose `facing:` or `frames:` puts it beside other pictures is a friendly error, and the way round is a sprite of its own for it. A scene that owns the sprite puts the picture up from the list as it is when the scene takes over again, and several scenes can each declare the sprite — `examples/hero.rb` keeps its map of the walk in the corner of the file screen too. It costs what painted tiles cost: one store for `changed`, one compare on a frame with nothing changed, one block copy of the picture's bytes on a frame with something. On `screen :bitmap` it is a friendly error, since a bitmap screen has `pixel` and `blit` for this.
- `colors :hurt, [:transparent, :yellow, :orange, :red]` then `hero.draw_with :hurt` — **a sprite drawn with a different list of colours while the game runs**: a character flashing warm while it cannot be hit, a poisoned enemy turning green, a team colour. `colors` declares a list no picture owns, laid out like a picture's own `colors:` list (see-through first, 2 to 16 colours), and the sprite is matched to it **by place**: a pixel drawn in the second colour of the sprite's list is drawn in the second colour of this one. So the shape and the shading stay exactly as drawn and only the colours move — nothing blinks and nothing is blended. It lasts until the sprite is told otherwise, and `hero.draw_with :own` is its own colours again. **One of several, by a number the game works out**: `hero.draw_with [:warm1, :warm2, :warm3, :warm4], showing: (frames >> 2) & 3` — the same `showing:` word `blit` and a menu row use — and a number outside the set is the sprite's own colours, so a value that ran off the end looks normal rather than wrong. Inside a pool's `each` it is per instance (`e.draw_with :hurt`), and an instance spawned into a slot starts in its own colours whatever the last one was doing. **The colours change on the frame the sprite's position and pose next do**, never a frame before or after, because on the console the choice is part of the sprite's table entry, written with them. **What it needs**: the sprite's pictures given a `colors:` list (art drawn in characters takes one too, beside the characters' colours; a sprite whose pictures come from `frames_from:`, `facing_from:` or `from_aseprite:` takes it once, `sprite ..., colors: [...]` or the name of a `colors` list, for every picture it imports), since a list swaps by place and a picture whose list the framework worked out has places nobody chose; a list at least as long as the sprite's own; and `screen :tiled`, since a bitmap screen keeps a whole colour in each pixel and has no list to swap. Each is a friendly error. So is one more, and it is the one worth knowing about before importing a palette: where the sprite's own list holds a colour at **two** places its art draws, and the list it is told to draw with gives those two places different colours, the build stops rather than recolouring half those pixels wrong — a picture stored as colours records no places, so nothing says which of the two a pixel came from. The error names both places, and the way round it is `places:` (above), which records them. **What it costs**: on the console, each different list takes one of the sixteen groups of colours sprites draw from (a sprite with its own colours takes one too, and two lists with the same colours share one), and running out is a friendly error naming the scene — a game with more sets of colours than groups puts them through one list with `recolor`, below. **The sixteen are one scene's, not the whole game's**: a sprite and a list declared inside a scene take their groups only while that scene is up, and that scene's colours are sent as it takes over (through any tint or fade in force, so its sprites never arrive at full colour on a dark screen), while the sprites every scene shows keep their groups throughout. A sprite told `draw_with` spends a read of which list and a few instructions a frame, and a game that never says it emits nothing new. A colour a picture's own list holds twice is drawn from its first place. Worked example: `examples/shmup.rb`, where the ship pulses warm while it cannot be hit and the boss does for a moment after each shot lands.
- `recolor :slot, :goblin` (also `recolor :slot, [:goblin, :bat, :crow], showing: room`, and `recolor :slot, :own`) — **a list of sprite colours that holds other colours while the game runs**, so one list dresses many different things in turn. `draw_with` picks which list a sprite reads, and every list it could pick takes one of the console's sixteen groups of sprite colours for as long as its scene is up — so an area whose things between them wear twenty sets of colours does not fit, though no one room of it shows more than a handful. This is how the console's own games get round that: the things in a room draw with a few lists that are **slots**, and walking into the next room says what each slot holds. Declare the slot with `colors` like any list (that is what it holds at power-on), tell sprites and pool instances `draw_with` it, and `recolor` says which colours it holds now: one other list, one of several by a number the game works out (the same `showing:` word), or `:own` for the colours it was declared with — which is also what a number outside the set means, so a counter that has run off the end looks right. `draw_with` and `recolor` can come in either order. **A list that is recoloured takes one group however many sets pass through it**, and however many sprites draw with it; that group is the list's alone, so a picture or another list with the same colours does not change with it. Every sprite and pool instance drawn with it shows the new colours **on the frame its position and pose next change**, the rule `draw_with` keeps, because both are written in the same gap between frames. It **says which colours the list holds**, the way `show_map` says which map is showing: once or every frame, from a branch or a scene, and the copy is made on the frame the answer changed and no other. The colours go in **through any tint or fade in force**, and a tint that moves afterwards moves the colours the list holds, not the ones it was declared with. **A list only one scene's sprites draw with has its group while that scene is up**: told to recolour while another scene is up, it shows the new colours when its own scene is back, and it still holds them after another scene, or a `screen :bitmap` scene, has been and gone. A list that sprites of several scenes draw with, or a sprite every scene shows, keeps one group throughout. **What it costs**, measured on the console: a list told the colours it already holds, about 40 instructions a frame, most of them the game's own line picking the number; a list told new colours, about 340 on that frame — so ten slots filled on the frame a room is entered are about 3,400, around a fortieth of a frame, with or without a tint in force. A game that never says it emits nothing new. **What a set needs**: a colour for every place the list itself has, since the sprites drawn with the list were checked against that many — a friendly error. Five more: a name that is not a `colors` list, several sets with no `showing:`, a list no sprite or pool draws with (a name spelled two ways), a set that would recolour a picture given as colours wrongly (the rule `draw_with` keeps about a colour at two places), and a background drawn with a list that is recoloured — `recolor` reaches sprites only, and a background has `draw_with ..., showing:` of its own for this. Worked example: `test/ruby_gba/builder/test_recolor.rb`.
- `mirror(:hero_right)` → **the same picture facing the other way**, as a picture name like any other — so it drops into `facing:`, `frames:`, a `pool` or a plain `blit` wherever a name goes. "Left is the right one, backwards" is how nearly every 2D game faces a character, and saying it used to mean drawing the art twice. Pass a list and get a list back (`facing: { right: WALK, left: mirror(WALK) }`), so a whole direction's frames turn round in one word. **On `screen :tiled` a mirrored pose costs no sprite memory at all**: the console draws an object reversed for nothing, so the build stores the picture once and says "that one, backwards". Measured on a character with an eight-frame walk drawn both ways, 256 tiles became 128 — and on a four-way character whose left mirrors its right, 320 became 240. **Nobody has to say so, either**: the sameness is judged on the pixels, so a game that drew its left-facing art by hand is noticed and stored once too, the same way two sprites showing the same picture already share it. What `mirror` saves you there is the art, not the memory. What it costs is on the drawing side and is small: a mirrored pose puts that sprite on the per-pose word described above, which measured 51 instructions a frame against 33 for the plain draw. Two things it does not do: a sprite that **turns or resizes** keeps both sets of pixels (the two attribute bits that reverse an object are the ones that name its rotation group once it is turning), and on `screen :bitmap` there is no such hardware, so a mirrored picture is drawn like any other. Naming a picture that is not defined is a friendly error. Worked example: `examples/hero.rb`, whose hero is drawn looking right and faces left by mirroring.
- `upside_down(:spike_up)` → **the same picture turned top to bottom**, which is `mirror`'s other way: `mirror` turns left to right, `upside_down` turns top to bottom. A reflection in water, a stalactite drawn from a stalagmite, an arrow that points up or down. It hands back a name, or a list for a list, exactly as `mirror` does, and the two compose: `mirror(upside_down(:arrow))` is the arrow turned both ways. Everything `mirror` says above holds for it: on `screen :tiled` the turned pose costs no sprite memory (the console draws an object upside down for nothing, and art drawn upside down by hand is noticed on its pixels too), it puts the sprite on the per-pose word, a sprite that turns or resizes keeps both sets of pixels, and `screen :bitmap` draws it like any other picture. Naming a picture that is not defined is a friendly error.
- `blit [:calm, :hurt, :dying], x, y, showing: damage` — **one of a set of pictures, picked by a number the game works out.** A face that watches you, a machine in four stages of wreckage, a dial drawn as a strip, a portrait picked by who is speaking. `showing:` is the same word a `menu` row and a two-colour `draw_text` already use for "this value decides which", and the number may be a variable or something worked out on the spot (`showing: hurt * 3 + look`). The pictures must all be the same size — one is drawn where the last was, so a smaller one would leave a bigger one's edges behind — and **a number outside the set draws nothing**, so a value still settling or one that ran off the end leaves the screen alone rather than drawing the wrong picture. It costs a test per picture, which is what writing it out by hand costs too — so for a set of a couple of dozen, consider laying them side by side in one picture and using `draw_column_at` instead, where which one to show becomes arithmetic rather than tests (that is what the Wolfenstein port's status-bar face does, and its comment says why).
- `blit :name, x, y` — draw an image at a runtime position (clips at edges). **On the tear-free screen** (`screen :bitmap, tear_free: true`) a solid picture draws too, with two rules that come from how that screen holds its pixels: it must start on an **even column** and be an **even number of pixels wide**. That screen takes two pixels at a time and will not take one, so a picture that starts or ends halfway through a pair cannot be copied in — the same rule `fill_rect` already lives by. Both are friendly build errors naming the number, and a column the game works out is fine as long as it can be *proved* even (`col * 2`), because a column nothing can prove is refused rather than drawn in the wrong place. A **see-through** picture there is a friendly error too (a solid one only, for now). It costs less than the same picture in direct colour — half as many units through the copying engine — and a tall picture costs more than a wide one of the same area, because every row is a copy of its own.
- **A sprite that never moves stops costing the frame anything, and nothing says so.** The console builds its picture from a table it re-reads every frame, and a row of that table stays exactly as it was last written — so a title screen's lettering, a border round the play area, a signpost in a room needs telling once and then never again. It used to be told on every frame like everything else, because nothing in a program says which of its sprites stand still. Now the build reads that off what the program DOES: a sprite is still when nothing that can run more than once changes where it is, which picture it shows, how it is turned or sized, or what colours it draws from. **What it buys is room in the console's quick memory**, which is the same 32K the framework keeps the frame's own code in, and which decides whether a whole frame runs about two and a third times faster or not — measured on `examples/shmup.rb`, the frame's code went from 10.8K to 7.7K and its work from 2951 instructions a frame to 2617; on `examples/dive` from 9.2K to 7.2K and 1469 to 1142. **It is judged pessimistically on purpose**: a sprite moved from anywhere at all — a scene, a routine, a timer's handler, a loop — keeps its per-frame write, and so does one whose position is worked out in a way the build cannot see through, one that keeps a single frame of its pictures in memory at a time, and one held out of a `fade … under:`. The one thing that may still change about a still sprite is whether it is SHOWN, since a sprite declared inside a `scene` is on screen exactly while that scene is; the frame asks that one question for every still sprite in the game together. A game that picks its scenes with two different variables gets none of this, and `rom.profile` shows the frame's size either way. **A sprite that DOES move, declared inside a scene, is written by a routine of that scene's own** rather than by the game loop's body — still in the gap after each frame, so nothing about which frame's numbers it shows changes. The game loop's body is the first thing kept in the quick memory, so a screen shown once used to take that memory from the scene the game is played in: a file-select screen's four sliding panels were 3K of code there. Now each scene's routine is placed like any other, by what a frame spends in it, and `rom.profile` lists it as "moving the sprites of scene :name". What it costs is one compare a frame per scene with moving sprites, and a call on that scene's frames.
- `sprite :name, at: [x, y]` → a sprite drawn each frame leaving no trail; the screen mode picks the kind. On `screen :bitmap` it's a software `Sprite` (save-under): `facing: {left: :img_l, …}` poses, `shown: false`, `hitbox:` (collision box — `:full` / an inset number / `[x,y,w,h]`; default is per-pixel collision, gated by the visible-pixel box), handle `x`/`y` (Values), `move(:left, by:)` / `move(dx, dy)`, `move_to`, `clamp_to_screen` (alias `stay_on_screen` — pin it fully on screen using its own size, no coordinate literals), `center_on_screen` (its sibling — put it in the middle, worked out the same way), `face`, `hide`, `show`, `overlaps?`, plus the screen-edge tests below. On `screen :tiled` it's a hardware (OAM) `HardwareSprite`, composited by the console: `x`/`y`/`move`/`move_to`/`clamp_to_screen`/`center_on_screen`/`hide`/`show`/`face(:left)`/`face_angle`/`turn`/`angle`/`overlaps?` handle plus `facing:` poses (the console swaps which uploaded picture it draws), and several stack in a stable order (later-declared in front, unless a `layer` says otherwise — see Layers; a `pool` with pictures stands among them where it was declared). Size must be an 8×8-tile multiple, up to 256 each way; one bigger than the console's largest picture is cut up for you (see above).
  - **Clearing the screen under a bitmap sprite is safe.** A bitmap sprite remembers the pixels it covers and puts them back as it moves, which is how it leaves no trail — and which would go wrong the moment the game repaints its field, for a new round or a change of scene, since what the sprite remembers is then a square of the picture that went. So `clear_screen` tells every sprite it is off the picture: nothing is put back, and the repaint before the next frame draws each shown sprite again over whatever the game painted after the clear — a wall drawn on the fresh field where the sprite stands is what it remembers from then on. A sprite declared before its field is cleared comes out right for the same reason. It is the WHOLE-screen clear that does this: a `clear_screen` inside an `inside` block clears that area and leaves the sprites alone, and painting over a sprite by hand (a `fill_rect` across it) is still yours to avoid, with `hide` before and `show` after. What it costs is a variable for each bitmap sprite, two stores a frame for each, and a store for each at every clear — 44 bytes of code a sprite, measured on `examples/sprite_mover.rb`. Clearing on EVERY frame is still the mistake it was, and still a friendly warning: the sprite is drawn in the gap before the frame and the clear wipes it straight after.
  - **Flipbook animation:** `sprite :name, at:, frames: [:f1, :f2, …], rate: N` (instead of `facing:`) cycles the same-size frames — one every N game-frames, timer hidden and managed — on either screen; composes with `move` (animate while moving). `facing:` and `frames:` are mutually exclusive (both drive the pose).
  - **A pose picked by a number the game works out:** `hero.face [:idle, :step1, :step2], showing: step` — the same `showing:` a `blit` and `draw_with` take, counting from 0, on either screen and on a pool's instance inside `each` (`g.face POSES, showing: g.state`). An animation step, a state, which variant of an effect: the pose a game wants is usually a number, and written as a test per pose (`(step == 0).then { hero.face :idle }` …) it is a few dozen bytes for every pose, which is how a character with a hundred frames ends up with kilobytes of code choosing one. This is the same few instructions whatever the number of poses: poses listed in the order they were declared are a sum, and any other order is read out of a small table built into the cartridge, one byte a pose. **A number outside the list leaves the pose as it was**, so a counter that has run past the last step holds the last one shown rather than jumping somewhere wrong. A list naming a pose the sprite was not given, one name with `showing:`, a number you wrote that is past the list, a name no variable has, a yes-or-no in place of a number, and a number holding a fraction are friendly errors.
  - **Directional animation:** give `facing:` a **list of frames per direction** — `facing: { left: [:walk_l1, :walk_l2], right: [:walk_r1, :walk_r2], … }, rate: N` — for a per-direction animation: the sprite runs that direction's cycle while it faces that way, so a character walks with its own cycle each way, or Pac chomps whichever way he moves (`examples/pacman.rb`). Every direction needs the same number of frames (two or more). The framework composes the facing and the frame into one pose for you (`face`/auto-facing `move` pick the direction, the hidden timer runs the frame). Works on both screen kinds.
  - **Import frames from a sprite sheet:** `sprite :name, at:, frames_from: "walk.png", tile: 16, rate: N, transparent: true` — slice one image file into equal-size frames (`tile:` is the frame size, a number or `[w,h]`) and cycle them; nothing to name or number. `transparent: true` honors a cut-out background. Path resolves next to your script. Mutually exclusive with `frames:`/`facing:`.
  - **Import directional poses from a sheet:** `sprite :name, at:, facing_from: "walk.png", tile: 16, dirs: [:down, :left, :right, :up], rate: N, transparent: true` — slice a four-way character's art from one file (the `facing:` counterpart to `frames_from:`). The sheet is a grid: each **row** is a direction (in `dirs:` order, top to bottom) and the **columns** of that row are its frames. One column = a still pose per direction (plain facing:, no `rate:` needed); several columns = a per-direction animation (feeds the directional-animation form above). `tile:` is the cell size, `transparent: true` honors a cut-out, path resolves next to your script. Mutually exclusive with `facing:`/`frames:`/`frames_from:`.
  - **A sprite put off the screen is off it, however far.** The console keeps a tiled sprite's row as one of 256 and its column as one of 512, and a place outside those is kept as a place inside them. Written straight against the console, a sprite parked at row 300 is drawn at row 44, and one that walks off the right edge and keeps going comes back in from the left. Here it does not: `enemy.move_to 0, 300` is a fine way to put a sprite away, a thing that flies off an edge never comes back, and each piece of a picture drawn as several is kept off by itself, so the far end of a big sprite cannot come round while the near end is on the screen. It works on a `pool`'s things too. **What it costs** is three instructions for the row and three for the column each time a sprite's place is written, none of them a branch (about nine for the row of the one tall box below) — measured on `examples/shmup.rb`, the frame went from 2999 instructions to 3025 — and nothing for text, whose places are written in the program. A sprite off the screen is still in the console's table, at its own place wherever the table can say it and at the first row below the screen or the first column right of it otherwise, so `v.sprites` in a test still finds it and still tells it from one the game hid. **One sprite can still show at the far edge, on both backends**: a sprite 64 pixels tall that *resizes* is drawn in a box of 128 rows about its middle, and the console counts only 96 rows past the bottom of the screen. So while its middle is 33 to 63 rows below the bottom edge and some of it is still on the screen, the bottom of that box shows at the top of the screen; and the same distance above the top edge, the top of the box shows at the bottom. Nothing can keep that part off short of hiding the sprite while some of it still shows, so both backends draw it. A game with such a sprite hides it before its middle is 33 rows past either edge, or keeps it to a size where none of it reaches the screen from there (up to about its drawn size). A 64-pixel sprite that only *turns* never does this, because its picture never reaches the rows that come round, and neither does any smaller sprite.
  - **Change size (tiled sprites):** `sprite.scale(1.5)` draws a `screen :tiled` sprite bigger or smaller about its own center — `1.0` is the size it was drawn at, `2.0` twice as big, `0.5` half. A boss that swells, an item that pops when you collect it, an enemy that shrinks into the distance. With no argument, `sprite.scale` hands back the size as a `Value` you can read and ease (`coin.scale.approach! 1.0, 0.05`), so growing over time is the expression DSL and nothing new; the size may be a whole number, a fraction, or something the game works out. It rides in the same hardware as `face_angle`, so a sprite can turn **and** resize at once for the price of either, and twice the drawn size is the ceiling (past that the picture runs out of the box the console gives it). It is the dearest thing a sprite does — drawing at a size means dividing by it, once a frame, which the framework does for you. On `screen :bitmap` resizing is a friendly error (draw the sizes you need as separate `image`s), and a size of 0 or less is a friendly error wherever you write it.
  - **Turn to any angle (tiled sprites):** `sprite.face_angle(degrees)` points a `screen :tiled` sprite at an exact heading — degrees clockwise from upright, pivoting on its own center — and `sprite.turn(degrees)` turns it by that much from where it points now (positive clockwise, negative counter-clockwise). Both wrap; `sprite.angle` reads the heading (0..359) as a `Value`. This is real rotation to any angle (the console's sprite rotate/scale), not the fixed-pose swap `face`/`facing:` do — a ship that points where it aims, a bird that tilts to climb (`examples/bird.rb`). `degrees` may be an Integer or a `Value`. Up to 32 sprites can turn at once (a friendly error past that); on `screen :bitmap` turning is a friendly error (a blitted sprite can't rotate — use `facing:` poses for a few fixed directions).
  - **Import from Aseprite (named animations):** `sprite :name, at:, from_aseprite: "bird.aseprite"` — import a sprite the way an artist authored it in Aseprite. Point it **straight at the native `.aseprite` file** (no export step) — the framework reads the binary directly: it composites the layers, decompresses the frames, resolves the palette, and reads each frame's duration and each **named animation** (frameTag). Or pass a `.json` export instead (both the array and hash layouts), where it slices the frames from the PNG named in the JSON's `meta.image` beside it. Either way it exposes each tag as an animation you play on demand: `hero.play(:walk)` / `hero.play(:attack)` (a `Sprite`/`HardwareSprite` method). The current animation loops until you play another; the first tag plays at boot (a file with no tags is one looping animation). The frame speed comes from the frames' durations. Path resolves next to your script. Mutually exclusive with the other pose sources.
- `rgb r, g, b` (0–31) / `rgb8 r, g, b` (0–255) / `color value` — make a 15-bit color.

## Tiled backgrounds

- `tiles :name, "#" => :brick, "." => :floor` — a tileset: map each character to a tile `image` (all same size). Add `solid: ["#"]` to mark wall tiles a sprite can't move through (see `blocked_by` under sprites). **A key need not be a character** — `tiles :room, 0 => :tile_0, 1 => :tile_1` — which is what a game whose level is worked out rather than typed already calls its tiles; `solid:` takes whichever keys the tileset has, with no change in spelling. **Import from a tile sheet** instead of naming images: `tiles :name, from: "tiles.png", tile: 8, "#" => 0, "." => 1` — each key points at a cell (a number counting left-to-right, or `[col,row]`); `tile:` is the tile size, `transparent: true` honors cut-outs, path resolves next to your script. **Import the WHOLE sheet as numbered tiles** (no characters): `tiles :name, from: "world.png", tile: 8` — every cell becomes a tile numbered 1, 2, 3… left-to-right (the numbering a map editor exports), and a map over it is written in those numbers, from a CSV or straight into `map:`; `solid:` then takes tile numbers (`solid: [1, 2]`).
- `box = tiles :box, from: canvas, count: 104, colors: :ink` then `box.changed` — **tiles whose pixels the game paints while it runs.** Every other tile is a picture fixed when the cartridge is built. These hold whatever the game works out: a name, a count, a message typed a letter at a time, a meter, a map drawn from where the player has been. `from:` is a `list ..., width: :byte` the game owns, and `count:` is how many tiles it holds. The tiles are keyed 1 to `count`, in the order their bytes sit in the list, so a background names them with Array rows (`map: [[1, 2, 3], [4, 5, 6]]`), and other keys in the same `tiles` call are ordinary tiles beside them (a box's frame). **The list holds the pixels the way the console's memory does**: a tile is 32 bytes, 8 rows of 4; each byte is two pixels, the left one in the low four bits; and each four bits is a place in `colors:` (a `colors` list by name, or the colours themselves, 2 to 16, place 0 see-through). That is what lets the copy be a plain copy, and what lets a game match another cartridge's buffer byte for byte. Writing into the list changes nothing on screen by itself. **`box.changed` shows it on the next frame**: the list is copied in the gap between frames, so a picture is never seen half copied. Saying it several times in one frame is one copy, and saying it every frame copies every frame. A scene that owns the tiles puts them up from the list as it is when the scene takes over again. **What it costs**: `changed` is one store, a frame with nothing changed pays one compare, and a frame with a copy pays one block copy of `count × 32` bytes — a 104-tile run measured at about a hundredth of a frame, and about two and a half hundredths when the list is in the roomy memory (`fast: false`). The tiles are never merged with any other tile, since two that look the same now may not on the next frame. Friendly errors: on a `screen :bitmap` (use `pixel` or `blit`, which already paint the screen); a list that is not `width: :byte`, or holds fewer than `count × 32` bytes; a `count:` that is not a whole number above 0; a `colors:` list missing or over 16; a key 1 to `count` also given a picture; a background that turns, or whose other tiles need more than 15 colours; and a list the game also `shift`s, anywhere in the game, since that moves its bytes out of order. **One run can be shown in several scenes** — a dialogue box in the overworld, a house and a shop — each scene by a background of its own, and each puts the box up from the list as it is when it takes over. A background every screen shows and a scene's own background can show the same run too, and so can two backgrounds on one screen: there is one copy, and each points at it. A scene that does not show the run can still say `changed`, and nothing is drawn there. What it costs is one store a frame in each scene, saying where the run sits on that scene's screen, and a load and a compare on each copy. A list starts empty, so a game fills it first (`repeat(3328) { canvas.push 0 }`) and then writes into it by index.
- `board = canvas :board, width: 208, height: 32, colors: :ink` then `background :box, tiles: :board, map: board.cells` — **a picture the game draws into with words while it runs**, and the friendly side of the entry above: the canvas keeps the list, packs every pixel for you and says `changed` after each word, so what you draw shows on the next frame. The words, all in colour names and all clipped at the canvas edge when a position is worked out as the game runs: `board.pixel x, y, :white`; `board.clear` (see-through) or `board.clear :blue`; `board.fill_rect x, y, w, h, :red` (any width, and 0 or less draws nothing — a meter); `board.blit :icon, x, y` (an `image`, whose see-through pixels leave the canvas alone and whose colours must be the canvas's); `board.draw_letter code, x, y, :white, font: :default`, where `code` is a character or a number the game works out — a name kept in a list, drawn a letter at a time — and which hands back how far across the letter reached, gap included, as a variable, so `pen.add! board.draw_letter(name[i], pen, 0, :white)` types; `board.draw_text "HELLO", x, y, :white`; and `board.draw_number score, x, y, :white, digits: 5`, right-aligned with no leading zeros like `draw_number`. `board.cells` is the canvas's tiles as rows of map keys, ready for a `map:`, and keys given to `canvas` itself are ordinary tiles in the same tileset beside it (a box's frame). `as: :sprite` makes the canvas a sprite's picture instead (`sprite :board, at: [x, y]`), and then it is a size the console draws a sprite at. `board.list` is the packed bytes, for a game that wants to write some itself (say `board.changed` after). Each side is a whole number of tiles, so a multiple of 8, and a colour the canvas does not have, a position written as a number outside it, and a canvas on a bitmap screen are friendly errors. **What it costs**, measured on the console: a pixel is about 140 instructions; a letter of the 5x7 default font about 5,600; clearing a 208x32 canvas about 3,400, since it is filled four bytes at a time; a 20x8 rectangle about 4,000, and about 6,100 when its left and right edges fall on odd columns, since a byte holds two pixels and an odd edge pixel is drawn on its own — on top of the copy the tiles above cost on a frame something was drawn. Worked example: `examples/hero.rb`, whose signpost types which file you are in and how far you have walked, and whose corner map gains a dot wherever you go.
- `bg.set_tile col, row, "."` — **one cell of the scenery becomes a different tile, while the game runs.** A door that opens, a pot that breaks, a wall a bomb takes out, a block the player pushes: every one of those is one tile changing, and without this every one of them has to be a sprite instead, out of a budget a game would rather spend on things that move. `col` and `row` are **cell** coordinates, not pixels, and either may be something the game works out; the tile is named the way the map was — one of the tileset's own keys, whether those are characters or the numbers a computed level counts in, or a number from an imported sheet — so nothing here is a place in video memory. **A cell outside the map is left alone**, so a coordinate that ran off the edge needs no test around it. A changed cell lasts until the map is put up again: `show_map`, or, for a background declared inside a scene, that scene taking over again (see `show_map`, below), or, for any background, a scene on a `screen :bitmap` coming between — that screen uses the same video memory, so the background comes back as declared, showing its first map. Every tile the tileset names is shipped whether the map used it or not, so a door can be drawn in the tileset and only ever appear once something opens it. A tile the tileset does not name, and `set_tile` on a `screen :bitmap` background (which is painted into the picture once, so it has no cells left), are friendly errors. `bg.cols` / `bg.rows` read the map's size back. **What it costs** is one write — the change lands where you call it rather than being held for the frame boundary. A cell is a single half-word, so it can never be read half-written; the whole effect of writing while the display draws is that one 8-pixel cell can be split across a single frame, and only when the write lands inside that cell's own six-thousandths of a frame. What that does not cover is a **bulk** change — a whole room swapped in one frame — where half the old room and half the new really would show at once; that is `show_map`, below. Worked example: `examples/tiles.rb`.
- `background :rooms, tiles: :set, map: { hall: HALL, cave: CAVE }` then `rooms.show_map :cave` — **the whole background becomes a different map, while the game runs.** That is what walking through a door is in a game with a lot of rooms: a room is a map, and going into one is naming it. Give `map:` (or `from:`, for CSV files) a **Hash** of them instead of one map and the background has several, one showing at a time; the first is the one showing when the game starts. **They can be different sizes** — a hut and a field on one background — and then each is kept at its own size, so a small room does not cost a big one's room (see "bigger than the grid" below for what that changes). `show_map` takes one of those names, or **a number counting from 0 in that order — and that number may be something the game works out**, which is what a game with hundreds of rooms wants: the room number IS the map number, so walking is arithmetic rather than a test per room. `rooms.showing` reads back which one is showing as a `Value`, `rooms.map_number(:cave)` turns a name into its number for comparing, and `rooms.map_count` is how many there are. **A number naming no map leaves the picture alone**, so a room number that ran off the end needs no test around it. **The map comes back exactly as declared**: a cell you had changed with `set_tile` — a door you opened — is shut again when you return to that map, because the whole map is copied in over whatever was there. A game that remembers such things opens them again on the way in, which is where it wants that decision anyway. **Coming back to a scene is the same thing**: a background declared inside a scene is put up as declared each time that scene takes over, so a cell changed with `set_tile` is back as drawn and the background is showing its first map again (`showing` reads 0), whatever the last visit did. **What it costs**: one copy, in the gap between frames, and only on a frame where the answer changed — so saying the map already showing costs a single comparison, and `show_map` can be written every frame, from a branch, from a scene. Nothing in the program names video memory or a moment it is safe to write. **A mover is blocked by the walls of the room it is in**: `blocked_by` reads the grid of the map that is really showing, so a cell that is a wall in the hall can be open floor in the cave, and the room you are standing in is the room that stops you. The map to read is worked out once for the whole check rather than once per cell, so sixty-four rooms ask exactly what two do (measured: the same emitted check, and one room's worth of bytes more than a background with a single map). It reads the map really IN the cells rather than the one the game last asked for — those differ for the one frame `show_map`'s copy is pending, and a player can feel being stopped by a wall that is not on screen where they cannot feel a frame of lag. What it cannot do is `show_map` on a `screen :bitmap` background, for the same reason `set_tile` is. The maps are stored uncompressed, because finding the map you asked for is arithmetic on where the first one starts. Worked example: `examples/tiles.rb`, where LEFT and RIGHT walk between three rooms while A and B open and shut a door in one of them.
- `background :ground, tiles: { shrine: :shrine_tiles, clearing: :clearing_tiles }, map: { shrine: { hall: HALL, stairs: STAIRS }, clearing: { glade: GLADE } }` — **a background whose rooms are in different AREAS, each area drawn from its own set of tiles.** That is how a game with a lot of world fits: the console's tile memory holds one area's tiles at a time, so a game holds the area the player is in, and walking into the next area brings that area's tiles in, and the colours they are drawn in with them. `tiles:` names each area's tileset and `map:` gives each area's maps under the same name, in the same order; the maps are counted area after area, which is the number `show_map` takes, so `ground.show_map room` with a room number the game works out walks between areas as it walks between rooms. **What has to fit is one area, not all of them**: each area's tiles on their own must fit beside everything else on the screen, and each area's colours beside the colours every area shares. Several backgrounds can walk together — a ground and the scenery over it — and the ones that name the same area share its colours, so they must change area on the same frame, which they do when each is told `show_map` with the same room. **When it shows**: on the same frame a `show_map` within one area would, on both backends. The area's tiles, its colours and the map all go in in the gap before that frame, with the background layers switched off while they do, so no frame shows a map over the wrong area's tiles; a whole area is thousands of bytes, so the frame that brings one in can run late, and a copy longer than the gap shows the backdrop at the top of that frame instead of half an area. **The colours arrive through whatever tint or fade is in force**, so an area walked into on a dark screen arrives dark and a fade back in shows its own colours. Walls follow the area like they follow the room (`blocked_by` reads the map really showing), a scene that comes back shows its first area again, and `rom.profile` counts each area brought in under the background's name. **What it costs every other frame is a question and a call**: bringing an area in is a routine of each background's own, kept in the cartridge and listed by the profile as "bringing background :name another set of tiles", so the game loop holds only the test for whether the area is changing — about sixty bytes a background, where the work written out in the loop was most of the loop and took the quick memory from routines every frame of play runs. Friendly errors: maps not under the area names, two maps of one name, `set_tile` (a tile name can be in several areas, so give each look of a room a map of its own), walking backgrounds that start in different areas, `draw_with`, a tile of more than 15 colours, a painted tile, a turning background, an area whose colours do not fit, and areas whose tiles are different sizes.
- `bg.draw_with :dusk` (also `bg.draw_with [:s0, :s1, :s2, :s3], showing: step`, and `bg.draw_with :own`) — **the whole layer drawn from a different list of colours, while the game runs.** Shafts of light that shimmer, water that turns murky as you go down, a sky that walks from day to dusk, a room that changes with the weather. It is the same word a sprite already takes and it means the same thing: the lists are declared with `colors`, see-through first, and matched to the list the tiles were drawn from **by place** — so every pixel keeps the place it was drawn at and only the colour that place shows changes. The scenery is not redrawn, not one cell of the map moves, and the art is drawn once however many times of day it has. **A number outside the set is the colours it was drawn in**, so a counter that has run off the end looks right rather than wrong, and `showing:` is the same word a `blit`, a `menu` row and a sprite's own `draw_with` use. **A layer drawn from SEVERAL lists** — a backdrop with more colours than sixteen, each tile drawn from one of its lists — steps them all together: name each list its tiles were drawn from (`colors :sea, [...]` then `image :wave, ..., colors: :sea`), and give `draw_with` a hash of those names to what each walks through, `backdrop.draw_with({ sea: %i[sea0 sea1 sea2], sky: %i[sky0 sky1 sky2] }, showing: step)` — one number picks the same step of every list, which is how a retail title animates a full-screen backdrop across four groups of colours at once. `backdrop.draw_with({ sea: :sea_dusk })` gives one list each, with no number; a list the hash leaves out stays as drawn; and a number outside the steps draws every list as drawn. Giving such a layer a single list is a friendly error naming its lists, and so are a name none of its tiles is drawn from and lists with different numbers of steps. It costs one copy of sixteen colours for each list the layer is drawn from, on the frame the step changes and no other. **What it needs**: the tiles given a `colors:` list of their own (a swap goes by place, and a picture whose list the framework worked out has places nobody chose), a list at least as long as theirs, and `screen :tiled` — a bitmap background is stamped into the one picture where it is declared, so it has no colours left to swap (a friendly error). A **turning** background is a friendly error too, whichever order the two are written in: its cells hold a tile number and nothing else, so its tiles read every colour in the game rather than a list of their own, and there would be nothing to swap. **What it costs**: one copy of sixteen colours, in the gap between frames, and only on a frame where the answer changed — so saying the list already showing costs a single comparison, and it can be written every frame, from a branch, from a scene, exactly like `show_map`. It costs the same however much of the layer is on screen, because the console draws every pixel by looking its colour up in a table and this moves the table. The one thing it spends is a group of sixteen colours: a layer that can be recoloured is given colours **nobody else reads**, since the write lands in the table and anything else drawing from those sixteen would change colour with it — so two layers drawn from the same art can shimmer one at a time. A **fade or a tint** over such a layer darkens or moves the list it is really drawing from, not the one it was drawn in, so the two compose and neither has to know about the other. Worked example: `examples/dive`, whose title screen has two sheets of light shafts drifting at different speeds and shimmers the near one.
- **Two tiles that come out the same are stored once, and nothing says so.** Nothing about a tileset says which of its tiles are really the same picture — a wall's interior repeats in every variation of that wall, half a metatile of grass is the same grass in dozens of cells — and on a real tileset that is a large fraction of it. The build notices; you write the tileset you drew, and it costs nothing at run time because a tile number is a tile number. **A tile that is another tile MIRRORED is stored once too** — reversed left to right, upside down, or both — because a map cell can say "draw it turned round" and the console does that as it draws, for nothing. A room's left wall is its right wall reversed and a corner is the same corner four ways, so on a real area this is often half the tiles: counted on one game's twenty-room area by cutting its rooms into tiles, a layer of 1,553 different tiles is 708 once mirrors are one, which is the difference between past the about a thousand one layer can name and comfortably inside it. `set_tile` and `show_map` name the tile the same way the map did, so a changed cell shows it the right way round. `rom.profile` says how many tiles turned out to be repeats and how many were mirrors, and a layer still too big after this says how many mirrors it found. A **turning** background cannot do this: its cells hold a tile number and nothing else, so it keeps each mirror as a picture of its own.
- **How many different tiles a game can have, which used to be one number for the whole game and is now the memory.** A cell of a map names its tile by counting from a starting point, and it has ten bits to count with — so **one layer reaches about a thousand tiles** (twice that where the art needs more colours, since those tiles are stored at twice the size). That used to be the ceiling for a whole game, because every layer counted from the same place. Now **each layer counts from its own**, worked out at build time from where its tiles landed, so a second layer picks up where the first left off and what a game holds is simply what fits: **roughly nineteen hundred small tiles across two layers**, against the 256 a whole game got before any of this. Nothing in the program says a word about it, and it costs nothing at run time. It is not always exactly free of MEMORY: the console allows a starting point only at four fixed marks, so lining a layer up with one can leave a gap behind it, and `rom.profile` says how big — along with how much of the memory the tiles and the maps have each taken, which is the number to watch, since they share it and grow toward each other. A tileset too big for one map to count across is a friendly error naming the background and saying to declare it before the bigger ones.
- `background :name, tiles: :set, map: <<~MAP … MAP` → a `Background`; stamps a grid of tiles (`map` is rows of tileset keys — a string or array of row strings, one character per cell, a space = empty cell). **Or write the grid the build worked out:** a row may be an **Array** instead of a String, one element per cell, and then a cell is whatever the tileset is keyed by rather than a single character (`nil` = empty cell) — `background :room, tiles: :room, map: [[0, 1, 1, 2], [3, nil, 1, 2]]`. That is the third way a game gets a level, beside a person typing it and an editor exporting it, and the one that had no spelling: a level decoded from somewhere has a tile *number* per cell and never had characters, and a screenful of a real game holds far more distinct tiles than the 94 printable characters anybody would read. Same verb, same argument, same tileset; nothing about the level is a file on disk. **Or import the map from a file:** `background :name, tiles: :set, from: "level.csv"` reads a CSV tilemap exported from a map editor like Tiled — a grid of tile numbers, one row per line, `0` = empty cell (path resolves next to your script). Give `map:` or `from:`, not both. **Or a Hash of several maps** the game can walk between — see `show_map` above. Drawn by the tile hardware in `screen :tiled`, and like tiled text it is **declared once — above `game_loop`, or inside a `scene`** — and drawn for you every frame from then on; declaring it inside `game_loop` on a tiled screen is a friendly build error (show another map from the loop with `show_map`). A `screen :bitmap` background is painted where it is written, so the loop is no error there. **Say what STOPS a mover apart from what it SHOWS:** `walls:` is a grid of its own, the same shape as the map, saying which cells cannot be entered — `background :rooms, tiles: :set, map: { hall: HALL, cave: CAVE, sky: SKY }, walls: { hall: HALL_WALLS, cave: CAVE_WALLS }`. Leave it out and the walls are the tileset's `solid:` tiles, read off the picture, which is what a small game wants and what every game wrote before this existed. Write it and the two are separate data, which is what a real game's collision already is: a room's walls are authored, imported or decoded beside its picture rather than worked out from which tile happened to be drawn — so the same brick can be a wall in one room and scenery in the next with nothing about the art changing. **A map `walls:` does not name has no walls**, which is the explicit way to say a room is somewhere you walk anywhere: a fly-over map, a cut-scene tableau, scenery rather than a place. That is one missing line, not a second background, and it is visible at a glance beside the maps themselves. A cell is a wall unless it is BLANK — a space, a `.`, a `0`, or nothing at all — so a grid drawn by hand and a collision layer decoded out of somewhere else both drop in with no table of which value means what. A `walls:` key naming no map is a friendly error, because it would quietly leave that one room walkable, which reads as broken collision rather than as the typo it is. **Scroll it:** `bg.scroll_by dx, dy` / `bg.scroll_to x, y` move the visible window over the map (in pixels; a map that fits the console's grid wraps at its edge) — call them anywhere in the frame, from a branch or deep in a scene; the framework applies the camera once a frame so scrolling can never tear. **Up to 64×64 tiles** — 512×512 pixels, more than four screenfuls — and the map wraps at that edge, not at the last row you wrote (past the rows you filled in you see the backdrop, and the picture comes round again at the grid's edge; that is what a background does, and both backends agree on where). You write the rows you want and the framework picks the smallest of the console's grid sizes that holds them; a map bigger than one piece of video memory is cut up and laid out for you, and nothing in the program says so. **A map BIGGER than the grid works too, and nothing says so either** — a room of 126×126 cells, a field a dozen screens across. The console's grid is at most 64×64 cells, so such a background keeps its whole map in the cartridge and, in the gap before each frame, copies in the column or row of cells coming into view; a 32×32 grid that comes round under the view is all it needs, since the screen shows 31 columns and 21 rows at most. The same happens to a background whose maps are of different sizes. **What it changes is the edge**: past the edge of such a map there are no cells, so the view shows the backdrop and the layers behind there, rather than the map coming round again — a room has edges, and a small repeating backdrop that fits its grid still comes round as before. A `show_map` to another room, a scene taking over, and a view that moved more than eight cells in a frame fill the whole view again in that same gap, so **the frame the view lands on already shows the right picture**, and a room of another area comes in with its tiles exactly as a small one does (see the area entry above). `blocked_by` reads each room's walls at that room's own size. **What it costs**: a few dozen instructions and no copy on a frame the view stayed inside one cell; a column of 21 cells or a row of 31 on a frame it crossed one, a handful of instructions a cell; the whole view, 21 rows of 31, on a jump. `rom.profile` counts it as "bringing the view of background :x along its map", and lists a routine of that name: the work is one routine for each such background, called from the scroll and from wherever the whole view is filled, and placed like a routine somebody wrote, by what a frame spends in it, so a game that scrolls a big map can keep it in the quick memory while there is room. Friendly errors: `set_tile` on such a background (its cells are copied in again as the view moves, so give each look of a room a map of its own), turning it (a layer that turns has to hold its whole map), and `scroll_each_row` on it (a bent row reaches past the cells around the view). Worked example: `examples/meadow.rb`, where a hero walks out of a one-screen cabin into a meadow of 120x100 cells on the same background. Sprites compose over a scrolling background (the console draws them on top for free) — a hero centered while the world scrolls under it is a follow-cam (`examples/hero.rb`). **Stack layers:** declare more than one `background` (up to 4 showing at one time — declare them inside a `scene` and each scene gets its own four) and they compose — the first declared is the backmost (unless a `layer` says otherwise — see Layers), each later one in front, and a front layer's see-through tiles (empty cells, or `:transparent`/backdrop pixels) let the layer behind show; scroll a near and a far layer at different speeds for parallax (`examples/parallax.rb`).
- `bg.scroll_each_row { |row| offset }` — give every **row** of a background its own sideways offset, so the picture *bends* instead of moving as one flat rectangle. The block is handed the row (0 at the top of the screen, 159 at the bottom) and gives back how far across that row sits, on top of the background's own scroll — so a background can scroll and bend at once. Move a variable the block reads and the bend travels: rippling water, a heat haze, a reflection wobbling, a screen melting into a transition. Worked example: `examples/lake.rb`, where a sine table shifted a little each frame rolls a wave down a lake and the sun's reflection snakes. Declare it once where the background is declared — it keeps running from there, and calling it again replaces the bend. Rows bend sideways only. Tiled screens only (a bitmap screen has pixels you drew, not a layer to bend — a friendly error). **Your block runs once per row, in the gap between frames** — all 160 rows worked out before the picture is drawn, never while it is being drawn. That is what keeps a bend in step with everything else the frame moved (a sprite riding on the water shows the same frame the water does), and it is most of what the effect costs: about as much as running your block 160 times, whatever is in it. Write what you like there — a `table` read, arithmetic, a variable set, a `func` call. **It is not free.** **How many layers bend decides the rest.** Up to three at once are fed to the display by its own copying engines, with the CPU untouched, so a parallax pair of rippling layers costs nothing beyond the two blocks; a **fourth** is one more than there are engines and then the game is interrupted on every one of the display's 228 lines to hand the rows over, which is several times the price of the blocks themselves. A game playing `sample`/`instrument` audio is fed from an engine too, and then there is one left, so one layer.

- `bg.rotate degrees` / `bg.scale size` — turn or resize the WHOLE background as one piece, pivoting on the middle of the screen — the same trick a hardware sprite's `face_angle` / `scale` does, done to a background layer instead of one picture. `degrees` is clockwise from upright and wraps (370 is the same as 10); `size` is 1.0 at the size it was drawn, 2.0 twice as big, 0.5 half. `bg.angle` reads the heading back as a `Value`; `bg.scale` with no argument does the same for size, so easing it is the expression DSL (`bg.scale.approach! 1.0, 0.05`) same as a sprite's. **Works on `screen :tiled` as well as `screen :rotozoom`, and saying it is how the hardware gets picked**: a background that turns is the one thing the console cannot arrange alongside four scrolling layers, so writing `rotate` or `scale` is what asks for the arrangement that holds it — two scrolling layers plus this one. **It asks for it on THAT SCREEN only**: a scene that turns nothing keeps all four scrolling layers, in the same cartridge, because the console is told which arrangement it is in as each scene takes over. Nothing else in the program mentions it, the other layers keep their scroll, their `show_map`, their `set_tile` and a see-through layer, and a third scrolling layer beside it is a friendly error naming both counts. A `screen :bitmap` background cannot turn at all (a friendly error), because that screen has no layer — it has pixels you drew. **What a turning background gives up, wherever it lives**, and this is the part to read before moving one onto `screen :tiled`, because these used to read as facts about `screen :rotozoom` and are really facts about turning: its map must be **square** (16, 32, 64 or 128 tiles a side — it turns about its own middle), it can name at most **256 distinct tiles** (its cells hold one byte each, where a scrolling layer's hold two), its tiles are always stored at full size, and **`set_tile` cannot change one of its cells** (there is nothing in a cell but a tile number). Each is a friendly error naming the background. `show_map` still works. In exchange this background's own `scroll_by`/`scroll_to`, and `scroll_each_row`, become a friendly error, since panning this kind of layer is done by turning/resizing it, not by the plain scroll registers `screen :tiled` uses. **Its tiles are always stored at full size**, which is the one place the halving described under Images does not apply: this pair of layers reads a whole number per pixel whatever the art is drawn from, and its cells have no room to say otherwise — so a turning background drawn from four colours takes what one drawn from two hundred takes. Nothing to write; `rom.profile` shows it as tiles that got the big storage. **A size or angle written on the line that DECLARES the background — `background(:sword, tiles: :sword, map: grid).scale(16.0)` — is what the picture starts at, and it is applied once at power-on**, the same promise `var` makes about the value it is declared with. That matters inside a scene and nowhere else: a scene's body is reached on every frame that scene is up, so a size read as a per-frame write there would be put back at the top of every frame and whatever was easing it would get one step and no more — a title screen whose picture flies at the player would arrive stuck. Write the same number further down and it is what it says: set the size, here, every time this runs. **The display is told how the layer is turned only on a frame where the answer CHANGED**, the same bargain `show_map` and a scroll already make, and here it buys more than the time: a picture that has arrived costs two comparisons and no write at all, where writing every frame means writing on the frames a game starts late as well — and a write that lands after the picture has begun to be drawn moves the layer for the rest of that frame, so a picture that has stopped moving visibly jumps and snaps back every few seconds. Nothing in the program says any of this; a turn that moves is written on every frame it moves. Worked example: `examples/rotozoom_bg.rb`.
- `bg.turns_around x, y` — **which point on the screen the picture turns around**: the one place that stays still while the rest of it swings or grows about it, and the place the same point of the picture keeps landing on. The middle of the screen unless you say so, which is right for a picture that IS the whole screen — a spinning map, a race track that pulls away — and wrong for a picture that arrives somewhere in particular. A title screen where something flies at the player pivots wherever that thing comes to rest, and the difference is not cosmetic: at sixteen times magnified only a sixteen-by-ten patch of the picture is on screen, so a pivot eight pixels off puts the whole thing outside the screen for the first half of its arrival — it flies in from nowhere, and the art has to be moved inside its own grid to compensate, which then throws off where it comes to rest. **Say it once, where the background is declared** (`background(:sword, tiles: :sword, map: grid).turns_around(120, 72).scale(16.0)`): a picture turns around one point however many times the game turns it, so there is nowhere for a second answer to live. It takes two numbers you write — a point the game works out is a friendly error, because a pivot that MOVES is its own effect and a different one. **Nothing moves when only the pivot does**: at its drawn size, upright, a background lands in exactly the same place whatever it turns around, so this can be said before the animation that reads it exists. It costs nothing at all — the same one multiply-and-subtract per axis the middle of the screen already cost.

## Layers (a named place in the stack)

A game is drawn in layers — the scenery, the characters, the score on top — and without a name for them the only way to say what sits in front of what is the order the declarations happen to run in. That order is invisible, it lives in prose comments, and in a game split across files it depends on which file was required first.

- `layers :sky, :world, :actors, :ui` — declare the stack, **back to front**, one time. The order is global on purpose: "in front of" is a relation across the whole screen, so one line answers the question a reader of somebody else's game actually has. Naming a layer twice, or declaring the stack twice, is a friendly error.
- `layer :name do … end` — everything the block declares belongs to that layer. The block runs on the build, exactly like a `func` body, so **every verb works inside** and the parts-in-files pattern does too (`Enemies.new(self)`). What can take a layer is a `background`, a `sprite` (either screen kind — but see the bitmap note below), a `pool` with `image:`, and `draw_text`/`draw_number` on a tiled screen — the things the framework draws again for you every frame. Nesting one `layer` inside another, or naming a layer that isn't in `layers`, is a friendly error.
- `layer :water, transparency: 40 do … end` (also `transparency: 100 - mist` — **an amount the game works out**, for fog that thickens, water that gets murkier as you descend, a backdrop that dims in; write a variable or an expression where you would write a number) — **see through this layer to what is behind it**: water, glass, fog, a dimmed backdrop behind a menu. 0 is solid (the picture as drawn), 100 is invisible. What it means is what it looks like — whatever sits directly under the layer at a pixel shows through it, anything in **front** of it draws solid, and where the layer itself has a see-through tile what is behind shows plain — and that is also exactly what the console does, so there is one rule to learn, and it is about a see-through sprite over another sprite (below). **It costs nothing**: the display blends as it draws, so a see-through layer costs the same as the same layer drawn solid, however much is on screen. (An amount the game works out keeps that bargain for the blending and adds one thing: the display has to be told the new amount before each frame, which is a single register write the framework puts at the frame boundary for you. `rom.profile` says which of the two a picture got.) The property belongs to the layer, so it rides on the layer and there is no new verb; say it on the block, one time. Works for a layer of `background`s and a layer of `sprite`s alike (two different mechanisms in the console, and you never learn which one you got). **One see-through sprite — a ghost, a shield bubble — is a layer holding just it**, `layers :ghosts` and `layer(:ghosts, transparency: 50) { sprite :boo, at: [x, y] }`, and nothing else in the game has to name a layer, since what names none keeps the place it had; there is no per-sprite word, because it would reach the same bit of the sprite's table entry and share the console's one amount. The one thing the layer form cannot do is make a single member of a `pool` see-through, since a pool's instances cannot change layer. **A see-through sprite shows the scenery under it, never another sprite**: where a ghost passes over the hero, the hero is not seen there at all and the floor shows through the ghost instead. The console keeps only the front sprite at each pixel before it blends anything, so the sprite behind is gone by the time the mixing happens. To see a character through something, make that something scenery: a see-through layer holding a `background` does show the sprites behind it. **A SCREEN has one see-through layer, and a game can have one on each of its screens** — a title whose light rays shimmer and a menu whose window glows, in two scenes that are never up together. Two on one screen is a friendly build error naming both layers and the scene, because the console blends one layer with what is behind it, and a see-through layer sitting directly over another one is the one arrangement the two backends would draw differently. What a game with several pays is one compare a frame per layer, to tell the display the amounts of the one on screen. Needs `screen :tiled` — a bitmap screen paints its whole picture into one place before the display sees it, so there is nothing left behind a layer to see through (a friendly error). `transparency: 100` is a friendly warning: none of the layer shows, and the game still draws it (said only about a number you wrote — an amount the game works out passes through 100 whenever the fog clears, so nothing is said about one). **A fade does not disturb the layer** — it goes on showing what is behind it while the screen fades, and the whole picture (the layer, what is behind it, and the mix of the two) darkens together, which is what a fade out should look like. That is not free the way the blending is, and it is the only thing about a see-through layer that costs: seeing through a layer and darkening a finished picture are the display's *one* blend unit, so a game that does both moves the **colors themselves** toward black instead — a blend per color the game declared, never per pixel on screen, and only on a frame where the fade actually moves. It is measured on both backends rather than assumed, and `rom.profile` says so. A `tint` never took the layer's blend in the first place, so `flash_screen :red` costs the same and always did. **The one fade that still takes it is a PLACED one** (`fade … under:`), because placing a fade is the thing only the blend unit can do — that one leaves the layer solid until it lifts, and says so as a friendly warning at build time. Worked examples: `examples/lake.rb`, where half-see-through jellyfish drift across the lake and the ripple keeps travelling through their bells, and `examples/hero.rb`, where mist declared in front of the hero thickens as you walk north (`transparency: 100 - mist`) and clears on the way back.
- `layer :window, shows: 94, shows_behind: 63 do … end` — **the same see-through layer with its two amounts said apart**: `shows:` is how much of the layer itself shows and `shows_behind:` how much of what is behind it, each 0 to 100. `transparency: t` is the pair adding to 100, which is glass; these need not, and that is what light is — a shaft of sunlight shows ALL of the water behind it and some of itself on top, so where it crosses the water the picture is brighter than either, and a channel that runs past its brightest stops there, as the console's does. The display mixes in sixteenths, so each amount is taken to the nearest one: 94 and 63 are the 15 and 10 a cartridge that was drawn in sixteenths says (a file-select window over its backdrop), and `transparency:` keeps the rounding it always had. Either amount can be something the game works out (`shows: 57 - glow, shows_behind: 57 + glow`, light rays stepping through), at the same one register write a frame. The two go together — one without the other, or either beside `transparency:`, is a friendly error — and a `shows:` small enough to round to nothing is the same friendly warning `transparency: 100` gets. It costs exactly what `transparency:` costs. Worked example: `examples/dive`, whose title's near light shafts show three quarters of themselves over all of the water behind them, beside the dive's own see-through water on the next screen.
- **A layer holds things, not brushstrokes.** The instinct people arrive with is that a layer is a surface you draw on — clear this layer, put a pixel on this layer. Nothing on this console works that way, and it is not close: a bitmap screen has one framebuffer, a tiled screen's layers are grids of references to shared tiles rather than canvases of their own, and giving each layer its own pixels means blending two full screens in software every frame — over twice the time a frame has, and the memory besides. So `pixel`, `fill_rect`, `dma_fill_rect`, `draw_rect_at`, `blit`, `clear_screen` and bitmap `draw_text`/`draw_number` are a friendly error inside a `layer` block: they paint where you call them, and no ordering applied later can reach back and change where they landed. What you write instead is the retained-mode answer, which is what `sprite` already is: make a thing, and put the thing in the layer. `fade` and `camera` are a friendly error there too — they change the whole screen, so they cannot belong to one depth. An effect is **placed, not contained**: `fade :black, 100, under: :ui` says where in the stack it sits (see Drawing), which is a different thing from being one of the layer's things.
- **`draw_text` is the one verb whose nature changes with the screen** — layerable on `screen :tiled` (where the console draws each character for you every frame), a friendly error on `screen :bitmap` (where it paints into the framebuffer at the call). Same seam tiled text already has, where it must be declared once above the game loop or inside a scene; the error says which of the two you are in.
- **A scene is WHEN, a layer is WHERE IN THE STACK**, and they never need to know about each other. A HUD can be in `:ui` and in `:playing` — on top, and only while playing. Containment goes one way: `layer` blocks inside a `scene`. A `scene` inside a `layer` is a friendly error (a state holds things at many depths; a layer is one depth). A **routine** — a `func` or a `once_a_frame` — may sit inside a layer, but **declaring a `sprite` or a `background` inside one is a friendly error**: a routine's body is built later, when the layer is not in force, so it would quietly sit at no depth at all. The error names what you wrote and the way round that works (put the `layer` block inside the func; move a declaration out of a per-frame body, where it runs once anyway). What is refused is the *declaration*, not the routine — so a `func` that only moves the sprite it sits beside is fine, and so is every effect verb that declares a per-frame routine of its own (`pulse`, `camera_follows`, `fade_out`, `shake_screen`): a game says `pulse coin` on the line after it declares the coin.
- **A `background` can sit in FRONT of a sprite** — the fence a hero walks behind, grass that passes over their feet — by declaring its layer in front of theirs. That is the one arrangement a picture cannot fall into by accident, and it needs the console's own stacking, so it comes with two rules. **The console keeps four levels of depth**, and a level is spent only by a `background` (the sprites in front of one share its level), so you can name as many layers as you like and a game with one background and five sprite layers uses one level. Asking for more depth than that is a friendly build error that names the layer which cost the level and shows your stack — `rom.profile` lists the same thing for a build that fits. And once a background is in front of a sprite, **every** background and sprite must name a layer: the usual arrangement (scenery behind, everything that moves in front) is gone, so there is no longer a place to leave something that named none. That too is a friendly error.
- `hero.put_in_layer :walking` (also `hero.put_in_layer [:upper, :walking, :stairs], showing: floor`) — **a sprite that changes which layer it is in while the game runs.** A room drawn as two backgrounds has three places a character can stand: upstairs, in front of both; on the ground floor, behind the top one and in front of the bottom one; and on a flight of stairs, behind both, showing only where both are see-through. One cartridge holds rooms of every kind and a staircase moves the character between them mid-walk, so no one place in the stack is right for the whole game. Declare a layer for each place (`layers :stairs, :ground, :walking, :scenery, :upper`), declare the sprite in one of them, and name another as the game runs. A layer the sprite is only ever put in still gets a depth of its own, so the stairs are a layer behind every background with nothing else in it, and it is not a layer that holds nothing. `showing:` picks one of a list by a number the game works out, counting from 0, the same word `draw_with` and `face` take, and **a number outside the list puts the sprite back in the layer it was declared in**. The change shows on the frame the sprite's position and pose next do, never a frame before or after, since on the console the depth is part of the sprite's table entry and is written with them. Every layer it can be in spends depth the way the sprite in it would, so the stairs above take a level of the console's four. **Declare the character once and every room gets it right**: the console counts depth from the front, so the ground floor of a room with a top layer is one further back than in a room without one, and a sprite shown in both is told the number of the room that is up — read off the variable the game picks its scenes with, as the sprite is drawn. **What it costs**: a read of which layer and a table read a frame, a read of which room as well for a sprite whose rooms disagree, and a sprite never moved emits nothing new. Friendly errors: a layer the stack does not have, a game with no `layers`, several layers with no `showing:`, a sprite whose rooms disagree and are not picked by one `case_var` (declare it inside each scene instead), and the verb on `screen :bitmap` (whose backgrounds are painted in once and have nothing to go behind) are friendly errors. Hardware sprites only, not a `pool`'s instances.
- `draw_in_order hero, guard, guards` — **sprites drawn in an order the game works out, so whoever stands lower is in front.** Everywhere else, which sprite is in front is settled when the cartridge is built — the one declared later, unless a layer says otherwise — and a top-down game cannot live with that: walk round below something and you are drawn over it, walk round above it and it is drawn over you, and the answer changes every time two things pass each other. Name the sprites and pools that pass each other, and each frame they are drawn in the order of a number: the bottom of each one's box unless a block says otherwise (`draw_in_order(hero, puffs) { |thing| thing.bottom + thing.lift }`, handed the sprite, or one of a pool's things the way `each` hands it), with the highest number in front unless `front: :lowest` turns it round. A pool's things take part one by one. Things whose numbers are level keep the order they were already in, so two characters standing side by side never flicker in front of each other — with one exception: two level things of a pool can swap once when a thing older than both is removed, since a pool's things keep their places by age. They can be named in any order. **The order is among the things named**: they are drawn together where the backmost of them was declared, and anything else keeps its own place in front of or behind the whole run — so the things of one order are in one layer, and in one scene or none, and a layer orders the runs the way it orders sprites. The order is worked out in the gap before each frame from where everything stands then, the same moment the sprites themselves are drawn from. **What it costs**, measured on the console: three sprites, about 300 instructions a frame; a pool of 32 beside a hero, about 4,200 with four of them live and 4,900 with all 32, which is about a thirtieth of a frame. The number is worked out for every place a pool has, live or not, and the sort starts from last frame's order, so what costs is the size of the run rather than how often things pass. Each place in the run also keeps a copy of its row of the sprite table in work memory, 8 bytes a place. A game that orders nothing builds exactly as before. Friendly errors: a bitmap screen (a sprite there is painted into the picture, so there is no order left to change), anything but a sprite or a pool that draws, one sprite on its own, a thing in two orders, things in different layers or scenes, a `front:` other than `:highest` or `:lowest`, and a sprite in an order that is also told `put_in_layer`.
- **Only what named a layer is moved.** While the usual arrangement holds, a thing that named no layer keeps the exact place it had — so wrapping one part of a game in a layer can never pick up and move a part that says nothing about layers, which is what makes it safe to adopt a bit at a time. Two things in the same layer keep the order they were declared in.
- Layers are **opt-in**: a game that declares none keeps its ordering exactly (declaration order, and a HUD drawn last). What a layer becomes — a background layer, a sprite priority, the order things are painted — is the framework's business; you never write a BG index or a priority.
- **A stack decides the picture on both screens — with one exception, and it is about `background`.** Sprites follow their layer on either screen: on `screen :bitmap` the framework repaints them every frame, so it repaints them back to front and a sprite in a front layer covers one behind it, exactly as on `screen :tiled`. Worked example: `examples/sprite_mover.rb`, where the heart passes in front of one post and behind another. A **`background` on `screen :bitmap`** is the exception, and permanently: it stamps its tiles into the one picture where you declare it, and nothing draws it again, so no layer can move it afterwards. Where a stack asks a bitmap screen for a background order it cannot give — two backgrounds the stack reverses, or a background put in front of a sprite — that is a friendly build **warning** naming both orders, what you asked for and what the screen will show. On `screen :tiled` there is no exception at all.
- **`rom.profile` shows the stack** — each layer with what it holds, which of the console's four levels it landed on, and how many are left. That is the tiled screen's whole bargain, made visible: a background is drawn by the display for free once it is up, however big it is, so several layers sharing one level is the normal answer rather than a compromise. A see-through layer gets a line of its own, saying that the display blends it for nothing — and, in a game that also fades, a line saying which of the two ways of fading that bought: a whole-screen fade walks the colors and keeps the layer (and costs a blend per declared color on each frame it moves), where a fade PLACED in the stack takes the blend and leaves the layer solid until it lifts. What a layer COSTS is a question about time, and the measured half of the same report answers it by routine.
- **A layer that holds nothing** — a name in `layers` no `layer` block ever puts anything in — is a friendly warning too. It is harmless to the picture, and it is almost always a name spelled two ways or a leftover from an edit, which quietly stops the stack meaning what it says. A layer named only by an effect (`fade … under: :cut`) counts as used: it is deciding where the line falls.

## Collision

- `box x, y, w, h` → a `Box` (a rectangle to test; draws nothing). Coords may be `:var`/`Value`/`Integer`.
- **Screen-edge tests** (on anything with bounds — a `Sprite` or a `Box`): `off_screen?` (fully past any edge), and edge-specific `off_left?` / `off_right?` / `above_top?` / `below_bottom?` for when behavior depends on *which* edge (a bullet dies off the top, an enemy respawns off the bottom) — each returns a `Condition` for `.then`, read from the thing's own bounds and the 240×160 screen, so no coordinate literals. Pair with `sprite.clamp_to_screen` (keep it fully on screen using its own size). "Fully past" means nothing of it still shows.
- `a.overlaps?(b)` → a `Condition`; `.then { }` on it. Works on any two things with bounds — a `Box`, or a `Sprite` (which provides its own bounds), so `hero.overlaps?(coin)` needs no box. **Sprite-vs-sprite is per-pixel by default** (`sprite … hitbox:` picks the box): a hit needs the two sprites' *drawn* pixels to actually meet, any shape, following whichever animation frame is showing — a cheap box test gates it so far-apart pairs stay cheap. A `Box` (and a sprite given an explicit `hitbox:`) collides on its plain rectangle instead, so sprite-vs-box is a box test. Set a sprite's box with `hitbox:` (see the sprite verb): `:full` (whole image), an inset number (shrink each side), or `[x, y, w, h]`; the default box (used as the per-pixel gate, or as the collision box when you opt out) hugs the visible pixels.
- **Tile collision (tiled mode):** mark walls with `tiles ..., solid: ["#"]`, then `sprite.blocked_by(background)` — its `move` is checked automatically (stops at walls, slides along them). `sprite.can_move?(:left, by: n)` → a `Condition` for manual control; raw `move_to`/`x`/`y` are never checked (escape hatch). **A `pool` takes it too** — `guards.blocked_by(room)` once, and then every instance's `move` and `can_move?` are checked inside `each`, each sliding along walls on its own. That is the case that most wants it: a game with a roomful of movers. **What it costs does not depend on the room.** The framework asks the map whether the cell a mover is stepping into is solid, so a bare room and a maze of pillars are the same handful of reads — where testing the mover against every wall rectangle cost what the room was made of, and was written out afresh at every place a thing moved. Measured on a 30x20 room, eight movers: the game loop went from 353K, which does not fit the console's quick memory and drops the *whole* frame to cartridge speed, to 3K, which does. The check is one shared routine, so a second mover costs a call rather than another copy, and a pool of thirty-two shares it with a hand-declared sprite of the same size. Walking off the edge of the map is not blocked (there is nothing there to be solid), same as before.

## Text & numbers

- `draw_text "HELLO", x, y, color, font: :tiny` — fixed-origin text (`font:` picks a registered font; default `:default`).
- `draw_text "SOUND", x, y, [:gray, :white], showing: picked == 1` — **two colours, and a test saying which**: the second while it holds, the first when it does not. A label that highlights, a HUD figure that turns red when the health is low (`showing: hp < 20`). Written the long way — the same words drawn twice, under a test and its opposite — it says the same thing and paints the same pixels, and it costs twice as much on **either** screen. On a **tiled** screen the console draws each character as its own little sprite out of a table of 128: two draws are two sprites for every character with one of them always hidden, where this is **one sprite that changes colour**, because the pair becomes two poses on it and the console is already swapping which picture a sprite shows for free. That halving is what lets an eight-row `menu` fit. On a **bitmap** screen the words are painted pixel by pixel into code, so two draws are every pixel of them twice over, where this **paints them once** with the colour picked by a test just before — a handful of instructions for the second colour rather than a second copy of the words. Measured on the jukebox, whose song list is a menu of such rows, that took its code from 47K to 37K. Exactly two colours: a test is 0 or 1 and a pair has a 0 and a 1, so the choice can never land outside it. Three is a friendly error saying to draw the text under a test for each, and a pair without `showing:` (or `showing:` with one colour) is a friendly error too.
- `draw_number :var, x, y, color, digits: 3, font: :tiny` — a live number (right-aligned, no leading zeros).
- **Say where it goes instead of counting pixels**: where the left edge goes, both verbs also take `:left`, `:center` or `:right` — `draw_text "PONG", :center, 40, :white`. A number you write still means that column, and is still right when you actually want a column; what a number cannot be is CENTRED, because a proportional font has no per-character width to multiply by and the only thing that knows how wide "PRESS START" comes out is the font. Ask it and a label can be reworded with no stale number left behind. `within:` narrows what it is placed against — `within: 0..119` centres a caption in the left half, `:right, within: 0...120` pushes a label up against the middle from its left — and with no `within:` it is placed against the part of the screen an `inside` block is holding drawing to, else the whole screen, so a heading over a panel centres on the panel. A `draw_number` places its FIELD rather than the number in it, which is what stops a centred score jittering sideways as it counts up. Giving both a column and a `within:`, or a name the verb does not know, is a friendly error. Worked examples: `examples/pong.rb` (each score pushed against the net from its own half), `examples/jukebox.rb` (a menu column centred on its widest song name) and `examples/shmup/hud.rb` (a HUD flush against both edges).
- `text_width "SCORE"` / `text_height` (both take `font:`) — how wide a string comes out and how tall a line is, in pixels. Useful on its own for anything sized to fit words: a box behind a title, a menu window as wide as its longest row, the figures hung one gap off the end of their label. It is the same number on every screen, because every screen advances by each glyph's own width: a bitmap screen as it plots the pixels, a tiled one as it stands each character's little sprite. So a proportional alphabet stays proportional on `screen :tiled`. A live `draw_number` is the exception on both, and on purpose — each digit keeps a column as wide as the font's widest glyph, so a digit that changes never moves the ones beside it.
- **On `screen :tiled`** (no framebuffer) both draw each character as a little hardware-sprite glyph the console composites over the game. Same verbs/args, one rule: **declare them once — above `game_loop`, or inside a `scene`** (where they belong to that scene and show only while it's active), like a `sprite` — they're redrawn for you every frame and a live `draw_number` follows its variable and updates itself (so pass a variable, not a one-off expression). Declaring loose inside `game_loop` is a friendly build error. **A test around the declaration says when it shows**: `(blink == 1).then { draw_text "PRESS START", 76, 100, :gray }` is a blinking prompt — the condition rides onto the glyphs, so they are on screen exactly while it holds, and it is read again every frame like the rest of the HUD. That is one declaration, not a per-frame draw, so it is allowed above `game_loop` and inside a `scene` the same as a plain one (a `.else` shows its text while the condition is false). Glyphs use one 8×8 sprite each, so the built-in `:default`/`:tiny` fonts fit; a HUD costs a few of the 128 sprites.
- `font :name do glyph "A", <<~ART … ART end` — define a font from glyph art (sibling of `image`); built-ins `:default` (5×7) and `:tiny` (3×5 digits). **Or hand it pictures of the letters** — `font :name, glyphs: { "A" => rows_of_pixels, … }, blank: 0` — for a font that already exists, sliced out of an image or decoded from a game's own data, because nobody is going to retype an alphabet as hashes and dots. A glyph is rows of pixel values and a pixel that is not `blank:` is lit, so which ink the picture used never matters; each glyph keeps its **own width**, so an alphabet drawn proportionally stays proportional. Give a block or `glyphs:`, not both. On `screen :tiled` the console draws each character as one 8×8 sprite, so an imported alphabet can be too big for it — a friendly error names the widest character.

## Variables & math

- `var :name, init` → a `Value` handle; the initial value is applied **once at boot**, so declaring a variable inside a scene or loop still initializes it a single time. **One name is one variable however many places declare it**, so a helper that declares its state and is called twice is fine — but two declarations that start it differently (a fraction in one place and a whole number in another, or two different numbers, or a `save_var` and a `var`) are a friendly error naming both lines, because that is two parts of a game that each wanted their own scratch variable and would silently write the same one. `set! :name, value` re-assigns at that point (every time that code runs).
- `var :mode, :title` — **a variable that holds one of a set of NAMES** rather than a count, which is what a game state is: `:title`, `:playing`, `:over`; `:idle`, `:chase`, `:attack`. Write the names and the framework gives each one a number, in the order it first appears — the same bargain it already makes for colours, which you name while the console is handed a number out of a table it never shows you. `mode.set! :playing` moves it on, `(mode == :playing)` tests it, and **`call mode` runs the routine of that name** (see `call` under Scenes & funcs) — a `func`, or a `scene` of that name, and a variable whose names are scenes picks between screens exactly as `case_var` does: each scene owns its text, sprites and scenery and shows them only while it runs (a name that is both a scene and a func is a friendly error) — so a game's states, the tests on them and the routines behind them are one set of names, where otherwise they are a number per state that three separate places have to keep in step by hand. **A pool field says it the same way** (`pool :guard, state: :idle`) and then every instance keeps its own, which is thirty guards each doing their own thing from one line inside `each`. A name joins the set the first place it is used, wherever that is, so a state reached only from inside another routine counts too. It costs exactly what the number costs, since the number is all the variable holds and nothing about the names survives the build. Two friendly errors: `call` on a variable that holds plain numbers (it says to write the list form instead), and a name that has no routine of that name to run.
- `save_var :name, default` → a `Value` handle for a variable that **survives power-off** (a high score, an unlock, a setting). Used exactly like `var`, but its value is kept in the cartridge's save memory: it comes back at power-on with the value it had last time (or `default` the first time the game is ever run), and every change is saved for you automatically — no separate save step. `default` is a whole number. The framework picks and drives the save backend and emits the save-type signature emulators/flashcarts need; no SRAM addresses at the surface. A game can have 1023 of them, which is what the first 4K of save memory holds; one more is a friendly error saying to keep the rest in a `save_data` record. **On 64K or 128K a change is saved a pass later, not on the spot**: that save memory is flash, which takes a byte only once between two wipes of a 4K block, so writing each change in place would wipe a block every time a number moved. There the `save_var`s are kept together as a hidden record with one copy, saved in the background like a `save_data` one on the pass after any of them changes — and at most once in 300 passes of the game loop (five seconds, for a game running at full speed), so a number that changes every frame (a play clock) does not wear the chip out: a chip lasts about a hundred thousand wipes of a block, which that takes hundreds of hours of play to reach. Its last change is saved within 300 passes, and turning the power off before then keeps the save before it. An update to the game that adds a `save_var` keeps the ones saved, and the new one starts at its default. The 8K EEPROM (`save_memory: 8`) keeps them the same way, since it wears with each write too. A game with a `save_var` on flash or the EEPROM needs a `game_loop`, since that is what saves it, and one without is a friendly error. Nothing in the game changes, and on 32K a change is still written as it happens.
- `files = save_data :file, copies: 3 do keep hearts, name, flags end` → a record of the game's own state — variables and lists — **kept in save memory when the game says so**, which is the difference from `save_var`: a player who turns the console off without saving finds the game as it was when they last saved. `files[n]` is one copy (`n` may be worked out as the game runs; a written number the record does not have is a friendly error, and a worked-out one that names no copy does nothing and reads as empty). A copy **saves** (`files[n].save`) the kept things into save memory, **loads** (`files[n].load`) them back — and loading a copy that is not good changes nothing, so `settings[0].load` at power-on needs no test around it — and **erases** (`files[n].erase`). `files.copy 0, to: 2` copies one copy over another (only a good one; the one written over keeps its last save until the whole copy is in), and `files.reset` puts every kept thing back as it was declared — a new game, touching nothing in save memory. `files[n].state` is one of the names `:empty` (never saved), `:erased`, `:good` or `:damaged` (a save that was cut off after its first bytes went in and before it finished, with no earlier one to fall back on — cut before anything went in, the copy reads as it did before the save), with `good?`, `empty?`, `erased?` and `damaged?` as tests; and `files[n].peek(hearts)` reads a kept variable as that copy holds it, without loading it, which is how a file-select screen shows each file's hearts (0 for a copy that is not good); a kept list reads the same way, `files[n].peek(name)[i]` and `files[n].peek(name).length`, which is how it shows each file's name. **The record can come before what it keeps**: `files = save_data :file, copies: 3` with no block is a record the game can save, load, erase, copy and peek at straight away, and `files.keep hearts` adds to it later, from wherever the thing is owned — as many times, from as many places, as the game likes. That is what a file-select screen wants, since it comes first in a game and what it saves belongs to the gameplay declared after it; without it every kept variable had to be hoisted above the screen. A peek can name a thing before it is kept (`files[n].peek(:hearts)`), and is checked once the whole program is declared. The block form is the same `keep`, said at once. **A pool can be kept too**, which is what a save made in the middle of a level needs — every guard where it stood: `files.keep guards` keeps every field of every slot and everything that makes the pool whole again, which slots are live, which are free, how many there are, and each one's facing, place in its animation and colours where the pool has them — so a load puts the same guards back in the same slots and the next one spawned lands where it would have. `files.keep guards.field(:hp)` keeps one field on its own, and a load puts back that field in every slot and leaves the rest of the pool as the game has it. A pool is the dearest thing to keep, since every slot is kept whether it is live or not: thirty guards of a dozen word fields is over 1.4K a copy before the bookkeeping, and the fit check counts all of it. A `reset` (a new game) empties a kept pool, every slot free and every field nought. The record is laid out when the whole program is declared — where each thing sits, how big a copy is, and whether the records fit — so the order things are kept in is the record's shape, and moving a `keep` so that it comes before another changes the shape, which (as below) reads earlier saves as empty. Friendly errors: a record that ends the build keeping nothing, and a peek read the wrong way for what is kept (a list as one number, or a variable item by item). **A save is written in the background, and the game goes on while it is**: a save, an erase or a copy is written a piece each pass of the game loop — a full-size file (1204 bytes) in about five passes — so nothing the player is watching stops for it, even with the save code in the cartridge. What it saves is **the moment it was asked for**: the kept things are copied aside there and then, so a game that changes the hearts on the next pass does not save half of the change. `files.saving?` holds from the moment one is asked for until it is written, which is the game's cue to show saving however it likes — an icon, a line, a locked menu, or nothing — and `files.finished?` holds for the one pass after one is written, the place for "Saved!". `files.failed?` holds when the last one did not read back — the chip did not keep it. **Reading a copy finishes its save first**: `state`, `peek` and `load` of a record with a save still in hand write the rest of it on the spot, so a file screen shown straight after saving shows the save (that pass costs what the rest of the save costs). **Two saves at once**: `when_busy:` says what a save, erase or copy asked for while one of the record's is still in hand does — `:wait` (the default, and the one that loses nothing) goes in line and is written after it, `:replace` takes the place of a job on the same copy that is not written yet, and `:refuse` does nothing and makes `failed?` hold, for a game that locks its menu while it saves. A third job asked for while one is written and one waits finishes the first on the spot. Turning the power off before a save is written keeps the save before it, as a cut half way always did. **What it costs**: each record keeps two snapshots' worth of buffer in the roomy memory, filled at power-on, and a pass that asks for a save pays for copying the kept things aside; `rom.profile` names each save routine after its record ("saving save_data :file"). **Where its save routines run from**: `save_data :file, copies: 3, fast: true` keeps them in the console's quick memory, `fast: false` keeps them in the cartridge, and left out the build decides — the word `func` takes, meaning what it means there. It is worth saying `true` in one case, and it is a case no build can see for itself: a build that measures its game runs it with nobody at the controls, so the game never saves, and the routines that save are measured at nothing and left in the cartridge. The passes of a save then run at the cartridge's speed, and in a game that uses most of each frame one of them does not fit and the game is a frame behind from there — nothing a player would name, and exactly what a game counting its frames against another cannot have. Said, what is kept is what every pass of a save runs: the routine that writes a piece of it, the one that looks the copy over when the last piece is in, and the small routines that keep saves in line — for a game that saves, erases or copies, since a game that only loads writes nothing. The jobs themselves (save, load, erase, copy, reset) run once, on the pass that asks for them, and are a small part of it, so they are left to the build like any routine; kept as well, they came to more than twice the room. It is one record's word: another record that says nothing is left to the build. **What it takes is the reason it is a word and not what every game gets**: kilobytes of the 32K — the two came to about 4.6K for a record keeping one number, and they do not grow with what a record keeps. **They go in after the game loop and the routine that plays the music**, which every frame runs: a save is a few passes now and then, and a word that took the game loop's room would run every frame at the cartridge's speed so as to save at the quick memory's. So the word takes its room from routines a frame spends less in, and where it does not fit beside them that is a friendly error naming the record, never the game loop moved out in silence. Those two go first only where the build would keep them anyway: the routine that plays the music in a game that plays some, and neither in a build told not to choose (`fast_code: false`). A measured build first builds once without its measurement, which cannot yet tell the music is worth the room, so a record that does not fit even beside the game loop is refused there, naming the game loop alone. **On flash or the EEPROM it reaches less far**: the chip is written through a routine of its own for each byte, which always stays in the cartridge, so the word speeds up the save's own work and not the chip's. `fast: false` is for the other way round: a build that does not measure keeps the routines by what the frame can reach, and a game that wants that room for code it runs every frame says so; with every record kept out, the routines that keep saves in line are kept out too. A record whose routines do not fit is a friendly error naming the record, and a `fast:` that is not true or false is one too. **A save cut off half way loses nothing**: every copy is kept twice and a save goes into the older half, which only counts once the whole of it is written, so the power going off mid-save leaves the last good save in place and the other copies untouched. A record whose shape changes in a later build reads old saves as empty rather than as nonsense. **An update to the game keeps every save it did not change**: where each record lives is written in a small table in save memory and read back at power-on, rather than worked out from the records declared before it — so adding a setting to one record, declaring the records in another order, or dropping one leaves the others' saves where they were, and a record given more copies keeps the ones it had (moved into a bigger place when the room after it is taken). A record the game no longer declares keeps its room until a new one needs it. That table is written at power-on when the records changed, which on a first run is the first thing the cartridge writes, and it is kept the same safe way a save is; the one step that is not is the last resort for a nearly full save memory whose free room is in pieces, where records are slid together (and, for a record given more copies, the ones above it lifted to let it grow) and a cut during that can damage one; it is also the one slow step, a few frames at power-on, once. Room a record is given is wiped first, so a copy an earlier build dropped, or another record's old save, never reads as one of its saves. On 32K it all lives after the first 4K of save memory, which stays `save_var`'s, so the two never touch; flash keeps the `save_var`s in a record of their own (see `save_var`), which counts as one of the 16 records a game can have. **How much save memory there is, the build works out**: a cartridge has 32K, or 64K or 128K of flash, and the build picks the smallest that holds every record. `RubyGBA.game "NAME", save_memory: 128` (also on `RubyGBA.build`) names one instead, for a game that wants room to grow — and **`save_memory: 8` is the one size the build never picks**: an 8K EEPROM, the chip retail games with a small save used because it needed no battery and cost least. It is the slowest to write by far, since the console sends it eight bytes at a time a bit at a time and the chip then settles for most of half a frame: so on it a save writes eight bytes a pass, measured at 97 of a frame's 228 lines a pass, and a 1K save takes a little over two seconds while the game goes on. Its save_vars are kept in a record as on flash, for the same reason (it wears with each write). The half-kilobyte EEPROM some cartridges had is not offered: the table of places alone needs more than it holds. The chip is written a block of eight bytes at a time, so what a pass writes is held in a copy of one block and written back as the pass ends. Records that do not fit the size named are a friendly error saying the size they need, and a size no cartridge has is one too. `rom.profile` says which size the cartridge got and whether the game asked for it, what takes the room (each record's copies, the table of places, the block kept for `save_var` on 32K) and how much is free, and on flash or the EEPROM about how many passes a save of each record takes. Flash is wiped 4K at a time, so on it every half of a copy takes whole 4K blocks: a 5K save is 8K a half and 16K a copy, and 128K holds seven of them. **A save on flash takes longer and costs no more frames**: the chip takes a byte at a time and slowly, so a pass writes 32 bytes of a save rather than 256 — a full-size file in about forty passes — and the chip wipes a half before it is written, a block at a time, while the game goes on. The first power-on of a fresh flash cartridge takes a few frames, which is the table of places being written. Friendly errors: a record declared twice, or given `copies:` below 1; a record name that is not letters and digits with one underscore between words (`:file`, `:high_scores`), since a record's save routines are named after it and an odd name could run into another's; `keep` given anything but a `var`, a `list`, a `pool`, a pool's `field`, or `random_numbers`; a field a pool does not have; a thing kept in two records; a `save_var` kept in a record (it saves itself); `peek` of something the record does not keep; and records too big for save memory, naming each record's bytes. On the interpreter the save memory is a `RubyGBA::IR::SaveImage` handed to `Reference.new(save:)`, laid out byte for byte as the console lays out its chip, so the same one given to a second run is the same cartridge powered on again, and the Verifier takes it too (`save:`) to start the console from those bytes. **A test can write a save straight in rather than play until the game makes one**: `Reference.save_into(SaveImage.new, program, :file, 0, hearts: 12, name: [76, 73, 78, 75])` writes copy 0 of `:file` holding those values and hands the image back — a whole number for a variable, a Float for one holding a fraction, an Array for a list, `random_numbers:` for the random numbers — and what it does not name keeps the value it was declared with. The copy is written by the game's own save routine on the interpreter, so it is the copy the game would write, on 32K or flash alike, and the game treats it as its own: good, peeked, loaded, saved over (that save counting as newer), erased and copied. Other copies and records already in the image are left alone, so one built cartridge can start from as many saves as a test wants. A record that is not declared, a copy it does not have, a name it does not keep (the error lists what it keeps), a value of the wrong kind (a list for a variable, a Float for a whole number or the other way round), a list past its capacity and an item too big for its slot are friendly errors; so is a pool, or one field of one, which cannot be written yet. **A `save_var` is written the same way**: `Reference.save_vars_into(SaveImage.new, program, best: 9999)` hands back an image the game starts with that high score, written by the game's own code on 32K or flash alike, and the save_vars it does not name keep what power-on gave them. A name that is not one of the program's save_vars (the error lists them) and a value that is not a whole number are friendly errors. Worked example: `examples/hero.rb`, whose file screen shows three walks, greys CONTINUE on an empty file, and saves with START.
- `saves_keep_everything except: [:mode]` — **the build refuses a game whose records leave some of its state out**, for a game that saves in the middle of play. Such a save is right only while it keeps everything the play depends on, and the way it goes wrong is quiet: a variable added to the game later and never added to a record, and the load puts back everything else while that one thing stays as it was. Say this once, anywhere in the game, and at the end of the build every variable, list and pool the game declared — and the random numbers, if it rolls any — must be kept by some `save_data` record or named in `except:`, which is for what a load must leave alone (which screen the game is on, a setting the player chose). The friendly error names every thing no record keeps. A name that starts with `_` is scratch and never needed, a `save_var` saves itself, and nothing the framework keeps for itself counts. **A pool counts only when it is kept whole**: one field kept on its own leaves which slots are live as they were, so a game that means that names the pool in `except:`. The random numbers are `:random_numbers` there. A keep or a declaration written inside a `func` counts, since the check runs once every routine is built. It costs nothing in the cartridge. Friendly errors: a name in `except:` that the game does not declare, a name in `except:` that a record keeps after all, saying it with no record in the game, and saying it twice.
- `add! :name, operand` (alias `add_var!`) / `sub! :name, operand` (alias `sub_var!`).
- `copy! :dest, :src`, `negate! :name` (alias `flip!`), `abs! :name`, `negate_abs! :name`.
- `clamp! :name, min, max`, `approach! :name, target, step` (move toward, capped). Both `clamp!`'s bounds and `approach!`'s step can be fixed numbers **or** things the game works out as it runs (`x.clamp! 0, limit`, `level.approach! 100, speed`) — a limit that depends on the level, an easing whose speed changes. A floor worked out to above its ceiling gives the ceiling, since the value is held at the floor first and the ceiling second. A computed `approach!` step is read as a distance, so a negative one still moves toward the target and `0` holds still. Fixed values cost exactly what they always did; only a computed one costs more.
- **A word without `!` never changes a variable.** `abs`, `clamp`, `approach`, `flip` and `negate_abs` on a variable or a pool field are NEW numbers — the number the `!` word would store, with the variable left as it was — which is what Ruby's own `Integer#abs` and `Comparable#clamp` promise, and what `(apart.abs <= reach)` reads as. So `d.abs <= 5` asks how far d is from nought and leaves d's sign alone, `d.clamp(0, 9)` is a number to compare or store, and `d.approach(target, step)` is where d would be one step on. To change the variable, end the word in `!`: `d.abs!`, `d.clamp! 0, 9`. The old spelling on a line of its own now works out a number nobody keeps, which is a friendly error naming the `!` word, and a flat verb without its `!` (`abs :d`) is a friendly error too. A new number costs about what its `!` word does, with nothing stored: `abs` a compare and one instruction, `clamp` two compare-and-replace steps.
- Introspection: `variables`, `var_address :name`.
- **Expression DSL** (on a `Value`): `+ - * / %` and unary `-x` (the value the other way round, leaving `x` alone — `.flip` is the same number, and `.flip!` the same idea as a *mutation*), `.abs`, `.clamp(lo, hi)`, `.approach(target, step)` and `.negate_abs` (new numbers, see above), comparisons `> < >= <= == !=` → a `Condition`; change the variable with `.set!/.add!/.sub!/.clamp!/.flip!/.approach!/.abs!/.negate_abs!`. Compose conditions with `&` (both) / `|` (either); branch with `.then { } .else { }`. **An expression you build and never keep is a friendly error**, because it did nothing at all: `flags | 4` hands back a NEW number and leaves `flags` as it was, so changing the variable is `flags.set! flags | 4`. Take care with Ruby's own shorthand too — `flags |= 4` reads as `flags = flags | 4`, which moves the *Ruby* name onto the new number and leaves the game's variable untouched, with the name still looking right afterwards. `hp + 1` where you meant `hp.add! 1` is the same slip. Naming a handle on its own (`hero.x`) is not an error — it is pointless but harmless, since there was no work to throw away. A **comparison costs about twice what `+` or `-` does**, and there is nothing to write differently — adding two numbers is the answer, where comparing them leaves the console to turn its flags into a yes or a no. Worth knowing only where a condition sits in the hottest loop of a frame; anywhere else it is not the thing to look at.
- **Say how often a branch runs:** `.then(estimate: { usually: 0 }) { … }` — the same word a `list`, a `pool` and a `repeat` take, and it matters here for the same reason. A test the game works out is one nothing at build time can see through, so **unsaid, the body is counted on EVERY frame**, and that is often badly wrong: a death animation, a screen that repaints only when a number changed, a routine answering a rare event — each reads as ordinary every-frame work and sends you optimising the wrong thing. `usually:` is how many frames in every `in:` run the body, and `in:` left out means one frame — so `usually: 0` is "not on a normal frame" and `usually: 1, in: 60` is "about once a second". The **worst frame is unchanged**: a frame where the body does run pays for it whole, however rare you said it was. Unsaid keeps counting 1 on purpose, which is the opposite default from a loop's — an uncounted loop was charged *nothing* and had to be made loud, where an uncounted condition is merely pessimistic. Not quite free of consequence, and the one thing to know: what the framework keeps in the console's quick memory is chosen by what a frame costs, so telling it a body is rare can hand that memory to something that really does run every frame. That is the point rather than a side effect — it is a speed difference and never a difference in what the game does.
- **The bits themselves** — `&` `|` `^` `~` `>>` `<<` on a value, against a number you wrote or another value. **What they are for is packed data**, and packed data is what a real console's own files are made of: a background map cell holds a tile number, two flip flags and a colour group in one half-word; a collision shape is one bit per pixel; a save file is flags all the way down. `&` keeps the bits both sides have, which is how a field is pulled out and how a flag is tested; `|` keeps the bits either side has, which is how one is put back and how a flag is set; `^` keeps the bits exactly one side has, which turns a flag over; `~` turns every bit round, so `flags & ~DOOR_OPEN` clears one; and `>>` and `<<` slide the bits along. **Dividing is not a substitute, and that is why these exist rather than being sugar**: a mask over two fields that are NOT next to each other — asking about bits 2 and 7 in one go — has no arithmetic form at all, in any number of steps. They are also the cheap way to say what you already meant. `x & 15` and `x % 16` are the same single instruction, so the mask was always what got emitted and the surface simply could not name it; but `x >> 4` is one instruction where `x / 16` is three, because dividing has to correct the sign of a negative number and sliding the bits does not. **`>>` keeps the sign** — a negative number stays negative — which is what both the console and Ruby do. **A number you wrote can stand on the left of `&`, `|` and `^`** (`0x0F & flags`) but not on the left of a shift: Ruby will not have a worked-out number to the right of `<<` or `>>`, so `0x8000 >> col` is a friendly error saying to write `(row >> col) & 1` instead, which reads the one bit and is the same answer. **A count of 32 or more empties the number** — nothing left going up, and going down the sign filling in, so 0 or -1 — and **a negative count does the same rather than turning round and shifting the other way**. That is the one place the framework declines to follow Ruby, which does turn round: a negative shift count in a game is a mistake, and reversing direction quietly hides it. A count you wrote costs one instruction; a count the game works out costs a few more, since it has to be held inside that range first. **A count that empties the number and is written down is a friendly error**, since a person who wanted nothing would have written nothing; the same count worked out as the game runs is left alone, because that one comes out of data and can land anywhere. Two more friendly errors, both for slips this borrows straight from C. A bit operation on a number that **holds a fraction**: the fraction is kept in the low bits, so a mask would change the fraction and not the number you can see — use `.to_i` first. And **`.then` on a number**, which is how a flag test is written in C (`if (flags & MASK)`) and is the first thing most people write here: Ruby gives every object a `then` of its own, so that would run the block while the program was being BUILT and record its body with no test around it — the body running every frame with nothing said. Compare the number first: `((flags & MASK) != 0).then { … }`.
- **`%` wraps a value onto a range** — Ruby's meaning, so `-1 % 64` is 63. That's what you want for an angle that stepped below zero (it comes back near a full turn) or a map coordinate off the left edge (it comes back against the right one). `/` truncates toward zero (`-7 / 4` is `-1`), so `/` and `%` don't decompose on negatives — `%` follows Ruby because you know Ruby.
- **Dividing by zero has no answer, so the framework gives one**, and it is the same on the interpreter and on the console: `/` gives 1, or -1 for a number below zero, and `%` gives the number back as it was. The game does not stop on either, which is the point — a console has nobody to stop for, so a test on the interpreter shows what the cartridge will do. A number that holds a fraction gets the same bare 1 or -1, which it reads as the smallest fraction there is and not as 1.0. So a divisor that can reach zero wants a floor (`x / d.clamp(1, 99)`), the same advice the fraction divide gives below. A zero **written** as the divisor (`x / 0`, `x % 0`, or a fraction too small to keep, which is stored as 0) is a friendly error, since that one the build can read.
- **Dividing costs what its divisor makes it cost**, and there is nothing to write differently — the build works out which case you are in. A number **you wrote in the program** never calls the console's divide routine: a power of two (2, 64, 256) is a shift and costs about three quarters of a plain step, and any other fixed number (10, 60, 100) is turned into a multiply at build time and costs about twice a plain step. A divisor **the game works out** (`x / d`, where `d` is a variable) is the dear one, at about five times a plain step, and it is the only one whose cost depends on the numbers — it works the answer out a bit at a time, so a big answer costs about two and a third times a small one. `%` follows its `/`. (Throughout, **a plain step** is one ordinary statement — `x.add! 1`.) The build works out which of the three you wrote; a power of two is a shift and costs nothing worth naming.
- **Numbers with a fraction** — a variable holds whole numbers, so a game that needs halves and quarters (speeds, angles, anything smooth) has to keep them another way. **Write a Float and it is handled for you**: `var :px, 3.5` declares a variable that holds a fraction, `table :sin, (0...512).map { |a| Math.sin(...) }` a table of them. The scale is declared once, there and nowhere else — every handle for that variable carries it, and arithmetic carries it along.
  - `+ - < >` and friends: a number **written in your program** is converted for you (`speed + 1` means one faster). Mixing a fraction with a whole number **the game works out** is a friendly build error naming your line — say which you meant with `.to_f` or `.to_i`.
  - `*`: times a plain **count** is ordinary multiplication (`speed * 2` is twice as fast). Times another **fraction** is the one that would overflow — two multiplied-up numbers come out multiplied up twice, far too big for a variable (1.5 × 1.5 needs 9,663,676,416 on the way) — so the framework works that product out at full width automatically. You never have to spot which of your multiplies is the dangerous one, which was the whole problem.
  - `/`: by a plain count is ordinary division. By another **fraction** it is the mirror of the multiply above — two numbers multiplied up by the same amount would divide that amount straight back out, so the framework widens the numerator first and the answer keeps its fraction (`3.0 / 2.0` is `1.5`, not `1`). A plain number can stand on the left too: `WALL_HEIGHT / distance` is the perspective divide, and `examples/raycaster.rb` uses exactly that for its wall heights. **It is the dearest arithmetic there is** — about eighteen times a plain step, where every other divide is three quarters to five — because it walks the whole width of the answer, and a hot one is worth precomputing into a `table` instead. An answer too big to hold is held at the end of the range rather than wrapped, so dividing by something very near zero gives the biggest number there is and not a negative one. **That protection does not survive the next step, and this is worth knowing before you need it:** the answer is now AT the end of the range, so adding anything to it wraps — `(WALL_HEIGHT / distance + 0.5).to_i`, the ordinary way to round a perspective divide to the nearest pixel, comes back very NEGATIVE once the divide has saturated. It bit exactly where you would expect: a first-person view, a player standing a hair from a wall, and the wall vanishing because a negative height draws nothing. **Give the divisor a floor** (`WALL_HEIGHT / distance.clamp(NEAREST, FAR)`, which holds the number divided by and leaves `distance` itself alone) rather than the answer a ceiling — a floor on the distance costs one clamp and changes nothing you can see, where a ceiling on the height holds a near wall short across the whole last half-cell, which a player can see plainly.
  - `.to_i` — drop the fraction (rounds down), for a pixel coordinate or a table index. **One instruction**, not the divide it replaces. `.to_f` — give a whole number a fraction so it can meet one.
  - Worked example: `examples/raycaster.rb`, where positions, ray steps and distances all hold fractions and the word "fixed point" never appears.

## Control flow

- `game_loop do … end` — the per-frame loop. It runs its body once per frame: the framework waits for the screen and repaints your sprites and HUD at the top of every pass, so you never write a frame sync. **The screen stays switched off until the first of those frames is set up**, so whatever the game says before its loop — a flash or a fade it opens on, sprites placed, a picture painted — is all in force on the first frame anybody sees, however long setting up takes. A console with its picture switched off shows plain white, so a game that takes a while to set up opens on a frame or two of white, where it used to open on its picture without any of that. Build with `frame_sync: :manual` (on `RubyGBA.game` / `RubyGBA.build`) to place `wait_vblank` yourself.
- `repeat(n) { |i| … }` — runtime-counted loop (n may be a `Value`/list length). **A loop given `stop_when:` leaves as soon as that holds**, which makes `n` a ceiling rather than a number of passes — so `estimate: { usually: N }` says how many it normally makes, exactly as a `list` and a `pool` do, and changes nothing about how the game runs. It matters more here than for either of those, because a ceiling is picked so it can never be reached AND this kind of loop usually sits inside another one, so counting the ceiling multiplies: a ray that gives up after 48 crossings meets a wall in about 4, and 80 rays make that the whole frame. Nothing reads it today — it was written for a build-time estimate that has since been deleted in favour of measuring the game — and it stays as documentation of intent, because a ceiling is picked so it can never be reached and says nothing about a normal frame. **A loop counted by something the game WORKS OUT — `repeat(n)` where `n` is a variable — is the one shape with no number anywhere in the program**, neither how many passes it makes nor the most it could; that one takes `estimate: { usually: N, most: M }`, and `most:` is refused anywhere else because a written count or a `stop_when:` ceiling already says it. Counting, testing and jumping back costs something before the body does anything, so a long loop over a cheap body is mostly loop — and **what it costs depends on where the count is kept**, which the build decides and you do not write. Kept in the console's own registers it is less than a plain step a pass; kept in memory it is about one and a half. And **a loop whose body never uses `i` is cheaper still**, because nothing needs 0, 1, 2 and it can count down to nought instead, which spends no compare. The build uses registers whenever the body leaves them free, and a body that **calls a routine, holds another loop, runs a scene, or drops to raw instructions** needs them for that instead. One such statement is worth saving the registers around, so they are kept; two or more cost more to save around than memory does, so the count goes there — so moving a call out of a hot loop is worth doing, and `rom.profile` shows the routine getting cheaper when you do.
- `every(n) { … }` / `every(0.5, :seconds) { … }` — run on a beat. `after(n) { … }` — once, n frames in.
- `once_a_frame { … }` — run a body **once a frame**, wherever the game's own code goes that frame, and **once for each frame that really passed**. It differs from the same code written in `game_loop` in two ways. It always runs — a branch or a scene switch can step over a loop body, and this runs anyway, in the gap between frames — which makes it the home for an effect you set off once and something has to carry along afterwards (`shake_screen` is built on it, and it's the seam an effect pack uses). **And it keeps real time.** A pass of the game loop is one frame on a game that fits and two on a game that doesn't, so a body run once per *pass* silently slows down when the game does: a half-second fade would take a second and a half. This one is run again for each frame that really passed, so it takes as long as it says whatever the game is doing (a very slow pass is capped, so a game is never asked to catch up half a second inside one already-late frame). That makes it where anything that must keep time goes. **Movement written straight in a `game_loop` moves a step per pass**, so a game too heavy for a frame runs in slow motion — smoothly and uniformly, which is safe and is the default; move it in here and the world keeps real time instead (`once_a_frame { hero.walk }` with the drawing left in the loop). **What goes in here is what MOVES, not what a press does**: a button read on its edge (`pressed`) has to be read once per press, so leave the trigger in the loop — read here, one pull of it would fire a bullet for every frame a late pass answered for. Optional name (`once_a_frame(:name) { … }`) if something has to find the routine later.
- `timer :name, per_second: N` → a `Timer`: a free-running hardware counter that ticks N times a second, independent of the frame loop. `t.ticks` → a `Value` (how many ticks so far, wraps at 65536); `t.on_tick { … }` runs a body on every tick, precisely, off the timer's interrupt (a low-level building block higher-level verbs sit on — a game rarely writes it directly), and like `once_a_frame` it is the timer's from power-on wherever it is written — one inside a routine nothing calls still runs, and a second for the same timer replaces the first; `t.stop` freezes it. For frame-paced gameplay timing prefer `every`/`after`; reach for `timer` for precise/free-running timing (and it's the clock sampled audio will ride on). **A fast `on_tick` is not free:** the rate decides the cost, and it's written on the `timer` rather than near the handler — at `per_second: 4000` the body runs 67 times a frame, which is ~5 of a frame's 228 scanlines with a one-line body, and there is a cost per tick before the body does anything. **And a rate can be more than the console will deliver:** a tick that arrives while the last one is still being answered is lost — there is no queue — so a handler too long to finish between two ticks answers every second tick, or every third, and the game silently runs at a fraction of the rate you asked for. **`rom.profile` counts the ticks that really arrive** and says the rate you are getting against the rate you asked for, so this stops being silent. What it will NOT do is tell you whose fault it is, and that is measured rather than modest: **drawing costs ticks too**, because a transfer stalls the console and holds interrupts off while it runs — with a handler that does one addition, one full-screen `clear_screen` a frame costs about a fifth of a 4kHz timer's ticks and four of them cost three quarters. A handler too slow to keep up answers every second tick, which is half. The two ranges overlap completely, so no rule could tell them apart, and a warning that blamed your handler would send you to rewrite the wrong code. You get the number and both causes.
- Low-level (asm-tier): `if_eq` / `if_ne` / `if_gt` / `if_lt` / `if_ge` / `if_le` (`:var, operand`) with aliases `if_gte` / `if_lte`. Prefer the `(a > b).then { }` expression form.

## Scenes & funcs

- `func(:name) { … }` + `call :name` — a subroutine. A `func` or a `scene` that nothing calls is a friendly warning naming it, since it is still in the cartridge and never runs; a call from anywhere that runs counts — the game loop, the lines before it, a timer's handler, another routine that is itself called, a `case_var`, a call picked by number or by a variable's name. `func(:name, fast: true) { … }` keeps it in the console's quick memory, where code runs about **two and a third times faster** — you rarely need to say so, because the framework works out which routines a frame spends its time in (the game loop's own body first of all) and puts them there for you. Say `fast: true` to insist on one it didn't pick, or `fast: false` to keep one out. A `scene` takes the same word, and the routine the build makes to write that scene's moving sprites goes with it either way. `rom.profile` lists what it chose, **how big each one is**, how much of the 32K is left, and — the part worth reading — **what did NOT fit**, with what it wanted and what was left. A routine the frame spends real time in that just missed is where a game lost that whole factor, and nothing else can tell you afterwards. To stop it choosing at all, build with `RubyGBA.build(..., fast_code: false)` — a routine you marked `fast: true` still goes. It can never overrun the memory on its own: the choice is made afresh each build from what the game actually uses, so a game that grows gets a smaller share, never a broken build. **`func` is about SIZE as much as speed**, and this is the one thing about the framework you cannot work out by reading your own program: a plain Ruby method called from inside a build block runs at every call and records its work THERE, so a helper written once and called from eight places is emitted eight times. A `func` is emitted once and called eight times. Measured in a real game, two such helpers made one routine 27.9K — too big to keep in the quick memory, which cost the whole factor; as `func`s they were emitted once, both were kept, and the code they held ran at the quick memory's speed instead of the cartridge's. When a routine misses its place, `rom.profile` names its most repeated line and says whether several lines repeat together, which is what a helper looks like from the outside. **A body is built after the whole program block has run**, not at the line that writes `func` — which is why a `call` may come before the routine it names. And a `func` written inside another routine's body is built too, however deep that goes, so a routine can be declared **the first time something needs it**: a restart routine declared only by the code that asks for a restart is in the cartridge when a game restarts and costs nothing in one that never does.
- `call HANDLERS, number: opcode` — **one of several routines, picked by a number the game works out.** A plain `call` names one routine; give it a list instead, and `number:` says which of them, counting from 0. What it is for is a number that came out of DATA rather than out of your program: the instruction byte of a script read off a cartridge, the state kept on each of thirty guards, the move an enemy chose. **It goes straight to the routine that number names**, so a list of a hundred and thirty-nine costs exactly what a list of two does — where asking "is it this one?" of each name in turn costs a test per routine, and every one of them is asked on every call. Measured on a game dispatching sixteen times a frame: about 640 instructions a frame either way, against about 22,800 for the tests written out. **A number naming no routine calls nothing** — below 0, or past the end of the list — so a number read out of data needs no test around it, the same answer `show_map` and a song list give. The number may be a variable, something worked out on the spot, or **a field of an instance inside a pool's `each`**, which is the case this exists for: one line there runs a different routine for every one of them. A number you write in the program picks while the cartridge is built, so `call HANDLERS, number: 2` is the plain `call` it would have been. **Or write no number at all**: `call mode`, where `mode` is a variable declared with a name (see `var :mode, :title` under Variables & math), runs the routine that variable names — the same dispatch with the numbering taken off your hands. That is the one to reach for when the game invents its own states; this one is for a number that came out of data. Five friendly errors: `number:` on a single routine, a list with no `number:`, an empty list, something in the list that is not a routine's name, and a written number past the end of the list. A number that holds a fraction is a sixth (use `.to_i`), since the fraction is kept in the low bits and would pick by those.
- `scene(:name) { … }` — a named game state (a routine run once per frame while active). **It takes `func`'s `fast:` word, and the word carries the scene's sprites with it**: `scene :file_screen, fast: false` keeps both the scene's code and the routine that writes its moving sprites in the cartridge, and `fast: true` insists on both. Worth saying about a menu, a title or a game-over screen: what goes in the quick memory is picked by measuring every scene for the same number of frames, so a menu the player sees for seconds counts as much as the scene they play in, and a busy one can take the room ahead of the game — or push the game out. Nothing the scene does changes; `rom.profile` shows where it went. Hold the current state in a variable (`var :state, 0`); `case_var(:state) do when_val 0, :title; when_val 1, :playing; … end` runs exactly one scene per frame; `set! :state, N` transitions (e.g. `pressed(:start).then { set! :state, PLAYING }`).
- **A scene owns what it draws — and that is a budget, not only a look.** The console keeps every sprite picture a game might show in 32K, and a sprite declared inside a scene is on screen only while that scene is the active state — so no two scenes' pictures are ever wanted at once, and **the budget a game has to fit is one scene's, not the whole game's**. A game with more art than 32K still builds so long as no single scene has too much, which is what lets a game with hundreds of rooms declare each room's cast where it belongs. A scene's pictures are sent when it takes over rather than at boot, so staying in a scene costs one comparison a frame and changing scene costs a copy. Running out inside one scene is a friendly error naming that scene and its biggest pictures. **The same is true of BACKGROUND LAYERS**, and for the same reason: the console holds four scrolling layers at one time, a `background` declared inside a scene is up only while that scene is, and scenes take turns with them — so a game with many rooms declares each room's scenery in the scene the room belongs to and gets four layers in each, where four for the whole game would not go far. Scenery declared OUTSIDE any scene is up throughout, so it is in every scene's four (a backdrop plus three per scene). Running out is a friendly error naming the scene. **The scenery's MEMORY takes turns as well**: the console keeps every tile picture and map on screen in 64K, and a scene's own tiles and maps go in as it takes over, into room the other scenes use too — so a game whose scenes together hold far more than 64K of scenery builds, as long as no one scene (with what every scene shows) holds more. What it costs is a copy on the frame a scene takes over, with the layers switched off while it runs so the backdrop shows rather than half-sent art, and cartridge space: a scene's own art is stored unpacked, because the console unpacks slowly enough that a big scene took frames of game logic away on arrival. Unpacked, even the largest maps arrive inside the frame, and a scene's logic runs from the frame it takes over on both backends. A scene that runs out is a friendly error naming it. **So do the sixteen groups of colours sprites draw from** (see `draw_with`): a scene's sprites and lists take their groups while it is up, and running out inside one scene is a friendly error naming it. **And so do the groups BACKGROUNDS draw from** — fifteen of that table's sixteen, since the first holds the colour behind everything: the colours of the scenery every scene shows keep their places throughout, and each scene's own scenery takes the rest while it is up, its table sent with its tiles as it takes over and through any tint or fade in force. So a title whose light rays keep a group to themselves for `draw_with` and a room whose tiles fill every other group both fit, where one table for the whole game would not; a scene whose own backgrounds need more than there are is a friendly error naming it. What it costs is a copy of the table on the frame a scene with backgrounds of its own takes over. Nobody writes a layer number, and nothing about the picture changes: a game that declares no scenes is one screenful and comes out exactly as it did. And **two sprites showing the same picture store it once**, whatever they are — which is what makes a `pool` of thirty-two affordable, since each of its slots is a sprite of its own and used to keep its own copy of the art. Nobody writes any of this; `rom.profile` says how much of the 32K is used, how much of that sharing saved, and how many pictures turned out to be repeats.
- **A scene owns what it draws.** A `sprite`, `draw_text`, or `draw_number` declared **inside** a scene belongs to that scene — it's on screen only while that scene is the active state. Belonging to a scene *is* the visibility, so switching state switches the whole screen (a game-over screen hides the field and shows its own banner) with **no per-draw visibility flag**. Sprites/HUD declared at the top level (outside any scene) are always shown — a persistent HUD. Worked example: `examples/shmup.rb` (a PLAYING scene and a GAME OVER screen). **A sprite on `screen :bitmap` keeps that promise too, and there it is more than hiding**: a bitmap sprite is painted into the one picture and remembers what it covered, so a scene's sprite is put on the picture while its scene runs and taken off again, with what it covered put back, when another scene takes over. It is repainted in the gap before each frame like a sprite declared above the loop, in the same two passes, so the two kinds can cross each other and neither leaves a trail. **It first appears the frame after its scene's first pass**, one frame later than a tiled sprite does, and that is on purpose: the pass a scene takes over is its turn to paint its own field, and a sprite put down before that would remember the last scene's picture and put a square of it back a frame later. So paint a scene's field on its first pass, or where the game changes scene (`clear_screen :black` and then the state, with the leaving scene's sprite still up, is fine — see the `sprite` entry), and the sprite arrives on top of it. What it costs is one store a pass in each scene, saying which scene ran last; a game with no bitmap sprite inside a scene emits none of it. A sprite declared inside a `func` is repainted the same way, and belongs to no scene.
- **A scene can be a class in its own file.** Like the multi-file parts pattern, a screen can be a plain object: construct it *inside* its `scene` block (so its sprites/HUD are tagged to that scene) and call its per-frame `update` — `scene(:playing) { s = PlayingScreen.new(self); s.update }`.
- **Per-scene display mode.** A scene may declare its own `screen` at the top of its block (a direct-color bitmap title, a double-buffered play scene, a tiled game) and the framework switches modes on the transition — a scene's `sprite`/`draw_text`/`draw_number` pick software vs hardware from *its own* mode, and crossing bitmap↔tiled flips which display system presents so the old screen doesn't bleed through. This works on both backends: the reference interpreter models it (including a bitmap title handing off to a tiled game), and the GBA backend reconfigures the whole display live on the crossing (the mode register plus the VRAM/OAM layout — tiled assets are re-uploaded on entry since a bitmap scene reuses the same video memory). Coming back from a bitmap screen, a tiled scene shows its own backgrounds and sprites on a clean backdrop, and everything every tiled screen shows is put back too — the backgrounds declared outside any scene, as declared (cells changed with `set_tile` shut again and the first map showing, the same as a scene's own), still scrolled and turned as the game left them, and pictures the game paints from a list, each as its list holds it then. **A bitmap sprite every scene shows — declared above the loop, or inside a `func` — is on screen in the bitmap scenes only.** It is painted into a picture, and a tiled scene has none: the memory a bitmap screen keeps its pixels in is where a tiled one keeps its tile pictures, so painting the sprite there would write a sprite's worth of pixels over the tiles. So it is left off while a tiled or rotozoom scene is up, a `show` said then waits, and it is drawn again the frame after a bitmap scene's first pass, the same wait a scene's own sprite makes. A character meant to be on every screen of such a game is declared in each scene, where it gets the kind of sprite that screen draws. What it costs is one store a pass in each scene, saying which kind of screen it draws on, and a compare a frame for each such sprite; a game whose scenes are all bitmap emits none of it. A single-display-system ROM (all bitmap, or all tiled) is unaffected. `examples/` — see the per-scene-mode and scene-display-mode tests.
- `dump_func :name` — disassemble a func from the built ROM (debug).

## Input

- `held(:left)` — 1 while down; `pressed(:start)` — 1 on the press edge only. Use with `.then { }`.
- `held(:any)` / `pressed(:any)` — **any button at all**, which is how a game leaves an attract screen, a splash or a cut scene: `pressed(:any).then { mode.set! :title }`. `pressed(:any)` is true on a frame some button went down, the same edge each button has on its own — so A pressed while LEFT is still held counts, and a button held on and on is one press. It is one test against all ten buttons, cheaper than the ten `held` tests joined with `|` it replaces, and none can be left out. `:any` is not a button: a test's `hold(...)` and the command line's held keys refuse it, since holding "any" means nothing.
- Low-level: `if_held(:a) { }` / `if_pressed(:a) { }`. Buttons: `a b select start right left up down r l`.

## Menus

- `menu :name, at: [x, y] do |m| m.item("NEW GAME") { … } end` → a `Menu`: **a list of rows, a cursor that moves between them, and a block per row saying what picking it does.** Nearly every game has one, and what a game wrote before this verb existed was the same thirty lines every time — a variable holding which row is picked, two button tests doing the wrapping by hand, one pass drawing every row dull, a second redrawing the picked one bright, a cursor drawn beside it, and a test for the button that acts. `examples/jukebox.rb` is the worked example, and it wrote that badly enough to be worth reading twice. Up and down move the cursor and **wrap at both ends** (the half people get wrong is going up off the first row); the `press:` button runs the picked row's block, on the press edge, so holding it chooses one time. **Holding a direction walks the list** rather than moving one row and stopping — after a move it waits `repeat_every:` frames, and letting go clears the wait, so a tap always moves exactly one row however long you held the last one. **Which row is picked survives leaving and coming back**, so a submenu you back out of opens where you left it — that is free, because the pick is a variable and a variable's starting value is applied one time, at power-on. Call it where the frame's work goes — **inside your `game_loop`, or inside a `scene`** — since a menu reads the buttons and draws its rows again every frame; a menu above the loop is a friendly error. **That rule is the same on both screens**, which is the point of it being a verb rather than text you place: the menu owns its own drawing, so nothing about where it goes changes with the screen the way a bare `draw_text` does. **What it COSTS does change, and it is worth knowing before writing a long one.** On `screen :bitmap` the rows are painted into the picture, so they cost drawing time and no sprites. On `screen :tiled` (and `screen :rotozoom`) the console composites the text for you, and every character is one little sprite of its own — out of the same table of 128 the game's own sprites come from. So reckon **about one sprite per character** of a label, and none at all for a space: eight rows of ten characters is about 72, and twelve rows of twelve does not fit and says so. (One and not two because a row lights up by CHANGING COLOUR rather than by being drawn twice — see `draw_text`'s `showing:`. The cursor is the only per-row extra, being shown or hidden rather than recoloured.) A tiled menu takes a place in the stack like anything else the console redraws (wrap the call in a `layer` block); a bitmap one cannot, and the friendly error says `menu` rather than the `draw_text` underneath it. Worked example: `examples/pong.rb`, whose title menu runs on `screen :rotozoom` over a zooming backdrop.
- `m.item "SOUND", enabled: false, color:, picked:` — one row. **A row that cannot be picked is stepped OVER, not landed on**, in both directions, and is drawn in the menu's `disabled:` colour: a Load Game with no save, a Resume with nothing to resume. Which rows those are is settled as the program is built, so each one costs a single test and a menu with nothing disabled emits none at all. **A row the game opens and shuts** takes a test instead of true or false — `m.item "CONTINUE", enabled: files[0].good?` — or a variable holding 0 or 1: while it holds the row is drawn and picked as usual, while it does not the row is dim, the cursor steps over it, and the button does nothing on it (the cursor can be sitting on a row when the game shuts it). That costs a walk rather than a single test, since which rows to step over is only known as the game runs — never more than once round the list, so a menu whose rows are all shut holds still — and each such row is drawn under its test both ways; a menu with no such row pays none of it. `color:` and `picked:` give one row its own two colours (jukebox lights each song in its own accent). The block is what picking the row does, and a row can have none at all — on a screen where MOVING is the choice, like jukebox's, whichever row the cursor is on is the tune that plays.
- `m.item ["MUSIC: OFF", "MUSIC: ON"], showing: music` — **a row whose words change**, which is what a settings row is. Give it the list of things it can say and the variable that decides which, and the words the value points at are the ones on screen. They are **part of the row**: they light up with it, the cursor points at them, and the block under them is what changes the value they show — where a label plus a separate `draw_text` of the value beside it would leave the value outside the row, in whatever colour it was drawn in. A list without `showing:`, or `showing:` on a row that says one thing, is a friendly error. It costs what it says: each of the things the row can say is drawn under a test, so a two-way row is twice a plain one. Worked example: `examples/pong.rb`'s title.
- `menu :difficulty, at: [x, y], starts_on: 1 do |m| … end` — **which row the cursor opens on**, counting from 0. It opens on the first row that can be picked unless you say otherwise, which is right for almost every menu and wrong for the one that matters: a difficulty screen recommends a setting, and its rows run gentlest to hardest, so a player who presses the button straight through should get the game the author meant rather than the easiest one. That is a real difference in how hard the game is, not a cosmetic one. Writing the rows in another order would say it too, and would then lie about which is harder — so the recommendation is a number the menu is given instead. It applies **once, at power-on**: the cursor moves from there like any other, and a menu you back out of still opens where you left it rather than jumping back. Naming a row that cannot be picked is a friendly error (the cursor never lands on one, and quietly moving your start would hide the mistake), and so is a number outside the list, which says how many rows there are. Worked example: `examples/pong.rb`, whose title opens a difficulty screen of two rows with the cursor on the harder one.
- Decoration the game **says** rather than builds: `spacing:` (pixels from one row to the next; the font's line height plus a gap by default), `color:` / `picked:` / `disabled:` (the three row colours), `cursor:` (what is drawn to the left of the picked row, `">"` by default, `""` for none), `font:`, `press:` (which button chooses, `:a`), `repeat_every:` (frames a held button waits before it walks on).
- The handle reads back: `m.picked` → a `Value` (which row, counting from 0 — setting it jumps the cursor), `m.moved` → a `Condition` true on the frame the pick changed (a sound, a preview that reloads — `songs.moved.then { beep :blip }`), `m.length` → a build-time Integer.

## Lists (runtime-sized collection)

- `list :name, capacity: N` → a `List`: `push`/`<<`, `pop`, `shift`, `[]`, `[]=`, `first`, `last`, `length`, `each { |v| }`.
  - **Set it to one value at once:** `box.fill 0x77` sets every item the list holds now, and `box.fill 0xFF, from: f, count: n` a run of them — clearing the area a dialogue box letters into, a row of a board. The value, `from:` and `count:` may each be worked out as the game runs. What it is for is speed: the loop it replaces, `repeat(n) { |i| box[i] = v }`, works out an address and stores one item at a time, where this hands the whole words of the run to the console's copying engine and sets only the bytes at its ends one at a time — measured on a 3,328-byte clear a frame, about a fiftieth of the frame against more than two thirds. A run must stay inside the items the list holds now: the interpreter stops with an error past them, where the console only holds the run to the capacity. A list the game also `shift`s cannot be filled, since its items wrap round its memory. A run written past the list's capacity or from before its first item, a fill on a `table` (stored in the cartridge, so read-only), and a value of the wrong kind for the list (a fraction into whole numbers, or the other way round) are friendly errors.
  - **Copy a run of a table into it at once:** `name.copy_from letters, at: which * 64, count: 64` — the list then holds exactly `count` entries of the `table`, from entry `at` on: the picture of a letter a name is painted with, a frame of an animation, a row of a level. `at` may be worked out as the game runs and is held inside the table, so the run never reads past either end; `count` is a number you write. What it is for is speed: the loop it replaces, `repeat(64) { |i| name[i] = letters[start + i] }`, reads and writes one entry at a time, where this hands the whole run to the console's copying engine — measured on eighteen 64-byte runs a frame, a fiftieth of the frame against about a fifth, and the gap is far wider for a game whose code runs from the cartridge. It is widest when the start and the length are whole words (`which * 64` always is), and a run that is neither words nor halves is still copied, a byte at a time. The table and the list must keep entries the same width, and hold the same kind of number (both whole, or both with a fraction), since a copy moves them as they are; a count over the list's capacity or the table's length is a friendly error too.
  - **Where it lives, which you almost never have to say.** The console has two work memories — a small quick one and a large one that makes it wait about six times as long for a whole number — and everything a program declares used to come out of the small one, so a game with a lot of state **did not build**. Now what a frame touches goes in the quick one and the rest falls into the roomy one, so it does. Which is which is read off the program rather than guessed: a collection named anywhere in the per-frame path (the game loop, the scenes it runs, the routines those call, a timer's handler) is one a frame touches. **Say `fast: false`** about one you know is cold — a world state read when a menu opens — and it moves whatever the room, which hands the quick memory back to the things walked every frame; **`fast: true`** insists on one the framework did not pick. It is the same word `func` already takes for the same question about code, and it changes nothing the program does, only how long a read takes. Why it is worth a thought at all: the quick memory is **also** where the hot code is kept, so a big cold collection sitting there quietly pushes a routine the frame spends its time in out to the cartridge, at about two and a third times slower — and that is invisible from the program. `rom.profile` says what went where. A `pool` takes `fast:` too, and moves all its columns together. **A pool over 16K is too big to share the quick memory**, which is 32K and holds the hot code as well, so it is kept in the roomy one without being told — a thousand things of four fields is 25K, and builds. Saying `fast: true` about such a pool is a friendly error, since the game has asked for a place the pool cannot have. A pool bigger than the roomy memory itself, 256K, fits nowhere and is a friendly error at its own line; and a game whose collections do not fit the two memories together is refused by the check that adds up everything it declares, which names the biggest of them. **A collection's own numbers go with it**: a list keeps how many items it holds (and, one that is shifted, where its oldest is), and a pool keeps a dozen or more of its own — how many are live, the first and last of its order, where each walk of it has got to — and wherever the collection went, by `fast: false` or because the build moved it, those go too, so a cold pool leaves nothing of itself in the quick memory. Reaching one there costs what reaching the collection's items already costs. A **variable** the game declares cannot move and never will: it is reached by its distance from the start of the quick memory, which is what makes reading one two instructions instead of four — so a program with more variables than fit is a friendly error saying exactly that, and suggesting a list.
  - **Say it holds fractions:** `list :speeds, capacity: 8, holds: 0.0` — a list keeps whole numbers unless you show it otherwise, exactly as a variable does. Write a Float as the example and every value read out carries the fraction and every value put in is checked against it, so a game with many of something that moves in halves and quarters never picks a scale of its own. The number is only an example — a list still starts empty — and `length` stays a plain count whatever the items are. A pool field says the same thing with its default (`pool :spark, vy: 0.0`). Putting a fraction into a list of whole numbers, or a worked-out whole number into a list of fractions, is a friendly error naming the list.
  - **It holds exactly what you asked for, and what it COSTS depends on whether you `shift` it.** A list you only push onto and index into is a plain row of slots: `capacity: 145` takes 145 of them, and a read skips straight to the one you named. A list you `shift` — dropping from the front, which moves where the oldest item lives — is a ring instead, and a ring's slots are rounded up to the next power of two so the wrap can be a single step: `capacity: 145` then takes 256, and the 111 slots in between are room you pay for and can never fill. So a queue you shift is the one to give a power-of-two capacity. Nothing about this changes what the list holds or what it does; the framework works out which of the two you wrote. A plain row is also the FASTER of the two to read, having no head to look up first.
  - **Say how big one slot is:** `list :hurt, capacity: 64, width: :byte` — a slot holds a whole 32-bit number unless you say otherwise, and hardly anything a game keeps in one needs that much. A direction, a state number, a countdown, how many hit points are left, a plain yes-or-no: every one of those is a **byte**, at a quarter of the memory, and `:half` is a half. That memory is the console's 32K of quick memory, which is the same 32K the framework keeps your hot code in — so on a big collection this is the difference between the game's frame running fast and running from the cartridge. Reading and writing a narrow slot costs exactly what a wide one costs; only the room differs. **A narrow slot always goes below nothing** (`:byte` holds -128..127), and there is deliberately no way to ask for 0..255 instead: the case that decides it is a countdown, where `wait.sub! 7` followed by `(wait <= 0)` really does hold -4 while that test runs, and a slot that could not go below nothing would read -4 back as 252 and the test would never fire. Nothing at build time can see that coming, because the value is worked out as the game runs — which is also why a `table` CAN be asked and a list cannot: a table's values are all known while the cartridge is built. A number that has to reach past 127 asks for `:half`. A number too big for its slot keeps the low bits, exactly as the console does, and both backends drop the same bits (200 in a `:byte` reads back as -56 on each). A byte is the smallest there is — the console can load 8, 16 or 32 bits and nothing narrower, so a flag costs a byte and packing eight of them into one would cost several instructions on every read.
  - **Say how long it usually is:** `list :body, capacity: 256, estimate: { usually: 12 }` (or a range, `usually: 4..20`, which counts at its top). It changes **nothing** about how the game runs, and nothing reads it today — it was written for a build-time estimate that has since been deleted in favour of measuring the game. It stays because the thing worth knowing is still true: a collection sized for the worst moment of a game and walked item by item every frame is fine for the whole of development and falls over in the one session that fills it. A snake's body list is sized for the whole board and holds four cells for most of a game. **The build watches for that now, and measures it rather than working it out**: a build that measures its game (`build_rom`, `ruby game.rb`, the `ruby-gba` command) runs each scene a second time with every `list` and `pool` the game declared held at its capacity, and a scene that keeps up as it stands and falls behind full is a friendly warning naming the collections that do it and the frame rate it measured — each one held full on its own decides which to name, and where no one of them does it alone, the warning says it is all of them at once. Only the length is held: the items past the ones the game put there are whatever is in memory, usually nothing, so a walk whose work depends on an item's value (skipping an item that is nought, using an item as a loop count) is measured at what those values cost, which can be more or less than a real full list. It costs build time and nothing in the cartridge: a run per scene, and a run per collection for a scene that falls behind.

## Tables (build-time ROM lookup)

- `table :name, ruby_array, width: :half, signed: nil` → a `Table`: a build-time Ruby array shipped as read-only ROM data, read at run time by a Value index. `t[i]` → a `Value` (like `list` indexing, but const/ROM); `length` is a build-time Integer. `width:` is the element size (`:byte`/`:half`/`:word`); `signed:` is inferred from the values (any negative → signed) unless you set it. An out-of-range index is made safe: a power-of-two table wraps it (what an angle wants), any other size clamps to the ends — and **the length you pick decides what a read costs**, because wrapping is one step and clamping is a test against each end, about twice the work. A length like 256 or 512 is the cheap one; round a sine table up to it and the reads get cheaper for nothing. Precompute what the console can't do cheaply each frame — a sine or reciprocal/distance table (see `examples/raycaster.rb`). A value that doesn't fit the width is a friendly build error. **A read is not free** — reaching an element costs about three plain steps, so a table read in a hot loop is real work rather than the single load it looks like.

## Composition (pools of a component)

- `pool :name, field: default, …, capacity: N` → a `Pool`: many of a thing that has named fields and behaves (bullets, enemies, particles), without hand-managing parallel lists that desync. `spawn(field: value, …)` fills a free slot (safe no-op when full); `each { |b| … }` runs the body once per live instance with a row handle whose fields are mutable Values (`b.x.add! b.vy`, `b.y.set! 0`, read/compare `b.x`), which can retire itself (`b.remove`), and whose own slot `b.index` hands back as a Value — save it in a variable to remember which instance won a comparison (the nearest enemy, the one just hit) and act on it once the loop has ended; `count` (a Value) / `full?` (a Condition) introspect it. Behind the scenes it's parallel lists + an active column + a `repeat`, so the fields can never desync and the cost model prices it per-pool.
  - **`each` goes in the order things were spawned**, oldest first, whatever slot each one landed in: a thing removed leaves the order, and a new one always goes last, even in a slot an older one gave back. That is the order a player can see. Things that each roll `rand` in the walk roll one after another, so the same seed gives each thing the same numbers however the slots were shuffled by what came and went before; and things that act on each other or on something shared act first come, first served. It is how a console game keeps the things in a room. **During a walk**: a thing removed before its turn is passed over and every other thing is visited once, and a thing spawned during the walk is first visited by the next walk, so a thing that splits in two does not split again in the same pass. A thing removed during a walk keeps its slot until the walk ends, so a spawn in the same walk takes a different slot, and a pool that had no room still has none — `full?` says so, since it tells whether a spawn will find a free slot rather than counting what is live. The walk goes through the live things only, so it costs what is live rather than the capacity. Each `each` written in the game keeps three variables of its own, so a walk inside another walk of the same pool keeps its place. **`each(newest_first: true)` walks the other way**, newest first, for a game where the last thing added has to act first (which of two things in reach is struck, when the newest should win). It is the exact reverse of the plain walk, and every rule above about a walk holds the same way round, a pool's own routines included. It costs the same as the plain walk, and anything but true or false is a friendly error. It changes only the order that one walk visits things in: which thing is drawn in front stays as below. **Drawing order is the plain walk's order too**: where two things of one pool overlap, the one spawned first is in front, whatever slots they landed in. A thing spawned into a slot an older one gave back is still behind everything older than it, and a thing a full `:recycle_oldest` pool reuses goes behind the rest, as the newest. So a game that needs one of a pair in front spawns that one first — a bed's cover, then its pillow end — and the answer does not change as other things of the pool come and go. **What it costs** is one walk of the live things a frame. Each of the console's sprite rows has a fixed place in front of or behind the others, so before each frame is drawn the framework copies where each live thing is, which picture it shows and which colours it draws with into the order they are drawn in. That is one small routine per pool however many slots it has (`rom.profile` lists it as "putting the sprites of pool :name oldest in front"), a few bytes of memory a slot, and time for each LIVE thing rather than each slot: measured on `examples/dive`, with its six fish and up to twelve bubbles, the frame went from 3473 instructions to 4189, which is under half a hundredth of a frame. **Against a plain sprite, a pool takes the place it was declared in**, by the rule two sprites follow: a sprite declared after the pool is in front of all its instances, and one declared before is behind them. A game that needs one in front puts it in a sprite or a pool of its own, in a `layer`.
  - **Spawn-when-full policy:** `on_full:` decides what `spawn` does with no free slot — `:drop` (default, ignore it) or `:recycle_oldest` (reuse the longest-lived instance so a new one always appears — the usual choice for particles/effects). The longest-lived is the first in the walk order, so finding it costs one read whatever the capacity. The one exception is a spawn into a full pool from inside that pool's own walk: the walk is following the order, and moving its first thing to the end would cut the walk short (or, newest first, carry it past where it ends), so that spawn is dropped. `pool :spark, x:, y:, life:, capacity: 32, on_full: :recycle_oldest`. Worked example: `examples/sparks.rb`, a shower of particles walked every frame on a bitmap screen, each drawn by the body and removing itself off the bottom.
  - **A routine that works on ONE instance:** `guards.func(:chase) { |g| g.x.approach! hero.x, 1 }`, called from inside the walk — `guards.each { |g| call g.state }`. A pool's behaviour starts as a block inside `each` and wants to move out of it as a game grows, for two reasons: a block is emitted again at every place it is written (a `func` is emitted once, see `func` under Scenes & funcs), and a cast with states wants a routine per state rather than one block of tests. **What stops a plain `func` doing it** is that a routine is built once, wherever it is called from, so its own code has no way to say WHICH guard is chasing — `g` belongs to the block, and the routine is somewhere else entirely. This hands it the instance the walk is on, and everything the block form has comes with it: the fields by name, `g.remove`, `g.face`, the collision box. It pairs with `call g.state` (see `var :mode, :title`), which is a game's whole cast behaving in one line — every instance running the routine its own state names. **What it costs** is a write per live instance per pass, and **only a pool that declares such a routine pays it**: the write is taken out again at the end of the build when no routine reads it, so a pool of sixty bullets drawn inline is exactly what it was. Two walks over one pool (a pairwise test, or a routine that walks the pool it was called from) keep their places, because a walk puts the place back as it leaves — a save and a restore per walk, not per instance. **Calling one from outside a walk is a friendly error**, since there would be no instance for it to run on; the rule is to call it inside `each`, or from another routine of that pool, which is how a state hands over to the next one.
  - **Spriteful pool:** add `image: :art` (needs `x:`/`y:` fields and `screen :tiled`) and each live instance auto-draws as a hardware sprite at its x/y — `spawn` shows one, `remove` hides it, and the console composites them. The row handle then also has a collision box (its x/y plus the image's size), so `b.overlaps?(other)`, the screen-edge tests (`b.off_screen?` / `b.below_bottom?` / …) and `b.clamp_to_screen` work per instance. A pool declared inside a `scene` is scene-owned (its sprites show only while that scene is active). **The code that draws a pool's sprites is written once, however many the pool holds**: every one of them is drawn the same way from the same lists, so the build writes the drawing one time and goes round it. That code is what the build tries to keep in the console's 32K of quick memory, so a pool of forty-five asks that memory for what a pool of four does — a few hundred bytes, where a copy for each was most of 20K — and costs a frame a handful of instructions more for each thing. A pool whose things are kept out of a `fade … under:`, or that keeps one frame of its pictures in memory at a time, still gets a copy for each, and so does every sprite declared by hand; `rom.profile` shows the size either way. On a bitmap screen, drop `image:` and draw the pool yourself in `each`.
  - **Pooled things face and animate, each on its own.** Give the pool `facing:` or `frames:` (with `rate:`) *instead of* `image:` — the same words a `sprite` takes, meaning the same thing: `pool :guard, x:, y:, capacity: 32, rate: 6, facing: { left: [:walk_l1, :walk_l2], right: [:walk_r1, :walk_r2] }`. Inside `each`, `g.face :left` is the same verb a sprite has. **What is per-instance is the point:** the direction and the place in the cycle belong to each slot, so one test written once leaves ten guards leaning ten ways in the same frame, and one spawned just now starts its walk where it starts rather than in step with the rest. That is the pool's own bookkeeping — a hidden slot beside the fields, never a field you declare — and a slot reused by a later spawn starts fresh. Without this a game with a cast had two bad choices: ten sprites declared by hand with their state in parallel lists that desync, which is the exact thing `pool` exists to prevent, or ten identical statues. **What it costs** is one counter for the whole pool deciding *when* a step happens, so a frame that is not a step is one compare and a step walks the slots — a `rate: 6` makes that one walk in six. Naming two picture sources (`image:` and `facing:`), or a direction the pool was not given, is a friendly error. Worked example: `examples/shmup/enemies.rb`, where the enemies flap and turn to face the ship they are diving at.
  - **A field can be called almost anything.** A pool keeps lists of its own beside the fields — which slots are live, where each instance is in its animation, the order they came in — and none of them can meet a field, so a guard can have a field called `frame`, `active`, `count`, `colors` or `next`. Two kinds of name are refused, each a friendly error. One is a name an instance already answers to (`remove`, `index`, `move`, `face`, `draw_with`, `left`, `right`, `top`, `bottom`), since `g.remove` would mean the verb and never the field. The other is one of `pool`'s own words (`capacity`, `image`, `facing`, `frames`, `rate`, `on_full`, `estimate`, `widths`, `fast`), since a field is written the same way those are. A pool's own name cannot end in an underscore or hold two in a row (`:guard_walk` is fine).
  - **Say how big each field is:** `pool :guard, dir: 0, hp: 0, capacity: 145, widths: { dir: :byte, hp: :byte }` — a pool is one list per field, so a field left at its full width costs four bytes a slot to keep a direction or a flag, and a pool is sized for the worst moment of a game rather than a normal one. Naming the narrow ones is the single biggest thing you can do for a big pool: measured on Wolfenstein's guards, ten of thirteen fields narrowed freed about 3.7K of the console's 32K, which the framework then gave to three more routines of hot code. Same three widths a `list` takes, same rule about going below nothing (so a countdown is safe), and the same friendly error for a width the framework does not know. A field declared with a fraction (`x: 0.0`) cannot be narrowed and says so — a fraction is mostly its own fractional part and needs the whole word. **The pool's own bookkeeping is narrowed without being asked**, because unlike a field the framework knows exactly what it holds: the live-or-not column is a byte whatever the pool is, and the free-slot stack is as wide as the largest slot number needs.
  - **Say how many are usually live:** `pool :bullet, x:, y:, capacity: 64, estimate: { usually: 6 }` (or a range, `usually: 4..8`, which counts at its top) — the same hint a `list` takes, and like that one it changes **nothing** about how the game runs. Nothing reads it today — it was written for a build-time estimate that has since been deleted in favour of measuring the game — and it stays as documentation of intent, because a pool is sized for the worst moment of a game rather than a normal one: sixty-four bullets so the one frame that needs them has them, six on screen the rest of the time.

## Randomness

- `seed n` / `randomize` — seed the stream. `roll :var, 1..6` — store a random value. `rand(1..6)` — a random `Value`. `chance(25).then { }` — true 25% of the time.
- `random_numbers` — **the stream itself, for a `save_data` record to keep**: `keep hearts, random_numbers`. The random numbers are a hidden number the game keeps churning, so a save that leaves it out and a load that puts everything else back roll different numbers from there on — the guard that was going to miss now hits. Kept, a load puts the stream back where the save found it and play goes on exactly as it would have. It is nothing else: the numbers are still read with `rand`, `roll` and `chance`. A record's `reset` (a new game) leaves it rolling on rather than starting it where power-on does, which would play every new game's rolls the same. Keeping it in two records is a friendly error, like any kept thing.

## Sound & music

- `enable_sound`, `define_sound :name, frequency:, duty:, decay:, volume:`, `beep :tone` — SFX (channel 2).
- `noise :explosion` (also `:hit`/`:kick`/`:snare`/`:hat`/`:zap`, or `pitch:`/`decay:`/`volume:`/`metallic:`) — a percussion/explosion hit on the noise voice (channel 4).
- `wave :triangle, :C4` (shapes `:sine`/`:triangle`/`:sawtooth`/`:square`; pitch a note or Hz; `volume:` `:full`/`:three_quarter`/`:half`/`:quarter`/`:mute`), `stop_wave` — a sustained richer-timbre tone on the wave voice (channel 3). **Or give the waveform itself**, as 32 steps of 0 to 15, wherever one of those names goes — `wave PULSE_50, :C4`, `plays: PULSE_50`. The names are a convenience rather than the truth: this voice is not a set of timbres, it is 32 steps of four bits that the game writes, so music that came from somewhere else — decoded out of another cartridge, drawn in a tracker — arrives holding those 32 numbers and no name would be the waveform it actually has. A 50% pulse (`[15] * 16 + [0] * 16`) is the common one and is none of the four; played as a triangle it is a different instrument, which a player hears without being able to name. Name it in your own program and the call site still reads like game code. A list that is not 32 long, or a step outside 0 to 15, is a friendly error at the line that wrote it.
- `song(:name) { … }`, `play_song :name`, `stop_music` — music. Inside `song`: `tempo`, `note :C4, :quarter`, `rest :quarter`, `duty`, `volume`. **`loop_from_here`** marks where the song comes round to at its end, so what is written before it — a fanfare, an introduction — plays once and what follows repeats; mark it in one part, or at the same moment in every part (two different moments is a friendly error, and so is a mark with nothing after it). **A repeat with no note in it is a friendly error too** — a mark followed only by rests, where the song would play its introduction once and then fall silent for as long as the game plays it; a note held across the mark counts, since it sounds on into the repeat. Coming round, every part is put the way it was at that moment the first time: a part holding a note across the mark sounds that note again there (not on the first pass, where it is already sounding — and not at all if the song ends on that very note, which then simply carries on), and a part silent there is silenced there, whatever the end of the song left it doing. None of that costs anything a frame; a part holding a note across the mark costs a second copy of its notes after it, in the cartridge. Layer parts with `voice :melody do … end` / `voice :bass do … end` — the framework picks where each one plays. **A part can play a recorded instrument instead of the square wave**: `voice :melody, plays: :piano do … end`, where `:piano` is an `instrument` (its name or the handle). Each note plays the recording at that note's pitch, a rest silences it, and a note ends early if the recording runs out first — unless the recording says where a held note reads back to (`holds_from:`, see `instrument`). The part names the instrument, never a channel, and it sounds through the mixer on a voice of its own. **A part can shape its notes too** — `voice :melody, plays: :piano, envelope: { release: 0.25 } do … end`, and one note of it can say its own (`note :C4, :quarter, envelope: { release: 0.6 }`) for a note plucked where the rest are bowed. A part that says nothing takes whatever the instrument itself was declared with, which is where music decoded from elsewhere keeps it; see `instrument` for what the four words mean and why a note that stops dead clicks. A shape costs nothing per note in the cartridge, because a note already names the recording it plays and two notes on the same recording shaped differently are simply two entries in the table it names. **Or one of the console's own other two voices, and those cost NO mixer voice at all** — `voice :pad, plays: :wave do … end` and `voice :drums, plays: :noise do … end`. The **wave** voice loops a short waveform, so it is rounder than a square wave and reaches an octave lower: a pad, a bell, a bass. Name a timbre instead and you pick the waveform (`plays: :sine`, `:triangle`, `:sawtooth`; bare `:wave` is the triangle) — or give the 32 steps themselves (`plays: PULSE_50`), for music that arrived with a waveform none of the names is; see `wave` above. The **noise** voice makes a hiss rather than a pitched tone, which is the drums — a note's pitch is how HIGH the hiss sits, so a low note is a kick and a high one a hat, and the part says how fast a hit fades (`decay :fast`) and whether it rattles (`metallic true`). Why reach for these before another recording: the console makes both sounds itself, where every recorded part keeps one of the mixer's voices for as long as its note sounds — so a song with a pad and drums leaves fifteen of the sixteen free for the game's own sounds. There is one of each voice, so one part apiece. And `plays: :square` is a friendly error, because it reads two ways and the wrong reading is silent: a part plays the square wave when it names no instrument, so that is `plays:` left out. **How many parts a song can have**: 2 square-wave parts — the console has two square-wave voices for music — plus one on the wave voice and one on the noise voice, plus up to 16 that play an instrument, one per voice of the framework's mixer. That 16 is the framework's, not the console's: recordings are mixed in software, and 16 is how many the mixer sums today — a voice costs mixing only while it sounds, so the number is room rather than a price. Going past any of them is a friendly error naming the one you hit, and pointing at whichever voices still have room — checked on the finished program, so a `songs` list of Scores meets it the same as a `song` block. **A square-wave part cannot go below 64 Hz**, just under C2: a lower note is played AT 64 Hz, a different note, so it is a friendly warning naming the note and the lowest one that sounds right (music decoded off another cartridge, which played the note at 64 Hz too, can say so — see `low_notes_intended:` under `songs`). The note names stop at C2 and never reach it; a pitch in Hz or a Score's MIDI key can. A part on the wave voice goes an octave lower, and a part that plays an instrument has no such floor at all — those are the two ways to a bass that goes deeper. **A sound effect and a song part on the same voice interrupt each other**, which is a friendly warning naming the song: `beep` shares the voice a song's SECOND square part uses, and `wave` and `noise` share the one voice each of theirs uses — so a single part on either already collides, where one square part leaves the beep alone. And each part plays at most one note a frame, so **a note shorter than a frame** (a sixteenth at a tempo near 2000) would leave the note after it unplayable and the part silent until the song comes round — that is a friendly error saying which part and how far in. **The music and the game's own sounds share the mixer's voices**, each taking one only while it sounds: a recorded part's note takes a voice and its rest gives it back, so while a part rests — and on a title screen with no song at all — every voice is the game's. When they run out, **a stated rule decides who gives way**, the same on both backends. A song's note that has ended and is still fading away (see `envelope:` on `instrument`) gives way first, to anybody, the quietest of them first — it is on its way out already. Past that, a game `play` that finds no voice free is dropped, as it always was, but a song's note that finds none takes the voice of the game's sound that has been playing longest — one that plays once before one that loops, since a loop never ends by itself — so a song keeps playing right and an older sound is cut short. A sound effect's note does the same, and in a game whose effects play recordings there is one step more: with no game sound to take, a note takes the voice of the lowest-priority note of a song or an effect ranked below its own (see `sound_effects`), and with none of those it is not played — its part carries on in time and is heard again from its next note, and `rom.profile` counts it with the sounds that did not play. A part's next note takes over the voice its last note was using, rather than a second one — **unless that note has a shape**: then it fades away on its own voice while the next note takes another, because taking its voice over would stop the old wave dead mid-fade, which is the click the shape was there to remove. So a shaped part can hold a second voice for as long as a fade lasts, and a game that shapes nothing shares its voices exactly as before. A recorded part also leaves the square voice beeps use alone. Naming an instrument the game never declared is a friendly error. What it costs is measured: `rom.profile` names the mixing, which grows with each recorded note sounding, and the routine that answers the display, which plays the music. **`play_song` says which song is playing now**, the way `show_map` says which map is showing: the song plays from its start and loops, and saying the one already playing changes nothing — so it can be written once, or every frame, from a branch or a scene, and it is the same tune. Naming a different song starts that one from its beginning (a jukebox needs no `stop_music` between tunes), and `stop_music` silences the song playing; said again while nothing plays, it does nothing, so a "music off" setting can say it every frame without touching the voice sound effects play on. **A song named starts on the NEXT frame**: the player moves the music on as the screen finishes a picture, which is before the game's pass, so it hears the name a frame on. A cartridge whose own sound engine runs after its game's logic has the song a frame sooner than that, so a game rebuilt to match one — asking for each song on that cartridge's own frames — says **`play_song :theme, this_frame: true`** (and `music.play 2, this_frame: true`): the song is taken up and its first frame played right where it is named, with the screen's interrupt held off while it is, and the next frame plays its second. Every note is then a frame sooner, and the player's own record names the song on the frame the game named it. Naming the song already playing changes nothing either way, and a number naming no song in a list leaves the music as it is. It costs a call where it is said and a second copy of the player's frame of the tune, beside the player, which the game calls: measured at 740 bytes for a game with square and recorded parts, and it grows with the kinds of part a game's songs have. A game that never says it emits neither. Anything but `true` or `false` is a friendly error. **It keeps its tempo whatever the game is doing**: the framework moves the song on once for every frame the screen shows, off the screen's own clock as the mixer is, so a game running at thirty frames a second still hears its music at the speed it was written. That place is the screen finishing a picture, so a program that never waits for the screen has no frames and plays no song — a friendly warning. What it costs is a check per part on every frame a song plays, whatever its length, and a handful of instructions on a frame no song plays.
- `music_volume 50` — **how loud the music plays**, from 0 (silent) to 100 (as written), and it may be something the game works out (`music_volume slider`, for a settings screen). It reaches the song playing now — notes already sounding included, from the next frame — and every song after it until it is said again; anything past either end is held at that end. Sound effects are not the music and keep their own volume. **Every kind of part follows it**, each the way its voice allows: a held square-wave note is started again at the new volume (those voices take a volume only as a note starts, which is also how Nintendo's own sound engine changes one), the wave voice and a recorded part's mixer voice simply take the new volume while they play (the wave voice has five volumes, so it gets the nearest), and a drum hit on the noise voice keeps ringing at the volume it was struck with and the next hit takes the new one — striking it again would be a second hit. **What it costs** is nothing for a game that never says it; for one that does, a check each frame, and on a frame it moved, the held notes set again. **With no number it reads how loud the music is now**, 0 to 100, which is how a game waits for a fade to finish: `(music_volume == 0).then { track.set! next_track; fade_music_in }` switches songs while nobody can hear it.
- `fade_music_out` / `fade_music_in` (both take `frames:` or `duration:` in seconds, half a second by default) — **the music going down with the lights, and coming back up.** The pair to `fade_out`/`fade_in`, and said the same way: call each once, at the moment it begins, and the framework walks `music_volume` every frame from there. `fade_music_in` with no length comes up as fast as the music last went down. **A faded-out song goes on playing, silently** — the way a faded-out screen goes on being drawn — so what happens while nobody can hear it is the game's to say: stop it, switch to another song, or bring the same one back. That is also why a jukebox that names its song every frame can fade between songs without the old one starting over. `fade_music_in` brings the music up from wherever it is — after a fade out, from silence — and with the music already at full it has nothing to do. Calling either again while a fade runs turns it round from where it is, and a fade that is not running starts from the volume the music is at, including one the game set by hand. **A beep on the second square voice during a fade** is cut off each time the volume steps, since a held note on that voice is started again at every step — the same voice already interrupts beeps whenever a two-part song plays a note on it (see the song line), and a fade does it more often. A `fade_music_out` with no `fade_music_in` (or `music_volume` turning it back up) anywhere is a friendly warning, because every song after it plays at no volume. Worked examples: `examples/jukebox.rb` (moving the cursor fades one tune out and the next in) and `examples/pong.rb` (the music fades as the game ends, and a new game fades it back in).
- `sample :name, from: "clip.wav"` (or `pcm: [-128..127…], rate: N`, and `note:` — the pitch it was recorded at, default `:C4`) → a `Sample`: a recorded 8-bit PCM clip played through the sampled-audio hardware (Direct Sound), not a synthesized PSG tone. `from:` loads a `.wav` (any 8-/16-bit, mono/stereo PCM — converted for you, keeping its rate; file found beside your script); `pcm:` takes raw samples (an Array of -128..127 or a byte `String`) at `rate:` (default 8192). `s.play` plays it once; `s.play(loop: true)` replays it seamlessly as looping background music (any length — it streams from ROM a frame at a time); `s.play(volume: :half)` sets its level (`:full`/`:three_quarter`/`:half`/`:quarter`/`:mute`); `s.play(pitch: :E4)` plays it at a different note by reading through it faster/slower (one recorded note covers a whole keyboard — shifts from the sample's `note:`); `s.stop` cuts its voices off. **Several samples play at once** — a software mixer sums the sounding voices (background music under a handful of overlapping effects, or chords), up to 16 voices, shared with a song's recorded parts (see the song line for who gives way when they run out); a play that finds none free takes the voice of a song's or a sound effect's note that is fading away, and with none of those is dropped rather than stealing one. **A recording cannot be named `:sine`, `:triangle`, `:sawtooth`, `:wave`, `:noise` or `:square`** — a friendly error — because `plays:` reads those as the console's own voices, so a song part could never play a recording by that name, and it would sit in the cartridge unplayed with nothing to say so. **What a voice costs is the mixing, and only while it sounds**: each one sounding is about 11 instructions for every sample of sound, so at around 8000 samples a second a frame spends about a hundredth of itself on each — twice that at twice the rate — and a frame with nothing sounding costs next to nothing. `rom.profile` names the mix routine and its share. **The rate it all comes out at is the framework's to pick, not yours**, and this is the one place that shows: `rate:` says what a recording was MADE at, and the framework then plays everything at a single rate it works out from your recordings. It cannot be any rate at all — the sound hardware has to be clocked so that a whole number of samples, and a whole number of the lots its transfer engine moves, fits exactly in one frame, or every frame hands over mid-sample and the game plays with a rattle under it at the frame rate. So it picks the nearest rate that does fit, your recordings are resampled to it as they play (at the pitch and for the duration they were recorded at, so nothing changes but a little bandwidth or a little mixing), and `rom.profile` says which rate you got. Nothing in the program names it. The framework hides the FIFO/DMA/timer/mixing; sound needs a `game_loop` (the mixer refills once a frame) and reserves two hardware timers — one clocks the sound, one counts how much of it has played — so user `timer`s allocate from timer 2. **The count is what keeps the sound whole in a game too busy for its frame**: the hand-over to the sound hardware waits for anything the game is in the middle of (a whole-screen clear is a fifth of a frame), and a different wait every frame used to be a click every frame. The count says exactly how much sound went out meanwhile, and each frame's sound carries enough of the next one's start to cover a third of a frame of lateness. Past that, the sound clicks at that frame and picks up again.
- `music = songs :music, [score, …]` (or a Hash, `{ title: TITLE, forest: FOREST }`) → a `SongList`: **music handed over as data and played by number**, for a game whose music already exists as numbers — decoded out of another cartridge, read from a file — rather than written as `song` blocks. `music.play 2`, `music.play :forest`, or `music.play track` with a number the game works out; it says which song is playing now, exactly like `play_song` — `this_frame: true` included — and a worked-out number naming no song leaves the music as it is (the same as `show_map`). A written number or name the list does not have is a friendly error. `music.stop` is `stop_music`. Each entry is a `RubyGBA::Audio::Score`: `Score.new(parts: [Score::Part.new(plays: :flute, notes: [Score::Note.new(at: 0, key: 72, length: 22), …])], tempo: 150)`. **Time is in ticks, the way sequenced music is stored everywhere**: `ticks_per_beat:` (24 unless said) and `tempo:` in beats a minute — or a map, `[[0, 120], [960, 140]]`, for a tempo that changes — and the framework turns ticks into frames once, at build time, from exact fractions, so a long song never drifts. A note's `key:` is a MIDI note number (60 is middle C) or a name like `:C4`, or nothing for a rest; `length:` ends it early (otherwise it lasts until the part's next note), and it can name its own `instrument:`, `volume:` (0–15) and `envelope:`, so a part can change instrument, loudness or shape note by note. **On a part that plays a recording, a volume can hold a fraction** (`volume: 7.5`, or a Rational), and that note plays at a loudness between two whole volumes: the mixer has 256 steps where a console voice has 16, and `15 × L / 256` gives a note a loudness of exactly L 256ths of the recording's size, which its shape, if it has one, then scales. That is the scale a cartridge's own sound engine mixes a voice at, so music decoded off one keeps its loudest notes, about half the recording, at that level and its quiet ones heard, where rounding them to 16 steps would lose them. A volume that comes to less than one 256th is a rest. A volume with a fraction on a square, wave or noise part is a friendly error, since those voices have 16 volumes; and a `song` block's `volume` stays a whole number, so music that wants the finer steps is handed over as a Score. A `Part` takes `envelope:` too, for the whole line of music, and either takes the same two forms `instrument` does — a Hash of times, or the four numbers the console's own engine keeps, which is what a decoder already has. `length:` on the Score is where it comes round again, and left out it is where the last note ends. **`loop_from:` is the tick it comes round TO** — `loop_from: 384` plays the first 384 ticks once, as an introduction, and everything after over and over; left out, the whole song repeats. One tick serves the whole Score, since every part comes round at the same moment. **Music decoded off a cartridge can say its low notes are meant** — `Score.new(..., low_notes_intended: true)`. A square-wave note below 64 Hz is played at 64 Hz, and the build warns about one because in music written by hand it is a mistake. A cartridge's own sound engine plays such a note at 64 Hz too, so music lifted off one is already faithful, and every fix the warning offers would make it less so. The word leaves out that one warning for that one Score, and builds the same cartridge to the byte; a hand-written part in the same game still warns. A tick at or past the end, or one with no note sounding after it, is a friendly error — the second because the song would fall silent after its first time through. See the song line above for what a part holding a note across that point does. **A song that ends says `plays_once: true`**, and then it does not come round at all. It lasts exactly its length; on the frame after its last, its parts go quiet the way `music.stop` silences them, and nothing plays until the game says otherwise. Music decoded off a cartridge knows which kind each song is — a track there ends with a mark that sends it back or with one that stops it — so a title jingle, or the tune a legend is told under, stops where the original's does. It is counted on the frames the screen shows, like the rest of the music, which a game counting frames beside the song cannot do on a screen that runs late. `play` still says which song is playing now, so a game that names the song on every pass hears it once: naming the song already named changes nothing, ended or not. To hear it again, stop the music and name it (`music.stop` and `music.play :legend`, in one pass or two), or name another song first. `music_volume` and the music fades reach it like any song while it plays. `plays_once:` beside `loop_from:` is a friendly error, and a sound effect plays once whatever its Score says. It costs a game with such a song a load and a compare a frame, and a game with none nothing. The same part limits as a song block, and each mistake in a Score — a note before tick 0, a key that is not a note, a note naming an instrument on a square-wave part — is a friendly error naming the part and the note. Worked example: `test/ruby_gba/audio/test_scores.rb`.
- `sfx = sound_effects :sfx, { hit: HIT, spark: SPARK }` then `sfx.play :hit` (or `sfx.play which`, a number the game works out) → a `SoundEffectList`: **Scores played once, over the song that is playing.** A sword hit, a door, a chest opening: each is a short run of notes the same shape as a tune, decoded from the same place, and each plays over the room's music without stopping it. It starts on the frame after it is asked for, the same step `play_song` takes, and it goes quiet at its end rather than coming round again. **`sfx.play :hit, this_frame: true` starts it where it is asked**, the way `play_song` takes the word: its first frame is played there, so every note is a frame sooner — and any effect a group is cutting off is cut off there too, so its voices are free for the new one. Nothing else sounding is moved on. That is for a game asking on another cartridge's own frames; see `play_song`. It costs a call where it is said and a short routine beside the player that walks the table once (measured at 180 bytes); a game that never says it emits neither. **Asked for again while it sounds, it starts again from its first note**; several different effects sound at once, each on its own. **Unless they share a group, and then they cut each other off** — `Score.new(..., group: :voice)`, a name, because a character has one voice: a hurt cry replaces a swing cry rather than playing over it. Asked for while another of its group is sounding or already asked for, an effect of at least that one's priority stops it (its voices go quiet on the next frame, a shaped recorded note falling away) and starts in its place; one of lower priority is not played at all, and the log does not say it started. A tie goes to the one asked for last, since that is the one the game wants now. One of a group asked for again while it sounds stops before it starts again, so a part whose first note comes later is quiet until then. Groups belong to the Scores, not the lists, so one list can hold every effect a game has and a number decoded from its data still picks one, whatever its group; an effect that names no group plays alongside any other. That is how a cartridge's own sound engine plays effects — each on one of a few players, one at a time — so a decoder hands over the player as the group. What a group costs is on the asking: the game holds the screen's interrupt off while it looks at each of the group, a load and a compare or three apiece, and asking for an effect from a list with no group in it is one store. A `songs` Score with a group is a friendly error. A number naming no effect plays nothing, and a written number or name the list does not have is a friendly error. **When an effect and the song, or two effects, want the same voice at once, the higher `priority:` sounds on it** — `Score.new(..., priority: 68)`, a whole number 0 to 255 on each Score, the song's too, because a cartridge's own sound engine carries one on every sequence and a decoder hands it straight over. The one that loses the voice carries on in time, silent there, and is heard again from its next note once the voice is free; the note it lost is not played late. A note at volume 0 lets the voice go, the same as a rest. On a tie an effect takes the voice from the song, so a game that says nothing about priority hears its effects, and between two effects the one declared first takes it. That tie is the framework's choice: a cartridge's own engine can settle a tie between its tune and an effect the other way, so music decoded from one with a tie in it wants the priorities made different. A song that stops or starts over leaves an effect's voice alone, and `music_volume` never reaches an effect, which keeps its own volume. **What an effect can play is every voice a song can: the two square voices, the wave voice, the noise voice and recordings** — a character's cry, a voice line, a hammer, a key appearing in a round tone. **A note on the wave voice sounds in its own waveform**, the effect's while the effect holds the voice and the song's again once the song's next note has it, whichever timbre or 32 steps each part names. The voice has room for one waveform, so a note puts its own in place first when another is there — on the frames the waveform changes and no others — and a tune that changes while an effect holds the voice waits for its first note to have the voice before its waveform goes in. On that voice a note too quiet for its five volumes lets the voice go, the same as a rest. A part that plays a recording (`Score::Part.new(plays: :grunt, notes: ...)`) sounds each note on a voice of the mixer at that note's pitch, the same as a song's recorded part, shaped the same way and its own volume whatever `music_volume` says. **When every mixer voice is busy, priority decides there too**: a note that finds no free voice and no note fading away takes the voice of the game's own sound playing longest (the game's sounds rank below every song and effect), and past that the voice of the lowest-priority note ranked below its own — so an effect over a song with a full mixer is heard, and cuts one of the song's notes short. With none of those the note is not played, and its part is heard again from its next note. Two parts of the same song or the same effect never take each other's voice, and a recorded note at volume 0 is a rest here too: it takes no voice. That is the rule a cartridge's own sound engine keeps, with two differences worth knowing when music comes from one: among notes fading away the quietest gives way first rather than the lowest priority, and the mixer here has 16 voices where a cartridge may set fewer, so a note that cartridge would drop can still play. `loop_from:` is a friendly error, since an effect plays once. An effect's Score takes `low_notes_intended: true` the same way a song's does (see `songs`). The interpreter's log says `[:sound_effect, name]` on the frame each one starts, so a game's own test can say which effect started when without the emulator, and `[:voice, channel, who, frequency, volume]` each time the song or an effect sets one of the console voices, which is who sounded on it; for the mixer, `sound_owners` says whose each sounding voice is — `:game`, `[:song, part]` or `[effect, part]` — and the console's `voices` say the same. **What it costs**: a game with no sound effects emits nothing new. One with them keeps a small table in the roomy memory, and the screen's interrupt walks it every frame, a load and a compare for an effect that is not sounding. A sounding effect costs a check per voice it uses, and more on a frame one of its notes is due. A game whose effects play recordings adds a compare per busy voice when a note looks for one, and one whose effects play the wave voice a short call on each note there, to compare the waveform with the one in place, and the copy of a waveform on a frame it changes. `rom.profile` counts that inside the routine that answers the display. Worked examples: `examples/jukebox.rb` (A and B play two effects on a piano over a tune whose big chord fills the mixer, one ranked above it and one below) and `test/ruby_gba/dsl/test_sound_effects.rb`.
- `instrument :piano, from: "piano.wav", envelope: { release: 0.25 }, holds_from: 0.4` — **how a note on this recording starts and how it ENDS**, which is worth reading before you write any music at all, because the thing it fixes sounds like a bug in the recording. A note that simply stops leaves the speaker wherever the wave happened to be, and the jump from there to silence is a CLICK — louder than anything in the music, since a note cut at the top of its wave moves the speaker further in one step than the music ever does. And it comes and goes: a note that ends near the middle of its wave is silent about it. So it arrives as "sometimes there's a pop at the end of a lick", which is the worst kind of thing to be handed. Give the note a shape and it gets quieter over a few frames instead of stopping, and the click is gone. **Four words, all optional, and what you leave out stays as it was** — so `envelope: { release: 0.25 }` says the one thing most music needs: `attack` is how long it takes to reach full when the note starts, `decay` how long it then takes to fall back, `sustain` where it holds while the note lasts (a fraction of full, 0.0 to 1.0), and `release` how long it takes to fade away once the note ends. The three times are in seconds. A struck instrument — a piano, a bell — is `{ decay: 0.4, sustain: 0.3, release: 0.5 }`; a bowed or blown one climbs instead, `{ attack: 0.08, release: 0.15 }`. **Any release removes the click, however short** — the loudness slides across each frame's samples rather than stepping at the frame boundary, so even the fastest release on a retail cartridge (89, silent in six frames) ends a note without one. A note that comes before the last one has finished fading does not cut the fade off either (see the song line). **Or give the four numbers the console's own sound engine keeps**, 0 to 255 each, with `RubyGBA::Audio::Envelope.new(attack: 255, decay: 245, sustain: 180, release: 216)` — for music decoded out of another cartridge, whose instruments already carry them and need no converting (attack is ADDED to the level each frame; decay and release are what it is MULTIPLIED by, out of 256; sustain is where it holds). **What it costs** is one pass over the sounding voices once a frame, where the four numbers move the level, and one addition per sample per sounding voice in the mix, to slide the loudness there — and a game that shapes no note emits none of it.
- `instrument :piano, from: "piano.wav", holds_from: 0.4` — **where a held note reads back to**, so a note can OUTLAST its recording. A piano recorded for half a second and held for two seconds otherwise ends where the recording does, which is both too early and a click. Say where the body of the note begins — after the strike — and a long note reads round that point for as long as it lasts, so the attack is heard once and the note goes on. A time in seconds (a Float), or a sample number (a whole number), which is what a recording lifted out of another game arrives with. A point outside the recording is a friendly error naming the recording and its length. A recording that says nothing runs out as it always did. Both words work on `sample` too.
- `instrument :name, from: "piano.wav", note: :C4` (same `pcm:`/`from:`/`rate:`/`note:` as `sample`) → an `Instrument`: a recorded sample you play *notes* on, one recording covering the whole keyboard. `inst.play(:E4)` plays a note; `inst.play(:C4, :E4, :G4)` a chord (each note a voice, sounding together); `inst.play(:E4, volume: :half)` sets level; `inst.stop` silences it. Pure sugar over `sample.play(pitch:)` — each note is a pitched voice in the mixer. Trigger notes live from input (`pressed(:a).then { piano.play(:C4) }`), or let a song play it: `voice :melody, plays: :piano` (see `song`).

## Measuring a finished game

Not verbs — these are called on the built cartridge.

- `rom.profile` (also `ruby-gba profile game.rb`) — **what the build made of your game, then where its frames actually went.** Two halves. First the build's: how big each routine came out, which fit in the console's quick memory and which missed, what a routine that missed wanted and what was left when its turn came, what each layer holds, **which collections went in the roomier of the console's two work memories** (a decision nobody wrote, and the only way to see it), and **how much of the console's picture memory the sprites and tiles took — with how much of the room left over came from storing the small-palette ones at half size**. None of that survives into a running cartridge, so nothing else can tell you afterwards (least of all the last one: the pictures are there at the size the build chose, and what they would have cost the other way is gone). Then the run's: which of your routines the console really spent its frames in, the rate it produced, and how much of each frame was left over. Nothing here is predicted, so nothing here can be wrong about a loop nothing could see through. `format: :json` gives the same facts as data, for comparing two builds.
- **The profile also says whether the PICTURE came out right**, which is a different question from where the time went, and there is one such question per screen. A game drawing straight into the picture the display is reading is asked whether it **tore** — how many rows went up before the game had finished them. A game on `screen :bitmap, tear_free: true` is asked whether it is **losing half its drawing**, which is that screen's own footgun: it keeps two pictures and shows them in turn, so a game that ADDS to what is already there (a dissolve, a trail, a plot filling in) puts half its additions in each and the screen alternates between two half-finished pictures. What the player sees is flicker, and nothing on screen explains it — every dot the program drew really was drawn. The report names how many pixels are stuck, where the first one is, and the two fixes: repaint the whole picture every frame, or use `keep_showing` for a part that changes now and then. A game is on one screen or the other, so exactly one of the two is ever asked, and a screen where neither applies says nothing rather than saying "no". **Both are measured on a real run, not read off the program** — which is the whole point, because the difference between a trail that is broken and one that is handled (wolf3d's death fizzle draws every dot on two frames running) is how many frames each drawing op runs on, and nothing at build time can see that.
- **The profile also says how many bytes the game COPIED INTO VIDEO MEMORY a frame, and what copied them** — tiles it paints from a list (`tiles ..., from: list` and `changed`), a whole map handed to a background (`show_map`), and a sprite kept to one frame at a time getting its next frame. Each is a copy in the gap between frames, and the processor waits while it runs, so the time lands on the routine that started it (see the next entry) and this line says what the copy was; a game typing a box of text can see what typing costs: a 104-tile run copied every frame says 3328 bytes a frame. It is counted off the console, from how many times the instruction that starts each copy ran, so nothing is added to the cartridge to count it. A kind of copy that did not run in the measured frames says nothing, and a game with none says nothing at all.
- **Each routine's line gives two shares: of the instructions run, and of the time the console was awake**, and the two part company at a copy. The console stops the processor until a copy is done, so a routine that sends a scene's pictures as the scene arrives runs a dozen instructions and can take most of a frame. The time is charged to the instruction that started the copy, so it lands on the routine that asked for it. A copy the screen or the sound starts by itself (a background's rows bending, recorded sound being fed) is left out of that: its time lands on whatever was running.
- **The profile also says when a pass ended a few lines too late.** A pass of the game loop waits for the NEXT break between pictures, so a pass that ends two lines after a break began sleeps a whole picture, and a game whose rate halves for two lines of work otherwise shows only the lower rate. The report says how many passes did it and how many lines sooner they had to end, and `format: :json` carries the same as `late_passes`. Measured on a real game's arrival in its play scene: four kilobytes more of pictures sent on arrival was five lines, and the pass ended two lines into the break. A game none of whose passes ends late says nothing.
- **The profile also says how many SOUNDS did not play.** `play` on a `sample` fills one of the mixer's voices, and with every voice busy the play is dropped — deliberately, since the alternative is cutting off a sound already sounding, which is worse and is never what anybody meant. So the game carries on, right in every other way, one sound quieter than you wrote it. A note of a song or a sound effect that finds no voice is counted too (see `sound_effects`). There is no error and nothing on screen, and no build can see it coming: whether it happens depends entirely on play — a burst of explosions, a chord of music underneath them. The report says how many were lost over the frames it measured, and — where a song was holding voices at the worst of those moments — **how the voices were being split**, which is the half you can do something about (a part moved onto the square wave, a shorter chord, fewer sounds at once). How many were *sounding* is never said, because a drop means every one of them was. A run that lost nothing says nothing, and a game that plays no samples says nothing either, so "we did not look" never reads as "nothing was wrong". It reports rather than warning: a game that fires twenty shots in a frame and hears sixteen sounds right, and whether the loss matters is a question about your game's sound that no count can answer.
- **Reaching the moment worth measuring is the whole problem**, because the interesting ones are the worst ones — the boss, the floor with sixty guards, the frame where a dozen things explode — and those are exactly the ones furthest from the title screen. A game boots to its title and **holding a button will not get past one**, because a menu reads the press *edge*, so a held button is one press however long it is held. There are three ways in, and the report always says which one it used, since the same cartridge measured on its title screen and measured in its boss fight are different numbers about different code.
  - `keys: [:left]` — held for the whole run. Worth passing wherever it helps: a game costs what the player makes it cost, so a profile with nothing held is a profile of a game standing still.
  - `scene: :playing` — **hold the game in one screen and measure that**, with nobody playing it. Which screen a game is on is just a variable and the build knows where that variable lives, so it is written before every frame. Written once is not enough and that is not a detail: a game left alone *leaves* almost at once — put snake into its playing scene with nobody steering and the snake is dead in a few frames, so every scene reports the game-over screen's routines under the wrong name. Held there, it measures the routines that scene runs. It is not a game anybody could play, and it does not need to be.
  - `from: "boss.state"` — **measure a moment you played to**, saved as an emulator save state. This is the general answer and the one for a moment a scene cannot give: a scene says which routines *run*, where a saved moment also carries the **state that makes them expensive**. The boss scene with nothing spawned is not the boss fight. Play to it once, in any emulator, save, and profile that moment for ever after.
- **A state from a different build is refused, loudly.** A saved moment holds addresses, and rebuilding the game — changing one number — moves every one of them, so reading it would give numbers about whatever code took those addresses over. That still looks like numbers, which is what makes it worth an error rather than a warning: measuring the wrong thing quietly is worse than not measuring. The emulator will not catch this for you (it only refuses a state from a different *game*, by the title in the cartridge header, and accepts one from a different *build* of the same game), so the framework compares the cartridge's own checksum, which the state records. **A build is deterministic**, so this never becomes a nuisance: building the same source twice gives the same cartridge, and simply re-running a build keeps every saved moment. Only a real change moves the addresses, which is exactly when the moment has stopped meaning anything.

## Playing a finished game with nobody at the controls

Not verbs either — these drive a built cartridge.

- `walk = RubyGBA.playthrough "walk to the signpost" do … end` → a **playthrough**: a game driven with nobody at the controls, from a **script** that says what to press. A game can otherwise only be played by a person, or poked by a test that writes out which button is down on which frame; a script says it the way a person would, and gives the same minutes of play every time. The block is read where the playthrough is declared, so a slip in it (a button the console does not have, a count of frames that is not a whole number above nought, two moments of one name) is a friendly error there and not part way through playing. Nothing is played until `play`. The block is run with the script as itself, so the steps need nothing written in front of them; a local variable from around the block is still in reach inside it, and a method or instance variable of the place it was written is not. (And a local called `hold` or `press` would hide the step of that name.) Inside the block:
  - `press :a` — **a tap**: the button goes down for one frame and comes up for one. The frame up is part of the tap, which is what makes two taps in a row two presses — a menu reads the press and not the hold, so a button simply left down would be one press however long it stayed there. `press :l, :r` taps several together. **A tap is never missed by a slow game**: the console notes a press on every frame and hands it to the game the next time the game looks. What a slow game can do is fold two taps of one button into one, when both land inside a single trip round its loop.
  - `hold :right, frames: 40` — keep one or more buttons down for that many frames, then let go. **Frames, not trips round the game's loop**: a game that fits its work into a frame sees the button forty times, so a character that walks two pixels a time has walked eighty; a game too slow for that goes round less often and sees it fewer.
  - `wait frames: 30` — let that many frames go by with nothing pressed, for an animation to finish or a screen to settle.
  - `wait_until("the file menu is up") { |game| game.var(:screen) == 1 }` — **let frames go by until something is true of the game.** Counting frames is exact and brittle: the day a screen takes a frame longer to come up, every step after it is a frame out. This asks the game instead. The block is handed the running cartridge — the same reader `play` hands out at a moment — and is asked after every frame, so the script carries on from the **first** frame the answer is yes. It always plays one frame at least, since the game is asked after a frame and never before one. The words say what is being waited for, written to sit in the middle of a sentence, and they are not decoration: they are what a wait that never ends has to say for itself. **The block has to answer true or false.** A number is a friendly error, because Ruby takes every number for yes, nought included — so `game.var(:flags) & 4`, the way the test is written in C, would end the wait on its first frame whatever the flags were. Compare it: `(game.var(:flags) & 4) != 0`.
  - `hold_until("the hero is at the door", :right) { |game| game.var(:px) >= 200 }` — the same, with buttons down while it waits. They come up when the wait ends. The words come first, as in `wait_until`, and the buttons after.
  - **A wait that never ends stops the playthrough** instead of hanging it. Both steps take `within:`, how many frames to go on asking (600, ten seconds of play, unless said). After that many the playthrough raises `RubyGBA::Playthroughs::GaveUp`, whose message says whose script it was, which wait in its own words, the frame it gave up on, and — on a line of its own, to copy — where it wrote a picture of the screen at that frame. The picture is usually the whole answer, because the game is on a screen the script did not expect. The error also answers `words`, `frame` and `picture`. The picture is left in a folder of its own in the machine's temporary files, and nothing takes it away.
  - **A script with a watching step is declared where it is used, not kept in a constant of a test class.** This suite runs each test on a core of its own, and a constant has to be something every core can read; a block that watches a game is not. A script that only counts frames can be a constant.
  - `moment :at_the_signpost` — **name the frame that has just been played**, so it can be asked for afterwards. A moment has to come after a step, since before the first one no frame has been played. The name is a symbol of letters, digits and underscores: a tape writes it down as a word, so it has to be one.
- **Open a script with a wait.** A cartridge spends its first frame or more setting itself up, and a press made then is deliberately forgotten — on a real console too — so that a button held through power-on is not taken as a press. A tap on the very first frame is not seen. How long setting up takes depends on the game, so a `wait_until` that watches for the first screen is the opening that survives the game changing; `wait frames: 10` is the one that needs no thought.
- `played = walk.play(cartridge) { |moment, game| … }` — play it, from power-on (or from a save, or after a lead-in: see the entries below), on a cartridge the build made (`RubyGBA.build`, `game.build_rom`), or on a cartridge file by its path (see below). At each named moment the block is handed the moment's name and the running cartridge, which answers everything a test of a running cartridge asks: `game.var(:px)`, `game.sprites(:hero)`, `game.pixel_gba(x, y)`, `game.frame_gba`. **What it is asked of the whole screen is cheap enough to ask on every frame**, because the emulator answers it in one pass over the picture: `game.only_color` (the one colour every pixel is, or nil), `game.brightness` (every pixel's red, green and blue added up, each 0 to 31), `game.frame_colors` (the screen as one string, two bytes a pixel, to keep a still as or to hash), `game.same_picture_as?(other)` and `game.difference_from(other)` (how many pixels differ, the box they lie in and the first of them with both colours), where `other` is another running cartridge or a `game.picture` kept from earlier. Each is answered at the precision a console shows, five bits each of red, green and blue (see `compare` below for why that is not the emulator's own bytes); `game.all_black?` is the one that asks the emulator's eight, as it always did, so a screen the display has darkened to almost nothing is black to `only_color` a frame before it is to `all_black?`. `game.frame_gba` is the same colours as a list of numbers, for looking pixels up in; it costs several frames' worth of time, so a script that only keeps or compares screens wants the others. `played.frames` is how many frames went by, `played.moments` the frame each moment fell on (`{ at_the_signpost: 42 }`), `played.game` the cartridge as the last frame left it, and `played.tape` the presses that were made (see the next entry). **`played.pictures` is the screen at each named moment** (`played.pictures[:at_the_signpost]`): every pixel's colour as the console's own 15-bit number, a row at a time from the top, so the pixel at (x, y) is at `y * 240 + x` — the same list `game.frame_gba` gives, and the one `RubyGBA::Graphics::PNG.write` takes. **To look at them, ask for files:** `walk.play(cartridge, pictures_in: "pictures")` writes each as a PNG named for its moment (`pictures/at_the_signpost.png`), making the folder if it is not there, and `played.picture_files` says where each went. With no `pictures_in:` no file is written and `picture_files` is empty. Each is written as its moment is reached and not at the end, so a playthrough that gives up further on leaves the pictures of how far it got. **A file already there under a moment's name is written over, and files an earlier playing left are not taken away**, so a folder used twice can hold pictures of both: give a playing an empty folder to tell them apart. Everything that can be wrong with the folder is a friendly error before a frame is played, since the first picture may be minutes of play in: a `pictures_in:` that is a file or is not a path, a folder that cannot be made or written to, and two moments whose names differ only in their capitals (`:Door` and `:door`), which are one file on a disk that does not tell a capital from a small letter. What the pictures cost is memory: each is kept for as long as what the playing handed back is, about a third of a megabyte a moment, whether or not it was written to a file. Worked example: `test/ruby_gba/playthroughs/test_playthrough_pictures.rb`. **A long playing does not pile its sound up in memory**: the running cartridge holds a minute of play at most, and the sound before that is written to a scratch file in the machine's temporary files, which is removed when the playing is no longer held or when the program ends. `game.audio_energy`, `game.sound?` and `game.audio_energy_by_frame` still answer for the whole playing, and they can be asked on every frame of it: how loud each frame was is worked out once and kept, so the only sound an asking reads is the frames played since the last one, and `game.audio_energy_by_frame.last` after a frame is how loud that frame was. The first asking of a long playing reads the file, once. (`game.audio_samples` is every sample of the playing at once, read from the file each time it is asked, so that one is slow to ask often and does hold a long playing's sound in memory.) **Frames are counted from 1**: frame 1 is the first one played. It plays in the emulator, as fast as the machine goes, and with no emulator installed it stops with what to install. Worked example: `test/ruby_gba/playthroughs/test_playthrough.rb`, which takes `examples/hero.rb` from its file screen out into the world.
- `walk.play("game.gba")` — **play a cartridge file**, wherever a cartridge goes: `play`, `tape.play` and both sides of `compare` take the path of one in place of a cartridge the build made. That is how a cartridge this framework did not build is driven — the original of a game being rebuilt, to lay the rebuilt one beside — and one of this framework's own, once it has been written to a file, is the same case. **Nothing in such a cartridge has a name.** Which variable is where and which sprite is which is what the build worked out, and that is kept beside a cartridge and never in it, so a file has none of it. **What can be read is what is really there**: the screen (`game.pixel_gba(x, y)`, `game.white?(x, y)` and the other colour tests, `game.frame_gba`), memory by its address (`game.mem8`, `game.mem16`, `game.mem32`), the sound, the save memory. **What cannot is anything by name**: `game.var(:px)` and `game.sprites(:hero)` are a friendly error saying the cartridge was not built here and what to read instead. So a script watches such a cartridge by a pixel or by an address — `wait_until("the title is up") { |game| game.pixel_gba(120, 40) == LOGO_RED }`, `hold_until("the door", :right) { |game| game.mem8(0x0300_1234) == 3 }` — where the address is one somebody found, since nothing here can say what it holds. Pictures at moments, tapes, saves and comparisons all work as on any cartridge. The framework never learns what the cartridge is: it runs the bytes it is given and keeps none of them, and all a tape says of it is the title in its heading and a checksum, for a person. **Nothing is written beside the file**: the console plays a copy of its own, and a save goes where every playthrough's does (see the next entry), so playing a cartridge twice plays the same cartridge twice. **Its save can be of any size.** Save memory comes in more kinds than this framework builds with; a save of a size its own cartridges have comes back as the same `IR::SaveImage` theirs does, and one of any other size is kept as its bytes (a `RubyGBA::Diagnostics::SaveBytes`), which is all that is known of it. Both answer `to_sav` and `write_sav`, and both start another playthrough. Nothing checks that a save handed to such a cartridge is one of its own, since nothing says how much save memory it has. Friendly errors before anything is played, on either side of a comparison: a path with no file at it, a file that is not a cartridge (every cartridge carries the same byte at one place in its heading, and a file without it is something else), the bytes of a cartridge given where its path was meant, and something that is neither a cartridge nor a path. Worked example: `test/ruby_gba/playthroughs/test_playthrough_cartridge_file.rb`.
- `walk.play(cartridge, save: saved)` and `played.save` — **start a playthrough holding a save, and get the save memory back when it ends.** A game that keeps its progress in the cartridge can only be played from its first screen otherwise, and the third room is then every playthrough's first three rooms over again. `played.save` is the cartridge's save memory as the last frame left it (a `RubyGBA::IR::SaveImage`, the same one the interpreter takes, or nil for a cartridge with no save memory), and `save:` takes one — so one playthrough plays to the save point and every other one starts there: `at_the_door = to_the_door.play(cartridge).save`, then `fight.play(cartridge, save: at_the_door)`. **Or a save file**: `played.save.write_sav("door.sav")` writes it as the file an emulator keeps a cartridge's save in, and `save:` takes the path of one (`save: "door.sav"`), from this framework or from an emulator a person played in. A save file is as big as its cartridge's save memory, which for a cartridge this framework built is 8K, 32K, 64K or 128K. **The save handed over is left as it was.** The game goes on to save over its own copy, and that is in the `played.save` that comes back, so one save can start as many playthroughs as wanted and each begins in the same place. **A game that saves needs time to**: this framework writes a save in the background, a piece each trip round the game's loop, so a script waits after the press that saves before it ends (see `save_data` for how long a save takes: a handful of trips for a kilobyte on the 32K memory, several times that on flash) — a playthrough that ends sooner hands back the save from before. **No save file is left beside the cartridge**, which is where an emulator left to itself writes one — and the next playing would then start in the last one's save. Each console keeps its save memory in a file of its own, in a folder the framework takes away when the program ends, so two playthroughs at the same moment never see each other's, and the save to keep is the one handed back. Friendly errors, before the console is switched on: a `save:` that is neither, a path with no file at it, the bytes of a save given where its path was meant, a file that is not the size of any save memory (a tape given in its place), and a save from a cartridge with another size of save memory than this one's. **A tape says which it was recorded from** — its third line is `starts from: power-on`, or `starts from: a save 0x1A2B3C4D` with a checksum of the save's bytes, for a person to tell which save the tape goes with (nothing holds the tape to that checksum, as nothing holds it to the cartridge's). One recorded from a save is refused without a `save:`, since the same presses from power-on are a different game; a tape recorded from power-on can be played from a save, and that is the caller's to mean. The save itself is not in the tape: a tape is the presses, and played on another cartridge it wants that cartridge's own save. A comparison starts both cartridges from power-on unless it is given a save for both (`save:` on `compare`, below), so a tape recorded from a save is compared with one. Worked example: `test/ruby_gba/playthroughs/test_playthrough_saves.rb`, which saves a walk in `examples/hero.rb` and starts again from it.
- `walk.play(cartridge, lead_in: past_the_logos)` — **a lead-in: another playthrough, played on the cartridge first and not counted.** A cartridge somebody else made shows its logos and an introduction before its first screen and another does not, so the same script from power-on finds the two in different places before a button is pressed. A lead-in gets a cartridge to where the playthrough should begin by its own road, which is usually a wait that watches for the first screen: `past_the_logos = RubyGBA.playthrough("past the logos") { wait_until("the title is up") { |game| game.pixel_gba(120, 40) == LOGO_RED } }`. **Nothing in it is counted**: frame 1 is the first frame after it, `played.frames` and `played.moments` count from there, and its presses are not on the tape. A moment it names is nobody's to ask for. It is played after the console is switched on holding its `save:`, so the two go together. **A tape says it was recorded after one** — its third line ends ` after a lead-in` (`starts from: power-on after a lead-in`) — and is refused without a `lead_in:`, since with none the same presses start in a different place. The lead-in itself is not on the tape, for the reason a save is not: it is how THIS cartridge gets to the start, and another cartridge has its own. A wait in a lead-in that never ends gives up as any wait does, saying it was the lead-in's. Something that is not a playthrough is a friendly error. Worked example: `test/ruby_gba/playthroughs/test_playthrough_lead_in.rb`.
- `tape = played.tape` → a **tape**: the presses of that playing, written down — which buttons were down on each frame, and the frame each named moment fell on. **A script says what to do; a tape says what was done.** The difference shows the moment a script watches the game: `hold_until("the door", :right)` is as many frames as *this* game took to reach the door, and the tape holds that number, so it needs nothing to watch. That makes a tape the same presses on the same frames whatever it is played on, which is what lets two cartridges be handed exactly the same game. `tape.play(cartridge) { |moment, game| … }` plays it, and gives back what playing a script gives back, pictures included (and `pictures_in:` writes them the same way). `tape.frames` and `tape.moments` read it without playing it. `tape.up_to(46)` is the same tape ending on that frame: a hold the frame falls inside is cut short, a moment is kept when the frame it names is still on the tape, and a frame past the end is the whole tape — play it and the cartridge is on that frame. `tape.presses_within(1..60)` says what was down on those frames, as a list of stretches each with its `frames` (a range) and its `buttons`. `tape.write("walk.tape")` writes it to a file and `RubyGBA::Playthroughs::Tape.read("walk.tape")` reads one back, the same tape. **The file is plain text**, a line for each stretch of frames with the same buttons down, so a person can read one, write one by hand, and see a change to one as a change to a few lines:

  ```
  ruby-gba tape 1
  recorded on: HERO 0x5C0FFEE5
  starts from: power-on

  10 -
  1 down
  1 -
  20 right up
  moment walked
  ```

  Three lines of heading, always those three in that order. Below them: a count, then the buttons down for that many frames, `-` for none; a moment on a line of its own, naming the frame the line before it ended on; and, for the reader, blank lines and lines that start with `#`. A hold of twenty frames is one line, and two lines that say the same buttons are read as one. **What it was recorded on is for a person**: the cartridge's title and a checksum of its bytes say which game and which build the tape came from, and nothing holds the tape to them — playing it on another cartridge is the point. (A title holding bytes that cannot be printed, as a cartridge somebody else made can, is written with `?` in their place.) A line that cannot be read is a friendly error naming the line, what is on it, and what a line there has to look like; a file that is not there, or is not a tape, is one too. **A tape can be kept in a constant** and read from any core, which a script with a watching step cannot: it holds nothing but names and numbers. Worked example: `test/ruby_gba/playthroughs/test_playthrough_tape.rb`.
- `result = walk.compare(ours, theirs)` (also `tape.compare(ours, theirs)`) → a **comparison**: two cartridges played side by side on the same presses, and the first frame on which their pictures differ. Somebody rebuilding an existing game wants to know where their cartridge has drifted from the original, and a change to a game that moves something a frame early wants catching without two people looking at two screens; both are the same question. `result.drift?` says whether the two ever differed, `result.drift.frame` the first frame they did, counted from 1, and `result.drift.moment` the last moment the script named before that frame, for a person to place it by — nil when it had named none, and a moment naming the very frame they drifted on is not before it. `result.drift.differed` is what differed on that frame: `[:picture]`, unless readings are compared too (see `readings:` below). `result.drift` is nil when they never did. `result.frames` is how many frames were played. **There are two ways to compare, and this is the one a comparison uses with nothing said** (the other, `same: :script` below, plays the script on each cartridge by itself and compares the two at each named moment, which forgives timing). **Both get the same presses on the same frames.** What is compared is a tape, so a script is first played on the FIRST cartridge alone, to make one — and where that script watches the game (`hold_until("the door", :right)`), it is the first cartridge it watched, and the second is handed exactly the walk the first one took. A second cartridge whose door is a frame further off is still walking when the first has stopped, and the two differ from there. A tape holds its presses already, so it is compared as it stands. **Every pixel of every frame, and it stops at the first drift**: one frame out is nearly always every frame after it out too, so the first is the one worth having, and `result.frames` is then how far it had played when it stopped. (`carrying_on: true`, below, plays to the end and lists every drift.) **The same colours are the same picture**, whatever the console built them from: a rebuilt game that draws with a sprite what the original drew with a background has not drifted, so long as every pixel comes out the colour the original's does. **A colour is compared at the precision a console shows**, five bits each of red, green and blue. The emulator keeps eight, and what it holds below the five is its own working: it fills a colour read out of the colour table in one way, and works a colour the display brightened, darkened or mixed out at all eight. So it can hold the same five-bit colour as two different numbers, and two screens that differ only down there are one picture here: a game that fades where the original swapped colours has not drifted, so long as its colours come out the same at five bits. What it costs is the two cartridges running at once and a compare of the two pictures a frame, which comes to about half the speed of playing one; a script costs one more playing of the first cartridge before that, which a tape does not. Worked example: `test/ruby_gba/playthroughs/test_comparison.rb`, which builds `examples/hero.rb` a second time with a quicker hero and finds the frame the two part on. **How alike is alike enough is said where the comparison is made**, on `compare`, with the settings below. With none of them said, one pixel out on one frame is drift — right for checking that a change to a game moved nothing, and wrong for a game being rebuilt to match another, where one stray pixel several minutes in would hide everything after it. Each is read before a frame is played, so one that makes no sense — or a setting `compare` does not have, which is a name spelled wrong — is a friendly error straight away:
  - `share_may_differ: 0.01` — **the share of the pixels that may be a different colour** before a frame counts as differing, from 0 to 1: a share and never a count, so `1` is every pixel there is. The screen has 38,400 pixels, so 0.01 is 384 of them and `1.0 / 38_400` is one. A frame differs when MORE than that share is out; exactly that many is still alike, however the share was written. **It is a share of the pixels that are looked at**: with half the screen ignored (below), 0.01 is 192 pixels, so ignoring more of the screen never makes the share looser than it says.
  - `frames_in_a_row: 3` — **how many frames running have to differ** before it is drift, 1 unless said, so that one frame of flicker is not. (Where readings are compared too, each thing counts its own: see `readings:` below.) The frame reported is the FIRST of the stretch and the moment the one before that frame, while `result.frames`, for a comparison that stops at its first drift, is the last frame it had to see to be sure. A stretch that ends sooner is forgotten, and so is one the tape runs out on.
  - `ignoring_rectangles: [[0, 128, 240, 32]]` — **rectangles of the screen that are not looked at**, each `[x, y, width, height]` in pixels from the top left: a status bar not drawn yet, a clock, a part known to differ. A difference wholly inside them is no difference; one that reaches outside still counts by the pixels outside. Rectangles can overlap. A rectangle has to lie on the screen, and one written with no list around it (`ignoring_rectangles: [0, 128, 240, 32]`) is a friendly error showing how one is written.
  - `ignoring_frames: [1..120, :title..:in_the_world]` — **stretches of the playthrough that are not looked at**: an opening the rebuilt game does not have yet, a screen that shows the time of day. Both cartridges are still played through a stretch, since the game has to get to the other side; what differs inside it is not counted, and the comparison carries on to the next drift outside it. A difference that begins inside a stretch and is still there when it ends is drift on the first frame after. **A stretch is a Ruby range, of frame numbers or of the names of two moments.** The named form is the one to reach for, because frame numbers all move the day a script gains a step and the moments move with the game. A moment stands for the frame it names, so `:title..:in_the_world` is those two frames and every frame between, the same on a script and on its tape. Both frames, because of how a moment usually comes to be: a script waits until the title is up and names that frame, which is the first frame OF the title, and leaving it in would report the title as drift on the one frame of it that was not left out. Being a range it means what one means: three dots leave its last frame out, `(900..)` runs to the end of the playthrough and `(..:title)` from its start. A range with neither end is every frame, and is refused: a comparison that looks at no frame finds nothing. A frame that is not looked at also breaks a run of differing frames, so with `frames_in_a_row:` the frames either side of a stretch are never frames in a row. Friendly errors, all before a frame is played: a moment the playthrough does not declare (naming the ones it does — a script says its moments where it is declared, so this costs no playing), two moments or two frames the wrong way round (shown the right way round), a range that goes below frame 1, a range that holds no frame, and one range written with no list around it. One is found later, because it is not known sooner: two moments a script declares one straight after the other name the same frame, and three dots between those leave out the only frame there is — refused once the script has been played and the frames are known, and on a tape before anything is played.
  - `readings: { paces: :paces, hero_x: [:px, ->(game) { game.mem16(0x0300_1234) }] }` — **named readings: numbers read off both running cartridges on every frame that is looked at and compared, as well as the picture.** Two games can show the same screen and be a long way apart underneath — a position a pixel out behind a wall, a counter that will run out a second early — and where the pictures do differ, "the hero is at 61 on one and 60 on the other" says what went wrong where two screenshots only say that something did. A reading is a name you choose and a way to read it, and there are three ways to say the way. **A variable's name** (`paces: :paces`) reads that variable from both, which is all it takes on two cartridges this framework built. **A block** (`where: ->(game) { [game.var(:x), game.var(:y)] }`) is handed each running cartridge in turn — the same reader a script's `wait_until` is handed — and what it gives back can be anything two of which can be the same: a number, a pair of them, a colour's name. **A list of two** (`hero_x: [:px, ->(game) { game.mem16(0x0300_1234) }]`) is one way for each cartridge, the first's and then the second's, each a variable's name or a block. That last one is what somebody rebuilding a game needs, because the two cartridges are not the same program: the rebuilt one keeps the hero's position in a variable with a name and the original keeps it at an address somebody found, and it is "the hero's position" all the same. **A reading that differs is drift on the first frame it differs**, like the picture: `ignoring_frames:` leaves it out of the same frames, and `share_may_differ:` and `ignoring_rectangles:` are about the picture only — a reading is the same on both or it is not. (Two values that are both not a number count as the same.) **With `frames_in_a_row:` each thing counts its own frames**: the picture has to differ that many frames running, or one reading has to. A picture that flickers for a frame and a count that is out on the next are two flickers and no drift, where counted together they would be two frames in a row. `result.drift.differed` then lists what differed from that frame for as long as it took, the picture first: `[:picture, :paces]`, or `[:paces]` for two cartridges whose screens agree. **`result.drift.readings` is every reading on both cartridges on that frame**, the ones that agree too, each name with the first cartridge's value and the second's (`{ paces: [1, 2], where: [22, 22] }`); the ones that agree say what the difference is not. With `frames_in_a_row:` they are of the frame the drift began. What it costs is each reading read once from each cartridge on every frame that is looked at, whether or not readings are compared, which for a variable or an address is one read of memory. **A block that stops with an error** raises `RubyGBA::Playthroughs::Comparison::ReadingFailed`, which says which reading and which cartridge (the block's own error is its `cause`); since every reading is read on the first frame that is looked at, that is where a block that cannot work is found. Friendly errors, before a frame is played: a variable's name on a cartridge that was not built here (a cartridge file has no names — give that side a block that reads memory by its address), a variable the cartridge does not have (naming the ones it does), a way that is none of the three, a name that is not a symbol, and a reading named `:picture` or `:frames_apart`, which are what the picture and the frames between the two are called where what differed is listed. Worked example: `test/ruby_gba/playthroughs/test_comparison_readings.rb`.
  - `comparing: [:readings]` — **what is compared, as a list**: `:picture`, `:readings`, or both. With nothing said it is the picture, and the readings where any were given. **The readings alone** is for a game whose numbers are right long before its pictures are: the hero walks at the right speed weeks before the scenery is drawn, and comparing the readings only says whether the game underneath has drifted while every frame of the picture still differs. **The picture alone, with readings given**, compares the picture and still reads the readings, so a drift in the picture says what each reading was on both cartridges without a reading that is known to differ being called the drift. Friendly errors: an empty list, something that is not a list, a thing a comparison cannot compare, and `:readings` with no `readings:` given.
  - `carrying_on: true` — **play on past the first drift, to the end, and list every stretch of drift.** It answers what the first drift cannot: do the two come back into step, or is everything after it different for one reason? A hero who takes a corner a frame late and is in step again a second later is a different finding from one who is a pixel out for the rest of the game, and the first drift is the same frame in both. `result.drifts` is every drift in the order they happened, and each says the frame it began on (`drift.frame`), the last frame of it (`drift.last_frame`), both as a range (`drift.stretch`, `46..48`), how it ended (`drift.ended`), and what any drift says: its moment, what differed, the readings on the frame it began. `result.drift` is still the first, and `result.frames` is then the whole tape. **How a drift ended is the answer to the question**: `:back_in_step` when the next frame was one on which the two were within the settings again (`drift.back_in_step?`), `:tape_ran_out` when the two were still apart on the last frame of the tape, and `:not_looked_at` when the next frame was one `ignoring_frames:` leaves out, where nothing is known and a difference still there afterwards is another drift. **A drift is under way while something goes on differing that has differed for as long as `frames_in_a_row:` asks**, and its last frame is the one before the frame on which nothing has. With one frame asked for, that is every differing frame until the first frame the two are alike again. With three, a reading that is out for a single frame straight after a picture's drift does not carry the drift a frame further — and a single frame alike in the middle of a long difference does end it, the rest being a drift of its own once it has lasted three frames again. **No frame is in two drifts**: where one thing stops differing while another that had already begun goes on long enough to count, that is one drift from the first frame of the one to the last of the other. **`drift.differed` is everything that differed for long enough while the drift lasted**, in the order each began, so a drift the picture began and a reading carried on says `[:picture, :late]`. **With nothing said it stops at the first drift**, `result.drifts` holds that one, and its `last_frame`, `ended` and `stretch` are nil: a comparison that stops never finds out how long the drift lasted. What it costs is the rest of the tape played, and with `reports_in:` a report written for every drift — so two cartridges that flicker differently on every other frame for a minute write nearly two thousand folders, and want `frames_in_a_row:` said first. Not `true` or `false` is a friendly error. Worked example: `test/ruby_gba/playthroughs/test_comparison_carrying_on.rb`.
  - `same: :script` — **play the same script on each cartridge by itself, in place of the same tape on both**, and compare the two at each named moment. There are two ways to compare and they find different things. **On the same tape**, which is what a comparison does with nothing said, the second cartridge is handed the first one's presses on the first one's frames: a door that opens a frame late is out of step from that frame on, and every frame after it differs. That is the strict comparison and the right one for a change that should move nothing, or for a rebuilt game that is nearly there. **On the same script** each cartridge presses A when its own text box is up and stops walking at its own door, so each arrives at "the door" however long it took, and the two are compared there. That forgives timing and finds a game that LOOKS different, which is the one to use while a rebuilt game is still frames out everywhere and the question is whether its screens are right. **The two are compared at the moments the script names and nowhere else**, since there is no frame they share: the picture and any readings, exactly as they were as each cartridge reached the moment. A drift then names the moment it is at (`drift.moment`), its `frame` is the frame the first cartridge reached it on, and it has no last frame, being one point. **`result.moments` is the frame each cartridge reached each moment on**, the first's and then the second's (`{ title: [12, 12], door: [200, 203] }`), so how long each took is always said, drift or not. (On the same tape it is there too, the same frame twice, for the moments reached before the comparison stopped.) `result.frames` is the frames the first cartridge played. It stops at the first moment that differs unless `carrying_on: true`, which lists every one. `share_may_differ:`, `ignoring_rectangles:`, `readings:` and `comparing:` mean what they mean on a tape; `ignoring_frames:` takes ranges of MOMENTS only and leaves out the moments a range covers. What it costs is each cartridge played once from start to end, whatever is found, and no comparing between moments. Friendly errors, before anything is played: a script that names no moment, or whose every moment `ignoring_frames:` leaves out (there is nowhere to compare), `frames_in_a_row:` or a range of frame numbers (each cartridge counts its own frames, so neither means anything), `same:` given anything but `:tape` or `:script`, and `same: :script` or `frames_apart:` given to a tape, which holds presses and no script. A script that gives up on one of the two — the second never reaches what the first reached — raises the playthrough's `GaveUp`, saying which cartridge, which wait and where its picture is; what the two had been through before that is not kept. Worked example: `test/ruby_gba/playthroughs/test_comparison_same_script.rb`.
  - `frames_apart: 5` — **how many frames apart the two may reach a moment**, on the same script. It is not checked unless said: a rebuilt game is compared for its look first, and for its timing when somebody is ready to. With it, two cartridges further apart than that at a moment drift there, `drift.differed` holding `:frames_apart`, though their screens are the same. It is a friendly error on the same tape, where the two are always on the same frame, and when it is not a whole number, 0 or more.
  - `lead_ins: [nil, past_the_logos]` and `save: "door.sav"` — **start the two cartridges in step.** Two cartridges from power-on are only in step when they are the same game built two ways. An original and a game rebuilt to match it differ before anything is pressed — logos, an introduction, a different number of frames to the first screen — and every frame after that is drift for a reason nobody is asking about. There are two answers and they can be used together. **A lead-in for each** is a playthrough of its own played on that cartridge first, the first cartridge's and then the second's, either of them `nil` for none (see `lead_in:` on `play`, above): each gets its cartridge to the same place by its own road, and the comparison starts there. Its frames are not on the tape and are not compared, and **frame 1 of the comparison is the first frame after both lead-ins**, so every frame number in the result and in a report counts from there. **One save for both** (`save:`, a save a playthrough handed back or the path of a save file, exactly as on `play`) switches both consoles on holding it, which skips whatever a game does before its save is loaded. A report says where the two started, and its tape says it too, whatever the tape that was compared said, so the tape is played back with the lead-in or the save it needs. **Where the two were started differently** — a lead-in for one and none for the other — a report holds a tape for each, `first-to-the-drift.tape` and `second-to-the-drift.tape`: the same presses under two headings, each playing its own cartridge. A tape recorded after a lead-in is compared with `lead_ins:` holding at least one, and one recorded from a save with `save:`; without, it is a friendly error. The save is read once and made to fit each cartridge before anything is played, so a save of the wrong size for either is a friendly error then, saying which cartridge. `lead_ins:` that is not a list of two, each a playthrough or `nil`, is a friendly error, and so is a save that is not one. A lead-in that gives up says which cartridge it gave up on.
  - `reports_in: "drift"` — **a folder to write a report of the drift into**, for a person to look at. A frame number says the two parted and nothing about how, so a comparison given a place writes one folder for the drift it finds, named for the frame (`drift/frame-000046`), and `result.drift.report` is that folder's path. A comparison that carries on writes one folder for each drift, as each ends, and each drift says its own. It holds these files. `first.png` and `second.png` are the two screens on the drifting frame. `difference.png` is the first screen in grey with every pixel that differed in magenta — only the pixels that were looked at, so a part left out with `ignoring_rectangles:` is never marked. `side-by-side.png` is the two screens and the difference in one picture, left to right, at twice the console's size: the one to open first, and the one to send somebody (on the same tape it is the picture `write_side_by_side_picture` writes for that frame: see below). `report.txt` says it in short sentences: the frame, how long the drift lasted and how it ended where the comparison carried on, the moment named before it, what differed and how many pixels did, every named reading on both cartridges whether it differed or not, which two cartridges were played (title and checksum), what was compared and every setting that was in force (a stretch left out is said as its frames, and one written in moments as the moments and the frames they came to), and which buttons were down on the drifting frame and for the second before it. `to-the-drift.tape` is every press up to that frame, and it is the file that matters most: a picture says what the two screens were, where the tape plays EITHER cartridge to that exact frame again, with a script asking it things, which is where finding out why starts. (Two cartridges that were started differently get a tape each: see `lead_ins:` above.) **On the same script the folder is named for the moment** (`drift/moment-door`) and holds two tapes in place of the one, `first-to-the-moment.tape` and `second-to-the-moment.tape`: each cartridge made its own presses, and its own tape is the one that plays it back to that moment. Its text says the frame each reached the moment on and the last second of presses on each. Since the folder is the moment's name, two moments that differ only in their capitals are a friendly error there, as they are for pictures. **With `frames_in_a_row:` it is all of the frame the drift BEGAN**, the same frame `result.drift.frame` names: by the time a stretch is long enough to be called drift both consoles have played past its first frame, so the two screens are kept from the start of every stretch. **Nothing is written when there is nothing to report**: with no drift not even the folder named is made, and with no `reports_in:` a drift's `result.drift.report` is nil. A folder that is not there is made, one that is already there is added to, and a report already in it for the same frame is written over. What it costs is two screens copied out at the start of each stretch of differing frames, and the writing once for each drift; a comparison given no place copies nothing. Friendly errors, before a frame is played: a place that is not a path, a place that is a file, and a place that could never be made — one inside a file, or inside a folder that cannot be written to. A report that still cannot be written when the drift is found (a disk that filled) raises `RubyGBA::Playthroughs::Comparison::ReportNotWritten`, which says the frame and holds the finding as `drift` — and, for a comparison that carried on, the drifts found before it as `earlier` — so the playing is not lost with it. Worked example: `test/ruby_gba/playthroughs/test_comparison_drift_report.rb`.
  - **What the settings cost**: next to nothing beside the playing. Two frames the emulator holds as the same bytes are known to be the same picture in one comparison of them, whatever is set, and a frame that is not looked at costs nothing but the playing. With a share or a rectangle said, a frame that differs at all is gone through to count what is out, and the emulator does the counting, in a small fraction of the time the frame took to play — so two cartridges that differ a little on every frame are compared about as fast as two that agree. `frames_in_a_row:` costs nothing more.
- `walk.write_side_by_side_picture(ours, theirs, "door.png", at: :at_the_door)` (also `tape.write_side_by_side_picture(ours, theirs, "frame-46.png", at: 46)`) → **one picture of one frame on two cartridges**, for a person to look at: the first cartridge's screen, the second's, and the difference between them, left to right in one PNG. A frame number says two cartridges parted and nothing about how; two screenshots side by side say it, and the third panel says where to look. A drift report holds this picture for the frame it reports (`side-by-side.png`, above), and this is the same picture for any frame somebody wants — one a comparison called alike, the frame before a drift, a moment that looks wrong. **Each panel is the console's screen at twice its size**, 480 by 320, with a thin grey strip between two panels. Nothing is written on it: the left panel is the first cartridge handed over and the middle one the second. **`at:` says which frame**, by its number, counted from 1, or by the name of a moment, which is the frame that moment names. **The third panel is the first screen in grey with every pixel that differs in magenta**, the marking a drift report's `difference.png` has, so the two never disagree about what differed; two screens that are the same give a grey panel with no mark in it. `difference: false` leaves the panel out, and the picture is the two screens. **Both cartridges get the same presses on the same frames**, as in a comparison on the same tape: a tape is played as it stands, and a script is first played on the first cartridge alone to learn its presses. So the picture a report of a drift at a moment holds (`same: :script`, where each cartridge made its own presses) is not one this writes. Some of a comparison's settings mean here what they mean there, and the rest are refused: `ignoring_rectangles:` (a part of the screen left out is never marked, though both screens still show it), and `save:` and `lead_ins:` to start the two in step — a tape recorded from a save or after a lead-in asks for them. They are said again here and not remembered from a comparison, so the picture of a frame a comparison reported matches the report's when it is given the same ones. The folder the file goes in is made when it is not there, a file already there is written over, and the path is handed back. What it costs is both cartridges played to that frame, with nothing compared on the way, and for a script one playing of the first cartridge before that. Friendly errors, before anything is played: a frame past the end of a tape, a moment the playthrough does not name (naming the ones it does), an `at:` that is neither or is left out, a place that is not a path, is a folder, is a file that cannot be written over, or is inside a file or a folder that cannot be written to, a `difference:` that is not true or false, and a setting a picture does not have. One is found later, because it is not known sooner: how long a script plays, so a frame past a script's end is refused once the script has been played on the first cartridge. The command line has no command of its own for it; `ruby-gba compare --reports-in` writes it in every report. Worked example: `test/ruby_gba/playthroughs/test_comparison_side_by_side_picture.rb`.
- `ruby-gba play walker.rb --script walk.rb` — **play a game from the command line**, and print how many frames went by and the frame each named moment fell on. The cartridge is a game file (a `.rb` that declares a game, built first the way `build` builds it, taking `--set`) or a cartridge file (a `.gba`, yours or somebody else's). **What to press is a script file or a tape.** A script file is a plain Ruby file that declares one or more playthroughs with `RubyGBA.playthrough "NAME" do … end` and nothing else, the way a game file declares a game; `--playthrough NAME` says which when it declares several, and several with none picked is a friendly error listing them. `--tape walk.tape` plays a tape in place of a script. A playthrough declared with a symbol for a name (`RubyGBA.playthrough :walk`) is picked by the same letters. `--save door.sav` starts from a save file, and `--lead-in NAME` plays another playthrough from the script file first and does not count it. **A lead-in is declared in a script file, so `--script` is needed for one even when a tape says what to press**; a tape recorded after a lead-in, or from a save, asks for what it needs by its flag. **What it writes is what it is asked for**: `--pictures-in DIR` the screen at each moment as a PNG named for the moment, `--write-tape PATH` the presses that were made, `--write-save PATH` the save memory as the last frame left it (a cartridge with none says so and writes nothing). A place a tape or a save cannot be written to is refused before a frame is played, since both are written after the last one. A script that gives up, a file that is not there and a setting that makes no sense are each said in a sentence, before the game file is built wherever that can be known, and the command ends as a failure. `ruby-gba help play` says all of this.
- `ruby-gba compare ours.gba theirs.gba --script walk.rb --reports-in drift` — **compare two cartridges from the command line**, and say the frame they drift on, the moment before it, what differed and where the report is. **How it ends is for another program to act on, and it is the way `diff` ends: with 0 when the two agree, with 1 when they drift, and with 2 when they could not be compared** — a file that is not there, a setting that makes no sense, a script that gave up — so a build, or a program working through a list of scripts, never takes a file name spelled wrong for a drift. Each cartridge is a game file or a cartridge file, and what to press is `--script` (with `--playthrough`) or `--tape`, as for `play`. `--set` goes to every game file, so one game built two ways is two game files, or a cartridge file built ahead of time with `ruby-gba build --set`. **Every setting `compare` takes from Ruby is the flag of the same name**, with a dash for each underscore, and means what it means there: `--share-may-differ 0.01`, `--frames-in-a-row 3`, `--ignoring-rectangles 0,128,240,32` (each rectangle `X,Y,WIDTH,HEIGHT`, several separated by spaces), `--ignoring-frames 1..120 title..in_the_world 900..` (ranges of frame numbers or of moments, a moment by its name with no colon in front, two dots or three to leave the last frame out, and an end left off for an open one), `--comparing picture readings`, `--carrying-on`, `--same script`, `--frames-apart 5`, `--save door.sav`, `--lead-ins past_logos -` (a playthrough from the script file for each cartridge, `-` for none, and `--script` needed for them even with `--tape`) and `--reports-in drift`. A message that comes from the library names a setting the way Ruby writes it, and a line under it says which flag that is. **A reading on the command line is a variable**: `--readings steps` reads the variable `steps` from both, `--readings where=x` reads `x` from both under the name `where`, and `--readings hero=px,hx` reads `px` from the first cartridge and `hx` from the second. A variable's name means something only on a cartridge built here, so a reading needs game files, and one that needs Ruby to read it — an address in somebody else's cartridge — is given from Ruby. With `--same script` it also prints the frame each cartridge reached each moment on. Worked examples: `test/ruby_gba/playthroughs/test_command_line_play.rb` and `test/ruby_gba/playthroughs/test_command_line_compare.rb`.
