# DSL verb reference — the flat `RubyGBA.build` API

The verbs you call inside a `RubyGBA.build "NAME", code:, maker:` block (they mix
into `Builder` from `lib/ruby_gba/builder/*.rb`). A **drift test**
(`test/test_dsl_reference.rb`) fails if a builder verb isn't mentioned here — so
when you add a verb, add a line below.

Conventions: coordinates are pixels, top-left origin, screen is 240×160. A
`:symbol` names a variable; an `Integer` is a literal; a `Value` (from `var`) is an
expression. `fill_rect`/`dma_fill_rect` need an **even width**; `draw_rect_at` takes any.

## Build / screen

- `screen :bitmap` — pick the display. `screen :bitmap, tear_free: true` = double-buffered (Mode 4). `screen :tiled` = tile backgrounds + hardware sprites (also decides which kind `sprite` makes). `screen :rotozoom` = a background that can turn and resize as one whole piece — a title screen that zooms in, a race track that spins and pulls away — instead of only scrolling straight the way `screen :tiled`'s layers do. See `background(...).rotate` / `.scale` under Tiled backgrounds. Its own screen mode, not a flag on `screen :tiled`, because it's a different pair of hardware layers (one background only, for now); a plain scroll on it is a friendly error pointing at `rotate`/`scale` instead.
- `screen :bitmap, tear_free: true, colors: [...]` — **say which colors the screen shows** instead of letting the framework work them out from the ones you name. The tear-free screen holds a number per pixel that picks a color out of a shared table, and normally the framework builds that table for you, silently, from the color names you write — which is right until your pictures come from somewhere that already decided. Art imported from another game or a paint program has pixels that are numbers picking out of *its* table, so give the colors in that table's order and the pictures line up. Everything else is unchanged: you still write color names everywhere, and you never write a slot number. **The order is the whole point** — nothing is moved, nothing is added (not even black, which the worked-out table always reserves at the front), and a color repeated in the list keeps both places, because dropping one would shift every color after it and move every pixel of every picture. Drawing with a color the screen was not given is a friendly error naming it; giving two screens different lists is a friendly error, because the display holds one table at a time; and `colors:` without `tear_free: true` is a friendly error, because a plain bitmap screen holds a whole color in every pixel and has no table to fill in.
- `wait_vblank` — wait for the safe window to draw. A `game_loop` already does this each pass, so you only write it in a program that has no game loop, or under `frame_sync: :manual`.
- `halt` — stop (branch to self). `debug_halt` — truncate the ROM here (bisecting).

## Drawing (Mode 3, direct color)

- `pixel x, y, color` — one pixel (fixed coords).
- `fill_rect x, y, w, h, color` / `dma_fill_rect x, y, w, h, color` — a filled rect (fixed, even w).
- `draw_rect_at xpos, ypos, w, h, color` — a rect whose **position and size** the game can all work out as it runs (each of `xpos`/`ypos`/`w`/`h` may be `:var`/`Value`). That's the bar-or-column shape: a health meter that empties sideways (`draw_rect_at 8, 8, health, 6, :red`), a wall column in a first-person view, a tower that grows. A width or height of 0 or less draws nothing, so a bar can empty without a test around it, and **any width works — odd included** (unlike `fill_rect`/`dma_fill_rect`, which still want an even one). A size fixed when you write it costs exactly what it always did.
- `draw_column_at :picture, slice:, x:, top:, height:, width: 1` — **one column of a picture, stretched to a height the game works out**. `width:` is how many pixels ACROSS the strip is (a number you write, 1 by default), and a view whose strips are wider than a pixel wants it rather than a loop of its own: every pixel of a strip shows the same picture column at the same height, so **one walk down the screen fills all of them** — calling it once per pixel works the same answer out that many times over, and measures about three times dearer for a three-pixel strip. This is what a first-person view is made of: for each strip across the screen, work out how far away the wall is, turn that into a height, and draw a column of wall that tall — near walls tall, far walls short. `slice` picks which column of the picture (which part of the wall you are looking at), `x` is where it lands on screen, `top` and `height` are where it starts and how tall it is; all four can be worked out as the game runs. A height of 0 or less draws nothing and anything past the top or bottom is clipped, so a wall you are nose-to-nose with needs no test around it. **Many textures fit in one picture**: `slice` is a runtime value, so lay the wall pictures side by side and `slice` becomes `which_wall * width + column` — no runtime picture choosing needed. Also what a scaled sprite is (a thing that grows as it nears you), and a door sliding open. **A see-through picture costs the rows that hold pixels, not its height.** A scaled sprite is mostly nothing — a lamp in a square of ceiling, a clip of ammunition in a square of floor — and the framework works out, for each column of such a picture, where that column holds pixels, then walks those and skips the rest. So a picture nine tenths empty costs about a tenth, and there is nothing to write for it: leaving the empty rows in is free, and cropping them away saves no time at all. Any picture up to 256 rows tall gets this. One taller walks every row instead, and `rom.explain` names it, says why, and says what to change. Horizontal is not this verb; a row stretched across the screen would be its sibling. **Say how tall it usually is:** `estimate: { usually: 40 }` (or a range) — the same hint a `list`, a `pool` and a loop that stops early take, and like those it changes **nothing** about how the game runs. It is there for `rom.explain`, which otherwise has no size to go on: a height the game works out is exactly what perspective produces, so this is every column of a first-person view and therefore most of what such a game costs. Unlike a loop's, this ceiling is known — a column is clipped to the screen, or to the part of it an `inside` names — so unsaid it guesses HALF of that and says so, where a list guesses a quarter. Half rather than a quarter because heights past the ceiling do not spread out, they pile up at it: a wall you are close to is clipped, not drawn shorter. Saying it on a column whose height you wrote as a number is a friendly error, because that one is already known.
- `clear_screen color` — whole screen, one DMA.
- `inside x, y, w, h do … end` — **everything the block draws stays inside that part of the screen**, and what falls outside is CUT OFF rather than covered up: those pixels are never worked out. That is the difference worth having, because a game with a panel — a strip of world with numbers under it, a map beside it, a letterboxed cut scene — would otherwise draw the world over the whole screen and paint the panel on top, having paid for every pixel underneath it. In a first-person view, where a wall you stand close to is drawn taller than the screen, that is most of a near wall: measured over a floor of Wolfenstein with a 32-row bar, one row in twelve was drawn and then covered. It **clips, it does not move**: a pixel drawn at (10, 10) is at (10, 10) whatever area is in force, so an area goes round drawing that already works and only what was falling outside changes. `clear_screen` inside one clears the area rather than the screen, which is what you meant. Drawing after the block is untouched by it — that is where the panel goes. The edges are settled while you write the program (where a panel goes is part of how a screen is laid out, not something a game works out as it runs — a computed edge is a friendly error), and areas do not nest (a friendly error too). Calling a `func` that draws from inside an area is a friendly error too: the routine is built once, for wherever it's called from, so it can't carry one call site's clip along with it — put the `inside` block inside the routine itself instead. Bitmap screens; on `screen :tiled` the console composes the picture and a `layer` is how depth is said.
- `camera x, y` — move the visible window over the whole picture (`camera 0, 0` = as drawn). Nothing is redrawn — the picture stays put and the window moves — so it costs the same whatever is on screen. Where the window falls off the picture, the backdrop shows along that edge. Bitmap screens only (on `screen :tiled`, scroll a `background` instead).
- `camera_follows hero, across: world` (also `at: [120, 80]`, where the character stands in the world) — the follow-you camera almost every adventure game uses: the character stays where it is on screen and the world slides underneath. Call it once where the sprite is declared; wherever the sprite is standing then is where it stays (pair it with `sprite.center_on_screen` for the middle, or put it low for a platformer). **What it changes is more than a line saved:** without it a game whose world is bigger than the screen has to keep the character's world position in variables of its own, so the character is a pair of numbers rather than a sprite and none of the sprite verbs reach it. With it you write `hero.move :right` like any other sprite and the world moves instead — so facing, walk cycles and poses all work. What does *not* line up is anything that reads the character's position as a place in the WORLD (`blocked_by`, `overlaps?` against something placed in the map), because its position is where it sits on the screen. Needs `screen :tiled` (a bitmap picture *is* the screen — use `camera`) and a `game_loop`. Worked example: `examples/hero.rb`.
- `fade :black` / `fade :white, 50` / `fade :black, 0` — fade the whole screen toward black or white. The second argument is how far, 0 (as drawn) to 100 (nothing but that color); it defaults to 100. Nothing is redrawn — the picture is still there and comes back untouched — so it costs the same however much is on screen, and it works on **either** kind of screen (unlike `camera`). It sets the level where you call it; to fade over time, move a variable and pass it (`fade :black, level`). A full fade left un-lifted is a friendly warning. In a game with a **see-through layer** it borrows that layer's blend (they are one piece of the display) and hands it back when it lifts — see `transparency:` under Layers.
- `fade :black, 100, under: :ui` — **put the fade at a place in the stack** instead of over everything: it names a layer, and that layer and everything in front of it are left as they are while everything behind it fades. "Fade the game out to the game-over screen and keep the score showing" is one word, and it is why a stack is worth naming (see Layers). Needs `screen :tiled` and the layer has to be one you declared — a bitmap screen paints the whole picture into one place before the display sees it, so there is nothing left there to tell apart (friendly error). Something that named no layer is never on the kept side. **This is the one member of the fade family that is not always free:** where the line falls between the *sprites* — a HUD kept out of a fade that reaches the player — the framework holds the fade off each kept sprite one at a time, which costs a sprite slot and a table write per frame for each, and `explain` gives it a line of its own ("keeping 5 sprites out of the fade under :ui"). A line that falls between two *backgrounds*, or that keeps every sprite (`under: :actors` — fade the scenery, keep everything that moves), still costs nothing at all.
- `tint :red` / `tint :orange, 30` / `tint :red, 0` — tint the whole screen toward **any** color, which is the part `fade` cannot do: red for damage, blue for cold water, orange for a sunset. Same second argument as `fade` — how far, 0 (as drawn) to 100 (nothing but that color), defaulting to 100 — and the same bargain: nothing is redrawn, the picture is all still there, and it comes back untouched when the tint lifts. It sets the level where you call it, so tinting over time is a variable moved a little each frame (`tint :red, hurt`). A full tint left un-lifted is a friendly warning. Works on **every** screen, and a tiled one tints the scenery and the sprites together. **What it costs depends on the screen**, and that is the one thing to know: `screen :bitmap` is free, like `fade`. The other two draw every pixel through a shared color table, so the framework moves the table instead — a blend per color the game declared (never per pixel on screen), and **only on a frame where the tint actually changes**, so holding one still, or holding it at 0, costs a single check. `explain` names and prices it (`tint — moving 34 colors, on a frame where it changes`). A tint and a fade are one effect on the display, so the last one you set is the one in force.
- `fade_out` / `fade_in` / `flash_screen` — the same fade walked over time, which is what a scene change and a hit flash both are. `fade_out` (`:black` by default, or `:white`; `frames:` / `duration:` in seconds, half a second by default) darkens the screen to nothing over that many frames; `fade_in` brings it back, and with **no arguments at all** it returns in the same color at the same speed, so a scene change is two words and no bookkeeping. `flash_screen` (`:white` by default) is the same thing in a hurry — full on the first frame, then falling back over a few — for a hit, a score, a life lost; pair it with `shake_screen`. Call each once at the moment it happens; the framework walks the level every frame from there, and stops working entirely once the screen settles. **Any color works** — `flash_screen :red` for damage is the one a game reaches for most, and `fade_out :red` is a redout for a death. Black and white are a brightness change (`fade` underneath); every other color is mixed in (`tint` underneath), so on a screen drawn through a color table a colored one costs what that many colors cost while it is moving, which `explain` prices. Nothing is redrawn either way, so it costs the same however much is on screen and works on **either** kind of screen. `fade_out` and `flash_screen` also take **`under:`** and place the whole game's fade in the stack the way `fade` does (`fade_out under: :ui` — dim the game, keep the HUD; `fade_in` then brings it back with nothing to repeat). A game has one screen fade and it sits in one place: two different layers is a friendly error, because the console has one set of blend registers and two fades at two depths cannot both be in force. A **colored** fade cannot be placed at all (the console can hide only a brightness change from what sits in front of it), so a game that says both is a friendly error whichever order it says them in. Two friendly warnings: a `fade_out` with no `fade_in` anywhere leaves the game running behind a flat screen, and a fade with no `game_loop` has no frames to run on. Worked examples: `examples/pong.rb` (`flash_screen :red` when the cpu scores), `examples/breakout.rb` (a red flash on losing a life, a fade between scenes) and `examples/shmup.rb` (`fade_out under: :ui` — the field and the ships in it go dark on the way to the game-over screen and the score stays readable).
- `fade_level` → a `Value`: how far the screen is faded right now, 0 (as drawn) to 100 (nothing but the color). This is what makes a **scene change** writable, because fading out leaves the screen dark on purpose — so whatever you draw next is invisible until something lifts it, and the switch has to wait for the fade to arrive: `(fade_level == 100).then { state.set GAME_OVER; fade_in }`. Swap screens while nobody can see it and the player sees one smooth dip to black and back. A value rather than a yes-or-no, so half way through is a place you can act too.
- `pulse sprite, to: 1.3` (also `from:`, and `over:` in seconds — one full round trip, 2.0 by default) — a sprite that breathes: it grows to that size, shrinks back, and keeps doing it. A collectable that begs to be picked up, a boss winding up, the selected item on a menu. Call it once where the sprite is declared; the framework runs the rhythm every frame from there, and calling it again on the same sprite replaces the rhythm rather than adding a second one. Tiled sprites only (it is built on `sprite.scale`), and it needs a `game_loop` — a friendly warning otherwise. Worked example: `examples/bird.rb`, where the bird drifts nearer and further.
- `shake_screen intensity: 3, frames: 8` (or `duration: 0.2` for seconds) — shake the screen on impact. Call it once at the moment of the hit; the framework jitters the camera every frame from there and puts the picture back exactly where it was. Calling it again mid-shake restarts it. Needs a `game_loop` (that is what gives it a frame to run on).
- `grid :name, cols:, rows:, cell:, over:` → a `Grid`: `set_cell cx, cy, color` / `clear_cell cx, cy` (cell coords; `over:` is the background).

## Images & sprites

- `image :name, "." => :transparent, "#" => :red do <<~ART … ART end` — ASCII art; or `image :name, width:, height:, data:` / `from: "file.png"` (file paths resolve next to your script).
- `blit :name, x, y` — draw an image at a runtime position (clips at edges). **On the tear-free screen** (`screen :bitmap, tear_free: true`) a solid picture draws too, with two rules that come from how that screen holds its pixels: it must start on an **even column** and be an **even number of pixels wide**. That screen takes two pixels at a time and will not take one, so a picture that starts or ends halfway through a pair cannot be copied in — the same rule `fill_rect` already lives by. Both are friendly build errors naming the number, and a column the game works out is fine as long as it can be *proved* even (`col * 2`), because a column nothing can prove is refused rather than drawn in the wrong place. A **see-through** picture there is a friendly error too (a solid one only, for now). It costs less than the same picture in direct colour — half as many units through the copying engine — and a tall picture costs more than a wide one of the same area, because every row is a copy of its own.
- `sprite :name, at: [x, y]` → a sprite drawn each frame leaving no trail; the screen mode picks the kind. On `screen :bitmap` it's a software `Sprite` (save-under): `facing: {left: :img_l, …}` poses, `shown: false`, `hitbox:` (collision box — `:full` / an inset number / `[x,y,w,h]`; default is per-pixel collision, gated by the visible-pixel box), handle `x`/`y` (Values), `move(:left, by:)` / `move(dx, dy)`, `move_to`, `clamp_to_screen` (alias `stay_on_screen` — pin it fully on screen using its own size, no coordinate literals), `center_on_screen` (its sibling — put it in the middle, worked out the same way), `face`, `hide`, `show`, `overlaps?`, plus the screen-edge tests below. On `screen :tiled` it's a hardware (OAM) `HardwareSprite`, composited by the console: `x`/`y`/`move`/`move_to`/`clamp_to_screen`/`center_on_screen`/`hide`/`show`/`face(:left)`/`face_angle`/`turn`/`angle`/`overlaps?` handle plus `facing:` poses (the console swaps which uploaded picture it draws), and several stack in a stable order (later-declared in front, unless a `layer` says otherwise — see Layers). Size must be an 8×8-tile multiple.
  - **Flipbook animation:** `sprite :name, at:, frames: [:f1, :f2, …], rate: N` (instead of `facing:`) cycles the same-size frames — one every N game-frames, timer hidden and managed — on either screen; composes with `move` (animate while moving). `facing:` and `frames:` are mutually exclusive (both drive the pose).
  - **Directional animation:** give `facing:` a **list of frames per direction** — `facing: { left: [:walk_l1, :walk_l2], right: [:walk_r1, :walk_r2], … }, rate: N` — for a per-direction animation: the sprite runs that direction's cycle while it faces that way, so a character walks with its own cycle each way, or Pac chomps whichever way he moves (`examples/pacman.rb`). Every direction needs the same number of frames (two or more). The framework composes the facing and the frame into one pose for you (`face`/auto-facing `move` pick the direction, the hidden timer runs the frame). Works on both screen kinds.
  - **Import frames from a sprite sheet:** `sprite :name, at:, frames_from: "walk.png", tile: 16, rate: N, transparent: true` — slice one image file into equal-size frames (`tile:` is the frame size, a number or `[w,h]`) and cycle them; nothing to name or number. `transparent: true` honors a cut-out background. Path resolves next to your script. Mutually exclusive with `frames:`/`facing:`.
  - **Import directional poses from a sheet:** `sprite :name, at:, facing_from: "walk.png", tile: 16, dirs: [:down, :left, :right, :up], rate: N, transparent: true` — slice a four-way character's art from one file (the `facing:` counterpart to `frames_from:`). The sheet is a grid: each **row** is a direction (in `dirs:` order, top to bottom) and the **columns** of that row are its frames. One column = a still pose per direction (plain facing:, no `rate:` needed); several columns = a per-direction animation (feeds the directional-animation form above). `tile:` is the cell size, `transparent: true` honors a cut-out, path resolves next to your script. Mutually exclusive with `facing:`/`frames:`/`frames_from:`.
  - **Change size (tiled sprites):** `sprite.scale(1.5)` draws a `screen :tiled` sprite bigger or smaller about its own center — `1.0` is the size it was drawn at, `2.0` twice as big, `0.5` half. A boss that swells, an item that pops when you collect it, an enemy that shrinks into the distance. With no argument, `sprite.scale` hands back the size as a `Value` you can read and ease (`coin.scale.approach 1.0, 0.05`), so growing over time is the expression DSL and nothing new; the size may be a whole number, a fraction, or something the game works out. It rides in the same hardware as `face_angle`, so a sprite can turn **and** resize at once for the price of either, and twice the drawn size is the ceiling (past that the picture runs out of the box the console gives it). It is the dearest thing a sprite does — drawing at a size means dividing by it, once a frame, which the framework does for you and `explain` prices as `N resizing`. On `screen :bitmap` resizing is a friendly error (draw the sizes you need as separate `image`s), and a size of 0 or less is a friendly error wherever you write it.
  - **Turn to any angle (tiled sprites):** `sprite.face_angle(degrees)` points a `screen :tiled` sprite at an exact heading — degrees clockwise from upright, pivoting on its own center — and `sprite.turn(degrees)` turns it by that much from where it points now (positive clockwise, negative counter-clockwise). Both wrap; `sprite.angle` reads the heading (0..359) as a `Value`. This is real rotation to any angle (the console's sprite rotate/scale), not the fixed-pose swap `face`/`facing:` do — a ship that points where it aims, a bird that tilts to climb (`examples/bird.rb`). `degrees` may be an Integer or a `Value`. Up to 32 sprites can turn at once (a friendly error past that); on `screen :bitmap` turning is a friendly error (a blitted sprite can't rotate — use `facing:` poses for a few fixed directions).
  - **Import from Aseprite (named animations):** `sprite :name, at:, from_aseprite: "bird.aseprite"` — import a sprite the way an artist authored it in Aseprite. Point it **straight at the native `.aseprite` file** (no export step) — the framework reads the binary directly: it composites the layers, decompresses the frames, resolves the palette, and reads each frame's duration and each **named animation** (frameTag). Or pass a `.json` export instead (both the array and hash layouts), where it slices the frames from the PNG named in the JSON's `meta.image` beside it. Either way it exposes each tag as an animation you play on demand: `hero.play(:walk)` / `hero.play(:attack)` (a `Sprite`/`HardwareSprite` method). The current animation loops until you play another; the first tag plays at boot (a file with no tags is one looping animation). The frame speed comes from the frames' durations. Path resolves next to your script. Mutually exclusive with the other pose sources.
- `rgb r, g, b` (0–31) / `rgb8 r, g, b` (0–255) / `color value` — make a 15-bit color.

## Tiled backgrounds

- `tiles :name, "#" => :brick, "." => :floor` — a tileset: map each character to a tile `image` (all same size). Add `solid: ["#"]` to mark wall tiles a sprite can't move through (see `blocked_by` under sprites). **Import from a tile sheet** instead of naming images: `tiles :name, from: "tiles.png", tile: 8, "#" => 0, "." => 1` — each character points at a cell (a number counting left-to-right, or `[col,row]`); `tile:` is the tile size, `transparent: true` honors cut-outs, path resolves next to your script. **Import the WHOLE sheet as numbered tiles** (no characters) for a CSV map: `tiles :name, from: "world.png", tile: 8` — every cell becomes a tile numbered 1, 2, 3… left-to-right (the numbering a map editor exports); `solid:` then takes tile numbers (`solid: [1, 2]`).
- `background :name, tiles: :set, map: <<~MAP … MAP` → a `Background`; stamps a grid of tiles (`map` is rows of tileset characters — a string or array of row strings, a space = empty cell). **Or import the map from a file:** `background :name, tiles: :set, from: "level.csv"` reads a CSV tilemap exported from a map editor like Tiled — a grid of tile numbers, one row per line, `0` = empty cell (path resolves next to your script). Give `map:` or `from:`, not both. Drawn by the tile hardware in `screen :tiled`. **Scroll it:** `bg.scroll_by dx, dy` / `bg.scroll_to x, y` move the visible window over the map (in pixels; the map wraps at its edge) — call them anywhere in the frame, from a branch or deep in a scene; the framework applies the camera once a frame so scrolling can never tear. Up to 32×32 tiles (256×256, larger than the screen). Sprites compose over a scrolling background (the console draws them on top for free) — a hero centered while the world scrolls under it is a follow-cam (`examples/hero.rb`). **Stack layers:** declare more than one `background` (up to 4) and they compose — the first declared is the backmost (unless a `layer` says otherwise — see Layers), each later one in front, and a front layer's see-through tiles (empty cells, or `:transparent`/backdrop pixels) let the layer behind show; scroll a near and a far layer at different speeds for parallax (`examples/parallax.rb`).
- `bg.scroll_each_row { |row| offset }` — give every **row** of a background its own sideways offset, so the picture *bends* instead of moving as one flat rectangle. The block is handed the row (0 at the top of the screen, 159 at the bottom) and gives back how far across that row sits, on top of the background's own scroll — so a background can scroll and bend at once. Move a variable the block reads and the bend travels: rippling water, a heat haze, a reflection wobbling, a screen melting into a transition. Worked example: `examples/lake.rb`, where a sine table shifted a little each frame rolls a wave down a lake and the sun's reflection snakes. Declare it once where the background is declared — it keeps running from there, and calling it again replaces the bend. Rows bend sideways only. Tiled screens only (a bitmap screen has pixels you drew, not a layer to bend — a friendly error). **Your block runs once per row, in the gap between frames** — all 160 rows worked out before the picture is drawn, never while it is being drawn. That is what keeps a bend in step with everything else the frame moved (a sprite riding on the water shows the same frame the water does), and it is most of what the effect costs: about as much as running your block 160 times, whatever is in it. Write what you like there — a `table` read, arithmetic, a variable set, a `func` call. **It is not free**, and `explain` prices it. **How many layers bend decides the rest.** Up to three at once are fed to the display by its own copying engines, with the CPU untouched, so a parallax pair of rippling layers costs nothing beyond the two blocks; a **fourth** is one more than there are engines and then the game is interrupted on every one of the display's 228 lines to hand the rows over, which is several times the price of the blocks themselves. A game playing `sample`/`instrument` audio is fed from an engine too, and then there is one left, so one layer. `explain` names and prices whichever you got, and says why when it is the dear one.

- `bg.rotate degrees` / `bg.scale size` — turn or resize the WHOLE background as one piece, pivoting on the middle of the screen — the same trick a hardware sprite's `face_angle` / `scale` does, done to a background layer instead of one picture. `degrees` is clockwise from upright and wraps (370 is the same as 10); `size` is 1.0 at the size it was drawn, 2.0 twice as big, 0.5 half. `bg.angle` reads the heading back as a `Value`; `bg.scale` with no argument does the same for size, so easing it is the expression DSL (`bg.scale.approach 1.0, 0.05`) same as a sprite's. Needs `screen :rotozoom` (a friendly error names it otherwise) — this background's `scroll_by`/`scroll_to` become a friendly error in exchange, since panning this kind of layer is done by turning/resizing it, not by the plain scroll registers `screen :tiled` uses. Worked example: `examples/rotozoom_bg.rb`.

## Layers (a named place in the stack)

A game is drawn in layers — the scenery, the characters, the score on top — and without a name for them the only way to say what sits in front of what is the order the declarations happen to run in. That order is invisible, it lives in prose comments, and in a game split across files it depends on which file was required first.

- `layers :sky, :world, :actors, :ui` — declare the stack, **back to front**, one time. The order is global on purpose: "in front of" is a relation across the whole screen, so one line answers the question a reader of somebody else's game actually has. Naming a layer twice, or declaring the stack twice, is a friendly error.
- `layer :name do … end` — everything the block declares belongs to that layer. The block runs on the build, exactly like a `func` body, so **every verb works inside** and the parts-in-files pattern does too (`Enemies.new(self)`). What can take a layer is a `background`, a `sprite` (either screen kind — but see the bitmap note below), a `pool` with `image:`, and `draw_text`/`draw_number` on a tiled screen — the things the framework draws again for you every frame. Nesting one `layer` inside another, or naming a layer that isn't in `layers`, is a friendly error.
- `layer :water, transparency: 40 do … end` (also `transparency: 100 - mist` — **an amount the game works out**, for fog that thickens, water that gets murkier as you descend, a backdrop that dims in; write a variable or an expression where you would write a number) — **see through this layer to what is behind it**: water, glass, fog, a dimmed backdrop behind a menu. 0 is solid (the picture as drawn), 100 is invisible. What it means is what it looks like — whatever sits directly under the layer at a pixel shows through it, anything in **front** of it draws solid, and where the layer itself has a see-through tile what is behind shows plain — and that is also exactly what the console does, so there is no rule to learn. **It costs nothing**: the display blends as it draws, so a see-through layer costs the same as the same layer drawn solid, however much is on screen. (An amount the game works out keeps that bargain for the blending and adds one thing: the display has to be told the new amount before each frame, which is a single register write the framework puts at the frame boundary for you. `explain` says which of the two a picture got.) The property belongs to the layer, so it rides on the layer and there is no new verb; say it on the block, one time. Works for a layer of `background`s and a layer of `sprite`s alike (two different mechanisms in the console, and you never learn which one you got). **A game has ONE see-through layer** — a friendly error naming the one it already has, because a see-through layer sitting directly over another one is the one arrangement the two backends would draw differently. Needs `screen :tiled` — a bitmap screen paints its whole picture into one place before the display sees it, so there is nothing left behind a layer to see through (a friendly error). `transparency: 100` is a friendly warning: none of the layer shows, and the game still draws it (said only about a number you wrote — an amount the game works out passes through 100 whenever the fog clears, so nothing is said about one). **A fade takes the blend while it runs** — seeing through a layer and fading the screen are the display's one blend unit, so `fade`/`fade_out`/`flash_screen` leave the layer solid until the fade lifts, when it comes back untouched. That is what a fade out should look like (everything darkens together), it is measured on both backends rather than assumed, and it is a friendly warning at build time because neither verb mentions the other. A `tint` is a different mechanism on a tiled screen and does *not* disturb the layer, so `flash_screen :red` blends right through it. Worked examples: `examples/lake.rb`, where half-see-through jellyfish drift across the lake and the ripple keeps travelling through their bells, and `examples/hero.rb`, where mist declared in front of the hero thickens as you walk north (`transparency: 100 - mist`) and clears on the way back.
- **A layer holds things, not brushstrokes.** The instinct people arrive with is that a layer is a surface you draw on — clear this layer, put a pixel on this layer. Nothing on this console works that way, and it is not close: a bitmap screen has one framebuffer, a tiled screen's layers are grids of references to shared tiles rather than canvases of their own, and giving each layer its own pixels means blending two full screens in software every frame — over twice the time a frame has, and the memory besides. So `pixel`, `fill_rect`, `dma_fill_rect`, `draw_rect_at`, `blit`, `clear_screen` and bitmap `draw_text`/`draw_number` are a friendly error inside a `layer` block: they paint where you call them, and no ordering applied later can reach back and change where they landed. What you write instead is the retained-mode answer, which is what `sprite` already is: make a thing, and put the thing in the layer. `fade` and `camera` are a friendly error there too — they change the whole screen, so they cannot belong to one depth. An effect is **placed, not contained**: `fade :black, 100, under: :ui` says where in the stack it sits (see Drawing), which is a different thing from being one of the layer's things.
- **`draw_text` is the one verb whose nature changes with the screen** — layerable on `screen :tiled` (where the console draws each character for you every frame), a friendly error on `screen :bitmap` (where it paints into the framebuffer at the call). Same seam tiled text already has, where it must be declared once above the game loop or inside a scene; the error says which of the two you are in.
- **A scene is WHEN, a layer is WHERE IN THE STACK**, and they never need to know about each other. A HUD can be in `:ui` and in `:playing` — on top, and only while playing. Containment goes one way: `layer` blocks inside a `scene`. A `scene` inside a `layer` is a friendly error (a state holds things at many depths; a layer is one depth). A **routine** — a `func` or a `once_a_frame` — may sit inside a layer, but **declaring a `sprite` or a `background` inside one is a friendly error**: a routine's body is built later, when the layer is not in force, so it would quietly sit at no depth at all. The error names what you wrote and the way round that works (put the `layer` block inside the func; move a declaration out of a per-frame body, where it runs once anyway). What is refused is the *declaration*, not the routine — so a `func` that only moves the sprite it sits beside is fine, and so is every effect verb that declares a per-frame routine of its own (`pulse`, `camera_follows`, `fade_out`, `shake_screen`): a game says `pulse coin` on the line after it declares the coin.
- **A `background` can sit in FRONT of a sprite** — the fence a hero walks behind, grass that passes over their feet — by declaring its layer in front of theirs. That is the one arrangement a picture cannot fall into by accident, and it needs the console's own stacking, so it comes with two rules. **The console keeps four levels of depth**, and a level is spent only by a `background` (the sprites in front of one share its level), so you can name as many layers as you like and a game with one background and five sprite layers uses one level. Asking for more depth than that is a friendly build error that names the layer which cost the level and shows your stack — `rom.explain` lists the same thing for a build that fits. And once a background is in front of a sprite, **every** background and sprite must name a layer: the usual arrangement (scenery behind, everything that moves in front) is gone, so there is no longer a place to leave something that named none. That too is a friendly error.
- **Only what named a layer is moved.** While the usual arrangement holds, a thing that named no layer keeps the exact place it had — so wrapping one part of a game in a layer can never pick up and move a part that says nothing about layers, which is what makes it safe to adopt a bit at a time. Two things in the same layer keep the order they were declared in.
- Layers are **opt-in**: a game that declares none keeps its ordering exactly (declaration order, and a HUD drawn last). What a layer becomes — a background layer, a sprite priority, the order things are painted — is the framework's business; you never write a BG index or a priority.
- **A stack decides the picture on both screens — with one exception, and it is about `background`.** Sprites follow their layer on either screen: on `screen :bitmap` the framework repaints them every frame, so it repaints them back to front and a sprite in a front layer covers one behind it, exactly as on `screen :tiled`. Worked example: `examples/sprite_mover.rb`, where the heart passes in front of one post and behind another. A **`background` on `screen :bitmap`** is the exception, and permanently: it stamps its tiles into the one picture where you declare it, and nothing draws it again, so no layer can move it afterwards. Where a stack asks a bitmap screen for a background order it cannot give — two backgrounds the stack reverses, or a background put in front of a sprite — that is a friendly build **warning** naming both orders, what you asked for and what the screen will show. On `screen :tiled` there is no exception at all.
- **`rom.explain` prices the stack** — each layer with what it costs a frame beside what it holds, then the share of the frame that comes to. It answers "which layer is expensive", which is a different question from the cost tree's "where in my code" (a sprite is in a layer *and* in a scene, so neither nests in the other). A layer that costs nothing shows no number at all, and that is the tiled screen's whole bargain: a background is drawn by the display for free once it is up, however big it is — only what the framework rewrites each frame charges. The usual surprise is that a **HUD is the most expensive layer in the game**, because tiled text is one hardware sprite per character. The share line matters as much as the numbers: most of a frame sits at no depth (logic, sound, drawing you wrote by hand), so `piano` spends ~0.4 of its ~37 on the stack while `lake` spends ~24.0 of ~24.2 — its one bending background *is* the frame. A see-through layer gets a line of its own there, saying which layer it is and that the display blends it for nothing — and, in a game that also fades, a second line saying the fade takes that blend while it runs.
- **A layer that holds nothing** — a name in `layers` no `layer` block ever puts anything in — is a friendly warning too. It is harmless to the picture, and it is almost always a name spelled two ways or a leftover from an edit, which quietly stops the stack meaning what it says. A layer named only by an effect (`fade … under: :cut`) counts as used: it is deciding where the line falls.

## Collision

- `box x, y, w, h` → a `Box` (a rectangle to test; draws nothing). Coords may be `:var`/`Value`/`Integer`.
- **Screen-edge tests** (on anything with bounds — a `Sprite` or a `Box`): `off_screen?` (fully past any edge), and edge-specific `off_left?` / `off_right?` / `above_top?` / `below_bottom?` for when behavior depends on *which* edge (a bullet dies off the top, an enemy respawns off the bottom) — each returns a `Condition` for `.then`, read from the thing's own bounds and the 240×160 screen, so no coordinate literals. Pair with `sprite.clamp_to_screen` (keep it fully on screen using its own size). "Fully past" means nothing of it still shows.
- `a.overlaps?(b)` → a `Condition`; `.then { }` on it. Works on any two things with bounds — a `Box`, or a `Sprite` (which provides its own bounds), so `hero.overlaps?(coin)` needs no box. **Sprite-vs-sprite is per-pixel by default** (`sprite … hitbox:` picks the box): a hit needs the two sprites' *drawn* pixels to actually meet, any shape, following whichever animation frame is showing — a cheap box test gates it so far-apart pairs stay cheap. A `Box` (and a sprite given an explicit `hitbox:`) collides on its plain rectangle instead, so sprite-vs-box is a box test. Set a sprite's box with `hitbox:` (see the sprite verb): `:full` (whole image), an inset number (shrink each side), or `[x, y, w, h]`; the default box (used as the per-pixel gate, or as the collision box when you opt out) hugs the visible pixels.
- **Tile collision (tiled mode):** mark walls with `tiles ..., solid: ["#"]`, then `sprite.blocked_by(background)` — its `move` is checked automatically (stops at walls, slides along them). `sprite.can_move?(:left, by: n)` → a `Condition` for manual control; raw `move_to`/`x`/`y` are never checked (escape hatch).

## Text & numbers

- `draw_text "HELLO", x, y, color, font: :tiny` — fixed-origin text (`font:` picks a registered font; default `:default`).
- `draw_text "SOUND", x, y, [:gray, :white], showing: picked == 1` — **two colours, and a test saying which**: the second while it holds, the first when it does not. A label that highlights, a HUD figure that turns red when the health is low (`showing: hp < 20`). Written the long way — the same words drawn twice, under a test and its opposite — it says the same thing and paints the same pixels; the difference is on a **tiled** screen, where the console draws each character as its own little sprite out of a table of 128. Two draws are two sprites for every character with one of them always hidden; this is **one sprite that changes colour**, because the pair becomes two poses on it and the console is already swapping which picture a sprite shows for free. That halving is what lets an eight-row `menu` fit. Exactly two colours: a test is 0 or 1 and a pair has a 0 and a 1, so the choice can never land outside it. Three is a friendly error saying to draw the text under a test for each, and a pair without `showing:` (or `showing:` with one colour) is a friendly error too.
- `draw_number :var, x, y, color, digits: 3, font: :tiny` — a live number (right-aligned, no leading zeros).
- **Say where it goes instead of counting pixels**: where the left edge goes, both verbs also take `:left`, `:center` or `:right` — `draw_text "PONG", :center, 40, :white`. A number you write still means that column, and is still right when you actually want a column; what a number cannot be is CENTRED, because a proportional font has no per-character width to multiply by and the only thing that knows how wide "PRESS START" comes out is the font. Ask it and a label can be reworded with no stale number left behind. `within:` narrows what it is placed against — `within: 0..119` centres a caption in the left half, `:right, within: 0...120` pushes a label up against the middle from its left — and with no `within:` it is placed against the part of the screen an `inside` block is holding drawing to, else the whole screen, so a heading over a panel centres on the panel. A `draw_number` places its FIELD rather than the number in it, which is what stops a centred score jittering sideways as it counts up. Giving both a column and a `within:`, or a name the verb does not know, is a friendly error. Worked examples: `examples/pong.rb` (each score pushed against the net from its own half), `examples/jukebox.rb` (a menu column centred on its widest song name) and `examples/shmup/hud.rb` (a HUD flush against both edges).
- `text_width "SCORE"` / `text_height` (both take `font:`) — how wide a string comes out and how tall a line is, in pixels. Useful on its own for anything sized to fit words: a box behind a title, a menu window as wide as its longest row, the figures hung one gap off the end of their label. It reports what **this screen** will really draw, which is not always the same number — a bitmap screen advances by each glyph's own width, where a tiled screen gives every character its own little sprite on a fixed grid so a HUD's columns line up.
- **On `screen :tiled`** (no framebuffer) both draw each character as a little hardware-sprite glyph the console composites over the game. Same verbs/args, one rule: **declare them once — above `game_loop`, or inside a `scene`** (where they belong to that scene and show only while it's active), like a `sprite` — they're redrawn for you every frame and a live `draw_number` follows its variable and updates itself (so pass a variable, not a one-off expression). Declaring loose inside `game_loop` is a friendly build error. **A test around the declaration says when it shows**: `(blink == 1).then { draw_text "PRESS START", 76, 100, :gray }` is a blinking prompt — the condition rides onto the glyphs, so they are on screen exactly while it holds, and it is read again every frame like the rest of the HUD. That is one declaration, not a per-frame draw, so it is allowed above `game_loop` and inside a `scene` the same as a plain one (a `.else` shows its text while the condition is false). Glyphs use one 8×8 sprite each, so the built-in `:default`/`:tiny` fonts fit; a HUD costs a few of the 128 sprites.
- `font :name do glyph "A", <<~ART … ART end` — define a font from glyph art (sibling of `image`); built-ins `:default` (5×7) and `:tiny` (3×5 digits). **Or hand it pictures of the letters** — `font :name, glyphs: { "A" => rows_of_pixels, … }, blank: 0` — for a font that already exists, sliced out of an image or decoded from a game's own data, because nobody is going to retype an alphabet as hashes and dots. A glyph is rows of pixel values and a pixel that is not `blank:` is lit, so which ink the picture used never matters; each glyph keeps its **own width**, so an alphabet drawn proportionally stays proportional. Give a block or `glyphs:`, not both. On `screen :tiled` the console draws each character as one 8×8 sprite, so an imported alphabet can be too big for it — a friendly error names the widest character.

## Variables & math

- `var :name, init` → a `Value` handle; the initial value is applied **once at boot**, so declaring a variable inside a scene or loop still initializes it a single time. `set :name, value` re-assigns at that point (every time that code runs).
- `save_var :name, default` → a `Value` handle for a variable that **survives power-off** (a high score, an unlock, a setting). Used exactly like `var`, but its value is kept in the cartridge's save memory: it comes back at power-on with the value it had last time (or `default` the first time the game is ever run), and every change is saved for you automatically — no separate save step. `default` is a whole number. The framework picks and drives the save backend and emits the save-type signature emulators/flashcarts need; no SRAM addresses at the surface.
- `add :name, operand` (alias `add_var`) / `sub :name, operand` (alias `sub_var`).
- `copy :dest, :src`, `negate :name` (alias `flip`), `abs :name`, `negate_abs :name`.
- `clamp :name, min, max`, `approach :name, target, step` (move toward, capped). Both `clamp`'s bounds and `approach`'s step can be fixed numbers **or** things the game works out as it runs (`x.clamp 0, limit`, `level.approach 100, speed`) — a limit that depends on the level, an easing whose speed changes. A computed `approach` step is read as a distance, so a negative one still moves toward the target and `0` holds still. Fixed values cost exactly what they always did; only a computed one costs more.
- Introspection: `variables`, `var_address :name`.
- **Expression DSL** (on a `Value`): `+ - * / %` and unary `-x` (the value the other way round, leaving `x` alone — `.flip` is the same idea as a *mutation*), comparisons `> < >= <= == !=` → a `Condition`; mutate with `.set/.add/.sub/.clamp/.flip/.approach`. Compose conditions with `&` (both) / `|` (either); branch with `.then { } .else { }`. A **comparison costs about twice what `+` or `-` does**, and there is nothing to write differently — adding two numbers is the answer, where comparing them leaves the console to turn its flags into a yes or a no. Worth knowing only where a condition sits in the hottest loop of a frame; anywhere else it is not the thing to look at.
- **Say how often a branch runs:** `.then(estimate: { usually: 0 }) { … }` — the same word a `list`, a `pool` and a `repeat` take, and it matters here for the same reason. A test the game works out is one nothing at build time can see through, so **unsaid, the body is counted on EVERY frame**, and that is often badly wrong: a death animation, a screen that repaints only when a number changed, a routine answering a rare event — each reads as ordinary every-frame work and sends you optimising the wrong thing. `usually:` is how many frames in every `in:` run the body, and `in:` left out means one frame — so `usually: 0` is "not on a normal frame" and `usually: 1, in: 60` is "about once a second". The **worst frame is unchanged**: a frame where the body does run pays for it whole, however rare you said it was. Unsaid keeps counting 1 on purpose, which is the opposite default from a loop's — an uncounted loop was charged *nothing* and had to be made loud, where an uncounted condition is merely pessimistic. Not quite free of consequence, and the one thing to know: what the framework keeps in the console's quick memory is chosen by what a frame costs, so telling it a body is rare can hand that memory to something that really does run every frame. That is the point rather than a side effect — it is a speed difference and never a difference in what the game does.
- **`%` wraps a value onto a range** — Ruby's meaning, so `-1 % 64` is 63. That's what you want for an angle that stepped below zero (it comes back near a full turn) or a map coordinate off the left edge (it comes back against the right one). `/` truncates toward zero (`-7 / 4` is `-1`), so `/` and `%` don't decompose on negatives — `%` follows Ruby because you know Ruby.
- **Dividing costs what its divisor makes it cost**, and there is nothing to write differently — the build works out which case you are in. A number **you wrote in the program** never calls the console's divide routine: a power of two (2, 64, 256) is a shift and costs about three quarters of a plain step, and any other fixed number (10, 60, 100) is turned into a multiply at build time and costs about twice a plain step. A divisor **the game works out** (`x / d`, where `d` is a variable) is the dear one, at about five times a plain step, and it is the only one whose cost depends on the numbers — it works the answer out a bit at a time, so a big answer costs about two and a third times a small one. `%` follows its `/`. (Throughout, **a plain step** is one ordinary statement — `x.add 1`.) `explain` names and prices the three apart — a `/ d` reads as `divide (worked out)` and a `/ 100` as `divide (fixed number)`, each with how many times a frame does it — so a hot `/ d` shows up as a real cost and a `/ 100` no longer does. (A power of two is a shift and gets no line of its own.)
- **Numbers with a fraction** — a variable holds whole numbers, so a game that needs halves and quarters (speeds, angles, anything smooth) has to keep them another way. **Write a Float and it is handled for you**: `var :px, 3.5` declares a variable that holds a fraction, `table :sin, (0...512).map { |a| Math.sin(...) }` a table of them. The scale is declared once, there and nowhere else — every handle for that variable carries it, and arithmetic carries it along.
  - `+ - < >` and friends: a number **written in your program** is converted for you (`speed + 1` means one faster). Mixing a fraction with a whole number **the game works out** is a friendly build error naming your line — say which you meant with `.to_f` or `.to_i`.
  - `*`: times a plain **count** is ordinary multiplication (`speed * 2` is twice as fast). Times another **fraction** is the one that would overflow — two multiplied-up numbers come out multiplied up twice, far too big for a variable (1.5 × 1.5 needs 9,663,676,416 on the way) — so the framework works that product out at full width automatically. You never have to spot which of your multiplies is the dangerous one, which was the whole problem.
  - `/`: by a plain count is ordinary division. By another **fraction** it is the mirror of the multiply above — two numbers multiplied up by the same amount would divide that amount straight back out, so the framework widens the numerator first and the answer keeps its fraction (`3.0 / 2.0` is `1.5`, not `1`). A plain number can stand on the left too: `WALL_HEIGHT / distance` is the perspective divide, and `examples/raycaster.rb` uses exactly that for its wall heights. **It is the dearest arithmetic there is** — about eighteen times a plain step, where every other divide is three quarters to five — because it walks the whole width of the answer; `explain` names it `divide (fraction)` and says how many times a frame does it, and a hot one is worth precomputing into a `table` instead. An answer too big to hold is held at the end of the range rather than wrapped, so dividing by something very near zero gives the biggest number there is and not a negative one. **That protection does not survive the next step, and this is worth knowing before you need it:** the answer is now AT the end of the range, so adding anything to it wraps — `(WALL_HEIGHT / distance + 0.5).to_i`, the ordinary way to round a perspective divide to the nearest pixel, comes back very NEGATIVE once the divide has saturated. It bit exactly where you would expect: a first-person view, a player standing a hair from a wall, and the wall vanishing because a negative height draws nothing. **Give the divisor a floor** (`distance.clamp(NEAREST, FAR)`) rather than the answer a ceiling — a floor on the distance costs one clamp and changes nothing you can see, where a ceiling on the height holds a near wall short across the whole last half-cell, which a player can see plainly.
  - `.to_i` — drop the fraction (rounds down), for a pixel coordinate or a table index. **One instruction**, not the divide it replaces. `.to_f` — give a whole number a fraction so it can meet one.
  - Worked example: `examples/raycaster.rb`, where positions, ray steps and distances all hold fractions and the word "fixed point" never appears.

## Control flow

- `game_loop do … end` — the per-frame loop. It runs its body once per frame: the framework waits for the screen and repaints your sprites and HUD at the top of every pass, so you never write a frame sync. Build with `frame_sync: :manual` (on `RubyGBA.game` / `RubyGBA.build`) to place `wait_vblank` yourself.
- `repeat(n) { |i| … }` — runtime-counted loop (n may be a `Value`/list length). **A loop given `stop_when:` leaves as soon as that holds**, which makes `n` a ceiling rather than a number of passes — so `estimate: { usually: N }` says how many it normally makes, exactly as a `list` and a `pool` do, and changes nothing about how the game runs. It matters more here than for either of those, because a ceiling is picked so it can never be reached AND this kind of loop usually sits inside another one, so counting the ceiling multiplies: a ray that gives up after 48 crossings meets a wall in about 4, and 80 rays make that the whole frame. Unsaid, the estimate guesses a quarter of the ceiling and says so; the worst case counts every pass either way. **A loop counted by something the game WORKS OUT — `repeat(n)` where `n` is a variable — is the one shape with no number anywhere in the program**, neither how many passes it makes nor the most it could, so unsaid it is charged NOTHING and the report says `x? (unbounded)` rather than implying cheap. That one takes `estimate: { usually: N, most: M }`: `usually:` is what a normal frame does and `most:` the ceiling for the worst-case figure, and `most:` is refused anywhere else because a written count or a `stop_when:` ceiling already says it. This is the hint most worth writing, because the loop that walks "everything I decided to draw this frame" is exactly this shape and reads as free without it. Counting, testing and jumping back costs something before the body does anything, so a long loop over a cheap body is mostly loop — and **what it costs depends on where the count is kept**, which the build decides and you do not write. Kept in the console's own registers it is about one and a half plain steps a pass; kept in memory it is not quite twice that. The build uses registers whenever the body leaves them free, and a body that **calls a routine, holds another loop, runs a scene, or drops to raw instructions** needs them for that instead. `explain` names the shape each loop got — "the loop itself (in registers)" or "(through memory — the body calls :bump)", with how many passes a frame — so moving a call out of a hot loop is a change you can see the price of.
- `every(n) { … }` / `every(0.5, :seconds) { … }` — run on a beat. `after(n) { … }` — once, n frames in.
- `once_a_frame { … }` — run a body **once a frame**, wherever the game's own code goes that frame, and **once for each frame that really passed**. It differs from the same code written in `game_loop` in two ways. It always runs — a branch or a scene switch can step over a loop body, and this runs anyway, in the gap between frames — which makes it the home for an effect you set off once and something has to carry along afterwards (`shake_screen` is built on it, and it's the seam an effect pack uses). **And it keeps real time.** A pass of the game loop is one frame on a game that fits and two on a game that doesn't, so a body run once per *pass* silently slows down when the game does: a half-second fade would take a second and a half. This one is run again for each frame that really passed, so it takes as long as it says whatever the game is doing (a very slow pass is capped, so a game is never asked to catch up half a second inside one already-late frame). That makes it where anything that must keep time goes. **Movement written straight in a `game_loop` moves a step per pass**, so a game too heavy for a frame runs in slow motion — smoothly and uniformly, which is safe and is the default; move it in here and the world keeps real time instead (`once_a_frame { hero.walk }` with the drawing left in the loop). **What goes in here is what MOVES, not what a press does**: a button read on its edge (`pressed`) has to be read once per press, so leave the trigger in the loop — read here, one pull of it would fire a bullet for every frame a late pass answered for. `explain` prices it as a frame's worth of it, which is what a game that fits runs, and its heaviest frame at the cap, which is what a late pass replays. Optional name (`once_a_frame(:name) { … }`) if something has to find the routine later.
- `timer :name, per_second: N` → a `Timer`: a free-running hardware counter that ticks N times a second, independent of the frame loop. `t.ticks` → a `Value` (how many ticks so far, wraps at 65536); `t.on_tick { … }` runs a body on every tick, precisely, off the timer's interrupt (a low-level building block higher-level verbs sit on — a game rarely writes it directly); `t.stop` freezes it. For frame-paced gameplay timing prefer `every`/`after`; reach for `timer` for precise/free-running timing (and it's the clock sampled audio will ride on). **A fast `on_tick` is not free:** the rate decides the cost, and it's written on the `timer` rather than near the handler — at `per_second: 4000` the body runs 67 times a frame, which is ~5 of a frame's 228 scanlines with a one-line body, and about 0.07 per tick before the body does anything. `explain` names each timer and prices the interrupt and the body apart. **And a rate can be more than the console will deliver:** a tick that arrives while the last one is still being answered is lost — there is no queue — so a handler too long to finish between two ticks answers every second tick, or every third, and the game silently runs at a fraction of the rate you asked for. That is a friendly build warning naming the rate that does fit, and `explain` prices the ticks that really arrive.
- Low-level (asm-tier): `if_eq` / `if_ne` / `if_gt` / `if_lt` / `if_ge` / `if_le` (`:var, operand`) with aliases `if_gte` / `if_lte`. Prefer the `(a > b).then { }` expression form.

## Scenes & funcs

- `func(:name) { … }` + `call :name` — a subroutine. `func(:name, fast: true) { … }` keeps it in the console's quick memory, where code runs about **two and a third times faster** — you rarely need to say so, because the framework works out which routines a frame spends its time in (the game loop's own body first of all) and puts them there for you. Say `fast: true` to insist on one it didn't pick, or `fast: false` to keep one out. `rom.explain` lists what it chose, **how big each one is**, how much of the 32K is left, and — the part worth reading — **what did NOT fit**, with what it wanted and what was left. A routine the frame spends real time in that just missed is where a game lost that whole factor, and nothing else can tell you afterwards. To stop it choosing at all, build with `RubyGBA.build(..., fast_code: false)` — a routine you marked `fast: true` still goes. It can never overrun the memory on its own: the choice is made afresh each build from what the game actually uses, so a game that grows gets a smaller share, never a broken build. **`func` is about SIZE as much as speed**, and this is the one thing about the framework you cannot work out by reading your own program: a plain Ruby method called from inside a build block runs at every call and records its work THERE, so a helper written once and called from eight places is emitted eight times. A `func` is emitted once and called eight times. Measured in a real game, two such helpers made one routine 27.9K — too big to keep in the quick memory, which cost the whole factor; as `func`s they were emitted once, both were kept, and the code they held ran at the quick memory's speed instead of the cartridge's. When a routine misses its place, `explain` names its most repeated line and says whether several lines repeat together, which is what a helper looks like from the outside.
- `scene(:name) { … }` — a named game state (a routine run once per frame while active). Hold the current state in a variable (`var :state, 0`); `case_var(:state) do when_val 0, :title; when_val 1, :playing; … end` runs exactly one scene per frame; `set :state, N` transitions (e.g. `pressed(:start).then { set :state, PLAYING }`).
- **A scene owns what it draws.** A `sprite`, `draw_text`, or `draw_number` declared **inside** a scene belongs to that scene — it's on screen only while that scene is the active state. Belonging to a scene *is* the visibility, so switching state switches the whole screen (a game-over screen hides the field and shows its own banner) with **no per-draw visibility flag**. Sprites/HUD declared at the top level (outside any scene) are always shown — a persistent HUD. Worked example: `examples/shmup.rb` (a PLAYING scene and a GAME OVER screen).
- **A scene can be a class in its own file.** Like the multi-file parts pattern, a screen can be a plain object: construct it *inside* its `scene` block (so its sprites/HUD are tagged to that scene) and call its per-frame `update` — `scene(:playing) { s = PlayingScreen.new(self); s.update }`.
- **Per-scene display mode.** A scene may declare its own `screen` at the top of its block (a direct-color bitmap title, a double-buffered play scene, a tiled game) and the framework switches modes on the transition — a scene's `sprite`/`draw_text`/`draw_number` pick software vs hardware from *its own* mode, and crossing bitmap↔tiled flips which display system presents so the old screen doesn't bleed through. This works on both backends: the reference interpreter models it (including a bitmap title handing off to a tiled game), and the GBA backend reconfigures the whole display live on the crossing (the mode register plus the VRAM/OAM layout — tiled assets are re-uploaded on entry since a bitmap scene reuses the same video memory). Today a mode-switched tiled scene shows hardware **sprites** on a clean backdrop; a tiled **background** owned by a mode-switched scene is a follow-on. A single-display-system ROM (all bitmap, or all tiled) is unaffected. `examples/` — see the per-scene-mode and scene-display-mode tests.
- `dump_func :name` — disassemble a func from the built ROM (debug).

## Input

- `held(:left)` — 1 while down; `pressed(:start)` — 1 on the press edge only. Use with `.then { }`.
- Low-level: `if_held(:a) { }` / `if_pressed(:a) { }`. Buttons: `a b select start right left up down r l`.

## Menus

- `menu :name, at: [x, y] do |m| m.item("NEW GAME") { … } end` → a `Menu`: **a list of rows, a cursor that moves between them, and a block per row saying what picking it does.** Nearly every game has one, and what a game wrote before this verb existed was the same thirty lines every time — a variable holding which row is picked, two button tests doing the wrapping by hand, one pass drawing every row dull, a second redrawing the picked one bright, a cursor drawn beside it, and a test for the button that acts. `examples/jukebox.rb` is the worked example, and it wrote that badly enough to be worth reading twice. Up and down move the cursor and **wrap at both ends** (the half people get wrong is going up off the first row); the `press:` button runs the picked row's block, on the press edge, so holding it chooses one time. **Holding a direction walks the list** rather than moving one row and stopping — after a move it waits `repeat_every:` frames, and letting go clears the wait, so a tap always moves exactly one row however long you held the last one. **Which row is picked survives leaving and coming back**, so a submenu you back out of opens where you left it — that is free, because the pick is a variable and a variable's starting value is applied one time, at power-on. Call it where the frame's work goes — **inside your `game_loop`, or inside a `scene`** — since a menu reads the buttons and draws its rows again every frame; a menu above the loop is a friendly error. **That rule is the same on both screens**, which is the point of it being a verb rather than text you place: the menu owns its own drawing, so nothing about where it goes changes with the screen the way a bare `draw_text` does. **What it COSTS does change, and it is worth knowing before writing a long one.** On `screen :bitmap` the rows are painted into the picture, so they cost drawing time and no sprites. On `screen :tiled` (and `screen :rotozoom`) the console composites the text for you, and every character is one little sprite of its own — out of the same table of 128 the game's own sprites come from. So reckon **about one sprite per character** of a label, and none at all for a space: eight rows of ten characters is about 72, and twelve rows of twelve does not fit and says so. (One and not two because a row lights up by CHANGING COLOUR rather than by being drawn twice — see `draw_text`'s `showing:`. The cursor is the only per-row extra, being shown or hidden rather than recoloured.) A tiled menu takes a place in the stack like anything else the console redraws (wrap the call in a `layer` block); a bitmap one cannot, and the friendly error says `menu` rather than the `draw_text` underneath it. Worked example: `examples/pong.rb`, whose title menu runs on `screen :rotozoom` over a zooming backdrop.
- `m.item "SOUND", enabled: false, color:, picked:` — one row. **A row that cannot be picked is stepped OVER, not landed on**, in both directions, and is drawn in the menu's `disabled:` colour: a Load Game with no save, a Resume with nothing to resume. Which rows those are is settled as the program is built, so each one costs a single test and a menu with nothing disabled emits none at all. `color:` and `picked:` give one row its own two colours (jukebox lights each song in its own accent). The block is what picking the row does, and a row can have none at all — on a screen where MOVING is the choice, like jukebox's, whichever row the cursor is on is the tune that plays.
- `m.item ["MUSIC: OFF", "MUSIC: ON"], showing: music` — **a row whose words change**, which is what a settings row is. Give it the list of things it can say and the variable that decides which, and the words the value points at are the ones on screen. They are **part of the row**: they light up with it, the cursor points at them, and the block under them is what changes the value they show — where a label plus a separate `draw_text` of the value beside it would leave the value outside the row, in whatever colour it was drawn in. A list without `showing:`, or `showing:` on a row that says one thing, is a friendly error. It costs what it says: each of the things the row can say is drawn under a test, so a two-way row is twice a plain one. Worked example: `examples/pong.rb`'s title.
- Decoration the game **says** rather than builds: `spacing:` (pixels from one row to the next; the font's line height plus a gap by default), `color:` / `picked:` / `disabled:` (the three row colours), `cursor:` (what is drawn to the left of the picked row, `">"` by default, `""` for none), `font:`, `press:` (which button chooses, `:a`), `repeat_every:` (frames a held button waits before it walks on).
- The handle reads back: `m.picked` → a `Value` (which row, counting from 0 — setting it jumps the cursor), `m.moved` → a `Condition` true on the frame the pick changed (a sound, a preview that reloads, a tune that starts over — `songs.moved.then { stop_music }`), `m.length` → a build-time Integer.

## Lists (runtime-sized collection)

- `list :name, capacity: N` → a `List`: `push`/`<<`, `pop`, `shift`, `[]`, `[]=`, `first`, `last`, `length`, `each { |v| }`.
  - **Say it holds fractions:** `list :speeds, capacity: 8, holds: 0.0` — a list keeps whole numbers unless you show it otherwise, exactly as a variable does. Write a Float as the example and every value read out carries the fraction and every value put in is checked against it, so a game with many of something that moves in halves and quarters never picks a scale of its own. The number is only an example — a list still starts empty — and `length` stays a plain count whatever the items are. A pool field says the same thing with its default (`pool :spark, vy: 0.0`). Putting a fraction into a list of whole numbers, or a worked-out whole number into a list of fractions, is a friendly error naming the list.
  - **It holds exactly what you asked for, and what it COSTS depends on whether you `shift` it.** A list you only push onto and index into is a plain row of slots: `capacity: 145` takes 145 of them, and a read skips straight to the one you named. A list you `shift` — dropping from the front, which moves where the oldest item lives — is a ring instead, and a ring's slots are rounded up to the next power of two so the wrap can be a single step: `capacity: 145` then takes 256, and the 111 slots in between are room you pay for and can never fill. So a queue you shift is the one to give a power-of-two capacity. Nothing about this changes what the list holds or what it does; the framework works out which of the two you wrote. A plain row is also the FASTER of the two to read, having no head to look up first.
  - **Say how big one slot is:** `list :hurt, capacity: 64, width: :byte` — a slot holds a whole 32-bit number unless you say otherwise, and hardly anything a game keeps in one needs that much. A direction, a state number, a countdown, how many hit points are left, a plain yes-or-no: every one of those is a **byte**, at a quarter of the memory, and `:half` is a half. That memory is the console's 32K of quick memory, which is the same 32K the framework keeps your hot code in — so on a big collection this is the difference between the game's frame running fast and running from the cartridge. Reading and writing a narrow slot costs exactly what a wide one costs; only the room differs. **A narrow slot always goes below nothing** (`:byte` holds -128..127), and there is deliberately no way to ask for 0..255 instead: the case that decides it is a countdown, where `wait.sub 7` followed by `(wait <= 0)` really does hold -4 while that test runs, and a slot that could not go below nothing would read -4 back as 252 and the test would never fire. Nothing at build time can see that coming, because the value is worked out as the game runs — which is also why a `table` CAN be asked and a list cannot: a table's values are all known while the cartridge is built. A number that has to reach past 127 asks for `:half`. A number too big for its slot keeps the low bits, exactly as the console does, and both backends drop the same bits (200 in a `:byte` reads back as -56 on each). A byte is the smallest there is — the console can load 8, 16 or 32 bits and nothing narrower, so a flag costs a byte and packing eight of them into one would cost several instructions on every read.
  - **Say how long it usually is:** `list :body, capacity: 256, estimate: { usually: 12 }` (or a range, `usually: 4..20`, which counts at its top). It changes **nothing** about how the game runs — it is there for `rom.explain`, which otherwise has only the capacity to go on and counts every walk over the list at the most it could ever hold. A snake's body list is sized for the whole board and holds four cells for most of a game, so the difference is the biggest line in the frame. Said or not, the estimate names the number it used: unsaid it guesses a quarter of the capacity and says so; the worst case still counts a full list, and the guardrail that warns when a growing list stops fitting in a frame still asks about a full one.

## Tables (build-time ROM lookup)

- `table :name, ruby_array, width: :half, signed: nil` → a `Table`: a build-time Ruby array shipped as read-only ROM data, read at run time by a Value index. `t[i]` → a `Value` (like `list` indexing, but const/ROM); `length` is a build-time Integer. `width:` is the element size (`:byte`/`:half`/`:word`); `signed:` is inferred from the values (any negative → signed) unless you set it. An out-of-range index is made safe: a power-of-two table wraps it (what an angle wants), any other size clamps to the ends — and **the length you pick decides what a read costs**, because wrapping is one step and clamping is a test against each end, about twice the work. A length like 256 or 512 is the cheap one; round a sine table up to it and the reads get cheaper for nothing. Precompute what the console can't do cheaply each frame — a sine or reciprocal/distance table (see `examples/raycaster.rb`). A value that doesn't fit the width is a friendly build error. **A read is not free** — reaching an element costs about three plain steps, and `explain` prices it, so a table read in a hot loop is real work rather than the single load it looks like.

## Composition (pools of a component)

- `pool :name, field: default, …, capacity: N` → a `Pool`: many of a thing that has named fields and behaves (bullets, enemies, particles), without hand-managing parallel lists that desync. `spawn(field: value, …)` fills a free slot (safe no-op when full); `each { |b| … }` runs the body once per live instance with a row handle whose fields are mutable Values (`b.x.add b.vy`, `b.y.set 0`, read/compare `b.x`), which can retire itself (`b.remove`), and whose own slot `b.index` hands back as a Value — save it in a variable to remember which instance won a comparison (the nearest enemy, the one just hit) and act on it once the loop has ended; `count` (a Value) / `full?` (a Condition) introspect it. Behind the scenes it's parallel lists + an active column + a `repeat`, so the fields can never desync and the cost model prices it per-pool.
  - **Spawn-when-full policy:** `on_full:` decides what `spawn` does with no free slot — `:drop` (default, ignore it) or `:recycle_oldest` (reuse the longest-lived instance so a new one always appears — the usual choice for particles/effects). `pool :spark, x:, y:, life:, capacity: 32, on_full: :recycle_oldest`.
  - **Spriteful pool:** add `image: :art` (needs `x:`/`y:` fields and `screen :tiled`) and each live instance auto-draws as a hardware sprite at its x/y — `spawn` shows one, `remove` hides it, and the console composites them. The row handle then also has a collision box (its x/y plus the image's size), so `b.overlaps?(other)`, the screen-edge tests (`b.off_screen?` / `b.below_bottom?` / …) and `b.clamp_to_screen` work per instance. A pool declared inside a `scene` is scene-owned (its sprites show only while that scene is active). On a bitmap screen, drop `image:` and draw the pool yourself in `each`.
  - **Say how big each field is:** `pool :guard, dir: 0, hp: 0, capacity: 145, widths: { dir: :byte, hp: :byte }` — a pool is one list per field, so a field left at its full width costs four bytes a slot to keep a direction or a flag, and a pool is sized for the worst moment of a game rather than a normal one. Naming the narrow ones is the single biggest thing you can do for a big pool: measured on Wolfenstein's guards, ten of thirteen fields narrowed freed about 3.7K of the console's 32K, which the framework then gave to three more routines of hot code. Same three widths a `list` takes, same rule about going below nothing (so a countdown is safe), and the same friendly error for a width the framework does not know. A field declared with a fraction (`x: 0.0`) cannot be narrowed and says so — a fraction is mostly its own fractional part and needs the whole word. **The pool's own bookkeeping is narrowed without being asked**, because unlike a field the framework knows exactly what it holds: the live-or-not column is a byte whatever the pool is, and the free-slot stack is as wide as the largest slot number needs.
  - **Say how many are usually live:** `pool :bullet, x:, y:, capacity: 64, estimate: { usually: 6 }` (or a range, `usually: 4..8`, which counts at its top) — the same hint a `list` takes, and like that one it changes **nothing** about how the game runs. It is there for `rom.explain`. `each` walks every slot whatever happens, and that walk is counted whole either way; what the number decides is how many times the **body** is counted, and a pool is sized for the worst moment of a game rather than a normal one — sixty-four bullets so the one frame that needs them has them, six on screen the rest of the time. Said or not, the report names the number it used: unsaid it guesses a quarter of the capacity and says so.

## Randomness

- `seed n` / `randomize` — seed the stream. `roll :var, 1..6` — store a random value. `rand(1..6)` — a random `Value`. `chance(25).then { }` — true 25% of the time.

## Sound & music

- `enable_sound`, `define_sound :name, frequency:, duty:, decay:, volume:`, `beep :tone` — SFX (channel 2).
- `noise :explosion` (also `:hit`/`:kick`/`:snare`/`:hat`/`:zap`, or `pitch:`/`decay:`/`volume:`/`metallic:`) — a percussion/explosion hit on the noise voice (channel 4).
- `wave :triangle, :C4` (shapes `:sine`/`:triangle`/`:sawtooth`/`:square`; pitch a note or Hz; `volume:` `:full`/`:three_quarter`/`:half`/`:quarter`/`:mute`), `stop_wave` — a sustained richer-timbre tone on the wave voice (channel 3).
- `song(:name) { … }`, `play_song :name`, `stop_music` — music. Inside `song`: `tempo`, `note :C4, :quarter`, `rest :quarter`, `duty`, `volume`. Layer parts with `voice :melody do … end` / `voice :bass do … end` (up to 2; the framework picks the channels — melody over a bass line). `stop_music` silences both music voices.
- `sample :name, from: "clip.wav"` (or `pcm: [-128..127…], rate: N`, and `note:` — the pitch it was recorded at, default `:C4`) → a `Sample`: a recorded 8-bit PCM clip played through the sampled-audio hardware (Direct Sound), not a synthesized PSG tone. `from:` loads a `.wav` (any 8-/16-bit, mono/stereo PCM — converted for you, keeping its rate; file found beside your script); `pcm:` takes raw samples (an Array of -128..127 or a byte `String`) at `rate:` (default 8192). `s.play` plays it once; `s.play(loop: true)` replays it seamlessly as looping background music (any length — it streams from ROM a frame at a time); `s.play(volume: :half)` sets its level (`:full`/`:three_quarter`/`:half`/`:quarter`/`:mute`); `s.play(pitch: :E4)` plays it at a different note by reading through it faster/slower (one recorded note covers a whole keyboard — shifts from the sample's `note:`); `s.stop` cuts its voices off. **Several samples play at once** — a software mixer sums the sounding voices (background music under a handful of overlapping effects, or chords), up to 8 voices; a 9th is dropped rather than stealing one. The framework hides the FIFO/DMA/timer/mixing; sound needs a `game_loop` (the mixer refills once a frame) and reserves one hardware timer (user `timer`s allocate from timer 1).
- `instrument :name, from: "piano.wav", note: :C4` (same `pcm:`/`from:`/`rate:`/`note:` as `sample`) → an `Instrument`: a recorded sample you play *notes* on, one recording covering the whole keyboard. `inst.play(:E4)` plays a note; `inst.play(:C4, :E4, :G4)` a chord (each note a voice, sounding together); `inst.play(:E4, volume: :half)` sets level; `inst.stop` silences it. Pure sugar over `sample.play(pitch:)` — each note is a pitched voice in the mixer. Trigger notes live from input (`pressed(:a).then { piano.play(:C4) }`).
